# Глава 30. Встроенные команды и история

Оболочка у нас получилась работящая: запускает программы, соединяет их в цепочки, перенаправляет потоки, разбирает кавычки, не умирает от Ctrl+C. Но одна простейшая команда до сих пор не работает:

```
myshell$ cd /tmp
myshell$ pwd
/Users/serik/Desktop/From-scratch/cpp-from-scratch/demo-shell
```

Папка не сменилась. Мы уже знаем почему: `cd` запустился в ребёнке, сменил рабочую папку ребёнку и умер вместе со своим достижением. Рабочая папка — свойство процесса, и никакая запущенная программа не может поменять её родителю.

Это не недоработка, а фундаментальное ограничение, и обходят его во всех оболочках мира одинаково: такие команды выполняются **внутри** оболочки, без `fork` и `exec`. Их называют встроенными. В этой главе добавим девять встроенных команд — `cd`, `pwd`, `export`, `unset`, `echo`, `history`, `type`, `alias` и `unalias` — и научим оболочку помнить историю между запусками.

## Три причины быть встроенной командой

Команды становятся встроенными по трём разным причинам, и их полезно различать.

Первая причина — необходимость. Команда меняет состояние самой оболочки, а значит, обязана выполняться в её процессе. Таких немного: `cd` меняет рабочую папку, `export` и `unset` — переменные окружения, `exit` завершает оболочку, `alias` заводит сокращения для будущих команд, `source` выполняет скрипт в текущем процессе, чтобы его переменные остались. Внешней программой ни одну из них сделать нельзя в принципе.

Вторая причина — скорость. `echo`, `pwd`, `test`, `[`, `printf` вполне могли бы быть отдельными программами — и они существуют, в `/bin/echo` и `/bin/pwd` можно ткнуть пальцем. Но каждый их запуск стоит `fork` плюс `exec` плюс загрузка исполняемого файла плюс инициализация библиотеки времени выполнения. В скрипте с тысячей проверок это заметно.

Насколько заметно, легко измерить. Я прогнал через нашу оболочку триста команд `echo hi` — сперва встроенной версией, потом явно указав `/bin/echo`:

```
300 раз echo (builtin):  11 мс
300 раз /bin/echo (exec): 920 мс
отношение: 83.7x
```

Восемьдесят три раза. Три миллисекунды на запуск процесса против сотых долей на вызов функции — вот и вся арифметика. Именно поэтому `[` в `bash` встроен, хотя файл `/bin/[` тоже лежит на диске ради совместимости со старыми скриптами.

Третья причина — доступ к внутренним данным оболочки. Команда `history` печатает список, который хранится в памяти нашего процесса; внешней программе его просто неоткуда взять. Сюда же относятся `jobs`, `fg` и `bg`, знающие про список фоновых задач.

## Точка входа

Весь механизм сводится к одной функции. Новый файл `include/builtins.h`:

```cpp
#ifndef SHELL_BUILTINS_H
#define SHELL_BUILTINS_H

#include <string>
#include <vector>

namespace shell {

// Попытаться выполнить встроенную команду. Возвращает true, если команда
// встроенная (вне зависимости от успеха/неуспеха выполнения; код в `out_code`).
// Возвращает false, если команда не встроенная — её надо запускать через exec.
bool try_builtin(const std::vector<std::string>& argv, int& out_code);

// Раскрыть алиас в первом слове строки. Возвращает строку без изменений,
// если алиас не найден. Раскрывается один уровень — рекурсию не поддерживаем.
std::string expand_alias(const std::string& line);

// История.
void history_add(const std::string& line);
void history_load(const std::string& path);
void history_save(const std::string& path);
const std::vector<std::string>& history();

}  // namespace shell

#endif
```

Обратите внимание на разделение двух вещей, которые легко перепутать. Возвращаемое значение `bool` отвечает на вопрос «это встроенная команда?», а не «получилось ли». Результат выполнения уходит в `out_code`. Если бы мы совместили их в одном `int`, вызывающему коду пришлось бы гадать, означает ли ненулевое значение ошибку команды или её отсутствие.

Подключение в `main.cpp`:

```cpp
// Builtin — только если одна команда и без редиректов (упрощение).
if (p.commands.size() == 1 && p.commands[0].redirects.empty()) {
    int code = 0;
    if (shell::try_builtin(first, code)) {
        if (code != 0) std::cerr << "[exit " << code << "]\n";
        continue;
    }
}

int rc = shell::run_pipeline(p);
```

Сначала пробуем встроенную, и только если её нет — запускаем внешнюю. Порядок именно такой во всех оболочках: встроенная версия побеждает одноимённую программу на диске. Поэтому `echo` в `bash` — это встроенный `echo`, а не `/bin/echo`, и чтобы позвать именно программу, приходится писать путь целиком.

## Почему встроенные команды не работают в конвейере

Условие `p.commands.size() == 1 && redirects.empty()` — упрощение, и стоит понять, что мы упростили.

Пусть пользователь написал `cd /tmp | cat`. Формально это конвейер из двух команд, значит, наше условие не выполняется, и `cd` уходит в `run_pipeline` — то есть запускается как внешняя программа в ребёнке. Проверим, что из этого выходит:

```
myshell$ cd /tmp | cat
myshell$ pwd
/Users/serik/Desktop/From-scratch/cpp-from-scratch/demo-shell
```

Папка не сменилась — ровно как в начале главы. И это правильное поведение: `bash` ведёт себя точно так же. Каждая команда конвейера выполняется в своём процессе, а изменение рабочей папки в чужом процессе бессмысленно по определению. Писать `cd` в конвейере просто не имеет смысла, и никакая оболочка не станет ради этого выдумывать особую механику.

С перенаправлениями сложнее. Команда `pwd > out.txt` вполне осмысленна, и `bash` её выполняет: он форкается, применяет перенаправление в ребёнке и там же выполняет встроенную команду. Мы этого не делаем — `pwd > out.txt` уйдёт во внешний `/bin/pwd`, и результат будет тот же самый, но лишним процессом. А вот `cd /tmp > log.txt` у нас сменит папку не там, где надо. Случай экзотический, и я оставил упрощение в силе, но в упражнениях есть задание его убрать.

## Реализации

Все команды живут в `src/builtins.cpp`, каждая — отдельная функция в анонимном пространстве имён, а наружу торчит только `try_builtin`.

### cd

```cpp
int builtin_cd(const std::vector<std::string>& argv) {
    std::string target;
    if (argv.size() < 2) {
        const char* home = std::getenv("HOME");
        if (!home) {
            std::cerr << "cd: HOME не задана\n";
            return 1;
        }
        target = home;
    } else {
        target = argv[1];
    }
    if (chdir(target.c_str()) < 0) {
        std::cerr << "cd: " << target << ": " << std::strerror(errno) << "\n";
        return 1;
    }
    return 0;
}
```

Вся команда — это один системный вызов `chdir` из `<unistd.h>`, меняющий рабочую папку текущего процесса. Он возвращает `0` при успехе и `-1` при ошибке, а причину кладёт в `errno`: `ENOENT`, если папки нет, `ENOTDIR`, если путь ведёт к файлу, `EACCES`, если нет прав войти.

Без аргументов `cd` уходит домой. Домашняя папка берётся из переменной окружения `HOME` функцией `std::getenv` из `<cstdlib>`; она возвращает указатель на строку внутри окружения процесса или `nullptr`, если переменной нет. Проверка на `nullptr` не паранойя: окружение можно очистить полностью, и тогда `HOME` действительно не будет.

Настоящий `cd` умеет больше: `cd -` возвращает в предыдущую папку, `cd ~user` ведёт в чужой дом, `cd` без аргументов в некоторых оболочках учитывает переменную `CDPATH`. Наш вариант — минимальный, и первые две возможности несложно добавить самому.

### pwd

```cpp
int builtin_pwd() {
    char buf[4096];
    if (!getcwd(buf, sizeof(buf))) {
        std::cerr << "pwd: " << std::strerror(errno) << "\n";
        return 1;
    }
    std::cout << buf << "\n";
    return 0;
}
```

`getcwd(buf, size)` записывает в буфер абсолютный путь текущей папки и возвращает указатель на него — или `nullptr`, если не влезло (`ERANGE`) либо папка была удалена у нас из-под ног (`ENOENT`, и такое бывает).

Размер 4096 взят из `PATH_MAX` — предельной длины пути на Linux; на macOS предел меньше, 1024. Пользоваться константой `PATH_MAX` напрямую соблазнительно, но она не так надёжна, как кажется: на некоторых системах её вообще нет, а на Linux она не учитывает, что путь длиннее предела всё-таки может существовать, если собирать его по частям. Надёжный вариант — передать `getcwd` нулевой указатель, тогда на Linux и macOS она сама выделит память нужного размера, а вы потом её освободите. Для учебной оболочки четырёх килобайт на стеке достаточно.

Полезно понимать, что `getcwd` не читает никакой переменной, а спрашивает ядро. Поэтому она всегда говорит правду — в отличие от переменной `PWD`, которую оболочки поддерживают сами и которая может отстать от реальности.

### export и unset

```cpp
int builtin_export(const std::vector<std::string>& argv) {
    if (argv.size() < 2) {
        // Без аргументов — печать всех переменных. Упростим: пропустим.
        std::cerr << "export: укажите KEY=VALUE\n";
        return 1;
    }
    for (std::size_t i = 1; i < argv.size(); ++i) {
        const std::string& kv = argv[i];
        auto eq = kv.find('=');
        if (eq == std::string::npos) {
            std::cerr << "export: ожидался формат KEY=VALUE: " << kv << "\n";
            return 1;
        }
        std::string key = kv.substr(0, eq);
        std::string val = kv.substr(eq + 1);
        if (setenv(key.c_str(), val.c_str(), 1) < 0) {
            std::cerr << "export: " << std::strerror(errno) << "\n";
            return 1;
        }
    }
    return 0;
}

int builtin_unset(const std::vector<std::string>& argv) {
    for (std::size_t i = 1; i < argv.size(); ++i) {
        if (unsetenv(argv[i].c_str()) < 0) {
            std::cerr << "unset: " << std::strerror(errno) << "\n";
            return 1;
        }
    }
    return 0;
}
```

Разбор `KEY=VALUE` делается через `find('=')` и два `substr`. Значение может содержать знаки равенства — `substr(eq + 1)` берёт всё до конца строки, так что `export X=a=b` даст переменной значение `a=b`, как и положено.

Третий аргумент `setenv` — флаг перезаписи. Единица означает «перезаписать, если переменная уже есть»; с нулём существующее значение осталось бы нетронутым.

Стоит убедиться, что это действительно работает — то есть что запущенные программы видят наши переменные:

```
myshell$ export FOO=bar
myshell$ sh -c "echo видно ли: $FOO"
видно ли: bar
myshell$ env | grep FOO
FOO=bar
myshell$ unset FOO
myshell$ env | grep FOO
[exit 1]
```

Обратите внимание на вторую строку: подстановку `$FOO` выполнил не наш токенизатор (он этого не умеет), а запущенный `sh`, которому строка досталась дословно. И значение он взял из своего окружения — унаследованного от нас. Последний `grep` не нашёл ничего и вернул код 1, что оболочка честно показала.

### Как окружение попадает в ребёнка

Раз уж речь зашла об окружении, стоит пояснить механику, потому что она устроена неочевидно.

Окружение процесса — это массив строк вида `KEY=VALUE`, оканчивающийся нулевым указателем. Он доступен через глобальную переменную `environ`, объявленную как `extern char** environ`, и через третий, малоизвестный параметр `main`:

```cpp
int main(int argc, char** argv, char** envp) {
    for (char** p = envp; *p; ++p) {
        std::cout << *p << "\n";
    }
}
```

`setenv` и `unsetenv` правят именно этот массив, а функция `execvp`, которой мы запускаем программы, молча передаёт текущий `environ` новому образу. Отсюда и получается наследование: мы изменили массив у себя — `fork` скопировал его ребёнку — `exec` передал дальше. Если бы понадобилось запустить программу с другим окружением, мы бы взяли `execve`, у которой окружение — явный третий аргумент.

И маленькое предупреждение про `getenv`: она возвращает указатель на строку внутри этого массива, а не копию. Указатель становится недействительным после следующего `setenv`, потому что массив может быть перевыделен. Правило простое: понадобилось значение надолго — скопируйте его в `std::string` сразу.

### echo

```cpp
int builtin_echo(const std::vector<std::string>& argv) {
    bool newline = true;
    std::size_t start = 1;
    if (argv.size() > 1 && argv[1] == "-n") {
        newline = false;
        start = 2;
    }
    for (std::size_t i = start; i < argv.size(); ++i) {
        if (i > start) std::cout << " ";
        std::cout << argv[i];
    }
    if (newline) std::cout << "\n";
    return 0;
}
```

Печатаем аргументы через пробел; условие `i > start` ставит разделитель перед каждым аргументом, кроме первого, — обычный приём, чтобы не получить лишний пробел в конце. Флаг `-n` отменяет перевод строки.

Разделение аргументов пробелом важно понимать правильно. Оболочка уже разобрала строку на слова, и `echo` печатает их заново через один пробел. Поэтому `echo a     b` выведет `a b` с одним пробелом — лишние съел токенизатор, — а `echo "a     b"` сохранит все пробелы, потому что это одно слово.

Флаг `-e`, включающий в `bash` разбор `\n` и `\t` внутри строки, мы не делаем: экранирование у нас уже отработал токенизатор из главы 29.

### exit

Единственная команда, которую мы обрабатываем не через `try_builtin`, а прямо в цикле:

```cpp
const auto& first = p.commands[0].argv;
if (!first.empty() && (first[0] == "exit" || first[0] == "quit")) {
    break;
}
```

Причина в том, что `exit` должен закончить цикл, а функция `try_builtin` этого сделать не может — она умеет только вернуть код. Пришлось бы либо заводить особое значение «пора выходить», либо звать `std::exit` изнутри. Второй путь хуже: `std::exit` прерывает работу немедленно, и `history_save` в конце `main` уже не выполнится — история потеряется. Явный `break` оставляет управление там, где ему положено быть.

`quit` как синоним `exit` — наша вольность, в настоящих оболочках такой команды нет.

### Диспетчер

```cpp
bool try_builtin(const std::vector<std::string>& argv, int& out_code) {
    if (argv.empty()) {
        out_code = 0;
        return true;
    }
    const std::string& cmd = argv[0];

    if (cmd == "cd")       { out_code = builtin_cd(argv);      return true; }
    if (cmd == "pwd")      { out_code = builtin_pwd();          return true; }
    if (cmd == "export")   { out_code = builtin_export(argv);   return true; }
    if (cmd == "unset")    { out_code = builtin_unset(argv);    return true; }
    if (cmd == "history")  { out_code = builtin_history();      return true; }
    if (cmd == "echo")     { out_code = builtin_echo(argv);     return true; }

    return false;
}
```

Цепочка сравнений выглядит примитивно, и рука тянется заменить её на `std::unordered_map` из имени в функцию — тем более что в главе 21 мы именно так сделали реестр команд RPG. Здесь я сознательно оставил простой вариант: команд девять, сравнение коротких строк стоит наносекунды, а читается такой код без единой мысли. Заводить таблицу стоит, когда команд становится два-три десятка или когда их нужно регистрировать динамически — например, для `alias`.

## alias: сокращения для команд

Ещё одна команда, которая обязана быть встроенной, — `alias`. Она заводит короткое имя для длинной команды, и заведённое должно жить в оболочке, а не в умершем ребёнке.

Хранилище — обычная упорядоченная таблица:

```cpp
#include <map>

namespace {
    std::map<std::string, std::string> g_aliases;
}
```

`std::map` вместо `std::unordered_map` выбран не случайно: он держит ключи в отсортированном порядке, и печать всех алиасов сразу выходит по алфавиту, без отдельной сортировки. Алиасов десятки, скорость поиска тут никого не волнует.

Сама команда работает в трёх режимах — показать все, показать один, задать:

```cpp
// alias           — показать все алиасы
// alias ll="ls -l" — задать алиас
int builtin_alias(const std::vector<std::string>& argv) {
    if (argv.size() < 2) {
        for (std::map<std::string, std::string>::const_iterator it = g_aliases.begin();
             it != g_aliases.end(); ++it) {
            std::cout << "alias " << it->first << "='" << it->second << "'\n";
        }
        return 0;
    }
    int rc = 0;
    for (std::size_t i = 1; i < argv.size(); ++i) {
        std::size_t eq = argv[i].find('=');
        if (eq == std::string::npos) {
            std::map<std::string, std::string>::const_iterator it = g_aliases.find(argv[i]);
            if (it == g_aliases.end()) {
                std::cerr << "alias: " << argv[i] << ": не найден\n";
                rc = 1;
            } else {
                std::cout << "alias " << it->first << "='" << it->second << "'\n";
            }
            continue;
        }
        g_aliases[argv[i].substr(0, eq)] = argv[i].substr(eq + 1);
    }
    return rc;
}

int builtin_unalias(const std::vector<std::string>& argv) {
    for (std::size_t i = 1; i < argv.size(); ++i) {
        g_aliases.erase(argv[i]);
    }
    return 0;
}
```

Разбор `KEY=VALUE` здесь тот же, что в `export`. Обратите внимание, что кавычки в `alias ll="ls -l"` до нас не доходят — их снял токенизатор, и в `argv[1]` лежит готовая строка `ll=ls -l`.

Теперь главное — подстановка. Алиас надо раскрыть **до** разбора строки, потому что он может содержать что угодно, включая перенаправления и черты конвейера:

```cpp
std::string expand_alias(const std::string& line) {
    // Берём первое слово строки — только оно может быть алиасом.
    std::size_t start = line.find_first_not_of(" \t");
    if (start == std::string::npos) return line;
    std::size_t end = line.find_first_of(" \t", start);
    std::string first = line.substr(start, end == std::string::npos
                                               ? std::string::npos
                                               : end - start);

    std::map<std::string, std::string>::const_iterator it = g_aliases.find(first);
    if (it == g_aliases.end()) return line;

    std::string rest = (end == std::string::npos) ? "" : line.substr(end);
    return it->second + rest;
}
```

И вызов в цикле `main`, перед разбором:

```cpp
// Алиас раскрываем до разбора: `ll -a` → `ls -l -a`.
std::string expanded = shell::expand_alias(line);

shell::Pipeline p;
try {
    p = shell::parse_pipeline(expanded);
    ...
```

Раскрывается только первое слово и только один раз. Настоящие оболочки идут дальше: раскрывают алиас рекурсивно (если раскрытое снова начинается с алиаса), а если значение алиаса кончается пробелом — проверяют и следующее слово. Рекурсию мы не делаем сознательно: без защиты от зацикливания `alias ls="ls -l"` подвесил бы оболочку намертво, а с защитой код перестаёт быть примером на десять строк. В `bash` от этой ловушки спасает правило «имя алиаса не раскрывается внутри собственного значения».

Заметьте ещё, что в историю попадает исходная строка, а не раскрытая. Так удобнее: пролистав историю, человек увидит то, что набирал.

```
myshell$ alias ll="ls -1"
myshell$ alias
alias ll='ls -1'
myshell$ ll src
builtins.cpp
exec_runner.cpp
main.cpp
pipeline.cpp
signals.cpp
myshell$ unalias ll
myshell$ ll src
exec 'll' failed: No such file or directory
[exit 127]
```

## Две разные вещи, которые называют переменными

С `export` связана путаница, которая живёт даже у опытных людей. В настоящей оболочке есть **два** вида переменных, и они устроены совершенно по-разному.

Переменные оболочки живут только в её памяти. Создаются присваиванием без всяких команд:

```bash
$ X=5
$ echo $X
5
```

Переменные окружения живут в массиве `environ` и передаются всем запускаемым программам. Обычная переменная становится переменной окружения после `export`.

Разницу видно в один опыт:

```bash
$ bash -c 'X=5; echo "в самом bash: $X"; sh -c "echo в ребёнке: [\$X]"'
в самом bash: 5
в ребёнке: []
```

Переменная есть в самой оболочке и отсутствует у ребёнка. Добавьте `export X` — и в квадратных скобках появится пятёрка.

Наша оболочка умеет только вторую половину: `export FOO=bar` работает, а простое присваивание — нет.

```
myshell$ X=5
exec 'X=5' failed: No such file or directory
[exit 127]
```

Строка `X=5` не распознаётся как присваивание и уходит в `execvp` как имя программы. Чтобы это заработало, в цикл нужно добавить проверку: если единственное слово команды содержит знак равенства до первого пробела и перед ним стоит допустимое имя, то это присваивание, и его надо положить в собственную таблицу переменных оболочки. А `export X` без значения должен переносить переменную из этой таблицы в окружение.

Заводить своё хранилище переменных мы не станем — это потянуло бы за собой подстановку `$X`, без которой переменные оболочки бесполезны. Но понимать разницу между двумя видами стоит: именно из-за неё скрипт, работающий при запуске вручную, ломается в `cron`, где окружение почти пустое.

## Как оболочка ищет программу

Ещё одна вещь, которую полезно понимать про встроенные команды, — порядок поиска. Когда вы вводите слово, `bash` проверяет варианты в строгой очерёдности: сначала функции оболочки, затем встроенные команды, и только потом ищет исполняемый файл в каталогах из `PATH`.

Убедиться можно командой `type`, которая как раз и рассказывает, чем окажется имя:

```bash
$ type echo
echo is a shell builtin
$ type ls
ls is /bin/ls
$ type cd
cd is a shell builtin
$ type -a echo
echo is a shell builtin
echo is /bin/echo
```

Последний вызов с ключом `-a` показывает сразу все варианты — и видно, что `/bin/echo` существует, но проигрывает встроенной версии.

Поиск по `PATH` за нас делает `execvp` — та самая буква `p` в её имени. Она берёт переменную `PATH`, разбивает по двоеточиям и пробует каждый каталог по очереди, пока не найдёт исполняемый файл. Если в имени команды есть косая черта (`./build/myshell`), поиск не выполняется вовсе — путь берётся как есть.

Отсюда, кстати, известное правило безопасности: текущий каталог `.` не должен входить в `PATH`. Иначе достаточно положить в общедоступную папку файл с именем `ls`, дождаться, пока кто-то зайдёт туда и наберёт привычную команду, — и чужая программа запустится от его имени. По этой же причине запускать программу из текущего каталога приходится с явным `./`.

### Свой type

Раз поиск устроен так просто, сделаем такую же команду у себя — заодно это будет седьмая встроенная и хороший пример работы с `PATH` руками:

```cpp
// type — рассказать, чем окажется имя: встроенной командой или файлом из PATH.
int builtin_type(const std::vector<std::string>& argv) {
    if (argv.size() < 2) {
        std::cerr << "type: укажите имя команды\n";
        return 1;
    }

    int rc = 0;
    for (std::size_t i = 1; i < argv.size(); ++i) {
        const std::string& name = argv[i];

        if (is_builtin_name(name)) {
            std::cout << name << " — встроенная команда\n";
            continue;
        }

        // Имя с косой чертой ищем как путь, без — перебираем PATH (так же,
        // как это делает execvp).
        if (name.find('/') != std::string::npos) {
            if (access(name.c_str(), X_OK) == 0) {
                std::cout << name << " — " << name << "\n";
            } else {
                std::cerr << "type: " << name << ": не найдено\n";
                rc = 1;
            }
            continue;
        }

        const char* path = std::getenv("PATH");
        std::string dirs = path ? path : "";
        bool found = false;
        std::size_t start = 0;
        while (start <= dirs.size()) {
            std::size_t colon = dirs.find(':', start);
            std::string dir = dirs.substr(start, colon == std::string::npos
                                                     ? std::string::npos
                                                     : colon - start);
            if (dir.empty()) dir = ".";
            std::string candidate = dir + "/" + name;
            if (access(candidate.c_str(), X_OK) == 0) {
                std::cout << name << " — " << candidate << "\n";
                found = true;
                break;
            }
            if (colon == std::string::npos) break;
            start = colon + 1;
        }
        if (!found) {
            std::cerr << "type: " << name << ": не найдено\n";
            rc = 1;
        }
    }
    return rc;
}
```

Здесь три вещи, о которых стоит сказать.

`access(path, X_OK)` спрашивает у ядра, можно ли запускать этот файл, — не открывая его. Кроме `X_OK` бывают `R_OK`, `W_OK` (право на чтение и запись) и `F_OK` (просто существует ли). Пользоваться `access` для проверки «а можно ли, прежде чем делать» вообще-то не рекомендуют: между проверкой и действием мир может измениться, и это классическая уязвимость гонки. Но для справочной команды вроде `type`, которая ничего не делает, а только рассказывает, — самое подходящее применение.

Разбор `PATH` вручную выглядит громоздко из-за возни с `find(':')` и `substr`, и это цена работы со строками в C++11 — в C++17 появился бы `string_view`, а с ним и деление без копирования (глава 50). Пустой элемент в `PATH` (два двоеточия подряд или двоеточие в начале) по традиции означает текущий каталог — отсюда `if (dir.empty()) dir = ".";`.

Порядок проверок повторяет настоящий: сначала встроенные, потом файлы. Поэтому наш `type echo` честно скажет, что победит встроенная версия.

```
myshell$ type echo
echo — встроенная команда
myshell$ type ls
ls — /bin/ls
myshell$ type cd
cd — встроенная команда
myshell$ type ./build/mycat
./build/mycat — ./build/mycat
myshell$ type nosuchprogram
type: nosuchprogram: не найдено
[exit 1]
```

## История команд

История — это просто список строк в памяти, который переживает выход из оболочки за счёт текстового файла.

```cpp
namespace {
    std::vector<std::string> g_history;
}

void history_add(const std::string& line) {
    if (line.empty()) return;
    if (!g_history.empty() && g_history.back() == line) return;  // не дублируем
    g_history.push_back(line);
}
```

Проверка на совпадение с последней записью убирает самый частый мусор: пять раз подряд нажали `make` — в истории одна строка. `bash` управляет этим переменной `HISTCONTROL` со значением `ignoredups`; мы включили такое поведение всегда.

Загрузка и сохранение — обычные потоки из главы 12:

```cpp
void history_load(const std::string& path) {
    std::ifstream in(path);
    if (!in.is_open()) return;
    std::string line;
    while (std::getline(in, line)) {
        if (!line.empty()) g_history.push_back(line);
    }
}

void history_save(const std::string& path) {
    std::ofstream out(path);
    if (!out.is_open()) return;
    for (const auto& line : g_history) {
        out << line << "\n";
    }
}
```

Формат — одна команда на строку. Никаких меток времени, никакого экранирования; многострочные команды мы и не умеем принимать. Если файла нет — молча выходим: при первом запуске истории просто ещё не существует, и ругаться не на что. Точно так же молча переживаем невозможность записи: не сохранённая история — не повод портить пользователю сессию сообщением об ошибке.

Печать с номерами:

```cpp
int builtin_history() {
    std::size_t i = 1;
    for (const auto& line : g_history) {
        std::cout << "  " << i << "  " << line << "\n";
        ++i;
    }
    return 0;
}
```

Путь к файлу собирается в `main.cpp`:

```cpp
namespace {

std::string history_path() {
    const char* home = std::getenv("HOME");
    if (!home) return "./.myshell_history";
    return std::string(home) + "/.myshell_history";
}

}  // namespace

int main() {
    shell::install_shell_signal_handlers();
    shell::history_load(history_path());

    while (true) {
        ...
        shell::history_add(line);
        ...
    }

    shell::history_save(history_path());
    return 0;
}
```

Точка в начале имени файла делает его скрытым — соглашение Unix, по которому настроечные файлы не мозолят глаза в `ls`. Запасной вариант `./.myshell_history` на случай отсутствия `HOME` нужен для запуска в необычном окружении, например внутри контейнера с очищенным окружением.

`history_add` вызывается сразу после разбора строки, но до выполнения команды. Так в историю попадают и команды с ошибками — и это правильно: чаще всего вспомнить хотят как раз ту команду, которая не сработала, чтобы её исправить.

### Компромисс с сохранением

Мы записываем историю один раз, при выходе. Это самый простой вариант, и у него есть очевидный недостаток: если оболочку убьют через `kill -9` или она упадёт, история сессии пропадёт целиком.

Настоящие оболочки поступают иначе — дописывают каждую команду в файл сразу, открывая его в режиме `O_APPEND`. Тогда переживает даже внезапная смерть, а из-за атомарности `O_APPEND` (о ней шла речь в главе 29) две одновременно запущенные оболочки не портят файл друг другу.

Цена — системный вызов на каждую команду. Для оболочки это несущественно: человек набирает команды в тысячи раз медленнее. В упражнениях есть задание переделать сохранение на этот лад.

## Почему не работает стрелка вверх

Раз есть история, хочется листать её стрелками. Не выйдет — и стоит объяснить, почему, потому что причина не в нашей лени.

Терминал по умолчанию работает в каноническом режиме. Драйвер терминала сам собирает строку, сам обрабатывает забой, сам показывает набираемое, и только по нажатию Enter отдаёт программе готовую строку. Наш `std::getline` получает её уже целиком.

Стрелка вверх в этом режиме не имеет никакого особого значения — терминал просто передаёт три байта, которые она порождает:

```bash
$ printf '\033[A\033[B' | cat -v
^[[A^[[B
```

`^[` — это символ escape с кодом 27, дальше идут `[` и буква. Стрелка вверх — `ESC [ A`, вниз — `ESC [ B`, вправо и влево — `C` и `D`. Пока мы читаем строки целиком, эти байты просто попадут в середину команды и испортят её.

Чтобы листать историю, нужен неканонический (сырой) режим. Схема такая: через `tcgetattr` получить текущие настройки терминала, снять флаги `ICANON` (построчная сборка) и `ECHO` (автоматический показ введённого), применить `tcsetattr`. После этого `read` начинает возвращать каждый нажатый байт немедленно — и всю работу приходится делать самому: показывать символы, обрабатывать забой, узнавать управляющие последовательности, двигать курсор теми же последовательностями (`ESC [ K` стирает остаток строки, `ESC [ nD` двигает курсор влево на `n` позиций). Не забыть восстановить настройки при выходе, в том числе аварийном, — иначе пользователь останется в терминале без эха, где ничего не видно при наборе.

Работы тут на пару сотен строк, и она не про C++, а про особенности терминалов, которых накопилось немало. Поэтому в реальных проектах берут готовую библиотеку: GNU readline или её более свободный по лицензии заменитель libedit. Подключается она в три строки и приносит сразу всё — историю со стрелками, поиск по Ctrl+R, автодополнение, редактирование строки. Есть упражнение и на это.

Кое-что, впрочем, работает и без сырого режима, потому что делается драйвером терминала: Ctrl+U стирает строку, Ctrl+W — последнее слово, Ctrl+D в пустой строке даёт конец файла и завершает оболочку.

## Главные правила главы

1. Команды, меняющие состояние оболочки (`cd`, `export`, `unset`, `exit`), обязаны быть встроенными — внешняя программа физически не может этого сделать.
2. Встроенная версия побеждает одноимённую программу на диске; чтобы позвать программу, указывают полный путь.
3. Скорость встроенной команды выше на два порядка: `fork` с `exec` стоят миллисекунды, вызов функции — наносекунды.
4. Встроенные команды в конвейере смысла не имеют: каждое звено выполняется в своём процессе.
5. `setenv`/`unsetenv` меняют массив `environ`, который `exec` передаёт запускаемой программе, — так работает наследование окружения.
6. `getenv` возвращает указатель внутрь окружения; нужное значение копируйте сразу.
7. Историю надёжнее дописывать после каждой команды в режиме `O_APPEND`, а не сохранять при выходе.
8. Стрелки и редактирование строки требуют сырого режима терминала; в настоящем проекте для этого берут readline или libedit.

## Упражнения

2. Выясните опытом, что происходит с `cd` в конвейере: выполните `cd /tmp | cat`, затем `pwd`. Объясните результат и скажите, как ведёт себя в этом случае ваш обычный `bash` или `zsh`.

3. Повторите замер из начала главы на своей машине: прогоните триста `echo hi` и триста `/bin/echo hi`, сравните время. Затем добавьте в оболочку встроенный `true` и сравните его с `/usr/bin/true`.

4. Добавьте `cd -` — возврат в предыдущую папку. Понадобится статическая переменная с прошлым путём, которую заполняет `getcwd` перед каждым `chdir`.

5. Реализуйте `export` без аргументов: печать всех переменных окружения по одной на строку. Пройдите по `environ` или по третьему параметру `main`.

7. Уберите упрощение с перенаправлениями: пусть `pwd > out.txt` тоже работает. Подсказка — форкнуться, в ребёнке применить `apply_redirects` и вызвать `try_builtin`, а в родителе дождаться. Проверьте, что `cd /tmp > log.txt` при этом по-прежнему не меняет папку оболочки, и объясните почему.

# Глава 23. Парсер скриптов локаций

До сих пор наш мир из трёх локаций был **зашит в C++**: функция `make_demo_world()` явно создавала их вручную. Чтобы добавить пещеру, нужно было править `world.cpp`, пересобирать программу, запускать. Это работает для трёх локаций, но не масштабируется.

В этой главе мы построим **парсер**: мир будет описываться в текстовом файле `data/world.txt`, и программа будет его читать. Добавил локацию — сохранил файл — запустил, никаких пересборок. Это огромный шаг: контент отделён от кода.

Заодно — это первая в книге задача парсинга. Очень полезный навык. Любая программа, читающая конфиги, JSON, XML, CSV, файлы данных — это тот же парсинг. Освоите принцип на простом примере — лучше поймёте сложные форматы.

## Зачем парсер

Несколько причин, по которым контент не зашивают в код:

1. **Скорость итерации.** Дизайнер игры (или вы сами) меняет локацию — сохранил файл — посмотрел в игре. Без перекомпиляции.
2. **Расширяемость пользователями.** Кто-то скачивает игру, открывает `world.txt`, добавляет свои локации. Получает свою версию.
3. **Локализация.** Тексты в файлах легко переводить, не лезя в C++-код.
4. **Разделение компетенций.** Программисту не приходится «писать тексты», дизайнеру — лезть в код.
5. **Скрипты vs данные.** Можно держать «движок» в C++, а «контент» в текстовых файлах.

Большие игры (Skyrim, World of Warcraft) хранят сотни тысяч объектов в файлах. Жёсткое разделение «движок против контента» — стандарт индустрии.

## Выбор формата

Какой формат файла? Варианты:

**JSON.** Стандарт. Хорошо парсится, есть библиотеки. Но многословный и требует кавычек:
```json
{
  "id": "glade",
  "name": "Лесная поляна",
  "description": "...",
  "exits": {"west": "village", "east": "forest"},
  "items": [
    {"type": "weapon", "name": "меч", "weight": 5, "damage": 8}
  ]
}
```

**YAML.** Менее многословно, но синтаксис со значимыми отступами тонкий.

**TOML.** Хорошо для конфигов, но плохо для иерархии.

**Свой формат.** Можно сделать максимально простой под свои нужды.

Для учебной цели свой формат лучше всего: меньше зависимостей, понятнее, что и как парсится. На реальном проекте — JSON или TOML через готовую библиотеку.

Наш формат — **линейно-ключевой**:

```
# Комментарий

location <id>
name <текст до конца строки>
desc <текст до конца строки>
exit <direction> <target_id>
item <type> <name> <weight> <extra>
```

Каждая строка — одна команда. Парсер читает построчно. Локация начинается с `location <id>`, дальше идут её свойства, пока не встретится новая `location` или конец файла.

## Архитектура парсера

Парсер состоит из:

1. **Read line** — читаем строку файла.
2. **Trim** — убираем пробелы по краям.
3. **Skip** — пропускаем комментарии и пустые строки.
4. **Tokenize** — извлекаем `keyword` и аргументы.
5. **Dispatch** — выполняем нужное действие на основе keyword.

Состояние парсера — текущая «черновая» локация. Каждый `name`, `desc`, `exit`, `item` модифицирует её. Каждая новая `location` — сохраняет старую и начинает новую.

Это **state machine**: два состояния — «нет активной локации» и «активная локация». Переход — по ключу `location`.

## Заголовок

`include/world_parser.h`:

```cpp
#ifndef RPG_WORLD_PARSER_H
#define RPG_WORLD_PARSER_H

#include "world.h"

#include <iosfwd>
#include <string>

namespace rpg {

// Парсер мира из текстового формата. Бросает WorldError при ошибках.
World parse_world(std::istream& in);
World load_world(const std::string& path);

}  // namespace rpg

#endif
```

Две функции:
- `parse_world(istream&)` — для тестов и для случаев, когда хотим читать не из файла.
- `load_world(path)` — удобная обёртка, открывает файл и зовёт `parse_world`.

`<iosfwd>` — заголовок с **forward declarations** для потоков. Объявляет `std::istream` и подобные, но без полных определений. Достаточно для параметров. Полная `<iostream>` тяжёлая (десятки тысяч строк через `<algorithm>` и прочие транзитивные include). `<iosfwd>` лёгкий.

В `.cpp` мы подключаем уже полные `<fstream>` и `<sstream>` — там нужно работать с потоками реально.

## Реализация: вспомогательные функции

`src/world_parser.cpp`:

```cpp
namespace {  // анонимное пространство — функции видны только в этом файле

std::string trim(const std::string& s) {
    auto b = s.find_first_not_of(" \t\r");
    if (b == std::string::npos) return {};
    auto e = s.find_last_not_of(" \t\r");
    return s.substr(b, e - b + 1);
}

std::string unescape_name(const std::string& s) {
    std::string r = s;
    std::replace(r.begin(), r.end(), '_', ' ');
    return r;
}

}  // namespace
```

`trim` — стандартная штука: убрать пробелы/табуляции/`\r` (на Windows-файлах в конце строки) с обоих краёв.

`unescape_name` — наш способ обработки пробелов в именах. В файле пишем `ржавый_меч`, в игре отображаем `ржавый меч`.

**Анонимное пространство** (`namespace { ... }`) — для функций, видимых только в этом `.cpp`. Альтернатива `static`. Я в книге использую `namespace { ... }` — это идиоматично в современном C++.

## Промежуточное состояние

Один блок в файле описывает локацию **постепенно** — сначала `name`, потом `desc`, потом несколько `exit` и `item`. Мы не можем создать `Location` сразу, нужно собирать.

Решение — **промежуточная структура**:

```cpp
struct LocationDraft {
    std::string id;
    std::string name;
    std::string desc;
    std::vector<std::pair<std::string, std::string>> exits;
    std::vector<std::unique_ptr<Item>> items;
};

Location finalize(LocationDraft& draft) {
    Location loc(std::move(draft.id), std::move(draft.name), std::move(draft.desc));
    for (auto& e : draft.exits) {
        loc.add_exit(e.first, e.second);
    }
    for (auto& item : draft.items) {
        loc.items().add(std::move(item));
    }
    return loc;
}
```

`LocationDraft` — простой POD (plain old data, набор полей). Мы её наполняем по мере чтения, а в конце `finalize` превращает в настоящий `Location`. После этого можно создать новый draft для следующей локации.

Это типичный паттерн **builder**: собираем «чертёж», в конце «строим».

## Парсинг строки предмета

```cpp
std::unique_ptr<Item> parse_item_line(std::istringstream& ss, int line_no) {
    std::string type, name;
    int weight = 0, extra = 0;
    if (!(ss >> type >> name >> weight >> extra)) {
        throw WorldError("строка " + std::to_string(line_no)
                         + ": неполная строка item");
    }
    std::string pretty = unescape_name(name);

    if (type == "weapon")     return make_unique<Weapon>(pretty, weight, extra);
    if (type == "armor")      return make_unique<Armor>(pretty, weight, extra);
    if (type == "consumable") return make_unique<Consumable>(pretty, weight, extra);

    throw WorldError("строка " + std::to_string(line_no)
                     + ": неизвестный тип предмета '" + type + "'");
}
```

`ss >> type >> name >> weight >> extra` — извлекает четыре поля через `std::istringstream` (мы их подробно рассмотрели в главе 12). Если поток в failure state — что-то не извлеклось, кидаем `WorldError`.

Дальше по типу диспатчируем: создаём `Weapon`, `Armor` или `Consumable`. Если тип неизвестен — ошибка.

Каждое исключение содержит **номер строки** — это критично для диагностики. Без него «строка item плохая» — где её искать?

## Главный цикл парсера

```cpp
World parse_world(std::istream& in) {
    World world;
    LocationDraft draft;
    bool have_draft = false;

    auto commit_draft = [&]() {
        if (have_draft) {
            world.add(finalize(draft));
            have_draft = false;
            draft = LocationDraft{};
        }
    };

    std::string line;
    int line_no = 0;
    while (std::getline(in, line)) {
        ++line_no;
        line = trim(line);
        if (line.empty() || line[0] == '#') continue;

        std::istringstream ss(line);
        std::string keyword;
        ss >> keyword;

        if (keyword == "location") {
            commit_draft();
            ss >> draft.id;
            if (draft.id.empty()) {
                throw WorldError("строка " + std::to_string(line_no)
                                 + ": location без id");
            }
            have_draft = true;
            continue;
        }

        if (!have_draft) {
            throw WorldError("строка " + std::to_string(line_no)
                             + ": '" + keyword + "' до 'location'");
        }

        if (keyword == "name") {
            std::string rest;
            std::getline(ss, rest);
            draft.name = trim(rest);
        } else if (keyword == "desc") {
            std::string rest;
            std::getline(ss, rest);
            draft.desc = trim(rest);
        } else if (keyword == "exit") {
            std::string dir, target;
            ss >> dir >> target;
            if (dir.empty() || target.empty()) {
                throw WorldError("строка " + std::to_string(line_no)
                                 + ": exit требует <direction> <target_id>");
            }
            draft.exits.emplace_back(std::move(dir), std::move(target));
        } else if (keyword == "item") {
            draft.items.push_back(parse_item_line(ss, line_no));
        } else {
            throw WorldError("строка " + std::to_string(line_no)
                             + ": неизвестный ключ '" + keyword + "'");
        }
    }

    commit_draft();
    return world;
}
```

Разберём.

**Лямбда `commit_draft`** — фиксирует «черновую» локацию в мире. Зачем лямбда? Используется дважды: при встрече новой `location` и в конце файла. Не хочется дублировать код. Захват `[&]` — нужно менять `draft`, `have_draft`, `world` снаружи.

**Цикл `while (std::getline(in, line))`** — читаем строки до конца файла. `getline` возвращает поток в булевом контексте: `true` пока всё OK, `false` при EOF/ошибке.

**`if (line.empty() || line[0] == '#') continue;`** — пропуск пустых строк и комментариев.

**`std::istringstream ss(line)`** — превращаем строку в поток для дальнейшего парсинга `>>`. Мы уже видели этот трюк в главе 12 и 13.

Дальше — диспатч по ключевому слову. Каждая ветка ожидает свои аргументы.

### `name` и `desc`

```cpp
if (keyword == "name") {
    std::string rest;
    std::getline(ss, rest);
    draft.name = trim(rest);
}
```

`getline(ss, rest)` берёт **весь остаток строки**, включая пробелы. Это нужно, потому что `name Лесная поляна` — поле из двух слов. Если бы мы делали `ss >> ss >> ...`, потеряли бы «поляна».

`trim(rest)` убирает ведущий пробел (тот, что между `name` и началом значения).

### `exit`

```cpp
} else if (keyword == "exit") {
    std::string dir, target;
    ss >> dir >> target;
    if (dir.empty() || target.empty()) {
        throw WorldError(...);
    }
    draft.exits.emplace_back(std::move(dir), std::move(target));
}
```

Два слова: направление и id цели. `emplace_back` конструирует `std::pair` прямо в векторе — без промежуточных копий (это глава 13).

### `item`

```cpp
} else if (keyword == "item") {
    draft.items.push_back(parse_item_line(ss, line_no));
}
```

Делегируем в `parse_item_line`. Внутри — четыре поля.

### Конец файла

```cpp
commit_draft();
return world;
```

Не забыть зафиксировать последний draft. До этого `commit_draft` вызывался только при встрече **новой** `location`; последний блок завершается концом файла.

## Уроки про парсинг

Несколько наблюдений из этой главы.

### Состояния парсера

У нас всего два: «нет активного блока» и «активный блок». Переход — keyword `location`. Это **machine с очень малым количеством состояний**.

Для большего формата (например, вложенные блоки) понадобились бы:
Для вложенных структур нужен либо стек состояний, хранящий текущую область, либо рекурсивный разбор, где каждому состоянию соответствует своя функция. Второй способ мы применим в главе 36, когда будем разбирать SQL.

JSON-парсер, например, использует рекурсию.

### Сообщения об ошибках

**Каждая ошибка содержит номер строки**. Это критично. Без номера пользователь не найдёт проблему.

Хороший парсер на ошибку:
Хорошее сообщение об ошибке указывает место — файл, строку, по возможности колонку, — говорит, что ожидалось, и показывает, что получено вместо этого. Три части, и без любой из них сообщение становится вдвое бесполезнее.

Мы это делаем. Можно ещё добавить контекст (несколько строк вокруг), но для учебного достаточно.

### Иммутабельность данных

Заметили: `Location` после конструктора **не меняется**. `name`, `desc`, `exits`, `items` устанавливаются один раз. Это упрощает логику и делает класс безопасным к ошибкам.

Если бы у `Location` были сеттеры (`set_name`, `set_desc`), можно было бы строить её итеративно. Но тогда повсюду риск: «а вдруг кто-то поменяет уже созданную локацию во время игры?». Мы избегаем этого через паттерн **builder** (`LocationDraft` → `finalize`).

Это **полу-immutable** дизайн. У `World` сеттер есть (`add`), но он используется только при загрузке.

### Tokenizer vs парсер

В нашем парсере токенизация и парсинг **смешаны**: `std::istringstream` сама делит строку на слова, и мы прямо в логике диспатчим.

В **больших парсерах** (компилятор C++, JSON-движок) это разделяют:
1. **Lexer/tokenizer** превращает текст в поток токенов (`KEYWORD`, `IDENTIFIER`, `NUMBER`, ...).
2. **Parser** работает с токенами, строит AST.

Для нашей задачи разделение overkill. Но знайте, что в больших задачах оно есть.

### Robust vs strict парсер

Наш парсер **строгий**: любая ошибка — `throw`. Запустился — мир загружен. Не запустился — игра не работает вообще.

Альтернатива — **прощающий** парсер: пропускать неизвестные ключи, не падать на одной плохой локации. Подходит для пользовательских моддинг-форматов: пользователь добавил кривую локацию — остальное всё равно загрузится.

Что лучше — зависит от задачи. Для разработки лучше строгий (баги видны сразу). Для пользователей — мягкий.

## std::variant — упоминание (C++17)

В нашем коде у Item-иерархии **три типа**: `Weapon`/`Armor`/`Consumable`. Мы держим их через `std::unique_ptr<Item>` и проверяем через `dynamic_cast`. Это классический ОО-подход.

В C++17 появился `std::variant<Weapon, Armor, Consumable>` — он хранит **один из** перечисленных типов. Доступ через `std::visit` (компилятор сам выбирает нужный код в зависимости от того, что сейчас в variant'е).

Преимущества `std::variant`:
Плюсы такого подхода: нет виртуальных вызовов, тип известен на этапе компиляции и потому доступен оптимизациям, структура плоская и без наследования.

Недостатки:
Минусы — закрытое множество типов, куда нельзя добавить четвёртый, не переписав всё, и более громоздкий способ работы через посетителя. Подробнее об этом в главе 48, где появится `std::variant`.

У нас C++11. `std::variant` нет. Альтернатива — **tagged union**: `struct { Type tag; union { Weapon w; Armor a; Consumable c; }; };`. Старо, многословно, но работает. В нашем коде проще остаться на наследовании.

## Главные правила главы

1. **Контент в файлах, движок в коде.** Разделение.
2. **Builder паттерн** для постепенного сбора объекта.
3. **Каждая ошибка с номером строки.** Без этого диагностика плачет.
4. **Анонимные пространства** для функций видимых только в .cpp.
5. **`std::istringstream`** для парсинга одной строки.
6. **`getline(ss, rest)`** для получения остатка строки (включая пробелы).
7. **Builder-объект + finalize** для постепенной инициализации иммутабельных классов.
8. **Большие парсеры разделяют tokenizer и parser**, маленькие — нет.

## Маленькое упражнение

1. Запустите игру (`make && ./build/rpg`). Попробуйте все 5 локаций.

2. Добавьте в `data/world.txt` локацию `tower` — высокая башня. Из деревни выход `north tower`, из башни — `south village`. Положите в неё `weapon магический_посох 3 20`. Запустите. Никаких изменений в C++ не делайте.

3. Намеренно сломайте `data/world.txt`: уберите `name` у одной из локаций. Запустите игру. Что произойдёт? Сообщение об ошибке понятное?

4. Добавьте в формат строку `start <id>` — указание стартовой локации. Сейчас зашито `glade` в `Game::Game()`. Сделайте, чтобы стартовая локация читалась из файла.

5. Добавьте поддержку `# inline комментариев` — комментарий **на конце строки**, например:
   ```
   exit west village  # дорога вниз
   ```
   Подсказка: найти `#` в строке и обрезать до него.

6. (Сложнее) Сделайте парсер прощающим: при ошибке вместо `throw` логировать предупреждение и продолжать. Подсказка — заменить `throw` на `std::cerr << ...; continue;` или собирать ошибки в `std::vector<std::string>` для итогового отчёта.

7. (Сложнее) Сделайте формат поддерживающим **NPC** — пока без логики, просто запись имени и тек. Расширьте `Location`, чтобы хранил список NPC-имён.

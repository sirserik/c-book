# Глава 26. Процессы — fork, exec, wait

Начинается **Часть III — mini-shell**. Шесть глав, в которых построим свою bash-подобную оболочку. Это другая половина C++: не «прикладной код через классы и STL», а **системное программирование** через POSIX API. Никаких новых языковых средств — но новый мир системных вызовов.

Эта глава — про **процессы**. Что они такое (повтор из главы 1 с подробностями), как их создавать через `fork`, как заменять их образ через `exec`, как ждать завершения через `wait`. К концу главы у нас работает **минимальный shell**: вводите `ls /tmp`, программа запускает `ls`, ждёт, печатает результат.

## Зачем shell

Shell (по-русски «оболочка») — это программа, которая:
1. Печатает приглашение (`$`).
2. Читает строку от пользователя.
3. Запускает указанную команду.
4. Ждёт завершения.
5. Печатает результат и возвращается к шагу 1.

В Unix вы каждый день пользуетесь shell — `bash`, `zsh`, `fish`. Они мощные, с автодополнением, историей, скриптами. Мы пишем простой, но настоящий.

Зачем это в книге про C++? Несколько причин:

1. **Учим POSIX API**. Системные вызовы `fork`, `exec`, `wait`, `pipe`, `dup2`, `signal` — это фундамент Unix. Понимая их, вы понимаете, как работает любой Linux/macOS-софт.
2. **Близко к ОС**. Мы выходим из «прикладного слоя» (RPG-игра, нажимаем кнопки) в системный (работаем с ядром).
3. **Полезный навык**. Часто нужно «запустить внешнюю программу из моей» — серверы, билд-системы, тестовые runner'ы. Это всё `fork+exec`.
4. **C++ может работать на низком уровне.** Не только Boost и шаблоны, но и сырые системные вызовы.

## Где не сработает

POSIX — это Unix-стандарт. Linux и macOS его поддерживают. **Нативный Windows — нет**. На Windows другой API: `CreateProcess`, `WaitForSingleObject`. Идея похожа, синтаксис другой.

Если вы на Windows — поставьте WSL2 (глава 6) и работайте оттуда. Всё, что я буду писать, будет работать. На нативном cmd.exe — не запустится.

## Что такое процесс — снова

В главе 1 я уже говорил, что процесс — это «запущенная программа». Расширим.

Каждому процессу ОС выделяет:

- **PID** (process ID) — уникальный номер.
- **Адресное пространство** — виртуальная память: код, данные, стек, куча. Изолировано от других процессов.
- **Открытые файловые дескрипторы** — обычно как минимум три: stdin (0), stdout (1), stderr (2).
- **Текущая рабочая папка** — где он «находится» в файловой системе.
- **Переменные окружения** — наследуемые от родителя.
- **Идентификатор владельца** (UID).
- **Идентификатор родительского процесса** (PPID).

Процессы связаны в **дерево**. У каждого процесса есть родитель. У корня всего дерева (PID 1, обычно `init` или `systemd`) родителя нет. Когда вы запускаете программу из терминала, ваш `bash` — родитель этой программы.

```
PID 1: systemd
├── PID 123: sshd
│   └── PID 456: bash    (терминал на котором вы)
│       └── PID 789: ls   (запустили ls — bash его родитель)
```

Когда процесс завершается, его статус возвращается **родителю**. Если родитель не забрал — процесс становится **зомби** (об этом ниже).

## Системный вызов fork

В Unix есть `fork()` — функция, **дублирующая** текущий процесс. После `fork()` есть **два** одинаковых процесса:
- **Родитель**: продолжает работать как раньше.
- **Ребёнок**: копия родителя в момент `fork`.

Оба возвращаются из `fork()` с разным значением:
- В родителе `fork()` возвращает **PID ребёнка** (положительное число).
- В ребёнке `fork()` возвращает **0**.
- При ошибке возвращает **-1**.

Это позволяет программе понять, где она сейчас:

```cpp
#include <unistd.h>
#include <iostream>

int main() {
    pid_t pid = fork();
    
    if (pid < 0) {
        std::cerr << "fork failed\n";
        return 1;
    }
    
    if (pid == 0) {
        std::cout << "Я ребёнок, PID = " << getpid() << "\n";
    } else {
        std::cout << "Я родитель, PID ребёнка = " << pid << "\n";
    }
    
    return 0;
}
```

Запустите — увидите две строки. Они выводятся в **одной** программе, но в **двух процессах**.

`pid_t` — тип для PID, обычно `int`. Объявлен в `<sys/types.h>` (но `<unistd.h>` его подтягивает).

### Что значит «копия»

`fork()` копирует **всё**: содержимое памяти, стек, открытые файлы. Сразу после `fork` оба процесса абсолютно одинаковы, кроме одной вещи — значения, возвращаемого `fork()`.

Полная копия процесса с 100 MB памяти — это дорого. Поэтому современные ОС используют **copy-on-write**: реальная копия не делается; ядро помечает страницы памяти как «общие, копировать при попытке записи». Если оба процесса только читают — данные общие. Если кто-то пишет — страница копируется на лету.

Это значит, что `fork()` сам по себе **быстрый**, даже на больших процессах.

### Что наследуется от родителя

- Память: всё содержимое.
- Открытые файловые дескрипторы.
- Текущая папка.
- Переменные окружения.
- Маски сигналов (что игнорировать).

Что **не** наследуется (вернее, обнуляется/новое):
- PID (у ребёнка свой).
- Время CPU (счётчик 0).
- Pending signals (ожидающие сигналы родителя — не передаются).
- Замки на файлы (`flock`).

### Где работа после fork разделяется

Сразу после `fork` процессы абсолютно одинаковы. Дальше каждый идёт своей дорогой:
- Родитель обычно **продолжает свою основную работу**.
- Ребёнок обычно **делает специальную задачу** и завершается.

В нашем shell:
- Родитель ждёт завершения ребёнка.
- Ребёнок вызывает `exec` чтобы стать другой программой.

## exec — заменить образ

`exec` сам по себе **не функция**, а семейство функций: `execv`, `execvp`, `execvpe`, `execl`, `execle`, `execlp`. Они различаются способом передачи аргументов и поиска программы.

Мы используем **`execvp`** (`v` = vector аргументов, `p` = искать в `$PATH`):

```cpp
#include <unistd.h>

char* argv[] = {"ls", "-l", "/tmp", nullptr};
execvp("ls", argv);
// если выполнилось — мы НЕ здесь, мы стали `ls`
```

`execvp(name, argv)` делает следующее:
1. Ищет программу `name` в `$PATH` (если есть слеш — ищет по этому пути напрямую).
2. **Загружает** её в текущий процесс, **заменяя** код, данные, стек.
3. Запускает с `main(argc, argv)`.

После `execvp` сама программа уже **другая**. Ваш C++-код не выполняется дальше. Это как «магически перевоплотиться».

**Если `execvp` вернулась** — значит, что-то не получилось (программу не нашли, прав нет, недостаточно памяти). Тогда обычно вызывают `_exit(N)` чтобы немедленно завершить ребёнка.

### `_exit` vs `exit`

- **`exit(N)`** — стандартная C-функция: вызывает все деструкторы global-объектов, `atexit`-обработчики, потом завершает.
- **`_exit(N)`** — POSIX: завершает **немедленно**, без деструкторов и cleanup.

В ребёнке после неудачного `exec` лучше **`_exit`**: ребёнок — это копия родителя, его global-объекты ещё «работают» в родителе. Если ребёнок начнёт их разрушать — будет хаос.

Возврат 127 — конвенция: «команда не найдена».

### Каноническая пара fork + exec

```cpp
pid_t pid = fork();
if (pid < 0) {
    // ошибка
} else if (pid == 0) {
    // ребёнок
    execvp("ls", argv);
    _exit(127);    // exec failed
} else {
    // родитель
    // ...
}
```

Это **базовый шаблон Unix**. Один процесс хочет запустить другой? Fork (создаём пустую заготовку), exec (превращаем в нужную программу), wait (ждём результат).

Винда делает то же одним `CreateProcess(...)`. Идея та же, синтаксис другой.

## wait и waitpid — собрать статус

Когда ребёнок завершается, его статус не теряется — он **ждёт**, пока родитель его заберёт. Если родитель не забирает — ребёнок остаётся **зомби** (записью в таблице процессов, занимающей PID и память для status).

Чтобы забрать статус, родитель вызывает **`wait`** или **`waitpid`**:

```cpp
#include <sys/wait.h>

int status;
pid_t finished = waitpid(pid, &status, 0);
```

- `waitpid(pid, ...)` — ждать конкретного ребёнка.
- `waitpid(-1, ...)` — ждать любого.
- `waitpid(0, ...)` — ждать любого в той же группе процессов.

Третий аргумент — флаги. `0` — блокировать до завершения. `WNOHANG` — не блокировать, проверить и вернуться.

Возвращает PID завершившегося (или -1 при ошибке, 0 если `WNOHANG` и никто не готов).

В `status` — кодированный статус. Распаковывается макросами:

- **`WIFEXITED(status)`** — true, если процесс завершился нормально (через `return` из `main` или `exit()`).
- **`WEXITSTATUS(status)`** — код возврата (если `WIFEXITED`).
- **`WIFSIGNALED(status)`** — true, если завершился из-за сигнала (например, SIGSEGV, SIGKILL).
- **`WTERMSIG(status)`** — номер сигнала (если `WIFSIGNALED`).
- **`WIFSTOPPED(status)`** — true, если приостановлен (через SIGSTOP).

Пример:

```cpp
int status;
waitpid(pid, &status, 0);

if (WIFEXITED(status)) {
    int code = WEXITSTATUS(status);
    std::cout << "exit " << code << "\n";
} else if (WIFSIGNALED(status)) {
    std::cout << "killed by signal " << WTERMSIG(status) << "\n";
}
```

## Зомби и orphans

Два особых состояния процесса.

**Зомби (zombie)**: процесс умер, но родитель не вызвал `wait`. Процесс присутствует в таблице, занимает PID и небольшой кусок памяти (для статуса). В `ps` помечается как `Z` или `<defunct>`.

Если зомби много — кончатся PID-ы (на Linux обычно лимит 32768). Поэтому каждый родитель **обязан** забирать статус всех своих детей.

**Орфан (orphan)**: ребёнок жив, родитель умер раньше. Ребёнок «усыновляется» PID 1 (`init`/`systemd`). Тот забирает статус и не оставляет зомби.

В нашем shell зомби не появятся: на каждый `fork` есть `waitpid`.

## Минимальный shell

Соединим всё.

`include/exec_runner.h`:

```cpp
namespace shell {

int run_external(const std::vector<std::string>& argv);
std::vector<std::string> tokenize(const std::string& line);

}  // namespace shell
```

`src/exec_runner.cpp`:

```cpp
#include "exec_runner.h"

#include <cerrno>
#include <cstring>
#include <iostream>
#include <sstream>
#include <vector>

#include <sys/wait.h>
#include <unistd.h>

namespace shell {

std::vector<std::string> tokenize(const std::string& line) {
    std::vector<std::string> result;
    std::istringstream ss(line);
    std::string tok;
    while (ss >> tok) {
        result.push_back(tok);
    }
    return result;
}

int run_external(const std::vector<std::string>& argv) {
    if (argv.empty()) return 0;

    std::vector<char*> c_argv;
    c_argv.reserve(argv.size() + 1);
    for (const auto& s : argv) {
        c_argv.push_back(const_cast<char*>(s.c_str()));
    }
    c_argv.push_back(nullptr);

    pid_t pid = fork();
    if (pid < 0) {
        std::cerr << "fork failed: " << std::strerror(errno) << "\n";
        return -1;
    }

    if (pid == 0) {
        execvp(c_argv[0], c_argv.data());
        std::cerr << "exec '" << argv[0] << "' failed: "
                  << std::strerror(errno) << "\n";
        _exit(127);
    }

    int status = 0;
    if (waitpid(pid, &status, 0) < 0) {
        std::cerr << "waitpid failed: " << std::strerror(errno) << "\n";
        return -1;
    }

    if (WIFEXITED(status)) return WEXITSTATUS(status);
    if (WIFSIGNALED(status)) {
        std::cerr << "[процесс прерван сигналом " << WTERMSIG(status) << "]\n";
        return 128 + WTERMSIG(status);
    }
    return -1;
}

}  // namespace shell
```

Разбор.

**`tokenize`** разбивает строку по пробелам через `istringstream` (это глава 12). Не учитывает кавычки и escape — добавим в главе 29.

**`c_argv`** — массив `char*`, чтобы передать в `execvp`. Используем `const_cast<char*>(s.c_str())` — `execvp` объявлена для `char*`, не `const char*` (исторически — API из C 1970-х). На самом деле программа не меняет аргументы; const_cast тут безопасен.

`c_argv.push_back(nullptr)` — обязательно. `execvp` ожидает массив, **оканчивающийся `nullptr`**.

**`fork()`** — создаёт ребёнка. Проверяем три случая: ошибка (`< 0`), ребёнок (`== 0`), родитель (`> 0`).

**В ребёнке** — `execvp(c_argv[0], c_argv.data())`. Если вернулась — exec не сработал. Печатаем причину через `strerror(errno)` (это глобальная ошибка из C), и завершаемся `_exit(127)`.

**В родителе** — `waitpid` блокирует до завершения ребёнка. Дальше расшифровываем статус.

`128 + WTERMSIG(status)` — конвенция bash: сигнал 9 (SIGKILL) даёт код 137, сигнал 11 (SIGSEGV) — 139. Так пользователь различает «нормальное завершение с кодом X» и «убит сигналом Y».

### main и REPL

`src/main.cpp`:

```cpp
#include "exec_runner.h"
#include <iostream>
#include <string>

int main() {
    std::cout << "=== myshell ===\n";

    while (true) {
        std::cout << "myshell$ ";
        std::cout.flush();

        std::string line;
        if (!std::getline(std::cin, line)) {
            std::cout << "\n";
            break;
        }
        if (line.empty()) continue;

        auto tokens = shell::tokenize(line);
        if (tokens.empty()) continue;

        if (tokens[0] == "exit" || tokens[0] == "quit") break;

        int rc = shell::run_external(tokens);
        if (rc != 0) {
            std::cerr << "[exit " << rc << "]\n";
        }
    }
    return 0;
}
```

REPL (read-eval-print loop):
1. Приглашение и флаш.
2. Чтение строки.
3. Если пустая — повтор.
4. Если `exit`/`quit` — выход.
5. Иначе — запуск.

`std::cout.flush()` — обязательно, иначе приглашение зависнет в буфере. Без явного flush текст появляется только после переноса строки.

## Что происходит под капотом

Сценарий «вы набрали `ls /tmp` в моём shell»:

1. **`getline(std::cin, line)`** — shell читает строку.
2. **`tokenize`** — `["ls", "/tmp"]`.
3. **`run_external`** вызывается с этим вектором.
4. **`fork()`** — ядро создаёт ребёнка. Сейчас у нас два процесса с одинаковой памятью.
5. **В ребёнке** — `execvp("ls", {"ls", "/tmp", nullptr})`. Ядро ищет `/bin/ls`, читает его исполняемый файл, **заменяет** код и данные процесса. Старая копия myshell в ребёнке **перестаёт существовать**. Дальше работает `ls`.
6. **`ls`** выполняется, печатает содержимое `/tmp` в свой stdout, который **наследовался от shell** и направлен в терминал.
7. **`ls` завершается** через `return 0` или `exit(0)`. Ядро записывает статус.
8. **В родителе** — `waitpid` пробуждается. Получает PID и статус.
9. **`WIFEXITED(status)`** = true, **`WEXITSTATUS(status)`** = 0.
10. `run_external` возвращает 0.
11. `main` идёт на следующую итерацию.

Десять шагов на одну команду. Каждый шаг — конкретный системный вызов или часть кода. Никакой магии.

## Тонкости

### Почему стандартные потоки наследуются

Файловые дескрипторы (включая stdin/stdout/stderr) **наследуются** при `fork`. После `exec` они **сохраняются** (если не отмечены флагом `FD_CLOEXEC`). Поэтому `ls`, запущенный из shell, пишет в тот же терминал. Если бы `exec` обнулил дескрипторы — `ls` ничего бы не вывел.

В главе 27 мы используем это поведение для пайпов: `dup2` подменит fd 1 (stdout) ребёнка на пайп, и вывод пойдёт в следующую команду.

### Среда (environment)

При `fork` копируются переменные окружения. `execvp` тоже их сохраняет (использует свою копию). Поэтому если в shell задана `LANG=ru_RU.UTF-8` — у запущенной программы тоже она будет.

Изменить — `setenv("KEY", "value", 1)` перед `exec`. Это редко нужно, но иногда полезно («запусти эту программу с переменной A=1»).

### Прерывание ребёнка

В нашем shell, если ребёнок зависает (например, `cat` без stdin), вы не можете его остановить. `Ctrl+C` посылает SIGINT — но **в нашу группу процессов**, включая родителя. Родитель тоже падает.

В настоящем shell сигналы разруливают так: shell в **своей** группе процессов, ребёнок в **отдельной**. `Ctrl+C` идёт ребёнку, родитель ловит и **игнорирует**.

Это глава 28 (сигналы).

### Что с zsh / bash подобными фичами

Наш shell — **очень** простой:
- Нет переменных (`x=5; echo $x`).
- Нет history.
- Нет автодополнения.
- Нет alias.
- Нет встроенных команд (`cd`, `export`).
- Нет skripts (`bash script.sh`).

Это всё надстройки. Базовый цикл fork+exec+wait у настоящего bash и у нашего myshell — одинаковый.

## fork без exec

`fork` без `exec` — это **просто параллельный код**. Можно так:

```cpp
pid_t pid = fork();
if (pid == 0) {
    // ребёнок — выполняет свою работу
    do_heavy_calculation();
    _exit(0);
}
// родитель — делает свою работу одновременно
do_other_work();
waitpid(pid, nullptr, 0);
```

Это **примитивный параллелизм**. Раньше так делали серверы — отдельный процесс на клиента. Сейчас обычно потоки (`std::thread`), потому что они дешевле. Но `fork` без exec тоже используется — например, в **prefork** моделях серверов (apache, php-fpm).

## Главные правила главы

1. **`fork` дублирует процесс, `exec` заменяет образ.** Стандартный паттерн запуска внешней команды.
2. **В ребёнке после exec НЕ должно быть кода**, кроме обработки ошибки и `_exit`.
3. **Каждый `fork` требует `waitpid`** — иначе зомби.
4. **`_exit` в ребёнке** на error path, не `exit` — чтобы не запустить деструкторы родителя.
5. **POSIX = Linux/macOS. Windows = WSL2.**
6. **`argv` массив для exec кончается `nullptr`.** Забыли — UB.
7. **`fflush` или `endl` перед чтением ввода.** Иначе приглашение зависнет.
8. **Сигналы и Ctrl+C** — отдельная тема, глава 28.

## Маленькое упражнение

1. Соберите `demo-shell` (`cd demo-shell && make`). Запустите. Поэкспериментируйте: `ls`, `pwd`, `date`, `whoami`, `echo hello`.

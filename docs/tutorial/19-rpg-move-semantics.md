# Глава 19. Move-семантика на бою

Move-семантика — одна из главных новинок C++11 и одна из самых страшно выглядящих. На самом деле идея простая: вместо копирования объекта **перемещать** его. Если объект тяжёлый — это огромная экономия. Если временный — это вообще без накладных расходов.

Мы уже несколько глав используем `std::move` и `&&` в сигнатурах, не объясняя глубоко. Эта глава — подробный разбор: что такое rvalue, что такое rvalue-ссылки, что **на самом деле** делает `std::move`, как пишут move-конструктор, что такое RVO и почему компилятор иногда вообще ничего не копирует.

После этой главы у вас в голове сложится цельная картина того, как объекты живут, копируются, перемещаются и умирают в C++.

## Зачем move

Допустим, у нас функция, возвращающая большую коллекцию:

```cpp
std::vector<int> generate(int n) {
    std::vector<int> result(n);
    for (int i = 0; i < n; ++i) result[i] = i * i;
    return result;
}

int main() {
    auto v = generate(1000000);
}
```

Что происходит?

1. Внутри `generate` создаётся `result` — миллион `int`-ов на куче.
2. `return result;` — возврат.
3. В `main` создаётся `v` — копия?

В C++98 — **да**, это была копия. Миллион `int`-ов выделить заново и скопировать — несколько мегабайт памяти. Дорого.

В C++11 благодаря move-семантике (и RVO ещё раньше) — **нет**. Никакой копии. `v` получает «внутренности» `result` напрямую. Скорость — наносекунды.

Этот сдвиг изменил, как пишут на C++. Большие объекты можно свободно возвращать из функций, передавать в контейнеры. Раньше использовали указатели и аллокации руками, а в современном C++ — просто значения. И они быстрые.

## lvalue и rvalue

Начнём с фундамента. В C++ есть две категории выражений (упрощённо):

**lvalue** — то, что имеет адрес в памяти, на что можно «указать». Имеет имя и/или живёт дольше одного выражения.

```cpp
int x = 5;   // x — lvalue, у неё есть адрес &x
int& r = x;  // r — тоже lvalue (другое имя для x)
x = 10;      // OK: можно присвоить
```

**rvalue** — временное значение. Живёт ровно одно выражение. Адреса нет (формально).

```cpp
5             // rvalue (литерал)
x + 1         // rvalue (результат вычисления)
foo()         // rvalue (если foo возвращает по значению)
std::move(x)  // rvalue (об этом ниже)
```

Можно попробовать:

```cpp
&5;       // ОШИБКА: cannot take the address of an rvalue
&(x + 1); // ОШИБКА: то же
&x;       // OK: x это lvalue
```

«L» от «left side of assignment»: `x = 5;` — слева lvalue, справа rvalue. «R» — соответственно «right».

Это упрощённая модель. В современном C++ категорий выражений больше (lvalue, xvalue, prvalue, glvalue), но для нашего обсуждения хватит lvalue/rvalue.

## Главное различие на практике

С rvalue можно делать вещи, которых нельзя с lvalue:
- «Ограбить» — забрать у него внутренности. Раз он временный — никто не заметит.

С lvalue вообще-то тоже можно (объявлено как `std::move`), но это **программистское решение**: «я знаю, что эту переменную больше использовать не буду, можно её опустошить».

## Rvalue-ссылки: T&&

Чтобы функция могла различать lvalue и rvalue, в C++11 добавили **rvalue-ссылки**:

```cpp
void f(int& x)  { std::cout << "lvalue\n"; }
void f(int&& x) { std::cout << "rvalue\n"; }

int main() {
    int a = 5;
    f(a);     // "lvalue"
    f(5);     // "rvalue"
    f(a + 1); // "rvalue"
    f(std::move(a));  // "rvalue"
}
```

`int&` — обычная ссылка на lvalue.
`int&&` — ссылка на rvalue.

Двойной амперсанд `&&` это **отдельный знак**, не два амперсанда. Логического И тут нет.

Обе ссылки — это «псевдоним переменной». Различие — в том, **какую категорию выражения** они принимают.

### Что внутри rvalue-ссылки

Парадокс: переменная-rvalue-ссылка сама является **lvalue**:

```cpp
void f(int&& x) {
    // x — это rvalue-ссылка, но сама x — lvalue
    int& r = x;   // OK: lvalue
    
    // чтобы передать дальше как rvalue:
    int&& r2 = std::move(x);
    // или
    other_function(std::move(x));
}
```

Это путает. Запомните: rvalue-ссылка — это **способ принять rvalue**, но внутри функции переменная имеет имя и адрес, то есть lvalue.

## Move-конструктор и move-присваивание

Раз можно перегружать функции по rvalue, можно перегрузить и **конструктор**. Это и есть move-конструктор:

```cpp
class Buffer {
public:
    // Обычный (copy) конструктор: принимает lvalue
    Buffer(const Buffer& other);
    
    // Move-конструктор: принимает rvalue
    Buffer(Buffer&& other) noexcept;
};
```

Зачем? Copy-конструктор делает **глубокую копию** — выделяет новую память, копирует байты. Move-конструктор просто **забирает** указатель из источника:

```cpp
class Buffer {
public:
    // copy: новая память + копирование
    Buffer(const Buffer& other)
        : data_(new int[other.size_]),
          size_(other.size_) {
        for (std::size_t i = 0; i < size_; ++i) {
            data_[i] = other.data_[i];
        }
    }
    
    // move: забираем чужие внутренности
    Buffer(Buffer&& other) noexcept
        : data_(other.data_),
          size_(other.size_) {
        other.data_ = nullptr;   // обнуляем источник
        other.size_ = 0;
    }
    
    ~Buffer() {
        delete[] data_;   // если data_ == nullptr, delete[] просто ничего не делает
    }

private:
    int* data_;
    std::size_t size_;
};
```

Сравним стоимость:
- Copy: `new int[N]` + `memcpy(N*sizeof(int))`. На миллионе элементов — миллисекунды.
- Move: четыре присваивания указателей и чисел. **Наносекунды.**

В сто-тысячу раз быстрее. Особенно для строк и контейнеров.

### noexcept на move-конструкторе

Заметили `noexcept` в сигнатуре move-конструктора? Это обещание «не бросает исключений». Важно!

Если move-конструктор может бросить — `std::vector` при перевыделении (когда `push_back` исчерпал capacity) **откажется** его использовать и упадёт на copy. Стандарт говорит: контейнерам нужна **сильная exception guarantee**. Они полагаются на `noexcept` move.

**Правило**: помечайте move-конструктор/присваивание `noexcept`, если не делаете ничего, что может выкинуть. Обычно так и есть — простые присваивания указателей и чисел.

### Move-присваивание

Тот же принцип для оператора `=`:

```cpp
class Buffer {
public:
    Buffer& operator=(const Buffer& other) {
        if (this != &other) {
            delete[] data_;
            data_ = new int[other.size_];
            size_ = other.size_;
            for (std::size_t i = 0; i < size_; ++i) {
                data_[i] = other.data_[i];
            }
        }
        return *this;
    }
    
    Buffer& operator=(Buffer&& other) noexcept {
        if (this != &other) {
            delete[] data_;        // освобождаем своё
            data_ = other.data_;    // забираем чужое
            size_ = other.size_;
            other.data_ = nullptr;
            other.size_ = 0;
        }
        return *this;
    }
};
```

Move-присваивание сначала освобождает свои ресурсы, потом забирает чужие. И обнуляет источник.

`if (this != &other)` — проверка от **self-assignment** (`a = std::move(a);`). Без неё `delete[] data_` уничтожил бы то, что мы потом пытаемся забрать у того же объекта.

## std::move — что это на самом деле

Я говорил «std::move — это перемещение». На самом деле — **не совсем**.

`std::move(x)` **ничего не перемещает**. Это просто **приведение типа** — оно превращает `x` в rvalue.

Грубо:

```cpp
template <typename T>
typename std::remove_reference<T>::type&& move(T&& x) noexcept {
    return static_cast<typename std::remove_reference<T>::type&&>(x);
}
```

Это шаблон, который принимает что угодно и кастует к rvalue-ссылке. Никакого «перемещения» в этой функции нет. Имя `move` — обманчивое, лучше бы было `rvalue_cast`.

**Перемещение** делает потом — move-конструктор или move-присваивание, к которым приводит эта rvalue.

```cpp
Buffer a(100);
Buffer b = std::move(a);
// std::move(a) превратило a в rvalue
// потом вызывается Buffer(Buffer&&) — move-конструктор
// внутри он опустошает a
```

Сам по себе `std::move` не делает ничего. Без move-конструктора (если вы его не определили) `std::move` бесполезен — компилятор откатится на copy.

## Когда move бесплатен

Move-конструктор имеет смысл, когда у класса есть **дорогой ресурс**: динамическая память, файл, сокет, мьютекс.

Для классов с одними тривиальными полями (`int`, `double`, `bool`) move = copy. Никакой разницы.

Стандартные классы, у которых полезный move:

- `std::string` — для длинных строк.
- `std::vector` — внутренний массив переходит к новому владельцу.
- `std::unique_ptr` — указатель переходит (мы уже это делали).
- `std::shared_ptr` — указатель + контрол блок (но без атомарного увеличения счётчика).
- `std::map`, `std::unordered_map`, `std::set`, `std::list`, и так далее.

Для собственных классов с динамической памятью — пишите move.

## Rule of five детально

В главе 11 и 16 я упоминал rule of five. Теперь полная картина.

Если ваш класс **управляет ресурсом** (нетривиальный деструктор), вам нужны **пять** специальных функций:

1. **Деструктор** — освобождает ресурс.
2. **Copy-конструктор** — глубокая копия (или запрет).
3. **Copy-присваивание** — глубокое копирование с предварительным освобождением.
4. **Move-конструктор** — забор ресурса с обнулением источника.
5. **Move-присваивание** — освобождение своего + забор + обнуление.

Это **rule of five**. C++11 разделил его на «обязательную часть» (1-3) и «опциональный плюс» (4-5).

Если все пять не нужны, явно их пишите как `= delete` или `= default`:

```cpp
class Unique {
public:
    Unique() = default;
    ~Unique() = default;
    
    Unique(const Unique&) = delete;
    Unique& operator=(const Unique&) = delete;
    
    Unique(Unique&&) noexcept = default;
    Unique& operator=(Unique&&) noexcept = default;
};
```

«Я не копирую, перемещаю по умолчанию».

### Когда компилятор сам генерирует move

По умолчанию (без `= default`) move-конструктор и move-присваивание **генерируются автоматически**, но только если:

- Вы не объявили **никакой** из специальных функций (деструктора, copy-конструктора, copy-присваивания).
- Все поля — движимые.

Если объявили деструктор — move **не** генерируется. Если объявили copy — тоже.

Это «правило zero»: для класса с только стандартными полями (`std::string`, `std::vector`, ...) — ничего не пишете, всё генерируется правильно.

## RVO и NRVO

В коде:

```cpp
Buffer make_buffer() {
    Buffer b(100);
    return b;
}

int main() {
    Buffer x = make_buffer();
}
```

Сколько раз вызывается конструктор?

В C++11 — **один** раз, благодаря RVO/NRVO.

**RVO** (return value optimization): компилятор замечает, что возвращаемый объект — это конкретный возвращаемый объект. Вместо «создать в `make_buffer`, потом скопировать в `main`» — он строит `x` **прямо в стеке `main`**. Никакого `make_buffer::b` отдельно нет. Всё в одном месте.

**NRVO** (named RVO) — то же, но для именованных переменных (`Buffer b` в нашем коде). Чуть сложнее реализовать; компилятор делает это эвристически.

С C++17 **RVO стало обязательным** — компилятор гарантированно не делает копию для prvalue. Для NRVO — пока на усмотрение компилятора (обычно делает).

Это значит: вы пишете `return some_local;` для большого объекта **без страха**. Компилятор сам оптимизирует.

### Когда RVO не работает

NRVO ломается в нескольких случаях:

```cpp
Buffer make_buffer(bool flag) {
    Buffer a(100);
    Buffer b(200);
    return flag ? a : b;   // !! NRVO не сработает
}
```

Компилятор не знает заранее, какой возвращать. Не может построить «прямо в месте назначения». Тут будет move (если есть) или copy.

Ещё:

```cpp
Buffer make_buffer() {
    Buffer b(100);
    return std::move(b);   // !!! НЕ ДЕЛАЙТЕ ТАК
}
```

Многие новички думают «помогу компилятору с move». На самом деле — **испортите**. С `std::move` компилятор не может применить NRVO; вместо нуля копий получится move. Move дешевле, чем copy, но дороже, чем ничего.

**Правило**: **не пишите `std::move` в `return`** на локальную переменную. Компилятор сам разберётся.

## Perfect forwarding и std::forward

Мы уже использовали `std::forward` в шиме `make_unique`:

```cpp
template <typename T, typename... Args>
std::unique_ptr<T> make_unique(Args&&... args) {
    return std::unique_ptr<T>(new T(std::forward<Args>(args)...));
}
```

Что тут происходит?

**Forwarding reference** (universal reference) — `T&&` в шаблоне. Особенный зверь: он принимает и lvalue, и rvalue. Компилятор «свёртывает» ссылки:

- Вызвали `make_unique<Weapon>(arg)` где `arg` — lvalue (`std::string& name`):
  - `T = std::string&`, `T&& = std::string& &&` = `std::string&` (свёртывание).
  - Параметр `args` принимает по lvalue-ссылке.
- Вызвали `make_unique<Weapon>(std::move(arg))`:
  - `T = std::string`, `T&& = std::string&&`.
  - Параметр принимает по rvalue-ссылке.

Внутри функции `args` — это переменная (всегда lvalue), и нужно **передать дальше с сохранением категории**. Для этого — `std::forward<T>(args)`. Это похоже на `std::move`, но условный:
- Если `T` — `std::string&` — вернёт lvalue-ссылку.
- Если `T` — `std::string` — вернёт rvalue-ссылку.

Это и есть **perfect forwarding** — переслать аргументы дальше «как есть», без потери rvalue-ности или lvalue-ности.

Используется в шаблонах, особенно в фабричных функциях. В обычном коде редко нужен.

## std::move vs std::forward

- **`std::move`** — безусловное приведение к rvalue. Используете, когда **знаете**, что переменная — lvalue, и хотите её переместить.
- **`std::forward<T>`** — условное. Используется в шаблонах с forwarding reference. Сохраняет «категорию» аргумента.

Если в обычном коде хотите переместить — `std::move`. `std::forward` оставьте для шаблонов.

## Что после move

Состояние объекта **после** перемещения:
- Валидное, но **неопределённое**. Можно вызывать любые методы, которые не требуют конкретного содержимого.
- Деструктор сработает корректно.
- Присвоить новое значение — можно.
- Использовать содержимое — нельзя (точнее, оно есть, но какое — неопределено).

Для стандартной библиотеки конкретно:
- `std::string` после move — пустая или содержит что попало; вызвать `.size()` можно, но какое значение — неизвестно.
- `std::vector` после move — обычно пустой.
- `std::unique_ptr` после move — точно `nullptr`.

Иногда говорят «moved-from object is in valid but unspecified state». Запомните: после `std::move(x)` использовать `x` нельзя, только присвоить новое значение или уничтожить.

```cpp
std::string s = "hello";
std::string t = std::move(s);

// s сейчас в moved-from состоянии
std::cout << s;           // OK, но что внутри — неизвестно
s.size();                  // OK, но размер непредсказуем
s = "new";                 // OK, можно присвоить новое
```

## Демонстрация

Соберём пример. Класс `Buffer` владеет массивом, печатает все вызовы:

```cpp
class Buffer {
public:
    explicit Buffer(std::size_t n, const std::string& tag)
        : data_(new int[n]), size_(n), tag_(tag) {
        std::cout << "[" << tag_ << "] ctor\n";
    }

    ~Buffer() {
        std::cout << "[" << tag_ << "] dtor\n";
        delete[] data_;
    }

    Buffer(const Buffer& other)
        : data_(new int[other.size_]),
          size_(other.size_),
          tag_(other.tag_ + "_copy") {
        std::cout << "[" << tag_ << "] copy ctor\n";
        for (std::size_t i = 0; i < size_; ++i) data_[i] = other.data_[i];
    }

    Buffer(Buffer&& other) noexcept
        : data_(other.data_),
          size_(other.size_),
          tag_(std::move(other.tag_) + "_moved") {
        std::cout << "[" << tag_ << "] move ctor\n";
        other.data_ = nullptr;
        other.size_ = 0;
    }

private:
    int* data_;
    std::size_t size_;
    std::string tag_;
};

int main() {
    std::cout << "--- 1. Копирование ---\n";
    Buffer a(5, "a");
    Buffer b = a;   // copy

    std::cout << "\n--- 2. Перемещение ---\n";
    Buffer c = std::move(a);   // move

    std::cout << "\n--- 3. vector с резервом ---\n";
    std::vector<Buffer> v;
    v.reserve(2);
    v.push_back(Buffer(10, "x"));   // временный → move
    v.push_back(Buffer(20, "y"));
}
```

Вывод:

```
--- 1. Копирование ---
[a] ctor (size=5)
[a_copy] copy ctor from a

--- 2. Перемещение ---
[a_moved] move ctor

--- 3. Push в vector с резервом ---
[x] ctor (size=10)
[x_moved] move ctor
[] dtor
[y] ctor (size=20)
[y_moved] move ctor
[] dtor

[y_moved] dtor
[x_moved] dtor
[a_moved] dtor
[a_copy] dtor
[] dtor
```

Видно:
- Копирование `Buffer b = a` вызывает copy ctor — `[a_copy] copy ctor from a`.
- `Buffer c = std::move(a)` вызывает move ctor — `[a_moved] move ctor`.
- `v.push_back(Buffer(10, "x"))` создаёт временный `x`, потом `vector` использует move ctor (потому что он `noexcept`!) — `[x_moved] move ctor`. После — деструктор пустого источника — `[] dtor` (тег пуст, потому что `tag_` был перемещён).

Этот тест входит в `demo-rpg/tests/test_move.cpp` — соберите и убедитесь сами.

## Где move применяется в нашем коде

В `demo-rpg/` мы уже несколько раз использовали `std::move`:

**1. В конструкторах** для передачи параметров без копирования:

```cpp
Player::Player(std::string name, int max_hp)
    : name_(std::move(name)),  // забираем у параметра
      ...
```

`name` — параметр по значению. Внутри функции — lvalue. `std::move(name)` превращает в rvalue, что позволяет `name_` забрать байты строки.

Альтернатива — принимать параметр по `const &`:

```cpp
Player::Player(const std::string& name, int max_hp)
    : name_(name),    // копия
```

Здесь нет move, потому что параметр — `const`-ссылка. Какая лучше?

- **`std::string name` + `std::move`**: одна копия при передаче в функцию (при `Player("Alice", ...)` — для строкового литерала; для `Player(s, ...)` с lvalue — копия `s`), один move.
- **`const std::string& name` + copy**: одна копия в любом случае (внутри).

Для коротких строк (SSO) разницы нет. Для длинных — оба варианта примерно одинаковы. Но **`std::string name` + `move`** позволяет вызывающему передать `std::move(s)`, и тогда копий не будет вообще. Так чуть гибче.

**2. В `World::add`**:

```cpp
void World::add(Location location) {
    std::string id = location.id();
    locations_.emplace(std::move(id), std::move(location));
}
```

`location` принят по значению — он наш. `std::move(location)` отдаёт его в `emplace` без копии.

**3. В `Inventory::add`**:

```cpp
void Inventory::add(std::unique_ptr<Item> item) {
    if (item) {
        items_.push_back(std::move(item));
    }
}
```

`unique_ptr` **нельзя** копировать. Только перемещать. Без `std::move` была бы ошибка компиляции.

## Главные правила главы

1. **Rule of zero** — лучший выбор. Стандартные поля → ничего не пишете, всё генерируется правильно.
2. **Rule of five** — если управляете ресурсами руками. Реализуйте все пять или явно `= delete`/`= default`.
3. **`noexcept` на move** — обязательно, иначе контейнеры откатятся на copy.
4. **`std::move` — это приведение типа**, не само перемещение. Перемещает move-конструктор.
5. **Не пишите `std::move` в `return`** — мешает RVO.
6. **После `std::move(x)`** объект `x` в valid-but-unspecified состоянии. Не используйте.
7. **`std::forward` — для шаблонов**, обычный код обходится `std::move`.
8. **Принимать параметр по значению + `std::move`** — гибче, чем `const T&`. Особенно для конструкторов.

## Маленькое упражнение

1. Скомпилируйте `test_move.cpp`. Сопоставьте вывод с тем, что я показал.

2. Закомментируйте `noexcept` в move-конструкторе `Buffer`. Запустите снова. В push_back изменится: теперь `vector` сделает copy вместо move (потому что не доверяет «бросающему» move). Увидите ли вы `copy ctor` в логе?

3. Уберите `reserve(2)` в `vector`. Что произойдёт при втором `push_back`? Пересмотр (capacity → 2, опять move старых элементов).

4. Замените `Buffer c = std::move(a)` на просто `Buffer c = a`. Будет copy. Сравните логи.

5. Добавьте операторы `= default` для move-конструктора (`Buffer(Buffer&&) noexcept = default;`). Что сгенерирует компилятор? Будет ли это правильным? (Подсказка: данные-член `data_` — сырой указатель, копирование которого не сделает move. Дефолтный move просто скопирует адрес — но не обнулит источник. Это значит, что и `a`, и `c` имеют один указатель, и оба будут пытаться `delete[]`. Сломается.)

6. (Сложнее) Сделайте функцию `Buffer make_big_buffer(int n)`. Внутри один путь возврата — RVO сработает (вы увидите только `ctor` и `dtor`, без move/copy). Добавьте `if (n < 0) return Buffer(0, "small"); else return Buffer(n, "big");` — RVO может не сработать. Проверьте.

7. (Сложнее) Перепишите `Buffer` с `std::unique_ptr<int[]>` вместо сырого `int*`. Большая часть rule of five станет тривиальной — `unique_ptr` сам перемещается. Можно ли использовать `= default` для всех специальных функций?

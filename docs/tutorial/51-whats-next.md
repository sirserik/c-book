# Глава 51. Куда дальше — обзор C++20/23 и маршрут роста

Вот и финал. Вся книга стояла на C++11 — фундаменте, который соберётся даже на старом компиляторе. Две предыдущие главы показали, что добавил C++17. Эта, последняя, — взгляд вперёд: что принесли **C++20** и **C++23**, и, главное, **куда расти**, когда вы закроете книгу.

Сразу честно: код в этой главе — **обзорный**. Многое из C++20 уже работает в свежих GCC, Clang и MSVC, но не везде и не всё (модули и корутины до сих пор местами болезненны). Поэтому не ждите, что каждый листинг соберётся «прямо сейчас» — читайте их как «вот к чему язык пришёл и куда движется». Цель главы — чтобы вы узнали эти штуки в чужом коде и понимали, зачем они.

## Концепты — конец SFINAE-ужасов

Вспомните главу 20. Чтобы шаблон принимал только подходящие типы, мы городили SFINAE — `std::enable_if`, проверки через `decltype`, нечитаемые конструкции, которые я сам назвал страшными. И сообщения об ошибках были под стать: вместо «тип не подходит» компилятор вываливал три экрана подстановок.

C++20 ввёл **концепты** (concepts) — именованные требования к типам, написанные по-человечески:

```cpp
// C++20
#include <concepts>

template <typename T>
concept Numeric = std::integral<T> || std::floating_point<T>;

template <Numeric T>          // принимаем только числа
T square(T x) { return x * x; }

square(5);      // ок
square(3.14);   // ок
square("hi");   // ошибка компиляции — и сообщение понятное:
                // "constraints not satisfied: 'std::string' is not Numeric"
```

Сравните с SFINAE из главы 20 — это небо и земля. Концепт `Numeric` читается как обычное условие, а ошибка прямо говорит, **что** не так. В стандартной библиотеке уже есть готовые концепты: `std::integral`, `std::floating_point`, `std::sortable`, `std::copyable` и десятки других.

Можно требовать конкретное «умение» типа через `requires`:

```cpp
template <typename T>
concept Drawable = requires(T obj) {
    obj.draw();              // у типа должен быть метод draw()
};
```

Если бы наша иерархия `Item` в RPG (главы 17-18) была на шаблонах, концепт `requires(T it) { it.describe(); }` заменил бы виртуальный интерфейс там, где он нужен только на компиляции.

## Ranges — конвейеры вместо «итератор, итератор»

Всю книгу алгоритмы STL мы вызывали через пару итераторов:

```cpp
std::sort(v.begin(), v.end());
std::copy_if(v.begin(), v.end(), std::back_inserter(out), is_even);
```

Это работает, но многословно, и сцепить два алгоритма в цепочку нельзя — приходится заводить промежуточные контейнеры. C++20 **ranges** решает обе беды. Во-первых, алгоритм берёт контейнер целиком:

```cpp
// C++20
#include <ranges>
#include <algorithm>

std::ranges::sort(v);                 // вместо v.begin(), v.end()
```

Во-вторых — и это главное — появились **views** и оператор `|`, собирающий обработку в конвейер (если писали на JS, Python или знаете LINQ из C#/Stream из Java — узнаете идею):

```cpp
// C++20
namespace rv = std::views;

std::vector<int> nums = {1, 2, 3, 4, 5, 6, 7, 8};

auto result = nums
    | rv::filter([](int n){ return n % 2 == 0; })   // только чётные
    | rv::transform([](int n){ return n * n; });     // возвести в квадрат
// result «лениво» даёт: 4, 16, 36, 64

for (int x : result) std::cout << x << " ";
```

Ключевое слово — **лениво** (lazy). `filter` и `transform` не создают промежуточных векторов; элементы протекают по конвейеру по одному, только когда вы их запрашиваете в цикле. Это и читабельнее цепочки `copy_if`+`transform`, и без лишних аллокаций.

## Корутины — функции, умеющие приостанавливаться

В главе 43 мы написали реактор на `poll`: один поток жонглирует сотней соединений, вручную сохраняя состояние каждого клиента в структуре. Код получился рабочим, но громоздким — машина состояний размазана по обработчику событий.

**Корутины** (coroutines, C++20) — это функции, которые умеют **приостановиться** на середине, вернуть управление, а потом продолжить с того же места. Состояние между приостановками компилятор сохраняет за вас:

```cpp
// C++20, обзорно
Task handle_client(Socket sock) {
    while (true) {
        std::string msg = co_await sock.read();   // приостановились, ждём данные
        if (msg.empty()) break;
        co_await sock.write("эхо: " + msg);        // снова приостановились
    }
}
```

`co_await` — точка приостановки: «жди, пока данные придут, а пока отдай поток другим». Снаружи это выглядит как простой последовательный код — `read`, потом `write`, потом снова — но под капотом работает тот самый реактор, только машину состояний строит компилятор, а не вы. Появились ключевые слова `co_await`, `co_yield`, `co_return`.

Честно: корутины в C++20 — **сложная** тема. Стандарт дал низкоуровневый механизм (`promise_type`, `coroutine_handle`), но не дал готовых высокоуровневых обёрток вроде `Task` из примера — их приходится либо писать самому, либо брать из библиотек. Это та область, где «легко пользоваться» пока не равно «легко устроено».

## Модули — прощание с #include

Всю книгу мы подключали заголовки через `#include`. В главе 7 я объяснял, как это работает: препроцессор тупо **вставляет** текст заголовка в каждый `.cpp`. Отсюда болезни — медленная компиляция (один и тот же `<vector>` парсится в каждом файле заново), хрупкость порядка включений, война с include guards.

**Модули** (modules, C++20) должны это похоронить:

```cpp
// C++20, обзорно
// файл math.ixx — объявляем модуль
export module math;

export int square(int x) { return x * x; }   // export = видно снаружи

// файл main.cpp
import math;                                   // не #include!

int main() { return square(5); }
```

`import math;` не вставляет текст — компилятор один раз компилирует модуль в бинарный формат и переиспользует. Быстрее, чище, без препроцессорной магии.

Почему «пока больно»: на момент написания поддержка модулей в сборочных системах (CMake и прочих) ещё сырая, флаги у GCC/Clang/MSVC разные, а большие проекты на модули переходят медленно. Механизм правильный, экосистема догоняет.

## Несколько штрихов C++23

C++23 — не революция, а шлифовка C++20. Что встретите чаще всего:

- **`std::expected<T, E>`** — «значение **или** ошибка» в одном типе. Мы в главе 22 обсуждали коды ошибок против исключений; `expected` — это аккуратный третий путь, без бросков и без out-параметров.
- **`std::print` / `std::println`** — наконец человеческий вывод вместо `std::cout <<`: `std::println("сумма = {}", total);`. По духу это `std::format` из C++20 (тоже как f-строки в Python), но сразу с печатью.
- **`std::flat_map` / `std::flat_set`** — словарь и множество, хранящие данные в плоском отсортированном массиве: компактнее и дружелюбнее к кэшу, чем дерево, когда вставок мало, а чтений много.

Язык продолжает развиваться: C++26 уже на подходе. Но гнаться за каждой новинкой не нужно — фундамент, который вы освоили, никуда не денется.

## Куда расти после этой книги

Вы прошли путь от «что такое бит» до собственной СУБД и сетевого чата. Это **много**. Но C++ — язык, который изучают годами. Вот честный маршрут, что делать дальше.

**Закончите упражнения-«посложнее».** В конце почти каждой главы есть задачи со звёздочкой, которые я нарочно не разбирал. Допилите RPG (новые предметы, бои, карта побольше), доведите shell до удобного (автодополнение, `&` для фона), научите СУБД делать `JOIN` двух таблиц, добавьте в чат приватные сообщения. Доделанный своими руками проект учит больше десяти прочитанных глав.

**Освойте инструменты профессионала.** В книге мы сознательно сидели на голом `make` и `g++`, чтобы видеть каждую стадию. В реальной работе вас ждут:

- **CMake** — стандарт сборки в индустрии. Возьмите любой наш демо-проект и перепишите его сборку на CMake.
- **Санитайзеры** — `-fsanitize=address` и `-fsanitize=undefined` ловят утечки, выходы за границы и UB на лету. Прогоните под ними RPG и DB — почти наверняка что-то всплывёт.
- **Отладчик** — `gdb` или `lldb`. Точки останова, просмотр стека, пошаговое выполнение. После `cout`-отладки это другой мир.
- **GoogleTest** — мы писали самодельный мини-фреймворк тестов (глава 25). Перенесите тесты RPG на GoogleTest и почувствуйте разницу.
- **Профайлер** — `perf` на Linux, Instruments на mac.  Найдите узкое место в бенчмарке СУБД не на глаз, а замером.

**Изучите то, что мы обошли.** Книга — фундамент, не энциклопедия. За её рамками остались: подробная многопоточность (`std::async`, `std::future`, lock-free структуры данных), сетевые библиотеки (Boost.Asio), метапрограммирование шаблонов вглубь, аллокаторы, и весь C++20/23 из этой главы по-настоящему, а не обзорно.

**Куда смотреть за надёжной информацией:**

- **cppreference.com** — справочник, которому стоит доверять. Открывайте его на каждый незнакомый тип или функцию.
- **Стандарт и предложения (proposals)** на open-std.org — если хочется понять, *почему* язык такой.
- **Конференции** — доклады CppCon, Meeting C++ есть на YouTube бесплатно. Там объясняют не «как», а «зачем» и «как НЕ надо».
- **Чужой код** — читайте исходники хороших библиотек. Сначала тяжело, потом незаменимо.

И последнее. Главного, чему я хотел научить, нет в синтаксисе. Это привычка **понимать, что происходит под капотом**: где аллокация, кто владеет памятью, когда вызовется деструктор, что делает каждая стадия компиляции. Мы ради этого и сидели на C++11 и голом `make` — чтобы ничего не пряталось за магией. Если теперь, глядя на любую строку C++, вы спрашиваете себя «а что здесь происходит на самом деле?» — значит, книга своё дело сделала.

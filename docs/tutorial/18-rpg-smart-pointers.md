# Глава 18. Умные указатели — unique_ptr, shared_ptr, weak_ptr

В предыдущей главе мы построили иерархию `Item`. Тестировали полиморфизм через `std::vector<Item*>`, выделяя предметы через `new` и освобождая через `delete`. Это работало, но было хрупко: забудьте `delete` — утечка, забудьте про виртуальный деструктор — UB, выкиньте исключение между `new` и `delete` — снова утечка.

Эта глава — про **умные указатели** (smart pointers). Они владеют объектом на куче и сами заботятся о его освобождении в нужный момент. Никаких ручных `delete`. Никаких утечек. Это и есть «современный C++» в одном понятии.

Параллельно построим класс `Inventory`, и в игре наконец-то можно будет брать и бросать предметы.

## Зачем нужны умные указатели

Вспомним проблему. У нас был такой код:

```cpp
std::vector<Item*> items;
items.push_back(new Weapon("меч", 5, 10));
// ...

for (Item* it : items) {
    delete it;
}
items.clear();
```

Что может пойти не так:

1. **Забыли `delete`.** Память не освобождена.
2. **Между `new` и `delete` исключение.** Деструкторы не вызовутся для оставшихся.
3. **Возвращаем `Item*` из функции.** Кто его освобождает? Без документации непонятно.
4. **Два указателя на один объект.** Оба пытаются `delete` — UB.
5. **Использование после `delete`.** Висячий указатель — UB.

В главе 11 я ввёл RAII как решение этих проблем. Умные указатели — это RAII для куча-указателей. Они конкретные классы, которые **владеют** объектом на куче и в деструкторе вызывают `delete`.

Их три:

- **`std::unique_ptr<T>`** — единоличный владелец. Только один указатель на объект.
- **`std::shared_ptr<T>`** — совладельцы. Объект живёт, пока есть хотя бы один указатель.
- **`std::weak_ptr<T>`** — наблюдатель. Сам не владеет, но может проверить, жив ли объект.

Все три — в заголовке `<memory>`.

## unique_ptr — основной рабочий

`std::unique_ptr<T>` — самый частый. Если вы выделяете объект на куче и есть **один** ответственный за его жизнь — это `unique_ptr`.

### Создание

```cpp
#include <memory>

std::unique_ptr<int> p(new int(42));
std::cout << *p << "\n";   // 42
```

`p` владеет `int`-ом со значением 42. Когда `p` выходит из области видимости (или уничтожается как-то иначе), его деструктор делает `delete` на хранимый указатель.

Полная безопасность: даже если будет исключение между `new int(42)` и концом функции — `p` всё равно уничтожится, `int` освободится.

Использование почти как обычный указатель:

```cpp
*p = 100;          // разыменование
p->method();        // вызов метода (если T — класс)
T* raw = p.get();   // получить сырой указатель (без передачи владения)
bool ok = bool(p);  // проверка на nullptr — p != nullptr
```

### Запрет копирования

Главное свойство: `unique_ptr` **нельзя копировать**.

```cpp
std::unique_ptr<int> p(new int(42));
std::unique_ptr<int> q = p;     // ОШИБКА компиляции
```

Почему? Если бы можно было — у нас стало бы два владельца, оба бы попытались `delete`. Двойное освобождение.

Поэтому копи-конструктор `unique_ptr` помечен `= delete`. Создатели стандартной библиотеки об этом подумали.

### Перемещение разрешено

Что можно — **переместить** владение:

```cpp
std::unique_ptr<int> p(new int(42));
std::unique_ptr<int> q = std::move(p);   // q теперь владеет, p пустой

if (!p) std::cout << "p пустой\n";   // выведется
std::cout << *q << "\n";              // 42
```

`std::move(p)` говорит: «забери у `p` всё, что он держит». После этого `p` становится `nullptr`, владельцем становится `q`.

Это идиома **передачи владения**. В функциях:

```cpp
std::unique_ptr<Item> make_sword() {
    return std::unique_ptr<Item>(new Weapon("меч", 5, 10));
}

void use_item(std::unique_ptr<Item> item) {
    // функция взяла владение
    std::cout << item->describe();
    // в конце item уничтожится, delete вызовется
}

int main() {
    std::unique_ptr<Item> sword = make_sword();
    // ...
    use_item(std::move(sword));
    // sword теперь пустой
}
```

Возврат `unique_ptr` из функции — нормально (move выполняется автоматически). Передача в функцию — через `std::move`.

### make_unique — фабричная функция

В C++14 добавили **`std::make_unique`**:

```cpp
auto p = std::make_unique<Weapon>("меч", 5, 10);
// эквивалент: std::unique_ptr<Weapon>(new Weapon("меч", 5, 10))
```

Преимущество — нет голого `new`. И ещё чуть-чуть исключение-безопасности (между `new` и конструктором `unique_ptr` теоретически могло что-то выкинуться, с `make_unique` — нет).

**В C++11 `make_unique` нет**. У нас C++11-база. Поэтому пишем шим:

```cpp
// include/util.h
template <typename T, typename... Args>
std::unique_ptr<T> make_unique(Args&&... args) {
    return std::unique_ptr<T>(new T(std::forward<Args>(args)...));
}
```

Поместил в `namespace rpg`, чтобы не конфликтовать с системным `std::make_unique` (хотя в C++11 его и нет — но в C++14+ есть, и наш код тогда должен работать).

`Args&&...` — variadic template, передаёт аргументы как они есть (perfect forwarding). Шаблоны и `&&...` — это глава 20. Сейчас просто принимайте как идиому: «`rpg::make_unique<T>(args...)` создаёт `unique_ptr<T>` с передачей args в конструктор T».

Использование:

```cpp
auto sword = rpg::make_unique<Weapon>("меч", 5, 10);
```

Это и есть современный способ выделения на куче в нашем коде.

### Кастомные deleters

`unique_ptr` обычно использует `delete` для освобождения. Иногда нужно другое — например, для C-API нужно вызвать `fclose`:

```cpp
auto deleter = [](FILE* f) { if (f) std::fclose(f); };
std::unique_ptr<FILE, decltype(deleter)> file(std::fopen("test.txt", "r"), deleter);
// file сам закроет файл
```

Это редко нужно — обычно лучше написать свой RAII-класс. Но в системном коде встречается.

### unique_ptr для массивов

Для массивов есть особая форма `unique_ptr<T[]>`:

```cpp
std::unique_ptr<int[]> arr(new int[100]);
arr[0] = 1;
arr[99] = 100;
// в деструкторе автоматически delete[]
```

Использует `delete[]` (не `delete`). Поэтому отдельный синтаксис.

В современном C++ почти всегда вместо `unique_ptr<T[]>` берут `std::vector<T>`. Вектор тот же массив на куче, плюс знает свой размер. Используйте `unique_ptr<T[]>` редко, для совместимости со старым кодом.

## shared_ptr — совладение

Иногда у объекта несколько владельцев. Пример: окно UI, на которое ссылаются и менеджер окон, и виджет внутри окна. Какой из них освобождает? Если кто-то один — другой может потом обратиться к освобождённой памяти.

Решение — **подсчёт ссылок**. Объект живёт, пока есть хоть один указатель на него. Уничтожается, когда последний пропадает.

```cpp
std::shared_ptr<int> a(new int(42));
std::cout << a.use_count();   // 1

{
    std::shared_ptr<int> b = a;   // КОПИРУЕТСЯ! не move
    std::cout << a.use_count();   // 2
    std::cout << b.use_count();   // 2
}
// здесь b уничтожается, счётчик становится 1

std::cout << a.use_count();   // 1
// в конце a уничтожится, счётчик = 0, объект delete'ится
```

В отличие от `unique_ptr`, **`shared_ptr` копируется** — это безопасно благодаря подсчёту.

### make_shared

```cpp
auto p = std::make_shared<Weapon>("меч", 5, 10);
```

Это **C++11** — у нас работает.

`make_shared` ещё лучше `make_unique`: он делает **одну** аллокацию для объекта и для счётчика (внутри `shared_ptr` есть «control block»). Если выделять через `shared_ptr<T>(new T(...))` — будут две аллокации (объект и control block отдельно). Маленькая, но реальная экономия.

### Цена shared_ptr

`shared_ptr` не бесплатный:

1. **Размер**: 16 байт (два указателя — на объект и на control block), вместо 8 у `unique_ptr`.
2. **Счётчик**: каждое копирование увеличивает счётчик (атомарная операция!), каждое уничтожение уменьшает. Это медленнее простого копирования.
3. **Косвенный доступ**: чтобы добраться до объекта, нужно идти через control block.

Поэтому правило: **используйте `unique_ptr` по умолчанию. `shared_ptr` только когда совладение реально нужно**.

В моих проектах — `shared_ptr` нужен раза в десять реже, чем `unique_ptr`.

### Циклы — главная ловушка shared_ptr

Допустим, у нас два класса, ссылающиеся друг на друга:

```cpp
struct Node {
    std::shared_ptr<Node> next;
    ~Node() { std::cout << "destroyed\n"; }
};

int main() {
    auto a = std::make_shared<Node>();
    auto b = std::make_shared<Node>();
    a->next = b;
    b->next = a;   // цикл!
}
```

Что произойдёт в конце `main`?

1. `b` уничтожается, счётчик на `b`-объекте становится 1 (он держится из `a->next`).
2. `a` уничтожается, счётчик на `a`-объекте становится 1 (держится из `b->next`).
3. Никого не уничтожаем — счётчики не дошли до нуля.

**Утечка.** Деструкторы не вызовутся, `"destroyed"` не выведется.

Это серьёзная проблема. `shared_ptr` не умеет автоматически разрешать циклы (для этого нужен сборщик мусора). Решение — **`weak_ptr`**.

## weak_ptr — наблюдатель без владения

`std::weak_ptr<T>` — указатель на объект, который не **держит** его. То есть не влияет на счётчик. Но может проверить, жив ли объект ещё.

```cpp
std::shared_ptr<int> s = std::make_shared<int>(42);
std::weak_ptr<int> w = s;

std::cout << s.use_count();   // 1 (weak не считается)

if (auto locked = w.lock()) {       // попытка временно получить shared_ptr
    std::cout << *locked << "\n";    // 42
} else {
    std::cout << "объект уничтожен\n";
}

s.reset();    // уничтожаем

if (auto locked = w.lock()) {
    std::cout << *locked << "\n";
} else {
    std::cout << "объект уничтожен\n";   // эта ветка
}
```

`w.lock()` пытается превратить `weak_ptr` в `shared_ptr`. Если объект ещё жив — возвращает рабочий `shared_ptr`. Если уничтожен — возвращает пустой `shared_ptr`.

Это позволяет разорвать цикл:

```cpp
struct Node {
    std::shared_ptr<Node> next;
    std::weak_ptr<Node> back;   // обратная ссылка слабая
};

auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->next = b;
b->back = a;   // weak — НЕ увеличивает счётчик a

// В конце оба уничтожаются нормально:
// b уничтожается → счётчик a остаётся 1 (только переменная a)
// a уничтожается → счётчик a = 0 → delete → a->next пустеет → b уже мёртв
```

В нашей игре `weak_ptr` нам пригодится для «NPC помнит, кто ему дал квест» — без weak это создавало бы цикл.

## Когда что

Сводная таблица:

| Указатель | Когда брать | Стоимость |
|-----------|-------------|-----------|
| `T*` (raw) | Только для «не владею, просто смотрю» — например, параметр функции. | бесплатно |
| `unique_ptr<T>` | Единственный владелец динамического объекта. | 8 байт |
| `shared_ptr<T>` | Несколько владельцев. | 16 байт + control block + атомарный счётчик |
| `weak_ptr<T>` | Наблюдатель в графе объектов с `shared_ptr`. | 16 байт |

**По умолчанию — `unique_ptr`**. Используйте `shared_ptr` только когда реально несколько владельцев. Используйте `weak_ptr` против циклов. Используйте сырой указатель когда не владеете.

## Inventory — наш первый shared_ptr… ах нет, unique_ptr

В нашей игре каждым предметом владеет ровно **один** держатель: либо локация (предмет на земле), либо инвентарь игрока. При подъёме — передача владения. При выбрасывании — обратная.

Это **классический случай для `unique_ptr<Item>`**.

`include/inventory.h`:

```cpp
class Inventory {
public:
    Inventory() = default;

    void add(std::unique_ptr<Item> item);
    std::unique_ptr<Item> take(const std::string& name);
    const Item* find(const std::string& name) const;
    bool empty() const;
    const std::vector<std::unique_ptr<Item>>& items() const;
    int total_weight() const;

private:
    std::vector<std::unique_ptr<Item>> items_;
};
```

Поле `items_` — `vector` из `unique_ptr<Item>`. Каждый предмет хранится через указатель на базу (`Item*` под капотом), что даёт **полиморфизм**: в одном векторе лежат `Weapon`, `Armor`, `Consumable`. При уничтожении вектора каждый `unique_ptr` сделает `delete` на свой указатель, виртуальный деструктор позаботится о правильной очистке.

### add — принимаем владение

```cpp
void Inventory::add(std::unique_ptr<Item> item) {
    if (item) {
        items_.push_back(std::move(item));
    }
}
```

Параметр `std::unique_ptr<Item> item` — **по значению**. Чтобы передать — нужно `std::move(...)` снаружи:

```cpp
inv.add(rpg::make_unique<Weapon>("меч", 5, 10));   // временный, move автоматический
```

Внутри `add` мы перемещаем `item` в вектор (`push_back(std::move(item))`). После этого локальный `item` пустеет.

### take — отдаём владение

```cpp
std::unique_ptr<Item> Inventory::take(const std::string& name) {
    auto it = std::find_if(items_.begin(), items_.end(),
                           [&name](const std::unique_ptr<Item>& p) {
                               return p && p->name() == name;
                           });
    if (it == items_.end()) {
        return nullptr;
    }
    std::unique_ptr<Item> result = std::move(*it);
    items_.erase(it);
    return result;
}
```

Находим предмет по имени через `find_if` с лямбдой. Лямбда: «возьми указатель из вектора, проверь, что он не пустой и что имя предмета совпадает».

Если нашли — `std::move(*it)` забирает предмет из вектора (теперь там пустой `unique_ptr`), а `erase` удаляет эту пустышку. Возвращаем найденный.

Вызывающий получает `unique_ptr<Item>` — владение перешло к нему.

### find — наблюдение без владения

```cpp
const Item* Inventory::find(const std::string& name) const {
    auto it = std::find_if(items_.begin(), items_.end(),
                           [&name](const std::unique_ptr<Item>& p) {
                               return p && p->name() == name;
                           });
    if (it == items_.end()) return nullptr;
    return it->get();
}
```

Возвращает **сырой** `const Item*`. Это «я не владею, я просто хочу посмотреть». Точно так же, как ссылка, но может быть `nullptr`.

Главное: **не вызывайте `delete` на этом указателе**. Владение остаётся у инвентаря.

`it->get()` — метод `unique_ptr`, возвращает сырой указатель без передачи владения.

### Лямбда с захватом по ссылке

В лямбдах `find_if`:

```cpp
[&name](const std::unique_ptr<Item>& p) { ... }
```

`[&name]` — захват по ссылке. Лямбда видит снаружи переменную `name` через ссылку. Это безопасно: лямбда живёт ровно столько же, сколько `find_if` (несколько миллисекунд), `name` не уничтожится за это время.

Если бы захват был по значению (`[name]`), копировалась бы строка. Для коротких имён ничего страшного, но привычка `&` для read-only — лучше.

## Применение в Location и Player

Локация теперь хранит `Inventory`:

```cpp
class Location {

    // ...
    Inventory& items();

```

Игрок тоже:

```cpp
class Player {

    // ...
    Inventory& inventory();
    const Inventory& inventory() const;

    // ...
    Inventory inventory_;

```

И заполняем локации в `make_demo_world`:

```cpp
glade.items().add(rpg::make_unique<Weapon>("ржавый меч", 5, 8));
```

Каждая локация теперь имеет один предмет.

## Команды take / drop / use

В `Game` добавились методы:

```cpp
void Game::cmd_take(const std::string& item_name) {
    Location* loc = world_.find(current_location_id_);
    if (!loc) return;

    std::unique_ptr<Item> picked = loc->items().take(item_name);
    if (!picked) {
        std::cout << "Здесь нет '" << item_name << "'.\n";
        return;
    }
    std::cout << "Вы подняли: " << picked->name() << "\n";
    player_.inventory().add(std::move(picked));
}
```

Логика: вынимаем предмет из инвентаря локации (получаем `unique_ptr`), кладём в инвентарь игрока. **Между двумя строками владение временно у локальной переменной `picked`** — без проблем, потому что в конце мы её отдаём через `std::move`.

Заметили: `World::find` теперь возвращает `Location*` (без `const`) — потому что мы модифицируем содержимое локации. Добавили перегрузку:

```cpp
Location* World::find(const std::string& id);              // для модификации
const Location* World::find(const std::string& id) const;  // для чтения
```

`cmd_drop` — наоборот:

```cpp
void Game::cmd_drop(const std::string& item_name) {
    std::unique_ptr<Item> dropped = player_.inventory().take(item_name);
    if (!dropped) {
        std::cout << "У вас нет '" << item_name << "'.\n";
        return;
    }
    Location* loc = world_.find(current_location_id_);
    // ...
    loc->items().add(std::move(dropped));
}
```

`cmd_use` — пример полиморфизма через `dynamic_cast`:

```cpp
void Game::cmd_use(const std::string& item_name) {
    const Item* item = player_.inventory().find(item_name);
    if (!item) {
        std::cout << "У вас нет '" << item_name << "'.\n";
        return;
    }

    if (const Consumable* c = dynamic_cast<const Consumable*>(item)) {
        int heal = c->heal_amount();
        std::cout << "Вы выпили " << c->name() << " (+" << heal << " HP).\n";
        player_.heal(heal);
        player_.inventory().take(item_name);   // удаляет
        cmd_status();
    } else {
        std::cout << "Это нельзя «использовать».\n";
    }
}
```

`find` даёт сырой `const Item*` — наблюдение. `dynamic_cast<const Consumable*>` проверяет, расходник ли. Если да — лечим и удаляем предмет. Если нет (оружие, броня) — отказ.

- Бросать обратно (`drop`).
- Использовать расходники (`use`).

И всё это **без единого ручного `delete`**. Каждый предмет с момента создания через `make_unique` и до конца программы безопасно владеется одним `unique_ptr`. Передачи владения через `std::move` явны.

## Сырой указатель — когда уместен

Может показаться: `unique_ptr` так хорош, что сырые указатели вообще не нужны. Это не так.

**Сырой `T*` уместен, когда вы не владеете объектом**. Например, как параметр функции:

```cpp
void print_item(const Item* it) {     // не владею, просто смотрю
    if (it) std::cout << it->describe();
}
```

Или возврат «может не найтись» (как `find`):

```cpp
const Item* find(const std::string& name) const;
```

Сырой указатель == **non-owning view**. Это его смысл в современном C++.

Если же функция **выделяет** объект и возвращает — берите `unique_ptr`. Если **принимает владение** — принимайте `unique_ptr` по значению. Без `unique_ptr` ваш интерфейс будет неясен: «кто освобождает? непонятно».

## Тонкость: передать unique_ptr нельзя по значению, можно только через move

Часто новички пишут:

```cpp
auto p = rpg::make_unique<Weapon>("меч", 5, 10);
inventory.add(p);     // ОШИБКА: unique_ptr нельзя копировать
```

Компилятор укажет на это. Решение:

```cpp
inventory.add(std::move(p));    // OK: передача владения
// после этого p пустой
```

Если же предмет создаётся «временным» — move происходит автоматически:

```cpp
inventory.add(rpg::make_unique<Weapon>("меч", 5, 10));   // OK без move
```

Временный объект — это rvalue, для него `unique_ptr` автоматически перемещается. Подробности — в главе 19.

## shared_ptr — куда мы его не применили

В нашей игре `shared_ptr` не появился, и это правильно. Каждый предмет имеет одного владельца — `unique_ptr` достаточно.

Кейс, где может пригодиться `shared_ptr`:
- **Шаблоны предметов**. Допустим, у нас 100 одинаковых «зелий лечения» в магазине, и игрок носит «ссылку» на шаблон. `shared_ptr<ItemTemplate>` — все 100 ссылок указывают на один шаблон. При удалении магазина шаблон жив, пока игрок носит зелье.
- **NPC, на которого указывают разные квесты**. Если один и тот же NPC участвует в 5 квестах — `shared_ptr<NPC>` от каждого квеста.

В нашем коде до 25-й главы `shared_ptr` появится в одном-двух местах, не больше. `unique_ptr` — рабочая лошадка.

## weak_ptr — куда мы его не применили

В нашей игре циклов нет (предмет не знает свой инвентарь, инвентарь знает предметы). Поэтому `weak_ptr` пока не нужен.

В большом проекте `weak_ptr` появляется в момент, когда вы заметили утечку через цикл `shared_ptr`. Тогда одно из направлений ссылок делаете `weak_ptr` — обычно «обратное» или «менее важное».

## Главные правила главы

1. **Никогда не пишите `new T(...)` без `unique_ptr` или эквивалента.** Голый `new` в C++17+ — почти всегда баг.
2. **`unique_ptr<T>` по умолчанию.** Самый дешёвый и понятный.
3. **`make_unique<T>(args)` через шим в C++11**, через стандарт в C++14+.
4. **`shared_ptr<T>` только когда совладение реально нужно.** Цена — двойной размер, атомарный счётчик.
5. **`weak_ptr<T>` против циклов в `shared_ptr`-графе.**
6. **Сырой `T*` означает "не владею".** Только для параметров и наблюдения.
7. **Передача `unique_ptr` через `std::move`**, временные — автоматически.
8. **`get()`** даёт сырой указатель без передачи владения. Используйте только когда нужно отдать в C-API.
9. **`reset()`** на `unique_ptr` освобождает текущий и опционально берёт новый.

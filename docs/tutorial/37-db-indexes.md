# Глава 37. Вторичные индексы и план запроса

Наша база умеет быстро находить строку по первичному ключу — за этим и строилось дерево. А что с остальными колонками?

```sql
SELECT * FROM items WHERE value = 250;
```

Дерево упорядочено по `id`, а не по `value`, поэтому единственный способ ответить — обойти все строки и проверить каждую. На тысяче записей это уже заметно, на миллионе — катастрофа.

В этой главе научим базу строить вторичные индексы — дополнительные деревья, упорядоченные по другой колонке, — и научим её выбирать способ выполнения запроса. А выбранный способ будем показывать по команде `EXPLAIN`, как это делают взрослые базы.

Заодно измерим обе стороны сделки: во сколько раз индекс ускоряет чтение и во что обходится при записи.

## Насколько всё плохо без индекса

Замер на тысяче строк, программа `utils/bench.cpp`:

```
Find by id (B+tree):   226 ms на 1000 запросов, 4411 запросов/с
Find by value (полный перебор, 100 запросов): 3386 ms, 29.5 запросов/с
```

Разница в полтораста раз, и она будет расти линейно с числом строк: поиск по ключу — логарифм, полный перебор — линия. На миллионе строк перебор станет в тысячу раз медленнее, чем сейчас, а поиск по ключу — всего вдвое.

Обратите внимание и на абсолютные числа: 4411 поисков в секунду по ключу — совсем не быстро для базы, где всё помещается в памяти. Виноваты наши упрощения: копирование страницы при каждом чтении и разбор узла в три вектора. Об этом подробнее в главе 39.

## Что такое вторичный индекс

Идея простая: завести второе дерево, где ключом будет значение колонки, а значением — идентификатор строки.

```
Основное дерево (по id):        Вторичный индекс (по value):
   1 → 100                          100 → 1
   2 → 250                          250 → 2
   3 → 250                          250 → 3
```

Теперь запрос `WHERE value = 250` выполняется в два шага: находим в индексе все идентификаторы с ключом 250, потом по каждому идентификатору достаём строку из основного дерева. Два поиска по логарифму вместо линейного перебора.

Почему во вторичном индексе хранятся идентификаторы, а не строки целиком? Из-за дублирования. Копия строки в каждом индексе означала бы, что при изменении строки надо обновить все копии, а при трёх индексах данные хранятся вчетверо. Ссылка на строку решает обе проблемы ценой второго обращения при чтении.

Впрочем, у копирования данных в индекс есть и своя ниша: если индекс содержит все колонки, которые нужны запросу, база может ответить, не заглядывая в таблицу вообще. Такие индексы называют покрывающими, и они бывают очень эффективны — но у нас всего две колонки, и говорить о покрытии особо не о чем.

## Реализация

Каждый вторичный индекс — это отдельный файл со своим деревом, своим страничным менеджером и своим журналом:

```cpp
struct SecondaryIndex {
    std::unique_ptr<PageManager> pm;
    std::unique_ptr<BPlusTree> tree;
    std::unique_ptr<WAL> wal;
    std::string column;
};

std::unordered_map<std::string, SecondaryIndex> indexes_;
```

Ключ в отображении — имя колонки, потому что именно по нему планировщик ищет подходящий индекс.

Полный набор из трёх компонентов на каждый индекс выглядит расточительно, но так устроено и в настоящих базах: индекс — это самостоятельное хранилище со своим жизненным циклом. Общий журнал был бы возможен и даже лучше (одна синхронизация вместо нескольких), но потребовал бы записывать в него, к какому дереву относится операция.

`std::unique_ptr` здесь потому, что `PageManager` некопируем — он владеет дескриптором, — а класть некопируемый объект в контейнер по значению не выйдет. Умный указатель решает и это, и вопрос времени жизни: закрылась база — закрылись все индексы.

### Создание

```cpp
void Database::execute_create_index(const Statement& st, std::ostream& out) {
    if (st.table != table_name_) throw SqlError("неизвестная таблица: " + st.table);
    if (st.columns.size() != 1) throw SqlError("ожидается одна колонка");
    const std::string& col = st.columns[0].first;
    if (col != col_names_[0] && col != col_names_[1]) {
        throw SqlError("неизвестная колонка: " + col);
    }
    if (indexes_.count(col)) {
        out << "Index уже существует\n";
        return;
    }

    open_index(st.index_name, col);
    SecondaryIndex& idx = indexes_[col];

    int populated = 0;
    tree_->scan([&](std::int64_t row_id, std::int64_t row_value) {
        std::int64_t key = (col == col_names_[0]) ? row_id : row_value;
        idx.wal->log_insert(key, row_id);
        idx.tree->insert_dup(key, row_id);
        ++populated;
    });
    idx.pm->sync();
    idx.wal->truncate();

    save_catalog();
    out << "Index '" << st.index_name << "' on " << col
        << " (" << populated << " rows indexed)\n";
}
```

Главное здесь — заполнение уже существующими данными. Индекс, построенный на непустой таблице, обязан сразу знать про все строки, иначе запросы начнут возвращать неполные ответы — та самая тихая поломка, о которой шла речь в главе 34.

Заполнение идёт полным обходом основного дерева, и на большой таблице это долгая операция. В нашем замере построение индекса на тысяче строк заняло 470 миллисекунд — примерно столько же, сколько вставка этой тысячи. В настоящих базах создание индекса на большой таблице занимает часы и блокирует запись, поэтому существуют отдельные режимы вроде `CREATE INDEX CONCURRENTLY` в PostgreSQL, которые строят индекс, не мешая работе.

После заполнения — `sync` и очистка журнала: индекс на диске полон, повторять нечего.

Вставки идут через `insert_dup`, а не `insert`. Это принципиально: вторичный ключ не уникален, и обычная вставка затирала бы строки с одинаковым значением. Историю этой ошибки мы разбирали в главе 34.

### Обновление при вставке

Индекс бесполезен, если он отстаёт от данных. Поэтому каждая вставка обновляет все индексы:

```cpp
wal_->log_insert(id, value);
tree_->insert(id, value);

for (auto& kv : indexes_) {
    const std::string& col = kv.first;
    std::int64_t key = (col == col_names_[0]) ? id : value;
    kv.second.wal->log_insert(key, id);
    kv.second.tree->insert_dup(key, id);
}
```

Вот она, цена индексов. Одна вставка при трёх индексах — это четыре записи в деревья и четыре синхронизации журналов. Отсюда правило, знакомое всем администраторам баз: индексы ускоряют чтение и замедляют запись, поэтому на таблицах, куда пишут потоком, их держат по минимуму.

Ещё одно следствие — при массовой загрузке данных индексы принято удалять перед загрузкой и создавать после. Построить индекс один раз по готовой таблице дешевле, чем поддерживать его на каждой из миллиона вставок.

### Каталог: чтобы индекс пережил перезапуск

Первая версия базы теряла индексы при закрытии. Файлы оставались на диске, но при следующем запуске никто про них не знал, и запрос снова уходил в полный перебор:

```
mydb> EXPLAIN SELECT * FROM items WHERE value = 250;
Plan: FullScan with filter (value = 250)
```

Ответ при этом оставался правильным — только медленным. Тихая потеря производительности, которую легко не заметить.

Лечится это каталогом — местом, где база хранит сведения о себе самой. У нас он предельно простой, текстовый файл `catalog.txt`:

```
goods
sku price
idx_price price
```

Первая строка — имя таблицы, вторая — имена колонок, дальше по строке на индекс: имя и колонка.

```cpp
void Database::save_catalog() {
    std::ofstream out(dir_ + "/catalog.txt");
    if (!out.is_open()) return;
    out << table_name_ << "\n";
    out << col_names_[0] << " " << col_names_[1] << "\n";
    for (const auto& kv : index_names_) {
        out << kv.second << " " << kv.first << "\n";
    }
}

void Database::load_catalog() {
    std::ifstream in(dir_ + "/catalog.txt");
    if (!in.is_open()) return;

    std::string table;
    if (!std::getline(in, table) || table.empty()) return;
    table_name_ = table;
    ...
    std::string line;
    while (std::getline(in, line)) {
        std::istringstream ls(line);
        std::string index_name, column;
        if (!(ls >> index_name >> column)) continue;
        open_index(index_name, column);
    }
}
```

Открытие индекса вынесено в отдельный метод, потому что нужно в двух местах — при создании и при загрузке каталога:

```cpp
void Database::open_index(const std::string& index_name, const std::string& column) {
    if (indexes_.count(column)) return;

    SecondaryIndex idx;
    idx.column = column;
    idx.pm    = mk<PageManager>(dir_ + "/idx_" + index_name + ".db", 32);
    idx.tree  = mk<BPlusTree>(*idx.pm);
    idx.wal   = mk<WAL>(dir_ + "/idx_" + index_name + ".wal");
    idx.wal->replay([&idx](std::int64_t k, std::int64_t v) {
        idx.tree->insert_dup(k, v);
    });

    indexes_.emplace(column, std::move(idx));
    index_names_[column] = index_name;
}
```

Обратите внимание, что при открытии индекса проигрывается его журнал — точно так же, как для основного дерева. Индекс — полноценное хранилище и восстанавливается после аварии по тем же правилам.

Теперь всё переживает перезапуск:

```
mydb> EXPLAIN SELECT * FROM goods WHERE price = 250;
Plan: SecondaryLookup(price=250)
mydb> SELECT * FROM goods WHERE price = 250;
sku      | price
---------+---------
2        | 250
3        | 250
(2 строки)
```

И имена колонок теперь тоже сохраняются — `sku` и `price`, как их создали, а не `id` и `value` из конструктора. Тот же каталог решил обе задачи.

Текстовый формат каталога — сознательное упрощение. Настоящие базы хранят каталог в обычных таблицах внутри той же базы (`pg_class`, `pg_index` в PostgreSQL; `sqlite_master` в SQLite), и это красиво: движок описывает сам себя своими же средствами, а запрос к каталогу выполняется обычным механизмом запросов. Нам для двух колонок и одного индекса хватит трёх строк текста.

## Планировщик

Теперь самое интересное: как база выбирает способ выполнения.

```cpp
std::string Database::plan_select(const Statement& st) const {
    if (!st.has_where) return "FullScan(primary)";
    if (st.where_col == col_names_[0] && st.where_op == "=") {
        return "PrimaryLookup(id=" + std::to_string(st.where_val) + ")";
    }
    auto it = indexes_.find(st.where_col);
    if (it != indexes_.end()) {
        if (st.where_op == "=") {
            return "SecondaryLookup(" + it->first + "=" + std::to_string(st.where_val) + ")";
        }
        return "SecondaryScan(" + it->first + " " + st.where_op + " "
             + std::to_string(st.where_val) + ")";
    }
    return "FullScan with filter (" + st.where_col + " " + st.where_op + " "
         + std::to_string(st.where_val) + ")";
}
```

Четыре стратегии, и выбор между ними — цепочка проверок сверху вниз.

Нет условия — обходим всё дерево, других вариантов и нет. Условие на первичный ключ с равенством — один спуск по дереву, самый быстрый случай. Есть индекс по нужной колонке: при равенстве — точечный поиск в индексе, при неравенстве — обход индекса. Ничего не подошло — полный перебор с проверкой условия на каждой строке.

Такой планировщик называют основанным на правилах: он выбирает по жёсткому списку предпочтений, не заглядывая в данные. Так работали первые версии Oracle, и так до сих пор работают простые встроенные базы.

Взрослые системы используют стоимостное планирование: для каждого способа оценивается стоимость в условных единицах, и выбирается самый дешёвый. Оценка строится на статистике — сколько всего строк, сколько различных значений в колонке, как они распределены. Именно поэтому в PostgreSQL есть команда `ANALYZE`, собирающая статистику, и именно поэтому после массовой загрузки данных запросы иногда «тупеют», пока статистику не пересоберут.

Разница видна на простом примере. Пусть в таблице миллион строк и индекс по колонке «город». Запрос `WHERE city = 'Алматы'`, если алматинцев в таблице десяток, отлично выполнится через индекс. Но если алматинцев девятьсот тысяч, поход через индекс окажется **медленнее** полного перебора: девятьсот тысяч случайных обращений к основному дереву против одного последовательного прохода. Планировщик по правилам этого не увидит, стоимостный — увидит, если знает распределение.

### EXPLAIN

Показать выбранный план — три строки:

```cpp
void Database::execute_select(const Statement& st, std::ostream& out) {
    if (st.table != table_name_) throw SqlError("неизвестная таблица: " + st.table);

    std::string plan = plan_select(st);

    if (st.is_explain) {
        out << "Plan: " << plan << "\n";
        return;
    }
    ...
}
```

И вот как это выглядит в работе:

```
mydb> EXPLAIN SELECT * FROM items;
Plan: FullScan(primary)
mydb> EXPLAIN SELECT * FROM items WHERE id = 2;
Plan: PrimaryLookup(id=2)
mydb> EXPLAIN SELECT * FROM items WHERE value = 250;
Plan: FullScan with filter (value = 250)
mydb> CREATE INDEX idx_val ON items (value);
Index 'idx_val' on value (3 rows indexed)
mydb> EXPLAIN SELECT * FROM items WHERE value = 250;
Plan: SecondaryLookup(value=250)
mydb> EXPLAIN SELECT * FROM items WHERE value > 100;
Plan: SecondaryScan(value > 100)
```

Один и тот же запрос до и после создания индекса выполняется по-разному — и `EXPLAIN` это показывает. Именно так им и пользуются на практике: запрос стал медленным, смотрим план, видим полный перебор там, где ожидали индекс, — и разбираемся почему.

Наш `EXPLAIN` печатает одну строку, потому что план у нас плоский. В настоящих базах план — дерево из соединений, сортировок и агрегатов, и `EXPLAIN` выдаёт его с отступами, оценкой строк и стоимости, а `EXPLAIN ANALYZE` — ещё и реальное время каждого узла.

## Выполнение

Каждой стратегии соответствует своя функция. Поиск по первичному ключу — самый прямой:

```cpp
void Database::run_primary_eq(const Statement& st, const std::vector<std::string>& cols,
                              std::ostream& out) {
    std::int64_t v = 0;
    if (tree_->find(st.where_val, v)) {
        ...
        print_row_count(1, out);
    } else {
        print_row_count(0, out);
    }
}
```

Работа с индексом сложнее — нужен второй шаг, поход в основное дерево за строкой:

```cpp
void Database::run_secondary(const Statement& st, const std::vector<std::string>& cols,
                             const SecondaryIndex& idx, std::ostream& out) {
    int rows = 0;
    auto emit = [&](std::int64_t row_id) {
        std::int64_t row_value = 0;
        if (!tree_->find(row_id, row_value)) return;
        ...
        ++rows;
    };

    if (st.where_op == "=") {
        // Вторичный ключ не уникален: на одно значение может приходиться
        // много строк, поэтому берём ВСЕ совпадения, а не первое.
        idx.tree->find_all(st.where_val, emit);
    } else {
        idx.tree->scan([&](std::int64_t key, std::int64_t row_id) {
            const auto r = st.where_val;
            const auto& op = st.where_op;
            bool ok =
                (op == "<"  && key <  r) ||
                (op == "<=" && key <= r) ||
                (op == ">"  && key >  r) ||
                (op == ">=" && key >= r) ||
                (op == "!=" && key != r);
            if (ok) emit(row_id);
        });
    }
    print_row_count(rows, out);
}
```

Лямбда `emit` — общая часть обеих ветвей: получить идентификатор, достать строку, напечатать. Проверка `if (!tree_->find(row_id, row_value)) return;` защищает от рассогласования индекса и таблицы: если в индексе есть ссылка на несуществующую строку, мы её молча пропустим, а не напечатаем мусор.

Ветка с неравенством выглядит подозрительно, и подозрение справедливо: она обходит **весь** индекс целиком, проверяя каждую запись. То есть `WHERE value > 100` через индекс делает столько же работы, сколько полный перебор, плюс ещё поход в основное дерево на каждое совпадение — то есть работает **медленнее**.

Правильно было бы спуститься по индексу к границе диапазона и идти по цепочке листьев, пока условие выполняется. У дерева для этого уже почти всё есть — не хватает метода `scan_range`, который вынесен в упражнения главы 34. Честно говоря, наш `SecondaryScan` — это заготовка под правильную реализацию, а не сама реализация, и в плане запроса стоило бы это отражать.

## Сколько выигрывают и сколько теряют

Полный замер, тысяча строк:

```
=== Бенчмарк мини-СУБД, N = 1000 ===

Insert:                453 ms, 2205 ops/s
Checkpoint:            2.2 ms

Find by id (B+tree):   227 ms, 4411 ops/s
Find by value (полный перебор, 100 запросов): 3386 ms, 29.5 ops/s
Build index:           470 ms
Find by value (индекс): 464 ms, 2157 ops/s

Ускорение find-by-value с индексом: 73x
```

Семьдесят три раза на тысяче строк. И это ещё скромно: выигрыш растёт линейно с размером таблицы, потому что перебор линеен, а поиск по индексу — логарифмичен. На ста тысячах строк разница была бы уже в тысячи раз.

Обратная сторона: поиск через индекс (2157 запросов в секунду) вдвое медленнее поиска по первичному ключу (4411), потому что делает два спуска вместо одного. Это нормально и ожидаемо — за универсальность платят.

Построение индекса на тысяче строк заняло 470 миллисекунд, столько же, сколько сама вставка этой тысячи. Логично: построение — это полный обход плюс тысяча вставок в новое дерево плюс тысяча записей в журнал.

## Чего мы не сделали

Составных индексов — по нескольким колонкам сразу. В настоящей базе индекс по паре «город, дата» отвечает и на запросы по городу, и на запросы по городу с датой, но не на запросы по одной дате. Правило левого префикса — первое, что узнаёшь, работая с индексами всерьёз.

Уникальных индексов, которые не просто ускоряют поиск, а запрещают дубликаты. У нас первичный ключ уникален по построению (обычная вставка заменяет), но объявить уникальной вторую колонку нельзя.

Удаления индексов: команды `DROP INDEX` нет, а файлы индекса живут вечно.

Оптимизации диапазона по первичному ключу. Запрос `WHERE id > 100` у нас получает план `FullScan with filter`, хотя дерево упорядочено именно по `id` и могло бы начать обход с нужного места:

```
mydb> EXPLAIN SELECT * FROM items WHERE id > 1;
Plan: FullScan with filter (id > 1)
```

Формально ответ правильный, но работы делается больше необходимого. Это самая заметная недоделка планировщика, и чинится она тем же `scan_range`.

И, конечно, нет статистики и стоимостного выбора — планировщик действует по жёстким правилам и не подозревает, сколько строк подойдёт под условие.

## Главные правила главы

1. Вторичный индекс — отдельное дерево «значение колонки → идентификатор строки»; чтение по нему требует двух спусков.
2. Индекс, построенный на непустой таблице, обязан быть заполнен существующими данными сразу.
3. Каждая вставка обновляет все индексы: чтение ускоряется, запись замедляется пропорционально их числу.
4. При массовой загрузке индексы выгоднее удалить и построить заново.
5. Сведения о таблице и индексах живут в каталоге, иначе после перезапуска база забудет про индексы и тихо станет медленной.
6. Планировщик по правилам выбирает из списка предпочтений; стоимостный смотрит на статистику и иногда предпочитает полный перебор индексу.
7. `EXPLAIN` — первый инструмент при разборе медленного запроса: он показывает, что база решила сделать, а не что вы задумали.
8. Диапазонный запрос через индекс без остановки на границе не имеет смысла: он делает больше работы, чем полный перебор.

## Упражнения

1. Соберите базу, создайте таблицу с индексом, вставьте несколько строк с повторяющимися значениями. Посмотрите `EXPLAIN` для запросов по обеим колонкам, с равенством и неравенством. Перезапустите базу и убедитесь, что план не изменился.

2. Удалите `catalog.txt` при закрытой базе и запустите её снова. Что покажет `EXPLAIN`? Объясните, почему данные при этом не потерялись.

3. Запустите `./build/bench 100`, `./build/bench 1000` и `./build/bench 5000`. Постройте зависимость ускорения от числа строк и объясните её форму.

4. Замерьте вставку тысячи строк без индекса и с двумя индексами. Во сколько раз медленнее? Сходится ли это с числом деревьев, которые надо обновить?

5. Реализуйте `DROP INDEX <имя>`: уберите индекс из отображения, удалите файлы, обновите каталог. Проверьте, что план после этого возвращается к полному перебору.

6. Добавьте план `PrimaryScan` для диапазона по первичному ключу: спуск к границе и обход по цепочке листьев с остановкой. Сравните время с `FullScan with filter` на десяти тысячах строк.

7. (Сложнее) Соберите простейшую статистику: при построении индекса посчитайте число различных значений. Научите планировщик выбирать полный перебор, если под условие подходит больше трети таблицы, и проверьте на данных, где одно значение встречается у большинства строк.

8. (Сложнее) Сделайте уникальный индекс: `CREATE UNIQUE INDEX` должен отвергать вставку строки с уже существующим значением. Продумайте, что делать, если в момент создания индекса дубликаты уже есть.

## Что дальше

Глава 38 — оболочка базы. У нас есть язык, но общаться с базой пока приходится через `printf` в конвейере. Сделаем нормальный REPL в стиле `psql`: многострочный ввод с продолжением, служебные команды с точкой, история между запусками, обработка ошибок без падения. Заодно разберёмся, почему разбор ввода в интерактивной программе — отдельная задача, не сводящаяся к разбору языка.

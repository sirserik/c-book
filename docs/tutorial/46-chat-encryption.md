# Глава 46. Шифрование и история

Две темы в одной главе, и обе про то, что происходит с сообщением после отправки.

Сначала шифрование — точнее, разговор о том, почему самодельное шифрование не работает. Мы напишем самый популярный из самодельных шифров, убедимся, что он выглядит убедительно, и сломаем его за пять минут, восстановив ключ. Это не упражнение в криптографии, а прививка от очень распространённой ошибки.

Потом — история сообщений на диске, чтобы новый участник видел несколько последних реплик, а перезапуск сервера не стирал разговор.

## Шифр, который придумывают все

Идея выглядит красиво: возьмём ключ и наложим его на текст побитовым исключающим ИЛИ.

```cpp
void xor_in_place(std::string& data, const std::string& key) {
    for (std::size_t i = 0; i < data.size(); ++i) {
        data[i] = static_cast<char>(data[i] ^ key[i % key.size()]);
    }
}
```

Свойство операции делает шифрование и расшифровку одной функцией: `(a ^ k) ^ k == a`. Ключ короче текста — повторяем его по кругу.

Смотрим на результат:

```
Plain:     'Hello, this is a confidential message!'
Plain hex: 48 65 6c 6c 6f 2c 20 74 68 69 73 20 69 73 20 61 ...

Cipher hex: 3b 00 0f 1e 0a 58 11 46 5b 1a 16 43 1b 16 54 50 ...

Decrypted: 'Hello, this is a confidential message!'
```

Выглядит убедительно: осмысленный текст превратился в невнятные байты и вернулся обратно. На этом месте обычно и останавливаются — и зря.

## Ломаем за пять минут

У шифра есть уязвимость, которую даже не надо искать: она следует из самой конструкции. Если известен хотя бы кусок исходного текста и соответствующий ему кусок шифра, ключ достаётся тем же исключающим ИЛИ:

```
шифр = текст ^ ключ
шифр ^ текст = ключ
```

В нашем чате известный кусок найти проще простого: все сообщения начинаются с `<имя> `, служебные — со слова «Привет». Даже не зная ничего, можно предположить типичное начало.

```cpp
std::string known = "Hello, ";
std::string recovered_key;
for (std::size_t i = 0; i < known.size(); ++i) {
    recovered_key.push_back(known[i] ^ cipher[i]);
}
```

```
=== Атака: known-plaintext ===
Зная начало plaintext, восстановили ключ:
  Восстановленный: 'secret1'
  Реальный:        'secret1'
```

Семь символов известного текста — семь символов ключа. Ещё немного известного текста — весь ключ, и дальше читается вся переписка.

Это называется атакой по известному открытому тексту, и повторяющийся ключ беззащитен перед ней в принципе. Причём для взлома даже не нужен известный текст: если ключ короткий, его длина определяется статистически (метод Касиски, известный с 1863 года), а дальше шифр распадается на несколько простых замен, которые вскрываются частотным анализом.

Есть ещё две беды. Одинаковые сообщения дают одинаковый шифр — противник видит повторы, даже не расшифровывая. И шифр никак не защищён от подмены: перевернув бит в шифре, вы перевернёте тот же бит в расшифрованном тексте, и получатель не заметит подлога.

Любопытно, что схема с одноразовым ключом длиной с сообщение — единственный шифр с доказанной невзламываемостью. Но ключ должен быть по-настоящему случайным, длиной с текст и использоваться ровно один раз. Стоит применить его дважды — и всё рушится: сложив два шифра, противник получает сложение двух открытых текстов, а это уже поддаётся разбору. Именно на таком повторном использовании ключей строилась операция «Венона», в ходе которой американцы десятилетиями читали советские шифровки.

## Что делать вместо

Правило, которому стоит следовать без исключений: **не изобретайте криптографию и не реализуйте её сами**.

Даже правильный алгоритм легко испортить реализацией. Сравнение хешей обычным `memcmp` выдаёт информацию через время выполнения — по нему подбирают значение побайтно. Случайные числа из `rand()` предсказуемы. Ключ, оставшийся в памяти после использования, попадёт в дамп при падении. Всё это не гипотетические опасности, а реальные уязвимости в реальных продуктах.

Для сетевого соединения ответ один — TLS. Его дают библиотеки OpenSSL, BoringSSL, mbedTLS, и в них уже решены вопросы, о которых самодельная реализация даже не подозревает: согласование версий и наборов шифров, проверка сертификатов, защита от повторной отправки, безопасное обновление ключей.

Если нужно зашифровать данные, а не соединение, берите готовые библиотеки высокого уровня — libsodium даёт разумные функции, в которых трудно ошибиться, и по умолчанию выбирает надёжные алгоритмы.

В нашем чате шифрования нет — и это честнее, чем самодельная схема, создающая ложное ощущение защищённости. Правильный путь для `demo-chat` — обернуть соединение в TLS, и это большое упражнение в конце главы.

## История сообщений

Вторая половина главы — память сервера. Сейчас перезапуск стирает всё, а новый участник входит в комнату, где, судя по всему, никто никогда не говорил.

Формат журнала знаком по главе 35 — записи с префиксом длины:

```
Формат записи (как в WAL):
  [4]   length u32 LE = 4 + 2 + 2 + 2 + name.size() + room.size() + text.size()
  [4]   timestamp u32 LE (секунды от epoch)
  [2]   name_len u16 LE
  [2]   room_len u16 LE
  [2]   text_len u16 LE
  [...] name + room + text (по len байтов)
```

Три длины подряд, потом три строки подряд. Такая раскладка — «сначала все размеры, потом все данные» — позволяет прочитать заголовок фиксированного размера и сразу знать, сколько занимает каждое поле.

Запись — только в конец, как и положено журналу:

```cpp
std::vector<std::uint8_t> framed;
w_u32(framed, static_cast<std::uint32_t>(body.size()));
framed.insert(framed.end(), body.begin(), body.end());

std::size_t off = 0;
while (off < framed.size()) {
    ssize_t w = ::write(fd_, framed.data() + off, framed.size() - off);
    if (w < 0) {
        if (errno == EINTR) continue;
        throw std::runtime_error("history write");
    }
    off += static_cast<std::size_t>(w);
}
::fsync(fd_);
```

Запись собирается целиком и отдаётся одним вызовом — по той же причине, что в журнале базы данных: половина записи в файле хуже, чем её отсутствие.

А вот `fsync` на каждое сообщение — решение спорное. Для базы данных оно оправданно: потерять подтверждённую транзакцию нельзя. Для чата — вопрос вкуса: сообщение уже разослано участникам, и потеря последних записей истории при внезапном выключении не катастрофа. Зато каждое сообщение стоит полутора сотен микросекунд, которые мы измеряли в главе 33. Разумный компромисс — синхронизировать не чаще раза в секунду; это упражнение.

### Чтение последних N

```cpp
std::vector<HistoryRecord> History::recent(const std::string& room, std::size_t n) {
    std::vector<HistoryRecord> all;
    int rfd = ::open(path_.c_str(), O_RDONLY);
    if (rfd < 0) return all;

    // Верхний предел на запись. Без него испорченный файл с мусором в поле
    // длины заставил бы нас выделить гигабайты — та же защита, что в разборе
    // сетевого протокола (глава 44).
    const std::uint32_t kMaxRecord = 1u << 20;   // 1 MiB

    std::uint8_t hdr[4];
    while (read_all(rfd, hdr, 4)) {
        std::uint32_t body_len = r_u32(hdr);
        if (body_len < 10 || body_len > kMaxRecord) break;   // битая запись — дальше не идём
        std::vector<std::uint8_t> body(body_len);
        if (!read_all(rfd, body.data(), body_len)) break;

        HistoryRecord rec;
        rec.timestamp = r_u32(body.data());
        std::uint16_t nl = r_u16(body.data() + 4);
        std::uint16_t rl = r_u16(body.data() + 6);
        std::uint16_t tl = r_u16(body.data() + 8);
        if (10u + nl + rl + tl > body_len) break;             // длины не сходятся
        std::size_t pos = 10;
        rec.name.assign(reinterpret_cast<const char*>(body.data() + pos), nl); pos += nl;
        rec.room.assign(reinterpret_cast<const char*>(body.data() + pos), rl); pos += rl;
        rec.text.assign(reinterpret_cast<const char*>(body.data() + pos), tl);

        if (room.empty() || rec.room == room) {
            all.push_back(std::move(rec));
        }
    }
    ::close(rfd);

    if (all.size() > n) {
        all.erase(all.begin(), all.end() - static_cast<std::ptrdiff_t>(n));
    }
    return all;
}
```

Две проверки в начале цикла появились не сразу, и стоит объяснить, почему они важны.

Первая ограничивает размер записи. Без неё файл, испорченный обрывом питания или чьей-то шалостью, мог бы содержать в поле длины четыре миллиарда — и `std::vector<std::uint8_t> body(body_len)` попытался бы выделить четыре гигабайта. Ровно та же уязвимость, что мы разбирали в сетевом протоколе главы 44, только источник данных другой — не сеть, а диск. Правило одно: **любая длина, пришедшая извне, проверяется до того, как ею воспользоваться**, и неважно, откуда она пришла.

Вторая проверка сверяет три длины с общим размером записи. Без неё поле `text` читалось бы за границей выделенного буфера — классическое чтение за пределами массива, ведущее к падению или утечке чужой памяти.

Заметьте, что при любой несостыковке мы прекращаем чтение, а не пропускаем запись. Логика та же, что в журнале базы: испорченный хвост означает обрыв, и всё, что после него, доверия не заслуживает.

### Наивность, о которой надо знать

Функция читает файл **целиком**, чтобы вернуть последние несколько записей. На истории в сто мегабайт это сто мегабайт чтения ради десяти строк.

Так делать нельзя, и в комментарии к классу это честно записано. Правильных решений два. Можно читать с конца файла: отступить, скажем, на десять килобайт, найти границу записи и разобрать хвост, — но границу в потоке записей переменной длины ещё надо найти, и придётся либо хранить смещения, либо добавить в формат маркер начала записи. Можно вести отдельный индекс: файл со смещениями последних записей каждой комнаты.

Есть и третий путь, самый практичный: ротация. История режется на файлы по дате или размеру, старые сжимаются и убираются, а `recent` смотрит только в последний. Так устроены почти все системы журналирования.

Мы оставили наивную реализацию, потому что она короткая и понятная, а объём учебной истории измеряется килобайтами. Но знать её предел обязательно — как раз о таких местах и говорят «работало на тесте, легло на продакшене».

```
=== Последние 10 в general ===
[1785407300] [general] <Alice> первое сообщение
[1785407301] [general] <Bob> ответ
[1785407303] [general] <Alice> ещё одно

=== Все записи (по всем комнатам) ===
[1785407300] [general] <Alice> первое сообщение
[1785407301] [general] <Bob> ответ
[1785407302] [tech] <Carol> что-то про код
[1785407303] [general] <Alice> ещё одно
```

Фильтр по комнате работает, пустое имя комнаты означает «все».

## Как это встроить в сервер

Две точки подключения.

При получении сообщения — записать в журнал перед рассылкой:

```cpp
case chat::kMessage: {
    if (c.room.empty()) { ... }
    HistoryRecord rec;
    rec.timestamp = static_cast<std::uint32_t>(std::time(nullptr));
    rec.name = c.name;
    rec.room = c.room;
    rec.text = payload;
    history.append(rec);

    std::string out = "<" + c.name + "> " + payload;
    broadcast_room(clients, rooms, c.room, fd, chat::kMessage, out);
    break;
}
```

При входе в комнату — отдать новичку последние реплики:

```cpp
for (const HistoryRecord& r : history.recent(c.room, 10)) {
    enqueue_frame(c, chat::kMessage, "<" + r.name + "> " + r.text);
}
```

Второе — та самая мелочь, которая отличает работающий чат от учебного примера: человек, вошедший в комнату, видит, о чём говорят, а не пустой экран.

Порядок здесь важен: сначала история, потом уведомление «вы вошли». Иначе новичок увидит сообщения о своём приходе раньше того, что было до него.

## Хранить ли переписку вообще

Вопрос не технический, и обойти его нельзя.

Журнал сообщений — это персональные данные, и в большинстве стран их хранение регулируется законом: нужны основание, срок хранения и возможность удаления по требованию. Хранить переписку вечно «на всякий случай» — не нейтральное техническое решение, а осознанный выбор с последствиями.

Отсюда практические выводы, которые стоит принимать до того, как система начнёт работать. Определите срок хранения и удаляйте старое автоматически. Не пишите в журнал больше, чем нужно: адрес, устройство, точное время — всё это данные, которые потом придётся защищать. Шифруйте хранилище на диске, если переписка хоть сколько-нибудь чувствительная. И помните, что сквозное шифрование, при котором сервер вообще не видит содержимого, снимает большую часть этих вопросов — но делает невозможной серверную историю.

Для учебного чата всё это неважно. Для настоящего — важнее, чем выбор структуры данных.

## Главные правила главы

1. Шифр с повторяющимся ключом вскрывается по известному куску текста: сложение шифра с текстом даёт ключ.
2. Одинаковые сообщения при таком шифровании дают одинаковый шифр — утечка информации без всякого взлома.
3. Не изобретайте и не реализуйте криптографию сами; для соединения берите TLS, для данных — готовую библиотеку.
4. Отсутствие шифрования честнее самодельного: оно не создаёт ложного ощущения защищённости.
5. Записи журнала пишут целиком одним вызовом, чтобы не оставить половину при обрыве.
6. Любая длина, пришедшая извне — из сети или из файла, — проверяется до того, как под неё выделяют память.
7. При несостыковке в журнале чтение прекращают, а не пропускают запись: испорченный хвост доверия не заслуживает.
8. Чтение всего файла ради последних записей работает на килобайтах и не работает на гигабайтах — нужен индекс или ротация.

## Упражнения

1. Запустите `./build/xor_demo` и повторите атаку руками: возьмите первые семь байт шифра и первые семь байт известного текста, сложите их и убедитесь, что получился ключ.

2. Зашифруйте одним ключом два разных сообщения, сложите шифры между собой и посмотрите на результат. Что можно сказать об исходных текстах, не зная ключа?

3. Запустите `./build/history_demo`, посмотрите файл истории через `xxd` и найдите в нём длины, метку времени и строки.

4. Испортите файл истории: поменяйте первый байт длины на `0xFF`. Что сделает `recent`? Уберите проверку `body_len > kMaxRecord` и повторите — чем закончится?

5. Встройте историю в сервер комнат: запись при каждом сообщении, выдача последних десяти при входе. Проверьте, что новый участник видит разговор.

6. Замените `fsync` на каждую запись синхронизацией не чаще раза в секунду. Замерьте, как изменилась скорость приёма сообщений.

7. (Сложнее) Сделайте ротацию: когда файл истории превысил мегабайт, переименуйте его с меткой времени и начните новый. `recent` должен уметь дочитать предыдущий файл, если в текущем записей не хватило.

8. (Сложнее) Оберните соединение в TLS через OpenSSL: серверу понадобится сертификат (самоподписанный сгодится), клиенту — проверка. Сравните объём работы с самодельным шифрованием и подумайте, почему разница именно такая.

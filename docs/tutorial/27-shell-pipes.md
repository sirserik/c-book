# Глава 27. Файловые дескрипторы и pipes

В прошлой главе мы научились запускать одну программу через `fork+exec+wait`. В этой — соединим программы в **пайплайн**: `ls | grep .cpp | wc -l`. Это самая красивая и мощная идея Unix: маленькие программы, каждая делающая одно дело, соединяются в цепочку через стандартный механизм.

Я долго подходил к этой главе — пайпы концептуально просты, но их реализация требует **дисциплины** в работе с файловыми дескрипторами. Один забытый `close` — и пайплайн зависнет навсегда. К концу главы вы напишете правильную реализацию, которая работает для произвольной длины цепочки.

## Что такое файловый дескриптор

В Unix **всё — файл**. Точнее, всё доступно через единый интерфейс «открыть/прочитать/записать/закрыть». Дисковый файл, терминал, сетевое соединение, пайп, даже устройство (`/dev/null`, `/dev/random`) — всё через одну абстракцию.

Чтобы программа работала с файлом, ядро даёт ей **файловый дескриптор** (fd) — небольшое целое число, указатель на запись во внутренней таблице ядра.

У каждого процесса своя таблица fd. По умолчанию первые три занимают:

| fd | Имя | Куда |
|----|-----|------|
| 0 | stdin | Ввод |
| 1 | stdout | Вывод |
| 2 | stderr | Ошибки |

Когда вы запустили программу из терминала, эти три fd связаны с терминалом. Программа пишет в fd 1 — текст появляется в окне.

Когда вы запустили через `./program > out.txt` — shell перенаправил fd 1 на файл `out.txt`. Программа сама не знает, что её stdout куда-то перенаправлен.

### Открыть файл

```cpp
#include <fcntl.h>
#include <unistd.h>

int fd = open("data.txt", O_RDONLY);
char buf[100];
ssize_t n = read(fd, buf, sizeof(buf));
close(fd);
```

`open` возвращает наименьший свободный fd. Обычно начинает с 3 (после 0/1/2).

`read(fd, buf, n)` читает до `n` байтов. Возвращает реально прочитанное число, 0 при EOF, -1 при ошибке.

`write(fd, buf, n)` — наоборот.

`close(fd)` — освобождает запись в таблице. После — `fd` снова свободен для нового `open`.

В C++ обычно пользуются `<fstream>` (глава 12), а не сырыми вызовами. Но для пайпов придётся работать на низком уровне.

## fd наследуются через fork и exec

Главное: **при `fork` ВСЕ открытые fd дублируются в ребёнка**. Они указывают **на ту же запись** в ядре, что и у родителя. То есть если родитель писал в `fd 5`, и ребёнок пишет в `fd 5` — оба пишут в **одно и то же** место.

При `exec` fd **сохраняются** (если на них не выставлен флаг `FD_CLOEXEC`). Поэтому новая программа в ребёнке видит те же 0/1/2 (и любые другие открытые).

Это и есть основа **пайпов и редиректов**. Shell открывает пайп **до `fork`**, дальше ребёнок наследует fd, и его stdout (или stdin) подменяется на пайп через `dup2`.

## pipe() — создать пайп

`pipe(fds)` — системный вызов, создающий **пайп**. На входе — массив из двух `int`. На выходе:
- `fds[0]` — fd для **чтения** из пайпа.
- `fds[1]` — fd для **записи** в пайп.

Пайп — это буфер в ядре. Что записывается в fds[1], можно прочитать через fds[0]. Размер буфера обычно 64 KB.

```cpp
#include <unistd.h>

int fds[2];
if (pipe(fds) < 0) {
    perror("pipe");
    return 1;
}

write(fds[1], "hello", 5);

char buf[10];
ssize_t n = read(fds[0], buf, sizeof(buf));
// buf = "hello", n = 5

close(fds[0]);
close(fds[1]);
```

В одном процессе пайп бесполезен. Но если **сначала `pipe`**, потом **`fork`** — у ребёнка тоже будут эти fd, и можно общаться:

```cpp
int fds[2];
pipe(fds);

pid_t pid = fork();
if (pid == 0) {
    // Ребёнок пишет:
    close(fds[0]);  // нам не нужен read end
    write(fds[1], "hi parent", 9);
    close(fds[1]);
    _exit(0);
} else {
    // Родитель читает:
    close(fds[1]);  // нам не нужен write end
    char buf[20];
    ssize_t n = read(fds[0], buf, sizeof(buf));
    std::cout << "received: " << std::string(buf, n) << "\n";
    close(fds[0]);
    waitpid(pid, nullptr, 0);
}
```

Этот код печатает «received: hi parent».

Зачем оба процесса закрывают **один** конец? Каждый fd — это **счётчик ссылок** в ядре. Пайп удалится только когда ВСЕ ссылки закрыты. Если ребёнок не закроет `fds[0]` — у пайпа двое читателей; неаккуратно.

### EOF на пайпе

Когда **все** ссылки на write-конец закрыты, читатель получает **EOF** (read возвращает 0). Это сигнал «больше данных не будет».

Если хоть один write-конец открыт — read **блокируется**, ожидая данных. **Это самая частая причина зависшего пайплайна**: какой-то процесс забыл закрыть write-конец, и пайп никогда не сигналит EOF.

## dup2 — перенаправить fd

Файловый дескриптор — это просто номер в таблице. Можно **переназначить** этот номер на другую запись через `dup2`:

```cpp
dup2(src, dst);
```

После этого `dst` указывает на то же, на что `src`. Старая запись по `dst` закрывается (если была открыта).

Это критический инструмент. Пример: перенаправить stdout в файл.

```cpp
int file = open("out.txt", O_WRONLY | O_CREAT, 0644);
dup2(file, STDOUT_FILENO);   // теперь fd 1 = файл
close(file);                  // оригинальный fd больше не нужен

write(1, "hello\n", 6);       // пишется в out.txt, не в терминал
// или через std::cout — то же самое, cout пишет в fd 1
std::cout << "world\n";
```

`STDOUT_FILENO` — макрос для 1. Аналогично `STDIN_FILENO` (0), `STDERR_FILENO` (2). Числа можно писать напрямую, но макросы яснее.

После `dup2(file, 1)`:
- fd 1 теперь связан с `out.txt`.
- Оригинальный `file` (например, 3) тоже связан с тем же.
- Программа может писать в любой из них — попадёт в файл.
- `close(file)` отзывает запись `fd 3`. Запись `fd 1` остаётся.

Это **основа** редиректов. Shell перед `exec` ребёнка делает `dup2(file, STDOUT_FILENO)`, и ребёнок пишет в файл без своего ведома.

## A | B — пайплайн на две команды

Соберём всё. Нужно реализовать `ls | grep .cpp`.

Алгоритм:
1. Создать пайп.
2. Fork первого ребёнка (`ls`):
   - `dup2(pipe_write, STDOUT_FILENO)` — его stdout идёт в пайп.
   - Закрыть `pipe_read` и `pipe_write` (после dup они не нужны).
   - `execvp("ls", ...)`.
3. Fork второго ребёнка (`grep`):
   - `dup2(pipe_read, STDIN_FILENO)` — его stdin идёт из пайпа.
   - Закрыть `pipe_read` и `pipe_write`.
   - `execvp("grep", ...)`.
4. Родитель: **закрыть оба конца пайпа** (важно!). Иначе `grep` не получит EOF.
5. Ждать обоих детей.

Псевдокод:

```cpp
int fds[2];
pipe(fds);

pid_t p1 = fork();
if (p1 == 0) {
    dup2(fds[1], STDOUT_FILENO);
    close(fds[0]);
    close(fds[1]);
    execvp("ls", argv_ls);
    _exit(127);
}

pid_t p2 = fork();
if (p2 == 0) {
    dup2(fds[0], STDIN_FILENO);
    close(fds[0]);
    close(fds[1]);
    execvp("grep", argv_grep);
    _exit(127);
}

close(fds[0]);
close(fds[1]);

waitpid(p1, nullptr, 0);
waitpid(p2, nullptr, 0);
```

Главные тонкости:

1. **`pipe` до `fork`** — иначе fd не наследуется.
2. **В каждом ребёнке закрываем оба конца** после `dup2`. Один нужный уже подменён на 0 или 1, дублировать не нужно.
3. **Родитель закрывает оба конца** перед `waitpid`. Если оставить открытыми — `grep` будет ждать EOF от пайпа, который никто не закрыл.

## A | B | C — длинный пайплайн

Обобщение на N команд:

- Создать **N-1 пайпов** (между каждой парой соседних команд).
- Fork **N** детей.
- Ребёнок i:
  - Если i > 0: `dup2(pipes[i-1][0], STDIN_FILENO)` — stdin из левого пайпа.
  - Если i < N-1: `dup2(pipes[i][1], STDOUT_FILENO)` — stdout в правый пайп.
  - Закрыть ВСЕ пайповые fd (они либо дублированы, либо чужие).
  - `exec`.
- Родитель: закрыть ВСЕ пайповые fd. Ждать всех детей.

```cpp
int N = commands.size();
std::vector<std::array<int, 2>> pipes(N - 1);
for (int i = 0; i < N - 1; ++i) {
    pipe(pipes[i].data());
}

for (int i = 0; i < N; ++i) {
    pid_t pid = fork();
    if (pid == 0) {
        if (i > 0)     dup2(pipes[i - 1][0], STDIN_FILENO);
        if (i < N - 1) dup2(pipes[i][1], STDOUT_FILENO);
        
        for (auto& p : pipes) {
            close(p[0]);
            close(p[1]);
        }
        
        execvp(...);
        _exit(127);
    }
    children.push_back(pid);
}

// родитель закрывает все
for (auto& p : pipes) {
    close(p[0]);
    close(p[1]);
}

// ждём всех
for (pid_t c : children) {
    waitpid(c, nullptr, 0);
}
```

Тот же алгоритм для двух команд, но обобщённый.

## Реализация в demo-shell

### parse_pipeline

```cpp
Pipeline parse_pipeline(const std::string& line) {
    Pipeline p;
    auto tokens = tokenize(line);

    std::vector<std::string> current;
    for (auto& t : tokens) {
        if (t == "|") {
            if (!current.empty()) {
                p.commands.push_back(std::move(current));
                current.clear();
            }
        } else {
            current.push_back(std::move(t));
        }
    }
    if (!current.empty()) {
        p.commands.push_back(std::move(current));
    }
    return p;
}
```

Разбираем строку. Каждый `|` — разделитель команд. Остальные токены — аргументы текущей команды.

Ограничение: `|` должен быть **окружён пробелами**. `ls|grep` не сработает (наш `tokenize` это один токен). Настоящий shell умеет без пробелов; мы оставим как упражнение.

### run_pipeline

```cpp
int run_pipeline(const Pipeline& p) {
    if (p.empty()) return 0;
    const int n = static_cast<int>(p.commands.size());

    std::vector<std::array<int, 2>> pipes(n - 1);
    for (int i = 0; i < n - 1; ++i) {
        if (pipe(pipes[i].data()) < 0) {
            std::cerr << "pipe failed: " << std::strerror(errno) << "\n";
            close_all_pipes(pipes);
            return -1;
        }
    }

    std::vector<pid_t> children(n);
    for (int i = 0; i < n; ++i) {
        pid_t pid = fork();
        if (pid < 0) {
            std::cerr << "fork failed\n";
            close_all_pipes(pipes);
            return -1;
        }
        if (pid == 0) {
            if (i > 0) {
                dup2(pipes[i - 1][0], STDIN_FILENO);
            }
            if (i < n - 1) {
                dup2(pipes[i][1], STDOUT_FILENO);
            }
            close_all_pipes(pipes);

            auto argv = to_c_argv(p.commands[i]);
            execvp(argv[0], argv.data());
            std::cerr << "exec '" << argv[0] << "' failed: "
                      << std::strerror(errno) << "\n";
            _exit(127);
        }
        children[i] = pid;
    }

    close_all_pipes(pipes);

    int last_status = 0;
    for (int i = 0; i < n; ++i) {
        int status = 0;
        waitpid(children[i], &status, 0);
        if (i == n - 1) {
            if (WIFEXITED(status)) last_status = WEXITSTATUS(status);
            else if (WIFSIGNALED(status)) last_status = 128 + WTERMSIG(status);
        }
    }
    return last_status;
}
```

`close_all_pipes` — утилита, проходящая по всем парам и закрывающая обе стороны:

```cpp
void close_all_pipes(std::vector<std::array<int, 2>>& pipes) {
    for (auto& p : pipes) {
        if (p[0] >= 0) { close(p[0]); p[0] = -1; }
        if (p[1] >= 0) { close(p[1]); p[1] = -1; }
    }
}
```

Обнуляем после закрытия — если случайно вызовется ещё раз, не закроем чужой fd.

**Код возврата пайплайна — у последней команды**. Это конвенция bash: `ls | grep foo` возвращает код `grep`, не `ls`. (В `bash` есть `pipefail` опция, меняющая это, но по умолчанию — последняя.)

## Тонкости пайпов

Несколько ловушек, на которые легко напороться.

### Зомби пайплайн

Если в ребёнке вы забыли `close_all_pipes` после `dup2` — у него осталось 2 лишних fd. После `exec` они тоже наследуются. Когда `grep` ждёт EOF — `pipe[0]` всё ещё открыт у `ls`-ребёнка (а тот скоро умрёт, но fd закроется... может, и не закроется, если что-то странное).

Более серьёзный случай: родитель забыл закрыть write-конец. У ребёнка-читателя есть открытый writer (родитель). EOF никогда не приходит. Программа висит.

**Правило**: после `dup2` и форка — **закройте всё, что не нужно**.

### Размер буфера

Буфер пайпа на Linux обычно 64 KB. Если писатель отправил больше, чем 64 KB, и читатель ещё не читал — `write` **блокирует** писателя. Поэтому пайплайн идёт **параллельно**: писатель пишет → буфер заполняется → читатель читает → буфер освобождается → писатель продолжает.

В нашем `ls | wc -l` — `ls` пишет, `wc -l` читает. Если бы `ls` производил 100 GB вывода, `wc` бы потреблял по 64 KB за раз; всё работало бы, не падая из-за памяти.

Это **streaming**. Огромное преимущество пайпов.

### SIGPIPE

Что произойдёт, если писатель пишет в пайп, у которого **закрыт** read-конец? Например, `yes | head -1` — `head` берёт одну строку и закрывает stdin.

Ядро посылает писателю сигнал **SIGPIPE**. По умолчанию он завершает процесс. Поэтому `yes` после первого вывода завершается. Это нормально.

Если хотите ловить ошибку самостоятельно — игнорируйте `SIGPIPE`:

```cpp
signal(SIGPIPE, SIG_IGN);
```

Тогда `write` вернёт `-1` с `errno == EPIPE`. Это глава 28 (сигналы).

### Когда пайп — overkill

Пайп — это **межпроцессное** соединение. Тяжелее, чем «функция вызывает функцию». Если ваши «команды» — это код, который вы пишете сами, не нужно их разделять в процессы; пишите функции.

Пайп оправдан, когда:
- Соединяются **разные программы** (вам не подвластные).
- Нужна **изоляция** (один процесс упал — другой жив).
- Хотите **параллелизм без потоков**.

В нашем shell — пайп оправдан, потому что мы соединяем чужие программы.

### Внутри одной программы — `fork+pipe`

Если внутри одной программы нужен пайп между двумя кусками логики (вы пишете оба), можно тот же `fork+pipe` использовать без `exec`:

```cpp
int fds[2]; pipe(fds);
pid_t pid = fork();
if (pid == 0) {
    close(fds[1]);
    // ребёнок читает из fds[0]
    char buf[1024];
    while (true) {
        ssize_t n = read(fds[0], buf, sizeof(buf));
        if (n <= 0) break;
        // обработать
    }
    _exit(0);
}
close(fds[0]);
// родитель пишет в fds[1]
write(fds[1], data, len);
close(fds[1]);
waitpid(pid, nullptr, 0);
```

Это межпроцессная очередь. Очень полезно для серверов, которые отделяют обработчики запросов в отдельные процессы.

## Главные правила главы

1. **fd 0/1/2 — stdin/stdout/stderr.** Это везде в Unix.
2. **`pipe` ДО `fork`.** Иначе fd не наследуется.
3. **После `dup2` закройте оригинальный fd.** Дублирующая запись больше не нужна.
4. **Закройте ВСЕ концы пайпа в каждом ребёнке** и в родителе. Один забытый — зависание.
5. **Пайп — это streaming.** Буфер 64 KB, всё параллельно.
6. **`SIGPIPE`** при записи в закрытый пайп. По умолчанию убивает писателя.
7. **Код возврата пайплайна — у последней команды** (bash-конвенция).
8. **`fork+pipe` без `exec`** — для своей внутренней коммуникации.

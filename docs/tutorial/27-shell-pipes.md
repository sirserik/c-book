# Глава 27. Файловые дескрипторы и каналы

В прошлой главе оболочка научилась запускать одну программу. В этой она научится соединять программы в цепочку: `ls | grep .cpp | wc -l`. Три процесса, два канала, один результат.

Это, пожалуй, самая красивая идея Unix. Вместо одной огромной программы, умеющей всё, — набор маленьких, каждая из которых делает ровно одно дело и умеет читать со стандартного входа и писать в стандартный выход. Соединяются они не хитрым API, а вертикальной чертой. `wc` ничего не знает про `ls`, `grep` ничего не знает ни про того, ни про другого, но вместе они считают строки в отфильтрованном списке файлов.

Реализуется всё это на удивление небольшим количеством кода, но требует дисциплины: один незакрытый дескриптор — и цепочка зависает намертво. Мы такое зависание сейчас специально устроим, чтобы вы увидели его своими глазами и потом узнавали в собственном коде.

## Что такое файловый дескриптор

В Unix почти всё выглядит как файл. Дисковый файл, терминал, сетевое соединение, канал, устройство `/dev/null` — со всем этим работают через один и тот же набор действий: открыть, прочитать, записать, закрыть. Разница спрятана внутри ядра.

Открытая сущность в программе представлена файловым дескриптором — маленьким неотрицательным целым числом. Это индекс в личной таблице процесса, а уже запись в таблице ведёт к настоящему объекту внутри ядра.

Три первых индекса заняты с самого запуска:

| Дескриптор | Имя | Макрос | Назначение |
|-----------|-----|--------|------------|
| 0 | stdin | `STDIN_FILENO` | стандартный ввод |
| 1 | stdout | `STDOUT_FILENO` | стандартный вывод |
| 2 | stderr | `STDERR_FILENO` | поток ошибок |

Когда программу запускают из терминала, все три связаны с терминалом. Когда вы пишете `./program > out.txt`, оболочка перед запуском подменяет дескриптор 1 на файл — и программа даже не подозревает об этом. Она как писала в дескриптор 1, так и пишет.

Посмотрим, как раздаются номера. Файл `fds.cpp`:

```cpp
#include <iostream>
#include <fcntl.h>
#include <unistd.h>

int main() {
    std::cout << "STDIN_FILENO  = " << STDIN_FILENO  << "\n"
              << "STDOUT_FILENO = " << STDOUT_FILENO << "\n"
              << "STDERR_FILENO = " << STDERR_FILENO << "\n";

    int a = open("/etc/hosts", O_RDONLY);
    int b = open("/etc/hosts", O_RDONLY);
    std::cout << "первый open вернул " << a << ", второй " << b << "\n";

    close(a);
    int c = open("/etc/hosts", O_RDONLY);
    std::cout << "после close(" << a << ") новый open вернул " << c << "\n";
    return 0;
}
```

```bash
$ g++ -std=c++11 -Wall -Wextra -pedantic fds.cpp -o fds && ./fds
STDIN_FILENO  = 0
STDOUT_FILENO = 1
STDERR_FILENO = 2
первый open вернул 3, второй 4
после close(3) новый open вернул 3
```

Правило простое и жёстко зафиксированное в стандарте: `open` всегда возвращает **наименьший свободный номер**. Освободили тройку — следующий `open` снова получит тройку. Это не любопытный факт, а рабочий инструмент: старый способ перенаправить вывод состоял в том, чтобы закрыть дескриптор 1 и сразу открыть файл — он неизбежно занимал освободившееся первое место. Мы будем делать то же самое явно, через `dup2`, потому что так понятнее и безопаснее.

### Сырые чтение и запись

В главе 12 мы работали с файлами через `<fstream>` — и в обычном коде так и надо делать. Но каналы живут на уровень ниже, поэтому здесь придётся звать системные вызовы напрямую:

```cpp
int fd = open("data.txt", O_RDONLY);       // <fcntl.h>
char buf[100];
ssize_t n = read(fd, buf, sizeof(buf));    // <unistd.h>
close(fd);
```

`read(fd, buf, n)` пытается прочитать до `n` байт. Возвращает, сколько реально прочитал, `0` — если данные кончились (конец файла), `-1` — при ошибке. `write(fd, buf, n)` симметрична.

Слово «до» здесь принципиально. `read` имеет полное право вернуть меньше, чем запрошено, даже если данные ещё не кончились, — так бывает с терминалом, сетью и каналами постоянно. Точно так же `write` может записать не всё. Поэтому любой честный код читает и пишет в цикле, пока не наберёт нужное. В Части V мы напишем такой цикл для сокетов и будем разбирать его подробно; здесь нам хватит того, что `read` возвращает `0` ровно тогда, когда источник закончился.

Тип `ssize_t` — знаковый размер: он должен вмещать и обычные размеры, и `-1`.

## Дескрипторы переживают fork и exec

Теперь ключевой факт, на котором держится вся глава. При `fork` таблица дескрипторов копируется в ребёнка — но копируются **номера**, а сами объекты внутри ядра остаются общими. Ребёнок и родитель смотрят на один и тот же открытый файл.

Насколько «один и тот же», показывает опыт. Файл `sharedfd.cpp`:

```cpp
#include <iostream>
#include <fcntl.h>
#include <sys/wait.h>
#include <unistd.h>

int main() {
    int fd = open("shared.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);

    pid_t pid = fork();
    if (pid == 0) {
        write(fd, "ребёнок\n", 15);
        std::cout << "ребёнок:  позиция после записи = "
                  << lseek(fd, 0, SEEK_CUR) << "\n";
        std::cout.flush();
        _exit(0);
    }
    waitpid(pid, nullptr, 0);

    write(fd, "родитель\n", 17);
    std::cout << "родитель: позиция после записи = "
              << lseek(fd, 0, SEEK_CUR) << "\n";
    close(fd);
    return 0;
}
```

`lseek(fd, 0, SEEK_CUR)` ничего не сдвигает, а просто возвращает текущую позицию в файле. Смотрим:

```bash
$ ./sharedfd
ребёнок:  позиция после записи = 15
родитель: позиция после записи = 32
$ cat shared.txt
ребёнок
родитель
```

Ребёнок записал 15 байт и сдвинул позицию на 15. Родитель начал писать не с нуля, а с пятнадцати — и получил 32. Позиция чтения-записи не принадлежит процессу; она хранится в объекте ядра, общем для обоих. Отсюда, кстати, понятно, почему `./prog >> log` из нескольких процессов не перемешивает строки как попало, а почему `>` из двух процессов затирает данные.

При `exec` дескрипторы тоже сохраняются — если на них не выставлен флаг `FD_CLOEXEC` («закрыть при exec»). Именно поэтому запущенный из оболочки `ls` пишет в тот же терминал: он унаследовал дескриптор 1, и никто ему ничего специально не передавал.

Из этих двух фактов складывается вся техника, которой посвящена глава. Оболочка готовит дескрипторы **до** `fork`, ребёнок их наследует, между `fork` и `exec` подменяет ими свои 0 и 1 — и запускаемая программа работает с каналом, будучи уверенной, что общается с терминалом.

## pipe — канал в ядре

Системный вызов `pipe` создаёт однонаправленную трубу: буфер внутри ядра с двумя концами. Принимает он массив из двух `int` и заполняет его: `fds[0]` — конец для чтения, `fds[1]` — конец для записи. Что записали в первый, прочитается из второго; порядок байтов сохраняется.

Запомнить, какой конец где, помогает аналогия со стандартными номерами: 0 — чтение, как stdin; 1 — запись, как stdout.

Файл `pipe1.cpp` — канал внутри одного процесса:

```cpp
#include <iostream>
#include <string>
#include <unistd.h>

int main() {
    int fds[2];
    if (pipe(fds) < 0) { perror("pipe"); return 1; }
    std::cout << "pipe дал fd " << fds[0] << " (чтение) и "
              << fds[1] << " (запись)\n";

    const char* msg = "привет через ядро";
    ssize_t written = write(fds[1], msg, std::char_traits<char>::length(msg));

    char buf[64];
    ssize_t n = read(fds[0], buf, sizeof(buf));
    std::cout << "записано " << written << " байт, прочитано " << n
              << ": " << std::string(buf, static_cast<std::size_t>(n)) << "\n";

    close(fds[0]);
    close(fds[1]);
    return 0;
}
```

```bash
$ ./pipe1
pipe дал fd 3 (чтение) и 4 (запись)
записано 32 байт, прочитано 32: привет через ядро
```

Номера 3 и 4 — те самые «наименьшие свободные». А 32 байта вместо семнадцати символов — потому что строка русская: в UTF-8 каждая кириллическая буква занимает два байта. Ядро про буквы ничего не знает, оно считает байты.

Внутри одного процесса канал бесполезен: проще положить строку в переменную. Смысл появляется, когда концы оказываются в разных процессах, — а для этого достаточно сделать `pipe` до `fork`.

## Канал между процессами и правило закрытия

Соберём канал между родителем и ребёнком — и заодно устроим то самое зависание. Файл `hang.cpp`, у него есть режим с закрытием пишущего конца и режим без:

```cpp
#include <iostream>
#include <string>
#include <sys/wait.h>
#include <unistd.h>

int main(int argc, char** argv) {
    bool close_write = (argc > 1 && std::string(argv[1]) == "close");

    int fds[2];
    pipe(fds);

    pid_t pid = fork();
    if (pid == 0) {
        close(fds[1]);                    // ребёнок-читатель: пишущий конец не нужен
        char buf[64];
        ssize_t n;
        while ((n = read(fds[0], buf, sizeof(buf))) > 0) {
            std::cout << "ребёнок прочитал " << n << " байт\n";
        }
        std::cout << "ребёнок: read вернул " << n << " — это EOF\n";
        std::cout.flush();
        _exit(0);
    }

    write(fds[1], "данные", 12);
    if (close_write) close(fds[1]);       // <-- вот эта строка решает всё
    close(fds[0]);

    waitpid(pid, nullptr, 0);
    std::cout << "родитель: ребёнок завершился\n";
    return 0;
}
```

Сначала правильный вариант:

```bash
$ ./hang close
ребёнок прочитал 12 байт
ребёнок: read вернул 0 — это EOF
родитель: ребёнок завершился
```

Теперь тот же бинарник без аргумента, то есть без `close(fds[1])`:

```bash
$ ./hang &
$ sleep 3; ps -o pid,ppid,stat,command -ax | grep hang
50443 50442 SN   ./hang
50445 50443 SN   ./hang
```

Оба процесса живы и будут жить вечно. Ребёнок сидит в `read` и ждёт данных, родитель сидит в `waitpid` и ждёт ребёнка. Классическая взаимная блокировка, и оба виноваты одинаково.

Разберём, почему так. Ядро считает ссылки на каждый конец канала. Ребёнок закрыл свою копию пишущего конца, но у родителя копия осталась открытой — значит, писатели ещё есть, значит, данные ещё могут прийти, значит, `read` обязан ждать. Конец файла на канале наступает только тогда, когда закрыты **все** копии пишущего конца во всех процессах.

Отсюда правило, которое стоит выучить наизусть: **каждый процесс закрывает все концы, которые ему не нужны, и делает это сразу**. Не «в конце функции», не «перед выходом», а немедленно после `fork`. Забытый конец не вызывает ошибки, не печатает предупреждения — он просто однажды подвешивает вашу программу, и искать причину вы будете долго.

Кстати, о том, как искать. Если что-то зависло, посмотрите, какие дескрипторы открыты у процесса: `lsof -p PID` на macOS и Linux, `ls -l /proc/PID/fd` на Linux. Лишний `FIFO` или `pipe` в списке — и виновник найден.

### Сколько влезает в канал

Канал — это буфер конечного размера. Что будет, если писать в него, а не читать? Проверим. Файл `pipesize.cpp` переводит пишущий конец в неблокирующий режим, чтобы вместо зависания получить ошибку:

```cpp
#include <cerrno>
#include <cstring>
#include <iostream>
#include <fcntl.h>
#include <unistd.h>

int main() {
    int fds[2];
    pipe(fds);

    int flags = fcntl(fds[1], F_GETFL, 0);
    fcntl(fds[1], F_SETFL, flags | O_NONBLOCK);

    char chunk[1024];
    std::memset(chunk, 'x', sizeof(chunk));

    long total = 0;
    while (true) {
        ssize_t n = write(fds[1], chunk, sizeof(chunk));
        if (n < 0) {
            std::cout << "write остановился на " << total << " байт, errno = "
                      << std::strerror(errno) << "\n";
            break;
        }
        total += n;
    }
    close(fds[0]);
    close(fds[1]);
    return 0;
}
```

```bash
$ ./pipesize
write остановился на 65536 байт, errno = Resource temporarily unavailable
```

64 килобайта — обычная ёмкость канала и на macOS, и на Linux. Без `O_NONBLOCK` вместо ошибки `EAGAIN` писатель просто заснул бы в `write`, пока читатель не разберёт накопившееся.

Это ограничение — не недостаток, а именно то, что делает конвейер конвейером. Когда вы пишете `cat huge.log | grep error`, файл не читается целиком в память: `cat` наполняет буфер, засыпает, `grep` разбирает, `cat` просыпается и пишет дальше. Два процесса работают одновременно, а памяти тратится 64 килобайта независимо от того, гигабайтный лог или терабайтный. По той же причине `head -1` на огромном файле возвращается мгновенно — до конца никто не дочитывает.

### Что будет, если читателя не стало

Обратная ситуация: писатель пишет в канал, у которого закрыт читающий конец. Так бывает постоянно — `yes | head -1` устроен ровно так, `head` берёт строку и уходит.

Файл `sigpipe.cpp`:

```cpp
#include <cerrno>
#include <cstring>
#include <iostream>
#include <sys/wait.h>
#include <unistd.h>

int main() {
    int fds[2];
    pipe(fds);

    pid_t pid = fork();
    if (pid == 0) {
        close(fds[1]);
        close(fds[0]);          // читатель сразу уходит и закрывает свой конец
        _exit(0);
    }

    close(fds[0]);
    sleep(1);                   // даём ребёнку время закрыться

    ssize_t n = write(fds[1], "кому это надо?", 26);
    std::cerr << "write вернул " << n << ", errno = " << std::strerror(errno) << "\n";
    waitpid(pid, nullptr, 0);
    return 0;
}
```

```bash
$ ./sigpipe
$ echo $?
141
```

Сообщение не напечаталось вовсе, а код возврата — 141. Узнаёте? По формуле из прошлой главы 141 = 128 + 13, а сигнал 13 — это SIGPIPE. Ядро увидело запись в канал без читателей и убило писателя, не дав ему дойти до `std::cerr`.

Поведение это разумное: в конвейере из пяти команд бессмысленно, чтобы первая продолжала работать, когда последняя уже закончила. Но для сервера, который пишет клиенту в момент обрыва связи, смерть от SIGPIPE — катастрофа. Поэтому сигнал часто отключают. Добавим одну строку в начало `main`:

```cpp
#include <csignal>
...
std::signal(SIGPIPE, SIG_IGN);
```

```bash
$ ./sigpipe2
write вернул -1, errno = Broken pipe
$ echo $?
0
```

Теперь вместо смерти — честная ошибка: `write` вернул `-1`, `errno` равен `EPIPE`. Программа продолжила работу и завершилась нормально. Наша оболочка так и сделает, но уже в следующей главе, целиком посвящённой сигналам. В Части V, когда будем писать сервер чата, эта же проблема встретится снова — и там она куда острее.

## dup2 — подменить номер

Осталась последняя деталь механизма. Мы умеем создавать канал, но как заставить чужую программу читать из него? Программа-то будет читать из дескриптора 0, ничего не зная про наш канал с номером 3.

Ответ — `dup2(oldfd, newfd)`. Этот вызов делает `newfd` вторым именем того же объекта ядра, на который смотрит `oldfd`. Если `newfd` был чем-то занят, он предварительно закрывается — молча и автоматически.

```cpp
int file = open("out.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);  // допустим, дал 3
dup2(file, STDOUT_FILENO);   // теперь дескриптор 1 ведёт в out.txt
close(file);                 // номер 3 больше не нужен, объект остаётся жив

std::cout << "эта строка окажется в файле\n";
```

Три строки, и весь вывод программы уходит в файл. Причём `std::cout` ничего не заметил: он как писал в дескриптор 1, так и пишет, просто теперь за этим номером стоит файл.

Порядок здесь важен. Сначала `dup2`, потом `close` — и ни в коем случае не наоборот: закрыв `file` до `dup2`, вы получите `EBADF` и молчаливую поломку. А закрывать `file` нужно потому, что после `dup2` объект ядра доступен через оба номера, и лишний номер — это ровно тот забытый дескриптор, из-за которого потом не приходит EOF.

`STDOUT_FILENO` — это просто макрос для `1`, объявленный в `<unistd.h>`. Можно писать и цифру, но с макросом код читается лучше.

## Цепочка из двух команд

Соберём `ls | grep .cpp` вручную, из уже знакомых деталей. Порядок действий такой: создать канал, породить первого ребёнка и подменить ему дескриптор 1 на пишущий конец, породить второго и подменить ему дескриптор 0 на читающий конец, закрыть все лишние копии везде, дождаться обоих.

```cpp
int fds[2];
pipe(fds);

pid_t p1 = fork();
if (p1 == 0) {                          // левая команда: ls
    dup2(fds[1], STDOUT_FILENO);        // вывод уходит в канал
    close(fds[0]);
    close(fds[1]);
    execvp("ls", argv_ls);
    _exit(127);
}

pid_t p2 = fork();
if (p2 == 0) {                          // правая команда: grep
    dup2(fds[0], STDIN_FILENO);         // ввод приходит из канала
    close(fds[0]);
    close(fds[1]);
    execvp("grep", argv_grep);
    _exit(127);
}

close(fds[0]);                          // родителю канал не нужен вовсе
close(fds[1]);

waitpid(p1, nullptr, 0);
waitpid(p2, nullptr, 0);
```

Обратите внимание на три места, где ошибиться проще всего.

Первое: `pipe` вызывается до обоих `fork`. Если создать канал после, ребёнок его не унаследует — дескрипторы копируются в момент раздвоения, и позже созданные объекты в чужую таблицу не попадают.

Второе: каждый ребёнок закрывает **оба** конца, включая тот, который только что продублировал. Нужный конец уже живёт под номером 0 или 1, копия под номером 3 или 4 не нужна и вредна.

Третье, и самое коварное: родитель закрывает оба конца **до** `waitpid`. Если этого не сделать, `grep` никогда не увидит конца данных — ведь в таблице родителя всё ещё открыт пишущий конец, — и вся конструкция повиснет ровно так, как мы уже видели на `hang.cpp`.

## Цепочка из N команд

Обобщение прямолинейное. Для `n` команд нужно `n-1` каналов: между первой и второй, между второй и третьей и так далее. Ребёнок с номером `i` берёт вход из канала `i-1` (если он не первый) и отдаёт выход в канал `i` (если он не последний).

Для `ls | grep .cpp | wc -l` картина такая:

```
             канал 0            канал 1
    ls  ──── write ───► read ── grep ── write ───► read ── wc
   (i=0)                       (i=1)                     (i=2)

  i=0: stdout → pipes[0][1]
  i=1: stdin  ← pipes[0][0],  stdout → pipes[1][1]
  i=2: stdin  ← pipes[1][0]
```

Каждый ребёнок после двух возможных `dup2` закрывает вообще все концы всех каналов — и своих, и чужих. Чужие ему тем более не нужны, а держать их открытыми опасно: если, скажем, `wc` оставит открытым пишущий конец первого канала, то `grep` не дождётся EOF.

## Реализация в demo-shell

Теперь всё это надо уложить в наш проект. Начнём с типов. Новый файл `include/pipeline.h`:

```cpp
#ifndef SHELL_PIPELINE_H
#define SHELL_PIPELINE_H

#include <string>
#include <vector>

namespace shell {

struct Command {
    std::vector<std::string> argv;
};

struct Pipeline {
    std::vector<Command> commands;

    bool empty() const { return commands.empty(); }
    std::size_t size() const { return commands.size(); }
};

// Разбирает строку в цепочку команд, разделённых '|'.
Pipeline parse_pipeline(const std::string& line);

// Запускает цепочку и возвращает код последней команды.
int run_pipeline(const Pipeline& p);

}  // namespace shell

#endif
```

`Command` пока состоит из единственного поля, и такая структура выглядит избыточной — казалось бы, хватило бы `std::vector<std::vector<std::string>>`. Но в главе 29 у команды появятся ещё и перенаправления (`> out.txt`, `2>&1`), и тогда структура окажется на своём месте. Заводить её сразу дешевле, чем потом переписывать сигнатуры.

Разбор строки, `src/pipeline.cpp`:

```cpp
#include "pipeline.h"
#include "exec_runner.h"

#include <array>
#include <cerrno>
#include <cstring>
#include <iostream>
#include <stdexcept>
#include <vector>

#include <sys/wait.h>
#include <unistd.h>

namespace shell {

Pipeline parse_pipeline(const std::string& line) {
    Pipeline p;
    std::vector<std::string> tokens = tokenize(line);
    if (tokens.empty()) return p;

    Command current;
    for (std::size_t i = 0; i < tokens.size(); ++i) {
        if (tokens[i] == "|") {
            if (current.argv.empty()) {
                throw std::runtime_error("пустая команда перед '|'");
            }
            p.commands.push_back(std::move(current));
            current = Command();
        } else {
            current.argv.push_back(tokens[i]);
        }
    }

    if (current.argv.empty()) {
        throw std::runtime_error("пустая команда после '|'");
    }
    p.commands.push_back(std::move(current));
    return p;
}
```

Проходим по токенам и накапливаем слова в `current`, пока не встретится `|`; тогда накопленное уходит в список, а накопитель начинается заново. Две проверки на пустоту ловят `| ls` и `ls |` — команды без имени запускать нечего, и лучше сказать об этом сразу, чем получить непонятную ошибку из `execvp`. Ошибки мы бросаем исключением, а ловит его `main`; в главе 22 мы договорились, что исключения — для ситуаций, которые обнаружены глубоко, а обрабатываются высоко, и разбор командной строки подходит под это описание идеально.

Пока `tokenize` из прошлой главы режет строку по пробелам, `|` должен быть окружён пробелами: `ls|grep` пойдёт одним словом и не разберётся. В главе 29 токенизатор поумнеет и это ограничение исчезнет.

Дальше две вспомогательные функции. Обе нужны только внутри этого файла, поэтому прячем их в анонимное пространство имён — тот же приём, что в парсере мира из главы 23:

```cpp
namespace {

void close_all_pipes(std::vector<std::array<int, 2>>& pipes) {
    for (std::size_t i = 0; i < pipes.size(); ++i) {
        if (pipes[i][0] >= 0) { close(pipes[i][0]); pipes[i][0] = -1; }
        if (pipes[i][1] >= 0) { close(pipes[i][1]); pipes[i][1] = -1; }
    }
}

std::vector<char*> to_c_argv(const std::vector<std::string>& args) {
    std::vector<char*> r;
    r.reserve(args.size() + 1);
    for (std::size_t i = 0; i < args.size(); ++i) {
        r.push_back(const_cast<char*>(args[i].c_str()));
    }
    r.push_back(nullptr);
    return r;
}

}  // namespace
```

В `close_all_pipes` каждый закрытый дескриптор помечается как `-1`. Это защита от повторного закрытия: функция вызывается и в детях, и в родителе, а закрыть один и тот же номер дважды — ошибка не безобидная. Между двумя `close` ядро может выдать этот номер новому `open` в другом потоке, и второй `close` прикончит чужой файл. Такие ошибки ищут неделями, поэтому дешёвая пометка `-1` стоит своих двух строк.

Теперь главное — запуск:

```cpp
int run_pipeline(const Pipeline& p) {
    if (p.empty()) return 0;
    const int n = static_cast<int>(p.commands.size());

    std::vector<std::array<int, 2>> pipes(n > 0 ? n - 1 : 0);
    for (int i = 0; i < n - 1; ++i) {
        if (pipe(pipes[i].data()) < 0) {
            std::cerr << "pipe failed: " << std::strerror(errno) << "\n";
            close_all_pipes(pipes);
            return -1;
        }
    }

    std::vector<pid_t> children(n);
    for (int i = 0; i < n; ++i) {
        pid_t pid = fork();
        if (pid < 0) {
            std::cerr << "fork failed: " << std::strerror(errno) << "\n";
            close_all_pipes(pipes);
            return -1;
        }
        if (pid == 0) {
            if (i > 0) {
                dup2(pipes[i - 1][0], STDIN_FILENO);
            }
            if (i < n - 1) {
                dup2(pipes[i][1], STDOUT_FILENO);
            }
            close_all_pipes(pipes);

            std::vector<char*> argv = to_c_argv(p.commands[i].argv);
            execvp(argv[0], argv.data());
            std::cerr << "exec '" << argv[0] << "' failed: "
                      << std::strerror(errno) << "\n";
            _exit(127);
        }
        children[i] = pid;
    }

    close_all_pipes(pipes);

    int last_status = 0;
    for (int i = 0; i < n; ++i) {
        int status = 0;
        if (waitpid(children[i], &status, 0) < 0) {
            std::cerr << "waitpid: " << std::strerror(errno) << "\n";
            continue;
        }
        if (i == n - 1) {
            if (WIFEXITED(status)) last_status = WEXITSTATUS(status);
            else if (WIFSIGNALED(status)) last_status = 128 + WTERMSIG(status);
            else last_status = -1;
        }
    }
    return last_status;
}

}  // namespace shell
```

Функция читается сверху вниз как список действий, но в ней есть несколько мест, о которых стоит сказать отдельно.

Каналы создаются все сразу, до первого `fork`. Иначе третий ребёнок не унаследовал бы второй канал.

`std::array<int, 2>` вместо `int[2]` — потому что массивы в стиле C нельзя хранить в `std::vector`, у них нет ни копирования, ни присваивания. `pipes[i].data()` отдаёт указатель на первый элемент, а `pipe` только этого и ждёт.

Ветка ребёнка — самая важная. Первый в цепочке не трогает свой ввод: он читает откуда читал, обычно с терминала. Последний не трогает вывод: пишет туда же, куда писала оболочка. Все промежуточные подменяют оба конца. Затем — обязательное `close_all_pipes()`, закрывающее в ребёнке вообще все дескрипторы каналов; нужные уже продублированы под номерами 0 и 1, а всё остальное — балласт, из-за которого потом не придёт EOF.

Родитель закрывает каналы сразу после цикла запуска, не дожидаясь никого. Тут легко ошибиться и написать `waitpid` внутри цикла — казалось бы, разница невелика. Разница огромна: пока родитель ждёт первого ребёнка, второй ещё не запущен, и первому некуда девать вывод; заполнив 64 килобайта, он заснёт навсегда. Именно поэтому сначала запускаем всех, потом закрываем свои копии концов, и только затем ждём.

Код возврата цепочки берётся у последней команды — так делает `bash`. `ls nosuchfile | wc -l` вернёт ноль, потому что `wc` отработал прекрасно, хотя `ls` и пожаловался. Поведение спорное, и в `bash` его можно изменить опцией `set -o pipefail`, после которой цепочка возвращает код первой упавшей команды. Наша оболочка следует поведению по умолчанию; сделать `pipefail` — хорошее упражнение в конце главы.

Заметьте: цепочка длиной один здесь тоже работает. Каналов создаётся ноль, `dup2` не вызывается ни разу, остаётся `fork` + `exec` + `wait` — ровно то, что делала `run_external` в прошлой главе. Поэтому `run_external` больше не нужна, и из `exec_runner.h` она уходит; в файле остаётся один `tokenize`.

Подключаем в `src/main.cpp` — меняется всего пара строк:

```cpp
#include "pipeline.h"

...

shell::Pipeline p;
try {
    p = shell::parse_pipeline(line);
} catch (const std::exception& e) {
    std::cerr << "syntax: " << e.what() << "\n";
    continue;
}
if (p.empty()) continue;

const std::vector<std::string>& first = p.commands[0].argv;
if (!first.empty() && (first[0] == "exit" || first[0] == "quit")) {
    break;
}

int rc = shell::run_pipeline(p);
if (rc != 0) {
    std::cerr << "[exit " << rc << "]\n";
}
```

Проверка на `exit` теперь смотрит в первую команду цепочки, а не в первый токен строки. Разбор обёрнут в `try`, потому что `parse_pipeline` умеет бросать: синтаксическая ошибка не должна ронять оболочку, она должна печатать сообщение и возвращать приглашение.

## Главные правила главы

1. Дескриптор — это индекс в таблице процесса; 0, 1 и 2 заняты стандартными потоками, `open` всегда выдаёт наименьший свободный номер.
2. При `fork` дескрипторы копируются, но объект ядра остаётся общим — включая позицию в файле.
3. `pipe` вызывают до `fork`, иначе ребёнку нечего наследовать.
4. Конец данных на канале наступает, только когда закрыты все копии пишущего конца во всех процессах.
5. После `dup2` оригинальный дескриптор закрывают; в ребёнке закрывают вообще все концы каналов.
6. Родитель закрывает свои копии концов до `waitpid`, иначе цепочка виснет.
7. Запись в канал без читателей даёт SIGPIPE и код 141; с `SIG_IGN` — `write` возвращает `-1` и `EPIPE`.
8. Код возврата цепочки берут у последней команды, если не включён `pipefail`.

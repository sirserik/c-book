# Глава 35. Write-Ahead Log

Глава 33 дала нам страницы и кэш. Глава 34 — B+tree поверх них. Сейчас мы добавим **третий критический слой**: журнал, защищающий нас от потери данных при крахе. WAL (Write-Ahead Log) — это идея, лежащая в основе **транзакций** в любой настоящей СУБД.

К концу главы наш `mydb` сможет:
- Вставлять записи через WAL + B+tree.
- Имитировать краш (отсутствие `sync()`).
- При следующем открытии **восстановиться** через WAL.
- После checkpoint — обрезать WAL, освободив место.

## Проблема, которую решает WAL

Без WAL наш цикл:
1. `pm.write_page(pid, page)` — данные в кэше памяти.
2. ... много операций ...
3. `pm.sync()` — все dirty страницы на диск + fsync.

Между шагом 1 и 3 может пропасть питание. Тогда страницы B+tree, которые мы изменили, **не дошли до диска**. На следующем запуске:
- Прочитаем старые версии страниц.
- B+tree может быть **в неконсистентном состоянии**: например, split добавил новую страницу, но parent ещё не записан с указателем на неё. Получится «потерянный» лист в файле, или ссылка на несуществующую страницу.

Это плохо. Особенно для серверов БД: пользователь сделал commit, получил «OK», после краха данные пропали.

**WAL решает обе проблемы**: durability (данные сохранены) и atomicity (операция либо завершилась, либо нет).

## ACID — короткое напоминание

Транзакции в СУБД характеризуются четырьмя свойствами:

- **Atomicity** — атомарность. Операция либо вся применена, либо вся откачена. Не «полусделана».
- **Consistency** — согласованность. Транзакция переводит БД из одного валидного состояния в другое.
- **Isolation** — изолированность. Одновременные транзакции не видят промежуточные состояния друг друга.
- **Durability** — устойчивость. После commit изменения сохраняются даже при крахе.

WAL отвечает за **A** и **D**.

**I** требует locking или MVCC — у нас однопоточно, проблемы нет.

**C** — на стороне приложения (constraints, integrity checks) — мы не реализуем.

## Идея WAL

«Write-Ahead» = «пиши заранее». Главный принцип:

> **Перед изменением данных запиши в журнал намерение это сделать. Дождись fsync журнала. Только потом меняй данные.**

Цикл:
1. Программа хочет: `insert(key=10, value=100)`.
2. Записать в WAL: «type=insert, key=10, value=100».
3. `fsync` WAL — журнал durable.
4. Вернуть пользователю «OK» — операция совершена.
5. Когда-нибудь потом изменить B+tree в кэше. Возможно, через час сделать `pm.sync()`.

Что произойдёт при крахе?

**До шага 3**: WAL не содержит записи. Пользователь видит ошибку. Дерево не тронуто. Всё консистентно.

**После шага 3, до 5**: WAL содержит запись. Дерево в файле — старое. При запуске **replay** проиграет запись в дерево.

**После шага 5, до `pm.sync()`**: WAL содержит запись, дерево в кэше изменено, но не сброшено. Краш → дерево в файле старое. Recovery replay'нет запись в дерево.

**После `pm.sync()` и checkpoint**: запись и в WAL, и в дереве на диске. Можно **truncate** WAL — данные уже надёжно в дереве.

WAL **никогда** не отстаёт от данных. Если запись в WAL — она проиграется в дерево при recovery, **даже если** она уже была применена раньше (важно: операция должна быть **идемпотентной**, и `insert` в B+tree это так — повторная вставка просто перепишет значение).

## Формат записи WAL

Каждая запись — фиксированная структура:

```
[0..3]   u32 length (всегда 17 для наших insert-записей)
[4]      u8  type (1 = insert)
[5..12]  i64 key
[13..20] i64 value
[21..24] u32 crc
```

Всего 25 байт. Поля:
- **length** — длина «полезной нагрузки» (type+key+value). Для будущих типов записей может быть переменной.
- **type** — что за операция. `1` = insert. В будущем `2` = delete, `3` = checkpoint marker и т.д.
- **key, value** — данные.
- **crc** — простая хеш-сумма от type+key+value, для отлова повреждений.

## Алгоритм replay

При открытии БД:

```cpp
WAL wal(wal_path);
wal.replay([&](key, value) {
    tree.insert(key, value);
});
```

Читаем записи **с начала**. Для каждой — вызываем callback. Callback применяет в B+tree.

Если по пути встретили **повреждение** (плохой crc, неполная запись) — **останавливаемся**. Это означает: либо writer не дописал, либо физический сектор испортился. Всё **после** повреждения считается недурабельным.

Идемпотентность: повторное применение записи **не вредно**. `tree.insert(10, 100)` дважды — оба раза значение 100. Поэтому неважно, дошли ли изменения до B+tree до краша — replay применит их «как минимум один раз».

## Truncation после checkpoint

Если WAL растёт без ограничений — место кончится. Поэтому периодически делаем **checkpoint**:

1. **Flush B+tree**: `pm.sync()` — все dirty страницы на диск + fsync.
2. После этого данные **в дереве на диске** идентичны WAL.
3. **Truncate WAL**: обнуляем файл.

После truncate, если краш — replay начинается с пустого WAL. Дерево уже на диске. Всё консистентно.

Когда делать checkpoint? Компромисс:
- Часто → много fsync дерева → медленно при высокой нагрузке.
- Редко → большой WAL → долгий recovery.

В production БД checkpoint делают **по таймеру** (каждые 5-30 минут) или **по размеру WAL** (когда превысил предел).

## Group commit

Каждый `fsync` — миллисекунды. Если транзакции прилетают тысячами в секунду, **по одному fsync каждой** — узкое место.

**Group commit**: собираем N транзакций, записываем их **все** в WAL, делаем **один** fsync, отвечаем «OK» всем сразу.

Эффект: время на одну транзакцию падает с миллисекунды до микросекунд (если очередь длинная).

Усложнение: нужно ждать, пока соберётся группа. Не делаем в нашем демо — однопоточно и нет очереди.

## Класс WAL

`include/wal.h`:

```cpp
class WAL {
public:
    explicit WAL(const std::string& path);
    ~WAL();

    WAL(const WAL&) = delete;
    WAL& operator=(const WAL&) = delete;

    void log_insert(std::int64_t key, std::int64_t value);
    void replay(std::function<void(std::int64_t, std::int64_t)> cb);
    void truncate();
    std::size_t size_on_disk() const;

private:
    std::string path_;
    int fd_;
};
```

Простой API: log/replay/truncate.

`O_APPEND` при `open` гарантирует, что все `write` идут в конец файла, даже если есть параллельные writers (важно для будущей многопоточности).

### log_insert

```cpp
void WAL::log_insert(std::int64_t key, std::int64_t value) {
    unsigned char payload[PAYLOAD_BYTES];
    payload[0] = 1;
    // ... сериализация key и value в little-endian ...
    std::uint32_t crc = crc32_simple(payload, PAYLOAD_BYTES);

    unsigned char rec[RECORD_BYTES];
    // ... запись length + payload + crc ...

    if (!write_all(fd_, rec, RECORD_BYTES)) {
        throw WALError(...);
    }
    if (::fsync(fd_) < 0) {
        throw WALError(...);
    }
}
```

Сериализуем запись в буфер, делаем **один** `write` (атомарность от ОС), потом **`fsync`**.

**`fsync` после каждой записи** — самая консервативная стратегия. Гарантирует, что после возврата из `log_insert` данные на диске.

Альтернатива: батчинг (group commit). Записываем в буфер ОС, fsync периодически. Быстрее, но при крахе теряется хвост, не достигший fsync.

`write_all` — обработка short writes как в главе 27. `EINTR` — повтор.

### replay

```cpp
void WAL::replay(std::function<void(std::int64_t, std::int64_t)> cb) {
    int rfd = ::open(path_.c_str(), O_RDONLY);
    // ...
    
    unsigned char header[4];
    while (read_all(rfd, header, 4)) {
        std::uint32_t len = parse_u32(header);
        if (len != PAYLOAD_BYTES) break;   // битый заголовок

        unsigned char body[PAYLOAD_BYTES];
        if (!read_all(rfd, body, PAYLOAD_BYTES)) break;

        unsigned char tail[4];
        if (!read_all(rfd, tail, 4)) break;

        std::uint32_t got_crc = parse_u32(tail);
        if (got_crc != crc32_simple(body, PAYLOAD_BYTES)) break;   // повреждение

        if (body[0] != 1) break;   // неизвестный тип

        int64_t key = parse_i64(body + 1);
        int64_t value = parse_i64(body + 9);
        cb(key, value);
    }
    ::close(rfd);
}
```

Открываем отдельный fd для чтения (writer-fd в append-mode, не подходит для seek в начало). Читаем header, body, tail. Проверяем crc. Вызываем колбэк.

Любая ошибка — **`break`**, не throw. WAL может быть «недописан» — это нормальное состояние после краха. Просто останавливаемся в этой точке.

### truncate

```cpp
void WAL::truncate() {
    if (::ftruncate(fd_, 0) < 0) {
        throw WALError(...);
    }
    if (::fsync(fd_) < 0) {
        throw WALError(...);
    }
}
```

`ftruncate(fd, 0)` обнуляет файл. `fsync` обязателен — иначе truncate может потеряться при крахе, и WAL вернётся к старому содержимому.

`O_APPEND` гарантирует, что новые записи будут писаться с offset 0 после truncate.

## Демо: имитация краха

Сценарий: вставили 5 записей через `wal.log_insert + tree.insert`, **не** сделали `pm.sync()`. Программа закрылась без flush B+tree.

```cpp
{
    db::PageManager pm(db_path, 8);
    db::BPlusTree tree(pm);
    db::WAL wal(wal_path);

    for (auto& kv : inserts) {
        wal.log_insert(kv.first, kv.second);
        tree.insert(kv.first, kv.second);
    }
    // НЕ вызываем pm.sync() — имитируем краш
}
```

После выхода из блока деструктор `PageManager` пытается `sync()`, но **в нашем коде из главы 33** деструктор глотает ошибки и не гарантирует durability при программных ошибках. В реальной production-БД мы бы здесь падали без sync, и страницы B+tree остались бы в **старом** состоянии.

Открываем заново — playback:

```cpp
{
    db::PageManager pm(db_path, 8);
    db::BPlusTree tree(pm);
    db::WAL wal(wal_path);

    wal.replay([&](key, value) {
        tree.insert(key, value);
    });
    // дерево восстановлено
}
```

`replay` читает 5 записей из WAL, для каждой вызывает `tree.insert`. Дерево в кэше теперь актуально. На следующем `pm.sync()` запишется на диск.

После `pm.sync()` — **checkpoint**: данные надёжно в дереве, можно `wal.truncate()`.

### Запуск

```bash
$ ./build/mydb
=== mydb (глава 35: WAL) ===

После вставок WAL размер: 125 байт
(5 записей × 25 байт = 125)
B+tree pages: 4

Имитируем краш — B+tree НЕ синхронизирован.

--- Восстановление ---
Реплейнуто 5 записей
Содержимое дерева после восстановления:
  10=100 20=200 30=300 40=400 50=500 

После checkpoint:
  WAL размер: 0 байт
  B+tree pages durable.

--- Второе открытие (WAL пуск) ---
find(30) = 300
```

Сценарий полный:
1. Вставили 5 записей. WAL 125 байт. Дерево в кэше, не на диске.
2. Имитация краха (закрытие без sync).
3. Открытие → replay → дерево восстановлено.
4. Checkpoint: sync дерева + truncate WAL.
5. Второе открытие → WAL пуст → дерево в дереве уже всё есть.

Это надёжность production-уровня. Чуть упрощённая (мы не делаем page checksums, не верифицируем дерево после recovery), но идейно та же.

## Ещё уровни сложности

Что добавила бы настоящая СУБД:

### LSN

**Log Sequence Number** — порядковый номер записи в WAL. Каждая запись имеет свой LSN. Каждая страница B+tree помечается LSN последнего изменения. При recovery: для каждой страницы знаем, до какого LSN она актуальна, и replay'им только записи после.

Это **incremental recovery** — не переигрываем уже применённые операции. Огромная экономия времени.

### Physical vs logical WAL

Наш WAL — **logical**: записи операций («insert key=X»). Recovery — переигрывание операций.

Альтернатива — **physical**: записи изменений байтов («на странице P смещение O изменился байт X на Y»). Recovery — байт-за-байт применение.

PostgreSQL использует **physical**. MySQL InnoDB — **physiological** (что-то среднее).

Logical проще писать, но требует идемпотентности и предсказуемости (не все операции легко переиграть). Physical — точное копирование изменений, нечувствителен к деталям логики.

### Checkpoint protocol

В production checkpoint — не просто `sync + truncate`. Это **алгоритм**:

1. Записать в WAL `BEGIN CHECKPOINT`.
2. Сбросить все dirty страницы.
3. fsync файла данных.
4. Записать в WAL `END CHECKPOINT`.
5. fsync WAL.
6. (Опционально) truncate WAL до точки `BEGIN CHECKPOINT`.

Если краш на любом шаге — recovery понимает, где остановились, и продолжает корректно.

### Full page writes

При крахе во время записи 4 KB страницы — частичная запись (page tearing). Решение: при **первом** изменении страницы после checkpoint — записать в WAL **всю страницу**. Recovery восстанавливает страницу из WAL.

Это **full page writes** в PostgreSQL. Увеличивает размер WAL, но защищает от tearing.

### WAL archiving

WAL хранит **все** изменения. Если копировать WAL-файлы куда-то ещё (например, на другую машину) — можно построить **репликацию** и **point-in-time recovery** (восстановиться на любой момент в прошлом).

PostgreSQL `archive_mode = on` копирует WAL на холодный хранилище. MySQL `binlog` — то же.

## Главные правила главы

1. **WAL — основа durability и atomicity.** Без него СУБД не серьёзная.
2. **Write-Ahead** — пиши в журнал ДО изменения данных. Сначала намерение, потом действие.
3. **`fsync` WAL обязателен** перед возвратом «OK» пользователю.
4. **Идемпотентность операций** — replay должен работать корректно после повторного применения.
5. **Crc для отлова повреждений.** При recovery — стоп на первом плохом.
6. **Checkpoint = sync дерева + truncate WAL.** Иначе WAL разрастается.
7. **Group commit** для масштаба. Объединяй fsync'и.
8. **LSN и physical WAL** — индустриальный уровень. Для нашей демо хватит logical.

## Маленькое упражнение

1. Соберите. Запустите. Изучите вывод.

2. Запустите без `wal.truncate()` (закомментируйте). Запустите дважды. Что происходит? Подсказка: replay сработает дважды, но идемпотентно.

3. Откройте `data/wal_demo.wal` через `xxd`. Изучите формат — найдите length (17), key, value, crc.

4. Сломайте WAL: измените байт в записи через hex-editor или `dd`. Запустите. Replay должен остановиться на этой записи.

5. Удалите `pm.sync()` после успешного replay. Сделайте `wal.truncate()`. Запустите снова. Что произойдёт? (Дерево потеряно, WAL пуст — данные исчезли.)

6. (Сложнее) Добавьте тип `2 = delete` в WAL и реализуйте `wal.log_delete(key)`. Замените на полноценный `tree.remove(key)` (см. упражнение 7 главы 34).

7. (Сложнее) Реализуйте LSN. В каждой записи WAL — порядковый номер. На каждой странице B+tree храните LSN последнего изменения. При replay пропускайте записи с LSN <= LSN страницы.

8. (Сложнее) Реализуйте **group commit**: накапливайте записи в буфер, fsync один раз каждые N записей или каждые M миллисекунд.

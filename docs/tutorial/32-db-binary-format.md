# Глава 32. Бинарный формат данных

Начинается **Часть IV — мини-СУБД**. Восемь глав, в которых построим маленькую, но настоящую базу данных. С файлом на диске. С B+tree-индексом. С журналом транзакций. С мини-SQL и REPL. Это самая «низкоуровневая» часть книги: байты, страницы, выравнивание, бинарные форматы.

Если в Части II (RPG) мы хранили сейв в **текстовом** виде с эскейпингом, в Части IV это **не подойдёт**: миллион записей в текстовом виде — мегабайты на диске, и парсинг каждый раз. **Бинарный формат** даёт компактность и нулевую цену чтения. Но за это надо платить: разобраться с выравниванием, endianness, packed-структурами.

В этой главе мы заложим **фундамент**: код, который читает и пишет числа и строки в бинарный буфер. Покажу, чего избегать (raw memcpy struct) и почему. Дальше — стройные страницы, B+tree, и всё остальное.

## Текст vs бинарь

Сравним хранение одной записи: `id=42, name="Alice"`.

**Текстовый формат** (CSV, наш сейв-формат, JSON):
```
42,Alice
```
9 байт. Чтобы прочитать `id`, надо: разделить по `,`, конвертировать `"42"` в `int` через `stoi`. Конвертация — это парсинг символов один за одним, мини-state machine.

**Бинарный формат**:
```
2A 00 00 00 05 00 00 00 41 6C 69 63 65
[--- id ---] [-- len ---] [---- "Alice" ----]
```
13 байт. Чтобы прочитать `id`, прочесть 4 байта, **сразу** интерпретировать как `int32_t`. Никакого парсинга. Скорость — наносекунды.

Парадоксально, бинарь иногда **больше** на маленьких числах (42 в тексте — 2 байта; в бинаре — 4). Но на больших — обратное (12345678 в тексте — 8 байт; в бинаре — 4). И главное: чтение бинаря **не парсится**. Это критично для миллионов записей в СУБД.

Минусы бинаря:
- Нечитаемо глазами.
- Зависит от endianness.
- Требует версионирования (изменишь поле — старый файл сломается).
- Не редактируется текстовым редактором.

В нашей мини-СУБД — бинарный, потому что:
- Скорость критична.
- Мы делаем настоящий движок, а не игрушку.
- Понимание бинарных форматов — нужный навык.

## Что такое struct в памяти

Возьмём:

```cpp
struct Row {
    std::uint32_t id;
    std::uint16_t age;
    std::uint64_t balance;
};
```

Naive ожидание: 4 + 2 + 8 = 14 байт. **Не так.**

Реальное размещение:

```
| id (4 bytes) | age (2 bytes) | PADDING (2 bytes) | balance (8 bytes) |
0              4               6                   8                   16
```

Компилятор **добавил padding** в 2 байта после `age`. Размер `sizeof(Row) = 16`, не 14.

Зачем? **Выравнивание** (alignment). Каждый тип имеет требование к адресу:
- `uint8_t` — любой адрес (выравнивание 1).
- `uint16_t` — адрес кратный 2.
- `uint32_t` — адрес кратный 4.
- `uint64_t` — адрес кратный 8.

Это не прихоть компилятора. На некоторых процессорах (ARM до v8) обращение к **не-выровненному** числу — это **fault** (программа падает). На x86 — работает, но **медленнее** (нужно несколько обращений к памяти).

Поэтому компилятор раскладывает поля **так, чтобы каждое было выровнено**. Если для этого надо вставить пустые байты — вставляет.

`balance` начинается с адреса 8 (кратно 8 — выравнивание `uint64_t`). После `age` на адресе 6 нужно «прыгнуть» на 8, отсюда 2 байта padding.

В конце структуры тоже может быть padding — чтобы при размещении в массиве каждый следующий элемент тоже был выровнен.

## alignof, alignas, offsetof

C++ даёт операторы для проверки:

```cpp
#include <cstddef>

std::cout << sizeof(Row);              // 16
std::cout << alignof(Row);             // 8 (по самому большому полю)
std::cout << offsetof(Row, id);        // 0
std::cout << offsetof(Row, age);       // 4
std::cout << offsetof(Row, balance);   // 8 (НЕ 6!)
```

`alignof(T)` — требование к выравниванию типа. `offsetof(struct, field)` — смещение поля от начала структуры в байтах.

Можно **принудительно увеличить** выравнивание через `alignas`:

```cpp
struct alignas(64) CacheLine {
    int data;
};

std::cout << sizeof(CacheLine);   // 64 (выровнено и дополнено)
```

Используется когда вам нужны cache-line-выровненные структуры (для производительности).

**Уменьшить** выравнивание стандартным C++ нельзя. Но многие компиляторы дают расширения:

## Packed-структуры

GCC и Clang поддерживают `__attribute__((packed))`:

```cpp
struct __attribute__((packed)) RowPacked {
    std::uint32_t id;
    std::uint16_t age;
    std::uint64_t balance;
};

std::cout << sizeof(RowPacked);   // 14 — без padding!
```

Все поля «упакованы» вплотную. Никакого padding.

MSVC использует `#pragma pack(push, 1) ... #pragma pack(pop)`.

Проблема packed: **обращение к полю — не-выровнено**:

```cpp
RowPacked r;
std::uint64_t b = r.balance;   // на ARM может быть медленным или fault
```

Современные компиляторы делают «безопасную» сборку для packed-полей: разбивают чтение на несколько маленьких. Медленнее, чем обычное чтение, но работает на всех архитектурах.

**Когда брать packed**: когда вам нужно **точное соответствие** структуры памяти и формату файла/сети. Например, заголовок TCP-пакета определён стандартом — каждое поле строго по своему смещению.

**Когда НЕ брать**: для всего остального. Просто оставьте компилятору выровнять. Padding — это копейки на структурах, но микро-секунды на доступе.

## Проблема №1: raw struct dump

Соблазн: «у меня есть `Row` в памяти, могу же я просто записать его в файл?»

```cpp
Row r{42, 25, 1000};
std::ofstream out("data.bin", std::ios::binary);
out.write(reinterpret_cast<const char*>(&r), sizeof(r));
```

И прочитать:

```cpp
Row r;
std::ifstream in("data.bin", std::ios::binary);
in.read(reinterpret_cast<char*>(&r), sizeof(r));
```

Это **компилируется и работает** на той же машине. Но **никогда не делайте этого** в production. Причины:

### 1. Padding бит — это мусор

Записанная структура содержит **padding-байты**, которые компилятор не инициализирует. Они могут быть **чем угодно** — мусором из стека/кучи, остатками других данных. Возможно даже **конфиденциальной информацией** (если перед этим в этой памяти лежал пароль).

Для bit-точной сравнения двух структур в файле — нужна определённость. Padding делает её невозможной.

### 2. Размер зависит от платформы

`sizeof(long)` на Linux x86-64 = 8, на Windows x86-64 = 4. Если вы записали структуру с `long` на Linux — на Windows не прочитаете правильно.

Используйте `std::int32_t`, `std::int64_t` (из `<cstdint>`) — у них **фиксированный** размер на всех платформах. Это глава 8.

### 3. Endianness

Числа в памяти кодируются байтами. В каком **порядке**?

**Little-endian**: младший байт первый. `0x12345678` лежит как `78 56 34 12`.

**Big-endian**: старший байт первый. `0x12345678` лежит как `12 34 56 78`.

x86-64 (Intel/AMD) — **little-endian**. ARM64 (Apple Silicon, мобильные) — настраиваемая, обычно little-endian. Сетевой стандарт TCP/IP — **big-endian** (called «network byte order»).

Если вы записали struct на little-endian машине, прочитали на big-endian — числа развёрнуты. Будет хаос.

### 4. Алайнмент зависит от ABI

Even разные компиляторы на одной платформе могут иначе выравнивать структуры (если есть необычные типы). С GCC vs MSVC будут разные `sizeof` для одной и той же struct.

### Вывод

**Никогда не записывайте сырую structure через `memcpy`/`write` для обмена между процессами/машинами**.

Что делать? Записывать **поле за полем**, в **фиксированном порядке**, **байт-за-байт**.

## Правильный подход: explicit serialization

Пишем по байтам, явно. Никаких struct-dump'ов.

`include/binary.h`:

```cpp
namespace db {

inline void write_u32(std::vector<unsigned char>& out, std::uint32_t v) {
    for (int i = 0; i < 4; ++i) {
        out.push_back(static_cast<unsigned char>((v >> (i * 8)) & 0xFFu));
    }
}

inline std::uint32_t read_u32(const unsigned char* p) {
    std::uint32_t v = 0;
    for (int i = 0; i < 4; ++i) {
        v |= static_cast<std::uint32_t>(p[i]) << (i * 8);
    }
    return v;
}

}
```

Разбор:

`write_u32(v)`: пишем младший байт первым (little-endian).
- `v & 0xFF` — младший байт.
- `(v >> 8) & 0xFF` — второй.
- `(v >> 16) & 0xFF` — третий.
- `(v >> 24) & 0xFF` — старший.

`read_u32(p)`: читаем 4 байта, собираем обратно.
- `p[0]` это младший.
- `p[1] << 8` сдвигается на второй.
- И так далее.

После этого `read_u32(p)` всегда даёт **то же число**, что мы записали через `write_u32`, на любой машине. **Эндианнес фиксирован**.

`unsigned char` (или `uint8_t`) для буферов — чтобы избежать UB при битовых операциях с `signed char` (где знаковый бит сложен).

Аналогично для `u16`/`u64`:

```cpp
inline void write_u16(std::vector<unsigned char>& out, std::uint16_t v) {
    out.push_back(static_cast<unsigned char>(v & 0xFFu));
    out.push_back(static_cast<unsigned char>((v >> 8) & 0xFFu));
}

inline void write_u64(std::vector<unsigned char>& out, std::uint64_t v) {
    for (int i = 0; i < 8; ++i) {
        out.push_back(static_cast<unsigned char>((v >> (i * 8)) & 0xFFu));
    }
}
```

И строки — длина + байты:

```cpp
inline void write_string(std::vector<unsigned char>& out, const std::string& s) {
    write_u32(out, static_cast<std::uint32_t>(s.size()));
    out.insert(out.end(), s.begin(), s.end());
}
```

Сначала 4-байтная длина, потом тело. Это **length-prefixed** формат. Лучше null-terminated (как C-строки) — длина известна заранее, не надо сканить.

## Sign vs unsigned, signed numbers

Для **signed**-чисел `int32_t` есть нюанс. Они хранятся в дополнительном коде (глава 2). Если мы запишем `int32_t` через каст к `uint32_t`:

```cpp
inline void write_i32(std::vector<unsigned char>& out, std::int32_t v) {
    write_u32(out, static_cast<std::uint32_t>(v));
}

inline std::int32_t read_i32(const unsigned char* p) {
    return static_cast<std::int32_t>(read_u32(p));
}
```

— байты сохранятся правильно. Например, `-1` в дополнительном коде = `0xFFFFFFFF`. Каст в `uint32_t` даёт `0xFFFFFFFF`. Записали 4 байта `FF FF FF FF`. Прочли — обратно `0xFFFFFFFF`, каст в `int32_t` = `-1`.

Работает **благодаря дополнительному коду**. Если бы числа кодировались иначе (вспомните прямой код из главы 2) — пришлось бы знаки обрабатывать отдельно. На современных платформах — все two's complement, дополнительный код. Безопасно.

## htonl и подобные

POSIX даёт функции для **network byte order** (big-endian):

```cpp
#include <arpa/inet.h>

std::uint32_t nbo = htonl(0x12345678);   // host-to-network long
std::uint32_t hbo = ntohl(nbo);          // обратно
```

`htonl` (host-to-network long) переводит из локального порядка в сетевой. На big-endian машинах — no-op. На little-endian — переставляет байты.

Полезно, если вы делаете протокол, использующий сетевой порядок (как TCP, HTTP/2 фреймы). Для **локального** файла наша СУБД использует little-endian — её формат предназначен для одной машины.

## Пример: всё вместе

`src/main.cpp` (демо):

```cpp
#include "binary.h"
#include <iostream>
#include <iomanip>
#include <vector>

int main() {
    std::vector<unsigned char> buf;
    db::write_u32(buf, 0x12345678);
    db::write_u64(buf, 0xCAFEBABEDEADBEEFull);
    db::write_string(buf, "hello");

    std::cout << "Сериализовано " << buf.size() << " байт:\n";
    for (std::size_t i = 0; i < buf.size(); ++i) {
        std::cout << std::hex << std::setw(2) << std::setfill('0')
                  << static_cast<int>(buf[i]) << " ";
        if ((i + 1) % 16 == 0) std::cout << "\n";
    }
    std::cout << "\n";
}
```

Вывод:

```
Сериализовано 21 байт:
78 56 34 12 ef be ad de be ba fe ca 05 00 00 00 
68 65 6c 6c 6f
```

Разбор:
- `78 56 34 12` — `0x12345678` в little-endian.
- `ef be ad de be ba fe ca` — `0xCAFEBABEDEADBEEF` в little-endian.
- `05 00 00 00` — длина строки (5) в little-endian.
- `68 65 6c 6c 6f` — буквы `hello` в ASCII.

Hexdump читается легко, отладка очевидна.

## Hexdump для отладки

Утилита **`xxd`** или **`hexdump`** показывает бинарные файлы в hex+ASCII:

```bash
$ xxd data.bin
00000000: 7856 3412 efbe adde beba feca 0500 0000  xV4.............
00000010: 6865 6c6c 6f                             hello
```

Слева — адреса, потом hex-байты, справа — ASCII (точка для непечатных).

Это **must-have** для отладки бинарных форматов. Когда что-то не парсится — открываете в `xxd`, смотрите глазами, ищете ошибку.

Аналог на macOS — `xxd` (тоже работает) или `hexdump -C`.

В коде на C++ можно написать свою функцию `hexdump(buf)` за 20 минут — посмотрите примеры на крёп-страницах.

## Versioning формата

Прежде чем разворачивать парсер, **версионируйте**. Самое начало файла — **magic number** и **version**:

```
mydb v1\n
[содержимое]
```

Или бинарно:

```
4D 44 42 01     ← magic "MDB" + version 1
[содержимое]
```

Парсер сначала проверяет: магия совпадает? версия моя? Если нет — отказ.

Когда выпустите v2 — добавите поля, новый формат, версию 2. Если читаете файл с версией 1 — либо отказываете, либо умеете читать v1 через специальную функцию.

Это **критическая инфраструктура** долгоживущих форматов. У нас уже было в save-формате RPG (глава 24). В мини-СУБД — обязательно.

## Что увидите в следующих главах

В этой главе — фундамент. Дальше:

- **Глава 33**: страничный файл. Файл — массив страниц по 4 KiB. Каждая страница — `vector<unsigned char>(4096)`. Page cache: LRU, чтобы часто используемые страницы лежали в памяти.
- **Глава 34**: B+tree. Структура для упорядоченного индексирования. Разбиение узлов при заполнении, слияние при опустошении.
- **Глава 35**: WAL (Write-Ahead Log). Журнал «сначала запиши что собираешься делать, потом делай». Восстановление после краха.
- **Главы 36-39**: мини-SQL, индексы, REPL, бенчмарки.

Каждая глава вносит свой слой, фундамент остаётся — байтовый формат.

## Главные правила главы

1. **Никогда не сохраняйте struct через `memcpy`** в файл. Padding, endianness, ABI — всё против вас.
2. **Сериализуйте поле за полем.** Явный код, явный порядок байтов.
3. **`std::int32_t`/`std::uint32_t`** вместо `int`/`long` — фиксированный размер.
4. **Little-endian** как default для локальных форматов. Network byte order — для сети.
5. **Length-prefixed строки** — длина (4 байта) + содержимое. Не null-terminated.
6. **Magic number и version** в начале файла. Обязательно.
7. **`alignof`/`offsetof`/`sizeof`** — ваши друзья при дизайне. Изучите, что лежит в памяти.
8. **`xxd`** для отладки. Поверьте, понадобится часто.

## Маленькое упражнение

1. Соберите `demo-db` и запустите. Изучите вывод. Сопоставьте hex-байты с числами.

2. Возьмите вывод программы, сохраните в файл (например, через `write` в файл). Откройте через `xxd file.bin`.

3. Напишите `write_i32` и `read_i32` для signed. Проверьте на `-1`, `INT32_MIN`, `INT32_MAX`.

4. Создайте `struct Row { uint32_t id; uint16_t age; uint64_t balance; };`. Узнайте `sizeof`, `alignof`, `offsetof` для каждого поля. Объясните padding.

5. Добавьте `__attribute__((packed))`. Узнайте `sizeof` снова. Что изменилось?

6. Запишите 1000 `Row` через **explicit serialization** (поле за полем) — узнайте размер. То же через **raw memcpy** — узнайте размер. Сколько разница?

7. (Сложнее) Напишите `hexdump(const void* data, size_t len)` — функция, печатающая hex+ASCII в стиле `xxd`.

8. (Сложнее) Реализуйте `write_varint` — переменно-длинная кодировка чисел (как в protobuf). Маленькие числа — 1 байт, большие — больше. На реальной СУБД часто более компактно.

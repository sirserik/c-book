# Глава 32. Бинарный формат данных

Начинается Часть IV, и в ней восемь глав мы будем строить базу данных. Настоящую, хотя и маленькую: со страничным файлом на диске, кэшем страниц, B+-деревом, журналом упреждающей записи, крошечным диалектом SQL, планировщиком запросов и командой `EXPLAIN`. Лежать всё это будет в `demo-db/`, а называться `mydb`.

Работа предстоит другая, чем в Части III. Там мы договаривались с операционной системой; здесь главными станут два слова — корректность и производительность. Что значит «база не теряет данные, даже если выдернуть питание посреди записи». Почему поиск по индексу быстрее перебора в десятки раз. Как выглядит план запроса изнутри и почему он иногда выбирает не то, что вы ожидали.

Начнём с самого низа — с байтов. В Части II мы сохраняли мир RPG в текстовом виде, и это было правильным решением: файл читается глазами, отлаживается тривиально, а размеры игрушечные. Для базы данных такой формат не годится, и в этой главе мы разберёмся почему, а заодно напишем фундамент — код, который укладывает числа и строки в байты так, чтобы прочитать их можно было завтра, на другой машине и другим компилятором.

## Текст против байтов

Возьмём одну запись: `id = 42`, `name = "Alice"`.

В текстовом виде это девять байт: `42,Alice`. Компактно и понятно. Но чтобы получить из этого число 42, программа должна пройти по символам, проверить каждый на принадлежность цифрам, умножить накопленное на десять, прибавить очередную цифру — и всё это ради одного маленького целого. Разбор одного числа занимает десятки операций.

В бинарном виде та же запись выглядит так:

```
2A 00 00 00 05 00 00 00 41 6C 69 63 65
[--- id ---] [-- длина -] [---- "Alice" ----]
```

Тринадцать байт — больше, чем текстовых девять. Зато чтобы получить число, достаточно взять четыре байта по известному смещению и сложить их в `uint32_t`. Никакого разбора: одно чтение, три сдвига.

Разница в размере обманчива и зависит от данных. Число 42 в тексте занимает два байта, а в бинарном виде четыре. Зато 1234567890 в тексте — десять байт, а в бинарном по-прежнему четыре. Для базы данных с миллионами записей выигрывает бинарный формат, и не столько по размеру, сколько по цене чтения: разобрать миллион текстовых чисел — это миллион маленьких разборов, а прочитать миллион бинарных — это миллион обращений к памяти.

Платить приходится читаемостью. Бинарный файл не откроешь в редакторе, не поправишь руками, не посмотришь глазами, что там не так. Поэтому в этой главе будет отдельный раздел про то, чем смотреть.

### Насколько именно быстрее

Разговоры о скорости стоят немного без чисел, поэтому измерим. Программа готовит миллион 32-битных чисел в двух видах — текстом через пробел и четырьмя байтами каждое, — а потом складывает их, разбирая тем и другим способом:

```cpp
// разбор текста
std::istringstream in(text);
std::uint32_t v;
while (in >> v) sum1 += v;

// чтение байтов
for (int i = 0; i < N; ++i) {
    const unsigned char* p = bin.data() + i * 4;
    std::uint32_t v = static_cast<std::uint32_t>(p[0]) |
                      (static_cast<std::uint32_t>(p[1]) << 8) |
                      (static_cast<std::uint32_t>(p[2]) << 16) |
                      (static_cast<std::uint32_t>(p[3]) << 24);
    sum2 += v;
}
```

Сборка с `-O2`, результат:

```
текстом:  10719377 байт
бинарно:  4000000 байт
разбор текста: 347 мс
чтение байтов: 451 мкс
суммы совпали
```

Данных в текстовом виде почти в три раза больше, а разбор занимает в семьсот с лишним раз больше времени. Триста сорок семь миллисекунд против половины миллисекунды — на миллионе чисел. Именно из-за этой разницы ни одна база данных не хранит строки на диске в текстовом виде: цена разбора платится при каждом чтении.

Оговорюсь: `std::istringstream` — не самый быстрый способ разбирать числа, ручной разбор был бы в несколько раз быстрее. Но и он не приблизится к чтению готовых байтов, потому что байты читать не надо — их надо просто взять.

## Что компилятор делает со структурой

Первое, что приходит в голову: раз нужен бинарный формат — возьмём структуру и запишем её в файл как есть. Прежде чем объяснять, почему так делать нельзя, посмотрим, что вообще лежит в памяти.

```cpp
struct Row {
    std::uint32_t id;
    std::uint16_t age;
    std::uint64_t balance;
};
```

Наивный подсчёт даёт 4 + 2 + 8 = 14 байт. Спросим у компилятора — программа `utils/binary_demo.cpp` в нашем проекте это и делает:

```bash
$ ./build/binary_demo
=== Как компилятор разложил Row ===
sizeof(Row)              = 16
alignof(Row)             = 8
offsetof(Row, id)        = 0
offsetof(Row, age)       = 4
offsetof(Row, balance)   = 8
sizeof(RowPacked)        = 14
```

Шестнадцать, а не четырнадцать. И поле `balance` начинается не с шестого байта, а с восьмого — между ним и `age` образовалась дыра в два байта.

Виновато выравнивание. У каждого типа есть требование к адресу, по которому он может лежать: `uint8_t` — по любому, `uint16_t` — по чётному, `uint32_t` — кратному четырём, `uint64_t` — кратному восьми. Компилятор обязан разложить поля так, чтобы требование соблюдалось для каждого, и если для этого нужно вставить пустые байты — он их вставляет.

Требование не выдумано на пустом месте. На части процессоров обращение к невыровненному числу — это аппаратная ошибка и падение программы; на x86 оно работает, но медленнее, потому что процессору приходится делать два обращения к памяти и склеивать результат. Пустые байты — плата за то, чтобы каждое обращение было одним.

Дыры могут появиться и в конце структуры. Если после последнего поля размер не кратен `alignof`, компилятор добавит хвост — иначе в массиве второй элемент оказался бы невыровненным.

Инструменты для разглядывания всего этого — `sizeof`, `alignof` и макрос `offsetof` из `<cstddef>`. Первые два — операторы языка, третий достался в наследство от C и принимает имя типа и имя поля.

Есть и обратная возможность — потребовать выравнивание побольше:

```cpp
struct alignas(64) CacheLine {
    int data;
};
// sizeof(CacheLine) == 64
```

Это нужно, когда структура должна занимать отдельную строку кэша процессора: в многопоточном коде две переменные, попавшие в одну строку, начинают мешать друг другу, даже если логически не связаны. Об этом ложном разделении речь пойдёт в главе 42.

Уменьшить выравнивание стандартными средствами C++ нельзя, но компиляторы дают расширения. У GCC и Clang это `__attribute__((packed))`, у MSVC — `#pragma pack`:

```cpp
struct __attribute__((packed)) RowPacked {
    std::uint32_t id;
    std::uint16_t age;
    std::uint64_t balance;
};
// sizeof(RowPacked) == 14 — дыр нет
```

Четырнадцать байт, как мы и считали изначально. Только теперь `balance` лежит по адресу, кратному шести, и каждое обращение к нему компилятор вынужден собирать из кусочков.

Здесь принято говорить, что плотная упаковка обходится дорого. Проверим — миллион структур, двадцать проходов, суммируем поле `balance`:

```
выровненная: sizeof=16, 21 мс
packed     : sizeof=14, 17 мс
```

Плотная версия оказалась быстрее. Не потому, что невыровненное чтение бесплатно, а потому, что на x86 оно стоит очень мало, зато структура на два байта короче — и в кэш процессора помещается больше записей. При обходе миллиона элементов подряд выигрывает тот, у кого меньше данных.

Не делайте из этого вывод «пакуйте всё». Тот же тест на ARM или на процессоре без быстрого невыровненного доступа дал бы обратный результат, а на некоторых архитектурах программа бы просто упала. Вывод правильнее сформулировать иначе: утверждения о производительности проверяются измерением на своей платформе, а не берутся из общих соображений.

Плотная упаковка по-настоящему оправданна, когда структура обязана точь-в-точь соответствовать чужому формату — например, заголовку сетевого пакета, где каждое поле стоит на месте, предписанном стандартом. Для своих данных лучше не трогать выравнивание вовсе и, как мы сейчас увидим, вообще не полагаться на раскладку структуры.

## Почему структуру нельзя писать в файл

Соблазн велик:

```cpp
Row r{42, 25, 1000};
std::ofstream out("data.bin", std::ios::binary);
out.write(reinterpret_cast<const char*>(&r), sizeof(r));
```

Это компилируется, работает и даже читается обратно — на той же машине, тем же компилятором, в тот же день. Дальше начинаются неприятности, и их четыре.

### Дыры не инициализируются

Те два байта между `age` и `balance` компилятор не обязан ничем заполнять. Что там лежит — вопрос везения: остатки предыдущих значений на стеке, куски освобождённой памяти, что угодно. Посмотрим своими глазами. Демо-программа специально пачкает память байтами `0xAB`, потом кладёт туда структуру и заполняет поля:

```bash
=== Мусор в padding-байтах ===
00000000  2a 00 00 00 19 00 ab ab  e8 03 00 00 00 00 00 00  |*...............|
байты 6 и 7 — padding, их никто не инициализировал
```

Всё на месте: `2a 00 00 00` — это 42, `19 00` — это 25, `e8 03 ...` — это 1000. А между ними торчат `ab ab` — тот самый мусор, который мы туда положили до присваивания полей.

Для файла это означает две беды. Побайтовое сравнение двух логически одинаковых записей может дать «не равны». А ещё в дыры может утечь то, чего в файле быть не должно: если раньше в этой памяти лежал пароль или кусок чужих данных, он окажется в файле. Реальные утечки такого рода случались в сетевых протоколах не раз.

### Размеры типов разные

`sizeof(long)` равен восьми на Linux и четырём на Windows. Записали на одной системе, читаете на другой — сдвиг на четыре байта и полный мусор дальше. Лечится это просто: в форматах используются только типы фиксированного размера из `<cstdint>` — `std::int32_t`, `std::uint64_t` и их родня. О них шла речь в главе 8, и в нашей базе других не будет.

### Порядок байтов

Число `0x12345678` в памяти x86 и ARM лежит как `78 56 34 12` — младший байт первым, это порядок little-endian. Есть машины с обратным порядком, big-endian, где то же число лежит как `12 34 56 78`; в этом же порядке принято передавать числа в сетевых протоколах, отчего его называют сетевым.

Записали структуру на одной машине, прочитали на другой — числа развернулись. Причём не сломались явно, а тихо превратились в другие числа, что гораздо хуже.

### Разные компиляторы раскладывают по-разному

Правила выравнивания задаются не языком, а соглашением о двоичном интерфейсе (ABI) конкретной платформы. Для простых структур все современные компиляторы совпадают, но стоит появиться битовым полям, наследованию или необычным типам — и `sizeof` начинает различаться между GCC и MSVC.

Вывод простой и без исключений: **структуру нельзя писать в файл как есть**, если файл проживёт дольше одного запуска или уедет на другую машину. Писать надо поле за полем, в явно заданном порядке, байт за байтом.

## Явная сериализация

Весь фундамент умещается в один заголовок. `include/binary.h`:

```cpp
#ifndef DB_BINARY_H
#define DB_BINARY_H

#include <cstdint>
#include <cstring>
#include <string>
#include <vector>

namespace db {

// Запись/чтение чисел в little-endian с фиксированным размером.
// Не полагаемся на raw struct dump'ы — портабельность важнее микро-эффективности.

inline void write_u16(std::vector<unsigned char>& out, std::uint16_t v) {
    out.push_back(static_cast<unsigned char>(v & 0xFFu));
    out.push_back(static_cast<unsigned char>((v >> 8) & 0xFFu));
}

inline void write_u32(std::vector<unsigned char>& out, std::uint32_t v) {
    for (int i = 0; i < 4; ++i) {
        out.push_back(static_cast<unsigned char>((v >> (i * 8)) & 0xFFu));
    }
}

inline void write_u64(std::vector<unsigned char>& out, std::uint64_t v) {
    for (int i = 0; i < 8; ++i) {
        out.push_back(static_cast<unsigned char>((v >> (i * 8)) & 0xFFu));
    }
}

inline void write_string(std::vector<unsigned char>& out, const std::string& s) {
    // Длина (u32) + байты.
    write_u32(out, static_cast<std::uint32_t>(s.size()));
    out.insert(out.end(), s.begin(), s.end());
}

inline std::uint16_t read_u16(const unsigned char* p) {
    return static_cast<std::uint16_t>(p[0]) |
           (static_cast<std::uint16_t>(p[1]) << 8);
}

inline std::uint32_t read_u32(const unsigned char* p) {
    std::uint32_t v = 0;
    for (int i = 0; i < 4; ++i) {
        v |= static_cast<std::uint32_t>(p[i]) << (i * 8);
    }
    return v;
}

inline std::uint64_t read_u64(const unsigned char* p) {
    std::uint64_t v = 0;
    for (int i = 0; i < 8; ++i) {
        v |= static_cast<std::uint64_t>(p[i]) << (i * 8);
    }
    return v;
}

inline std::string read_string(const unsigned char* p, std::size_t& consumed) {
    std::uint32_t len = read_u32(p);
    std::string s(reinterpret_cast<const char*>(p + 4), len);
    consumed = 4 + len;
    return s;
}

}  // namespace db

#endif
```

Логика записи одинакова во всех трёх функциях: берём число, отрезаем от него по байту начиная с младшего, кладём в буфер. Выражение `(v >> (i * 8)) & 0xFF` при `i = 0` даёт младший байт, при `i = 1` — следующий, и так далее. Чтение делает обратное: берёт байты по порядку и сдвигает каждый на своё место.

Ключевое свойство этого кода — он не зависит от того, как число лежит в памяти. Мы не смотрим на память числа, мы вычисляем байты арифметикой. Поэтому на big-endian машине функции выдадут ровно тот же файл, и прочитают его так же. Порядок байтов в файле мы задали сами, и он little-endian — не потому, что так лежит на x86, а потому, что мы так написали.

Буфер — `std::vector<unsigned char>`, и знаковость тут важна. У `char` она зависит от платформы, а с отрицательными значениями побитовые операции ведут себя неожиданно: при расширении до `int` знаковый байт `0xD0` превращается в `0xFFFFFFD0`. С `unsigned char` таких сюрпризов нет.

Функция `read_string` возвращает через параметр `consumed` количество съеденных байт — вызывающему нужно знать, где начинается следующее поле. Приём распространённый, хотя в C++17 его вытесняет возврат пары или `string_view` на исходный буфер.

Проверим на деле — тот же `binary_demo` пишет три значения подряд и печатает шестнадцатеричный дамп:

```
=== Явная сериализация ===
записано 21 байт
00000000  78 56 34 12 ef be ad de  be ba fe ca 05 00 00 00  |xV4.............|
00000010  68 65 6c 6c 6f                                    |hello|

читаем обратно:
  u32 = 0x12345678
  u64 = 0xcafebabedeadbeef
  str = "hello" (9 байт)
```

Каждый байт на своём месте: `78 56 34 12` — это `0x12345678` младшим байтом вперёд, затем восемь байт числа, затем четыре байта длины строки (`05 00 00 00`) и пять байт самой строки. Двадцать один байт, ни одного лишнего.

### Строки с префиксом длины

Строка записана как длина плюс тело, а не как в C — с нулевым байтом в конце. Разница принципиальная.

Нулевой байт в конце заставляет читателя идти по строке и искать этот ноль — то есть заранее не известно, сколько читать. Ещё хуже, что строка с нулевым байтом внутри становится непредставимой, а в базе данных это вполне законные данные: двоичный ключ, кусок картинки, что угодно.

Префикс длины снимает обе проблемы. Прочитали четыре байта — знаем, сколько читать дальше, можем сразу выделить память нужного размера и прочитать одним куском. Любые байты внутри допустимы. Именно так устроены почти все двоичные форматы, от Protocol Buffers до сетевого протокола, который мы напишем в главе 44.

### Знаковые числа

Отдельных функций для знаковых чисел в заголовке нет, и они не нужны:

```cpp
write_u64(buf, static_cast<std::uint64_t>(some_int64));
std::int64_t back = static_cast<std::int64_t>(read_u64(p));
```

Работает это благодаря дополнительному коду, о котором шла речь в главе 2. Число `-1` в нём представлено единичными битами во всех разрядах; приведение к беззнаковому типу битов не меняет, оно лишь меняет их истолкование. Записали `ff ff ff ff ff ff ff ff`, прочитали обратно, привели к знаковому — получили `-1`.

```
=== Отрицательные числа ===
00000000  ff ff ff ff ff ff ff ff  00 00 00 00 00 00 00 80  |................|
прочитали обратно: -1
```

Вторые восемь байт — это `INT64_MIN`, самое маленькое представимое число: единица в старшем бите и нули во всех остальных. Обратите внимание, что старший бит оказался в последнем байте, — это и есть порядок little-endian.

Начиная с C++20 дополнительный код закреплён в стандарте, до этого формально допускались и другие представления, но живых платформ с ними не осталось.

### Числа с плавающей точкой и правило про memcpy

Сдвигами можно разобрать целое число, но не `double` — сдвигать вещественные типы нельзя. А хранить их иногда нужно.

Приём тут такой: взять биты числа как целое, а дальше действовать как обычно. Соблазнительный способ взять биты — привести указатель:

```cpp
double d = 3.14159;
std::uint64_t bits = *reinterpret_cast<std::uint64_t*>(&d);   // так нельзя
```

Так делать нельзя, и дело не в занудстве. Стандарт запрещает читать объект одного типа через указатель на несовместимый тип — правило называется строгим соответствием типов (strict aliasing). Компилятор им пользуется при оптимизации: он вправе считать, что запись в `double` не может изменить то, что читается через `uint64_t*`, и переставить операции местами. Код при этом обычно работает — до тех пор, пока однажды не перестанет, причём только в сборке с оптимизацией.

Законный способ один — скопировать байты:

```cpp
double d = 3.14159;
std::uint64_t bits = 0;
std::memcpy(&bits, &d, sizeof(bits));
// дальше bits пишем через write_u64
```

```bash
$ ./aliasing
double 3.14159 в битах: 0x400921f9f01b866e
обратно: 3.14159
первый байт числа 1: 1  → little-endian
```

Опасение, что `memcpy` — это дорогой вызов функции, беспочвенно: при известном размере компилятор превращает его в одну команду пересылки. Я проверил ассемблер, который выдал `g++ -O2` для этой программы: ни одного вызова `memcpy` в нём нет.

Тот же приём даёт законный способ узнать порядок байтов своей машины: положить в `uint32_t` единицу и посмотреть на первый байт через `memcpy`. Если там единица — младший байт идёт первым, машина little-endian.

С форматом чисел с плавающей точкой на практике проблем не бывает: все живые платформы используют IEEE 754, и биты `double` означают на них одно и то же. Проверить это в коде можно через `std::numeric_limits<double>::is_iec559`.

### Сетевой порядок байтов

Раз речь зашла о порядке, стоит упомянуть готовые функции из `<arpa/inet.h>`:

```cpp
std::uint32_t nbo = htonl(0x12345678);   // из порядка машины в сетевой
std::uint32_t hbo = ntohl(nbo);          // обратно
```

`htonl` и `ntohl` переводят между порядком машины и сетевым (big-endian); есть ещё пара `htons`/`ntohs` для 16-битных. На big-endian машине они ничего не делают, на little-endian переставляют байты.

Пользоваться ими имеет смысл, когда формат задан снаружи и требует сетевого порядка, — так устроены заголовки TCP, кадры HTTP/2 и почти все старые протоколы. Наш формат файла мы придумываем сами, поэтому берём little-endian: на подавляющем большинстве машин это порядок процессора, и лишних перестановок не будет.

## Чем смотреть в бинарный файл

Отладка бинарного формата без инструмента невозможна, поэтому инструмент стоит завести сразу. В системе есть `xxd` (и `hexdump -C`, если `xxd` не установлен):

```bash
$ xxd /tmp/waldemo/data.wal
00000000: 1100 0000 0101 0000 0000 0000 0064 0000  .............d..
00000010: 0000 0000 00fe 9b83 7911 0000 0001 0200  ........y.......
00000020: 0000 0000 0000 c800 0000 0000 0000 f900  ................
00000030: 0bef                                     ..
```

Слева адрес, в середине байты, справа те же байты как символы — точка вместо непечатаемых. Это журнал нашей базы после двух вставок, и в нём уже можно кое-что разобрать: `1100 0000` — длина записи (17), `01` — тип «вставка», дальше восемь байт ключа (единица), восемь байт значения (`64` — это 100), затем четыре байта контрольной суммы. Вторая запись начинается со смещения 25 и содержит ключ 2 и значение 200 (`c8`). Формат журнала мы разберём в главе 35, а пока важно другое: открыв файл так, вы за минуту находите смещение, где формат разъехался.

Иметь такую же печать внутри программы удобно вдвойне: в отладчике не всегда есть `xxd`, а вывести дамп куска памяти прямо из кода — дело двадцати строк:

```cpp
void hexdump(const unsigned char* data, std::size_t len) {
    for (std::size_t i = 0; i < len; i += 16) {
        std::cout << std::hex << std::setw(8) << std::setfill('0') << i << "  ";

        for (std::size_t j = 0; j < 16; ++j) {
            if (i + j < len) {
                std::cout << std::setw(2) << std::setfill('0')
                          << static_cast<int>(data[i + j]) << " ";
            } else {
                std::cout << "   ";
            }
            if (j == 7) std::cout << " ";
        }

        std::cout << " |";
        for (std::size_t j = 0; j < 16 && i + j < len; ++j) {
            unsigned char c = data[i + j];
            std::cout << static_cast<char>((c >= 32 && c < 127) ? c : '.');
        }
        std::cout << "|\n";
    }
    std::cout << std::dec << std::setfill(' ');
}
```

Тонкость одна, и она про манипуляторы потоков. `std::hex`, `std::setfill` и `std::setw` ведут себя по-разному: первые два переключают режим потока навсегда, а `setw` действует только на ближайший вывод. Поэтому `setw` стоит перед каждым числом, а вот вернуть поток в десятичный режим и восстановить заполнитель нужно один раз в конце — иначе весь последующий вывод программы окажется шестнадцатеричным с ведущими нулями. Ошибка распространённая и ищется долго.

Приведение `static_cast<int>(data[i + j])` обязательно: без него `std::cout` напечатал бы байт как символ, а не как число.

## Метка формата и версия

Последнее, что нужно заложить в фундамент, — способ узнать, что за файл нам подсунули.

Мы будем открывать файл и читать из него страницы, доверяя, что там наши данные. А если это чужой файл? Или файл, записанный прошлой версией нашей же программы, где формат был другим? Без проверки программа честно прочитает мусор и начнёт делать вид, что это дерево, — с непредсказуемыми последствиями вплоть до бесконечного цикла.

Лечится это меткой в самом начале. В нашей базе нулевая страница отведена под метаданные дерева, и первые восемь байт мы разложили так: четыре байта — номер корневой страницы, затем три байта метки `MDB` и один байт версии формата.

```cpp
constexpr unsigned char MAGIC_0 = 'M';
constexpr unsigned char MAGIC_1 = 'D';
constexpr unsigned char MAGIC_2 = 'B';
constexpr unsigned char FORMAT_VERSION = 1;

void BPlusTree::save_metadata() {
    Page meta = make_page();
    write_u32_at(meta, 0, root_page_id_);
    meta[4] = MAGIC_0;
    meta[5] = MAGIC_1;
    meta[6] = MAGIC_2;
    meta[7] = FORMAT_VERSION;
    pm_.write_page(0, meta);
}

void BPlusTree::load_metadata() {
    Page meta = pm_.read_page(0);
    if (meta[4] != MAGIC_0 || meta[5] != MAGIC_1 || meta[6] != MAGIC_2) {
        throw PageError("это не файл mydb (нет метки MDB в странице 0)");
    }
    if (meta[7] != FORMAT_VERSION) {
        throw PageError("версия формата " + std::to_string(static_cast<int>(meta[7])) +
                        " не поддерживается (нужна " +
                        std::to_string(static_cast<int>(FORMAT_VERSION)) + ")");
    }
    root_page_id_ = read_u32_at(meta, 0);
}
```

Проверка стоит два сравнения и окупается первым же случаем, когда кто-то укажет базе на посторонний файл:

```bash
$ ./build/mydb /tmp/aliendir
mydb REPL — таблица 'items(id INT PRIMARY KEY, value INT)' по умолчанию.
Open: /tmp/aliendir
Не удалось открыть базу в /tmp/aliendir: это не файл mydb (нет метки MDB в странице 0)
$ echo $?
1
```

Отдельная польза от версии — она даёт путь к развитию формата. Когда в будущем понадобится добавить в узел новое поле, вы поднимете версию до двойки; старая программа честно откажется читать новый файл, а новая сможет распознать единицу и прочитать старый файл по старым правилам. Без версии обе программы будут читать чужие данные и делать вид, что всё в порядке.

Ту же метку мы уже заводили в формате сохранения RPG в главе 24 — там она называлась `RPGSAVE`. Приём универсальный: любой формат, который проживёт дольше одного запуска, начинается с метки и версии.

## Переменная длина: как сэкономить на маленьких числах

У формата с фиксированной шириной есть очевидная слабость: число 3 занимает те же восемь байт, что и три миллиарда. В базе, где большинство значений маленькие, это заметная переплата.

Лечится это кодированием переменной длины. Приём известен под именем varint и применяется в Protocol Buffers, в форматах Git, в SQLite. Идея: в каждом байте семь бит данных, а старший бит означает «есть продолжение».

```cpp
void write_varint(std::vector<unsigned char>& out, std::uint64_t v) {
    while (v >= 0x80) {
        out.push_back(static_cast<unsigned char>((v & 0x7F) | 0x80));
        v >>= 7;
    }
    out.push_back(static_cast<unsigned char>(v));
}

std::uint64_t read_varint(const unsigned char* p, std::size_t& consumed) {
    std::uint64_t v = 0;
    int shift = 0;
    std::size_t i = 0;
    while (true) {
        unsigned char b = p[i++];
        v |= static_cast<std::uint64_t>(b & 0x7F) << shift;
        if ((b & 0x80) == 0) break;
        shift += 7;
    }
    consumed = i;
    return v;
}
```

Запись отрезает по семь младших бит, пока число не станет меньше 128; на каждом байте, кроме последнего, поднимает старший бит. Чтение собирает обратно, останавливаясь на байте без старшего бита.

```
0: 1 байт (u64 занял бы 8)
1: 1 байт
127: 1 байт
128: 2 байт
300: 2 байт
100000: 3 байт
4294967295: 5 байт
```

Выигрыш на маленьких числах трёх-восьмикратный. Плата — трёхкратная: во-первых, размер записи заранее неизвестен, и её нельзя пропустить, не разобрав; во-вторых, разбор стоит цикла с ветвлением вместо простого чтения; в-третьих, самые большие числа занимают уже не восемь байт, а десять.

Из-за первого пункта мы varint в нашей базе не используем. Внутри страницы ключи лежат подряд, и поиск по ним делается двоичным — а он требует, чтобы к элементу с номером `i` можно было обратиться по смещению, без разбора предыдущих. С фиксированной шириной это `HEADER + i * 8`, с переменной пришлось бы читать всё подряд.

Общее правило звучит так: переменная длина хороша там, где данные всё равно читаются подряд (журналы, сетевые сообщения, архивы), и мешает там, где нужен произвольный доступ внутри блока.

Отдельная тонкость — отрицательные числа. Наивный varint для `-1` даст десять байт, потому что в дополнительном коде это все единицы. Поэтому знаковые числа сначала переводят зигзагом: `0 → 0`, `-1 → 1`, `1 → 2`, `-2 → 3`, что записывается как `(v << 1) ^ (v >> 63)`. После такого преобразования маленькие по модулю числа остаются маленькими.

## Развитие формата

Метка и версия дают возможность менять формат, но саму возможность надо ещё уметь использовать. Скажем, завтра нам понадобится хранить в узле дерева не только ключ и значение, но и время изменения. Есть три способа это пережить.

Самый простой — поднять версию и отказаться читать старые файлы. Годится для промежуточных данных, кэшей, временных индексов: пользователь просто пересоздаст файл. Для базы, где лежат чьи-то данные, не годится совсем.

Второй — читать обе версии. Разбор смотрит на номер версии и выбирает соответствующую функцию; при первой же записи файл переписывается в новом формате. Так поступает большинство программ, и это честная работа: старый код разбора приходится хранить, пока живы старые файлы.

Третий — сделать формат расширяемым заранее, чтобы новые поля не ломали старый разбор. Ровно для этого в Protocol Buffers каждое поле снабжено номером и типом: незнакомое поле старый код пропускает, не понимая, но и не ломаясь. Цена — служебные байты у каждого поля.

В нашем формате узла заложен маленький задел на будущее: заголовок узла занимает шестнадцать байт, а осмысленных полей в нём три — тип, число ключей и ссылка на следующий лист, всего восемь байт. Оставшиеся восемь зарезервированы. Добавив туда поле, мы не сдвинем ключи и значения, а значит, старый и новый форматы останутся совместимы по расположению данных.

Резерв в заголовке — приём почти бесплатный (несколько байт на страницу в четыре килобайта) и не раз выручавший. Закладывайте его в свои форматы.

## Разберём чужой формат руками

Всё, о чём шла речь, легко проверить на настоящей базе данных. Возьмём SQLite — он есть на любой машине, — создадим крошечную базу и посмотрим в неё:

```bash
$ sqlite3 demo.sqlite "CREATE TABLE t(a INT, b TEXT); INSERT INTO t VALUES (42,'Alice');"
$ xxd demo.sqlite | head -3
00000000: 5351 4c69 7465 2066 6f72 6d61 7420 3300  SQLite format 3.
00000010: 1000 0101 0c40 2020 0000 0002 0000 0002  .....@  ........
00000020: 0000 0000 0000 0000 0000 0001 0000 0004  ................
```

Первые шестнадцать байт — метка формата, причём человекочитаемая: строка `SQLite format 3` и нулевой байт. Ровно то, о чём мы говорили в разделе про версии, только здесь метку сделали текстовой, чтобы утилита `file` могла узнать базу по содержимому.

Дальше начинается заголовок, и первое же поле в нём — размер страницы, два байта по смещению 16: `10 00`. Здесь порядок байтов **старшим вперёд**, как в сетевых протоколах, поэтому это `0x1000` — четыре тысячи девяносто шесть. Те самые четыре килобайта, которые мы возьмём в следующей главе.

Размер файла подтверждает картину:

```bash
$ ls -l demo.sqlite
-rw-r--r--  1 serik  wheel  8192 ...
```

Восемь килобайт — ровно две страницы: заголовочная и одна с данными. Файл не растёт по байту, он растёт страницами.

А вот и наши данные, в самом конце файла:

```bash
$ xxd demo.sqlite | tail -2
00001fe0: 0000 0000 0000 0000 0009 0103 0117 2a41  ..............*A
00001ff0: 6c69 6365 0000 0000 0000 0000 0000 0000  lice............
```

Байт `2a` — это 42, наше целое, а следом лежат буквы `Alice`. Строка записана без нулевого байта в конце и без кавычек — её длина закодирована в заголовке записи, там же, где типы полей. Совсем как наш формат с префиксом длины, только упакованный плотнее.

Одна деталь стоит отдельного внимания: запись лежит в **конце** страницы, а не в начале. Так устроены страницы почти во всех базах — служебная информация растёт от начала страницы вперёд, записи кладутся с конца назад, а свободное место остаётся посередине. Мы к этой схеме вернёмся в главе 33.

Двадцать минут с `xxd` и описанием формата — и чужой файл перестаёт быть чёрным ящиком. Умение так смотреть окупается каждый раз, когда что-то «не читается», а документация молчит.

## Как выглядит остаток Части IV

Фундамент заложен, дальше будем строить слоями. В главе 33 появится страничный файл: файл станет массивом блоков по четыре килобайта, а над ним встанет кэш с вытеснением давно не использованных страниц. В главе 34 на страницах вырастет B+-дерево — структура, благодаря которой поиск по ключу обходится в считанные обращения к диску вместо перебора. Глава 35 добавит журнал упреждающей записи и ответит на вопрос, что происходит с базой при внезапном выключении питания.

Дальше — ближе к пользователю. Глава 36 даст крошечный SQL с разбором в дерево, глава 37 — вторичные индексы и планировщик запросов с `EXPLAIN`, глава 38 — многострочный REPL с историей, глава 39 — измерения, где мы наконец увидим в числах, ради чего всё затевалось.

Байтовый слой при этом останется тем же самым: все страницы, узлы и записи журнала пишутся функциями из `binary.h`.

## Главные правила главы

1. Структуру нельзя записывать в файл целиком: дыры от выравнивания не инициализированы, размеры типов и правила раскладки зависят от платформы.
2. Сериализуйте поле за полем, вычисляя байты арифметикой, — тогда формат не зависит от порядка байтов машины.
3. В форматах используйте только типы фиксированного размера из `<cstdint>`.
4. Буфер байтов — это `unsigned char`, иначе побитовые операции преподнесут сюрприз на отрицательных значениях.
5. Строки пишут с префиксом длины, а не с нулевым байтом в конце: так можно хранить любые байты и читать одним куском.
6. Знаковые числа сериализуются приведением к беззнаковым — дополнительный код сохраняет биты.
7. Любой долгоживущий формат начинается с метки и номера версии, и проверка обязана быть при открытии.
8. Заведите привычку смотреть на файл через `xxd` — без этого отладка бинарного формата превращается в гадание.

4. Запишите тысячу записей `Row` двумя способами — явной сериализацией и `write` структуры целиком — и сравните размеры файлов. Объясните разницу в байтах.

5. Испортите один байт в метке формата (`xxd` покажет, где она) и запустите `mydb`. Затем поменяйте байт версии на двойку. Разные ли сообщения об ошибке вы получили?

6. Реализуйте зигзаг-преобразование для знаковых чисел и скормите его varint. Проверьте, что `-1`, `-2` и `1` занимают по одному байту, а `INT64_MIN` — десять.

7. (Сложнее) Напишите функцию, которая печатает разницу двух буферов: те же строки шестнадцатеричного дампа, но байты, которые различаются, помечены. Такая печать бесценна, когда «файл после записи не совпадает с ожидаемым».

8. (Сложнее) Проверьте порядок байтов своей машины, не полагаясь на макросы: положите `std::uint32_t` со значением `1` и посмотрите на его первый байт через `unsigned char*`. Объясните, почему такой приём допустим, а чтение `int` через указатель на `float` — нет.

# Глава 44. Свой двоичный протокол

Наш чат до сих пор разделяет сообщения переводом строки. Работает — ровно до тех пор, пока в сообщении нет перевода строки. Стоит пользователю вставить многострочный текст, и одно сообщение превратится в несколько.

Это не единственная беда текстового разделителя. Отправить двоичные данные — картинку, файл — через него нельзя вовсе: в них встретится любой байт, включая разделитель. Нет и способа отличить одно действие от другого: «привет, я Аня» и «войти в комнату общая» — просто строки, и серверу приходится гадать по содержимому.

В этой главе напишем настоящий протокол: с префиксом длины, версией, типом сообщения и ограничением на размер. И проверим его на самом злом входе, какой бывает в сети, — потоке, нарезанном по одному байту.

## Три способа разметить границы

TCP, как мы выяснили в главе 40, границ сообщений не хранит. Способов расставить их самому ровно три.

Разделитель — то, что у нас сейчас: сообщения отделяются символом, который в данных не встречается. Так устроены HTTP, SMTP, IRC и вообще большинство текстовых протоколов. Плюсы — читаемость, отладка через `telnet`, простота. Минусы — разделитель нельзя использовать в данных, а если очень надо, приходится экранировать, и разбор усложняется.

Фиксированный размер — все сообщения одинаковой длины. Просто и негибко; годится для телеметрии, где записи однотипны.

Префикс длины — сначала число, потом столько байт данных. Читатель узнаёт размер заранее, может выделить память одним куском и не разбирать данные посимвольно. Любые байты допустимы. Так устроены Protocol Buffers, кадры HTTP/2, сообщения Redis, наш формат журнала из главы 32.

Для чата берём третий: сообщения могут содержать что угодно, а разбор должен быть быстрым.

## Формат кадра

```
Формат фрейма:
  [0..3]   u32 LE length (= 1 + 1 + payload.size(), т.е. size after length)
  [4]      u8 version
  [5]      u8 type
  [6..]    payload (length-2 байт)
```

Шесть байт заголовка, дальше данные. Каждое поле заслуживает объяснения.

Длина идёт первой и считает всё, что следует за ней. Такой выбор — вопрос вкуса; главное, чтобы обе стороны считали одинаково. Четыре байта хватило бы на четыре гигабайта, но мы ограничим размер отдельно.

Версия протокола позволяет менять формат в будущем и не ломать старых клиентов сразу. Проверка версии стоит одно сравнение, а спасает от попыток разобрать чужие данные как свои — та же мысль, что с меткой формата в главе 32.

Тип сообщения превращает поток данных в набор осмысленных действий:

```cpp
enum MsgType : std::uint8_t {
    kHello   = 1,   // payload = nickname (utf-8)
    kMessage = 2,   // payload = текст сообщения
    kNotify  = 3,   // payload = серверное уведомление (вошёл/вышел и т.д.)
    kJoin    = 4,   // payload = имя комнаты
    kLeave   = 5,   // payload = имя комнаты
};

constexpr std::uint8_t PROTO_VERSION = 1;
constexpr std::size_t  HEADER_BYTES = 4 + 1 + 1;
constexpr std::uint32_t MAX_PAYLOAD = 64 * 1024;   // 64 KiB — здравый лимит
```

Указание `: std::uint8_t` после имени перечисления задаёт его базовый тип — гарантирует, что значение занимает ровно байт. Без него компилятор вправе выбрать `int`, и запись в кадр пришлось бы приводить вручную.

Предел на размер данных — не формальность, а защита. Без него клиент, приславший в поле длины четыре миллиарда, заставил бы сервер попытаться выделить четыре гигабайта. Это готовый способ уронить сервер одним пакетом, и такие уязвимости находят в настоящем софте регулярно.

## Кодирование

```cpp
std::vector<std::uint8_t> encode(std::uint8_t type, const std::string& payload) {
    if (payload.size() > MAX_PAYLOAD) {
        throw std::runtime_error("payload too large");
    }
    std::vector<std::uint8_t> out;
    // length = version(1) + type(1) + payload(N)
    std::uint32_t len = static_cast<std::uint32_t>(2 + payload.size());
    out.reserve(4 + len);
    write_u32_le(out, len);
    out.push_back(PROTO_VERSION);
    out.push_back(type);
    out.insert(out.end(), payload.begin(), payload.end());
    return out;
}
```

Проверка размера стоит первой — до всякой работы. `reserve` избавляет от перевыделений при сборке кадра: размер известен заранее, зачем растить вектор по частям.

Запись числа — та же функция, что в главе 32, младшим байтом вперёд:

```cpp
void write_u32_le(std::vector<std::uint8_t>& out, std::uint32_t v) {
    for (int i = 0; i < 4; ++i) {
        out.push_back(static_cast<std::uint8_t>((v >> (i * 8)) & 0xFF));
    }
}
```

Здесь можно было бы взять сетевой порядок через `htonl` — так принято в старых протоколах. Мы выбрали little-endian, потому что на всех машинах, где будет работать наш чат, это родной порядок процессора, а преобразование всё равно делается арифметикой и от платформы не зависит. Главное — записать выбор в документацию протокола, что мы и сделали комментарием в заголовке.

Посмотрим на результат:

```
Hello 'Alice' (11 байт):
07 00 00 00 01 01 41 6c 69 63 65

Message 'Привет всем!' (28 байт):
18 00 00 00 01 02 d0 9f d1 80 d0 b8 d0 b2 d0 b5
d1 82 20 d0 b2 d1 81 d0 b5 d0 bc 21
```

Первый кадр: длина 7 (версия, тип и пять букв имени), версия 1, тип 1, дальше `Alice` в ASCII. Второй: длина 24, тип 2, дальше русский текст в UTF-8 — по два байта на букву, как мы разбирали в главе 31.

Обратите внимание, что кодировка нас вообще не касается. Для протокола данные — это байты; что они значат, договариваются приложения. Мы условились, что имена и тексты в UTF-8, и записали это в комментарии рядом с типами.

## Разбор

Вот здесь начинается настоящая работа. Кодирование — это сборка одного кадра, а разбор должен справляться с потоком, который приходит произвольными кусками.

```cpp
bool try_decode(std::vector<std::uint8_t>& acc,
                std::uint8_t& out_type,
                std::string& out_payload) {
    if (acc.size() < 4) return false;
    std::uint32_t len = read_u32_le(acc.data());
    if (len < 2 || len > MAX_PAYLOAD + 2) {
        throw std::runtime_error("invalid frame length: " + std::to_string(len));
    }
    if (acc.size() < 4 + len) return false;

    std::uint8_t version = acc[4];
    if (version != PROTO_VERSION) {
        throw std::runtime_error("unsupported version: " + std::to_string(version));
    }
    out_type = acc[5];
    out_payload.assign(reinterpret_cast<const char*>(acc.data() + 6), len - 2);

    acc.erase(acc.begin(), acc.begin() + 4 + len);
    return true;
}
```

Функция работает с накопителем — тем самым `recv_buf` из состояния клиента. Возвращает `true`, если удалось вынуть кадр, `false`, если данных пока мало, и бросает исключение, если данные испорчены. Три исхода, и каждый обрабатывается по-своему.

Порядок проверок здесь не случаен, и переставлять их нельзя.

Сначала смотрим, пришёл ли заголовок целиком: без четырёх байт длину не прочитать. Если нет — просто ждём, никакой ошибки.

Потом проверяем саму длину — **до** того, как ею воспользоваться. Слишком маленькая означает кадр без версии и типа, слишком большая — либо мусор, либо злой умысел. Именно эта проверка защищает от попытки выделить гигабайты.

И только затем смотрим, пришло ли тело. Тут снова возможен честный ответ «пока нет» — с исключением его путать нельзя.

Разница между «данных мало» и «данные испорчены» — ключевая мысль всего разбора потоковых протоколов. Первое случается постоянно и лечится ожиданием, второе означает, что соединение испорчено и его надо закрывать. Свалить их в один ответ — верный способ либо закрывать исправные соединения, либо вечно ждать данных, которых не будет.

Последняя строка удаляет разобранный кадр из накопителя. Тут прячется неэффективность: `erase` с начала вектора сдвигает весь остаток. При потоке из тысяч мелких сообщений это заметно, и настоящие реализации держат вместо вектора кольцевой буфер или пару индексов «начало данных, конец данных». Для учебного чата сдвиг допустим, а в упражнениях есть задание его убрать.

## Проверка на злом входе

Кадр, разрезанный по байтам, — не выдумка: так бывает при плохой сети, при работе через прокси, при отправке маленькими порциями. Проверим, что разбор это переживает.

```cpp
std::vector<std::uint8_t> acc;
std::vector<std::string> got;
for (std::size_t i = 0; i < wire.size(); ++i) {
    acc.push_back(wire[i]);              // добавляем ровно один байт
    while (chat::try_decode(acc, type, payload)) {
        got.push_back(payload);
    }
}
check_eq(got.size(), 3, "по одному байту собрались все три фрейма");
```

Три кадра, нарезанные на отдельные байты, собираются полностью. Работает и обратный случай — когда несколько кадров приходят одним куском:

```cpp
std::vector<std::uint8_t> acc = chat::encode(chat::kHello, "Ann");
std::vector<std::uint8_t> second = chat::encode(chat::kMessage, "два");
acc.insert(acc.end(), second.begin(), second.end());

int n = 0;
while (chat::try_decode(acc, type, payload)) ++n;
check_eq(n, 2, "из склеенного куска разобраны оба фрейма");
```

Обратите внимание на `while` в обоих случаях. Разбирать надо **в цикле**, пока кадры извлекаются: за один `recv` могло прийти сколько угодно сообщений. Написать `if` вместо `while` — распространённая ошибка, из-за которой сообщения начинают приходить с задержкой в одно следующее сообщение, а при паузе в разговоре застревают навсегда.

Проверяются и все три вида порчи: чужая версия, абсурдная длина, слишком короткий кадр. Каждый должен давать исключение, а не тихое непонятное поведение:

```
$ ./build/tests/test_protocol
все проверки прошли: 25/25
```

Протокол — идеальный кандидат для тестов: чистые функции, никакой сети, всё воспроизводимо. Отлаживать разбор на живом соединении — мучение, а на тестах он пишется за полчаса.

## Как это встраивается в сервер

В состоянии клиента накопитель меняет тип со строки на вектор байтов — данные теперь двоичные:

```cpp
std::vector<std::uint8_t> recv_buf;
std::vector<std::uint8_t> send_buf;
```

Чтение превращается в «добавить в накопитель и разобрать всё, что собралось»:

```cpp
s.recv_buf.insert(s.recv_buf.end(), buf, buf + r);

std::uint8_t type;
std::string payload;
try {
    while (chat::try_decode(s.recv_buf, type, payload)) {
        process_message(s, type, payload);
    }
} catch (const std::runtime_error& e) {
    // Испорченный кадр — закрываем соединение.
    drop_client(s.fd);
}
```

Обработка сообщения теперь начинается с выбора по типу, а не с разбора текста:

```cpp
switch (type) {
    case chat::kHello:   /* установить имя */      break;
    case chat::kJoin:    /* войти в комнату */     break;
    case chat::kMessage: /* разослать в комнату */ break;
    ...
}
```

Разница с текстовым протоколом принципиальная: раньше сервер разбирал строку и гадал, что она значит; теперь намерение клиента закодировано явно. Это и есть главная польза типизированного протокола — не экономия байтов, а исчезновение двусмысленности.

Отправка тоже упрощается: вместо склейки строк — кодирование кадра в буфер отправки.

```cpp
std::vector<std::uint8_t> frame = chat::encode(chat::kNotify, "вы вошли в комнату");
s.send_buf.insert(s.send_buf.end(), frame.begin(), frame.end());
```

Полностью на новый протокол сервер переходит в главе 45, где появятся комнаты.

## Плата за двоичный формат

Главная потеря — отладка. К текстовому протоколу можно подключиться `telnet` и поговорить руками; к двоичному — нет. Нужен свой клиент, а на первых порах — печать кадров в шестнадцатеричном виде, как в нашей демонстрационной программе.

Именно поэтому многие протоколы остаются текстовыми даже там, где двоичный был бы эффективнее: HTTP/1.1 текстовый, и вся его экосистема — `curl`, логи, прокси — построена на том, что запрос можно прочитать глазами. Только когда цена стала слишком высокой, появился двоичный HTTP/2 — и вместе с ним отдельные инструменты для разглядывания трафика.

Вторая потеря — жёсткость. Добавить поле в текстовый протокол легко, старые клиенты просто не заметят лишнюю строку. В двоичном формате с фиксированным заголовком любое изменение — новая версия. Поэтому в серьёзных протоколах поля описываются самоописывающимся способом, как в Protocol Buffers, где у каждого поля есть номер и тип, а незнакомые поля пропускаются.

## Чего нет в нашем протоколе

Контрольной суммы. В журнале базы данных она была нужна, потому что диск может отдать испорченные данные, а здесь за целостность отвечает TCP: у него своя проверка на каждый сегмент. Добавлять свою имеет смысл, если данные проходят через недоверенные преобразования — например, шифрование, — но об этом в главе 46.

Сжатия. Текст сжимается втрое-вчетверо, и на большом трафике это заметно. Обычно сжимают не отдельные кадры, а поток целиком, чтобы словарь накапливался.

Идентификаторов запросов. Если бы клиент мог послать несколько запросов и ждать ответов не по порядку, каждому кадру понадобился бы номер, а ответу — ссылка на него. Так устроен HTTP/2 с его потоками.

Согласования версии. Мы просто отвергаем чужую версию; правильнее было бы обменяться поддерживаемыми версиями при подключении и выбрать общую. Так делают TLS и почти все протоколы, которым нужна долгая совместимость.

## Главные правила главы

1. Поверх TCP границы сообщений размечает протокол: разделителем, фиксированным размером или префиксом длины.
2. Префикс длины позволяет читать двоичные данные и заранее знать размер, но лишает возможности отлаживать протокол вручную.
3. В заголовке должны быть версия и тип: первая спасает от чужих данных, второй убирает двусмысленность намерений.
4. Предел на размер данных обязателен и проверяется **до** выделения памяти.
5. Разбор различает три исхода: кадр готов, данных пока мало, данные испорчены — и путать второе с третьим нельзя.
6. Разбирать надо в цикле, пока кадры извлекаются: за одно чтение может прийти несколько сообщений.
7. Разбор потокового протокола проверяется на потоке, нарезанном по одному байту, — это худший и вполне реальный случай.
8. Удаление разобранного кадра сдвигом всего буфера работает, но на потоке мелких сообщений становится узким местом.

## Упражнения

1. Соберите `demo-chat`, запустите `./build/protocol_demo` и разберите вывод: найдите в шестнадцатеричном дампе длину, версию, тип и данные каждого кадра.

2. Запустите тесты (`make tests && ./build/tests/test_protocol`). Затем сломайте что-нибудь намеренно — например, уберите проверку версии — и убедитесь, что тест это заметил.

3. Замените `while` на `if` в цикле разбора внутри демонстрационной программы. Какие сообщения перестали доходить и почему?

4. Уберите проверку `len > MAX_PAYLOAD + 2` и отправьте серверу кадр с длиной `0xFFFFFFFF` (можно через `printf` и `nc`). Что произойдёт с сервером?

5. Добавьте тип сообщения `kPing` и `kPong`: клиент раз в тридцать секунд шлёт `kPing`, сервер отвечает `kPong`. Это стандартный способ обнаружить мёртвое соединение.

6. Замените в накопителе `std::vector` с `erase` на пару индексов «начало данных, конец данных» с периодическим уплотнением. Замерьте разницу на потоке из ста тысяч мелких сообщений.

7. (Сложнее) Добавьте согласование версии: клиент присылает список поддерживаемых версий, сервер выбирает максимальную общую и отвечает выбором. Что делать, если общей нет?

8. (Сложнее) Напишите утилиту-снифер: она подключается к серверу как клиент, но вместо разговора печатает все входящие кадры в человекочитаемом виде — тип, длина, данные. Такой инструмент окупается на первой же отладке.

## Что дальше

Глава 45 — комнаты. Соединим протокол из этой главы с циклом событий из предыдущей и получим чат, где сообщения видны только участникам той же комнаты. Появятся две связанные структуры данных вместо одной, состояние клиента превратится в маленький автомат, а мы разберём, почему удаление участника из комнаты — операция, в которой легко ошибиться порядком действий.

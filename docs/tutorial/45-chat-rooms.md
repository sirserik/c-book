# Глава 45. Комнаты

У нас есть цикл событий из главы 43 и двоичный протокол из главы 44. Соединим их и получим чат, в котором сообщения видны не всем подряд, а только участникам одной комнаты.

Заодно напишем наконец нормального клиента — того, который понимает наш протокол и умеет принимать сообщения в любой момент, а не только в ответ на свои.

## Что добавляется

К реактору из главы 43 добавляются три вещи.

У клиента появляются имя и комната. Имя приходит в сообщении `Hello`, комната — в `Join`. Пока имени нет, клиент почти ничего не может.

Появляется вторая структура данных — отображение из имени комнаты в множество дескрипторов её участников.

И появляется разбор по типам сообщений вместо разбора текста: `Hello`, `Join`, `Leave`, `Message`. Каждый тип — отдельное действие.

## Две структуры вместо одной

```cpp
struct ClientState {
    int fd;
    std::string name;       // пусто, пока не прислал Hello
    std::string room;       // пусто = не в комнате
    std::vector<std::uint8_t> recv_buf;
    std::vector<std::uint8_t> send_buf;
};

std::unordered_map<int, ClientState> clients;
std::unordered_map<std::string, std::unordered_set<int>> rooms;
```

Данные хранятся дважды, и это осознанно. По дескриптору надо быстро узнать, кто это (`clients`), а по имени комнаты — быстро получить список участников для рассылки (`rooms`). Одна структура не даёт обеих операций за постоянное время.

Плата за двойное хранение — необходимость держать их согласованными. Клиент, попавший в `rooms`, но исчезнувший из `clients`, — источник обращений к несуществующим данным. Все места, где эта связь может порваться, надо знать поимённо, и мы их сейчас разберём.

`unordered_set` для участников выбран потому, что нужны быстрые вставка и удаление и не нужен порядок. Обычный вектор дал бы удаление за линейное время, а при рассылке в комнату на тысячу человек это заметно.

## Обработка сообщений

Диспетчер по типу — это и есть весь протокол уровня приложения:

```cpp
void process_message(std::unordered_map<int, ClientState>& clients,
                     std::unordered_map<std::string, std::unordered_set<int>>& rooms,
                     int fd, std::uint8_t type, const std::string& payload) {
    auto ci = clients.find(fd);
    if (ci == clients.end()) return;
    ClientState& c = ci->second;

    switch (type) {
        case chat::kHello: {
            c.name = payload;
            enqueue_frame(c, chat::kNotify,
                          "Привет, " + c.name + ". /join <room> для входа.");
            break;
        }
        case chat::kJoin: {
            if (c.name.empty()) {
                enqueue_frame(c, chat::kNotify, "сначала Hello");
                break;
            }
            leave_room(clients, rooms, fd);
            c.room = payload;
            rooms[c.room].insert(fd);
            enqueue_frame(c, chat::kNotify, "вы в комнате " + c.room);
            broadcast_room(clients, rooms, c.room, fd, chat::kNotify,
                           c.name + " вошёл в " + c.room);
            break;
        }
        case chat::kLeave: {
            leave_room(clients, rooms, fd);
            enqueue_frame(c, chat::kNotify, "вы вышли");
            break;
        }
        case chat::kMessage: {
            if (c.room.empty()) {
                enqueue_frame(c, chat::kNotify, "не в комнате");
                break;
            }
            std::string out = "<" + c.name + "> " + payload;
            broadcast_room(clients, rooms, c.room, fd, chat::kMessage, out);
            break;
        }
        default:
            enqueue_frame(c, chat::kNotify, "неизвестный тип");
            break;
    }
}
```

Обратите внимание на две проверки состояния: `Join` без имени и `Message` без комнаты. Клиент, приславший их не вовремя, получает вежливое уведомление, а не падение сервера.

Дело в том, что состояние клиента — это маленький автомат:

```
     подключился ──Hello──► представился ──Join──► в комнате
                                  ▲                    │
                                  └───────Leave────────┘
```

Три состояния, переходы по сообщениям. В каждом состоянии допустим свой набор сообщений, и всё, что не допустимо, надо отвергать явно.

Это общее правило работы с сетью: **никогда не полагайтесь на то, что клиент присылает сообщения в правильном порядке**. Ваш клиент, может, и присылает, а вот случайно подключившийся сканер портов, старая версия программы или злоумышленник — нет. Сервер обязан выживать при любой последовательности входящих данных.

Заметьте ещё, что `Join` в другую комнату сначала зовёт `leave_room`. Иначе клиент остался бы участником двух комнат сразу, а поле `room` помнило бы только последнюю — и выйти из первой он бы уже не смог никогда.

## Выход из комнаты: порядок решает

Функция, в которой легче всего ошибиться:

```cpp
void leave_room(std::unordered_map<int, ClientState>& clients,
                std::unordered_map<std::string, std::unordered_set<int>>& rooms,
                int fd) {
    auto ci = clients.find(fd);
    if (ci == clients.end() || ci->second.room.empty()) return;
    std::string room = ci->second.room;
    rooms[room].erase(fd);
    if (rooms[room].empty()) rooms.erase(room);
    broadcast_room(clients, rooms, room, fd, chat::kNotify,
                   ci->second.name + " вышел из " + room);
    ci->second.room.clear();
}
```

Пять строк, и в каждой — решение.

Имя комнаты **копируется** в локальную переменную. Дальше мы будем чистить `ci->second.room`, и если бы работали со ссылкой на него, то к моменту рассылки читали бы уже пустую строку.

Участник удаляется из множества **до** рассылки. Иначе ушедший получил бы уведомление о собственном уходе. Формально `broadcast_room` исключает отправителя по `from_fd`, так что вреда бы не было, но полагаться на две защиты вместо одной — плохая привычка.

Опустевшая комната удаляется целиком. Без этой строки `rooms` копил бы пустые множества, и через месяц работы сервер держал бы в памяти тысячи комнат, в которых никого нет. Мелочь, из которой получаются утечки.

И только после всего — очистка поля `room` у клиента.

Ещё одна тонкость связана с отключением. При обрыве соединения `leave_room` надо звать **до** `close` и удаления из `clients`:

```cpp
if ((re & (POLLHUP | POLLERR | POLLNVAL)) || drop) {
    leave_room(clients, rooms, fd);
    ::close(fd);
    clients.erase(it);
}
```

Порядок обратный порядку создания, как и положено при уборке. Если сначала удалить клиента из `clients`, то `leave_room` не найдёт его и молча ничего не сделает — а дескриптор останется в множестве участников комнаты. Дальше рассылка попытается отправить на закрытый дескриптор; с флагом `MSG_NOSIGNAL` это безопасно, но участник-призрак останется в комнате навсегда.

## Рассылка

```cpp
void broadcast_room(std::unordered_map<int, ClientState>& clients,
                    std::unordered_map<std::string, std::unordered_set<int>>& rooms,
                    const std::string& room, int from_fd,
                    std::uint8_t type, const std::string& payload) {
    auto it = rooms.find(room);
    if (it == rooms.end()) return;
    for (int fd : it->second) {
        if (fd == from_fd) continue;
        auto ci = clients.find(fd);
        if (ci == clients.end()) continue;
        enqueue_frame(ci->second, type, payload);
    }
}
```

Функция ничего не отправляет — она только раскладывает кадры по буферам отправки, как мы договорились в главе 43. Отправкой займётся цикл, когда ядро сообщит о готовности сокетов.

Проверка `ci == clients.end()` — вторая линия обороны на случай, если согласованность двух структур всё-таки нарушилась. В правильно работающем сервере она не срабатывает никогда; оставлена потому, что цена — одно сравнение, а результат её отсутствия — обращение к несуществующему клиенту.

Кодирование кадра происходит для каждого получателя заново:

```cpp
void enqueue_frame(ClientState& c, std::uint8_t type, const std::string& payload) {
    auto frame = chat::encode(type, payload);
    c.send_buf.insert(c.send_buf.end(), frame.begin(), frame.end());
}
```

При рассылке в комнату на тысячу человек это тысяча одинаковых кодирований. Правильнее закодировать один раз и вставлять готовые байты — задание в упражнениях, и на большой комнате разница заметна.

## Клиент, понимающий протокол

Эхо-клиент из главы 40 для такого чата не годится: он отправляет строку и ждёт ответ, а сообщения в чате приходят когда угодно. Нужен клиент с двумя потоками — один читает клавиатуру, другой сокет.

```cpp
std::mutex g_out_mutex;          // вывод из двух потоков нужно защищать
std::atomic<bool> g_running(true);

void say(const std::string& line) {
    std::lock_guard<std::mutex> lock(g_out_mutex);
    std::cout << line << "\n";
    std::cout.flush();
}
```

Первое, обо что спотыкаются при написании такого клиента, — вывод. Два потока, пишущие в один терминал без защиты, перемешивают строки; иногда прямо посреди слова. Мьютекс вокруг печати обязателен, и это ровно тот случай из главы 41, когда общий ресурс — не переменная, а устройство.

Поток приёма читает сокет, накапливает байты и разбирает кадры — тем же способом, что сервер:

```cpp
void receiver(int fd) {
    std::vector<std::uint8_t> acc;
    char buf[1024];

    while (g_running) {
        ssize_t r = ::recv(fd, buf, sizeof(buf), 0);
        if (r == 0) { say("[соединение закрыто сервером]"); break; }
        if (r < 0) {
            if (errno == EINTR) continue;
            say(std::string("[recv: ") + std::strerror(errno) + "]");
            break;
        }
        acc.insert(acc.end(), reinterpret_cast<std::uint8_t*>(buf),
                   reinterpret_cast<std::uint8_t*>(buf) + r);

        try {
            std::uint8_t type = 0;
            std::string payload;
            while (chat::try_decode(acc, type, payload)) {
                if (type == chat::kMessage)      say(payload);
                else if (type == chat::kNotify)  say("* " + payload);
                else                             say("[тип " + std::to_string(type) +
                                                     "] " + payload);
            }
        } catch (const std::exception& e) {
            say(std::string("[ошибка протокола: ") + e.what() + "]");
            break;
        }
    }
    g_running = false;
}
```

Главный поток читает строки и превращает их в кадры:

```cpp
if (line == "/quit") {
    break;
} else if (line.compare(0, 6, "/join ") == 0) {
    ok = send_frame(fd, chat::kJoin, line.substr(6));
} else if (line == "/leave") {
    ok = send_frame(fd, chat::kLeave, "");
} else {
    ok = send_frame(fd, chat::kMessage, line);
}
```

И последняя деталь, без которой клиент не завершается:

```cpp
g_running = false;
::shutdown(fd, SHUT_RDWR);   // разбудит receiver, зависший в recv
rx.join();
::close(fd);
```

Флага `g_running` недостаточно: поток приёма в этот момент спит внутри `recv` и никаких флагов не проверяет. Разбудить его можно, закрыв соединение, — `shutdown` делает это, и `recv` немедленно возвращает ноль.

Разница между `shutdown` и `close` тут существенна. `close` закрывает дескриптор, и если его в этот момент читает другой поток, поведение непредсказуемо: номер может быть переиспользован новым сокетом. `shutdown` не трогает дескриптор, а разрывает само соединение — все ожидающие вызовы просыпаются, и только потом, после `join`, дескриптор можно спокойно закрыть.

## Слабые места

Список честный, потому что в сетевом коде такой список важнее, чем описание работающего.

Буфер отправки не ограничен. Если клиент перестал читать — завис, ушёл в спящий режим, — его `send_buf` растёт с каждым сообщением в комнате. Сотня активных собеседников и один зависший дадут гигабайты в памяти сервера. Настоящие серверы ставят предел и отключают клиента, который в него упёрся; иногда вместо отключения выбрасывают старые сообщения. Это первое, что нужно добавить перед выпуском в мир.

Нет ограничения на частоту. Клиент может слать тысячу сообщений в секунду и занять сервер целиком. Лекарство — счётчик сообщений в единицу времени на каждого клиента.

Нет проверки имён. Двое могут назваться одинаково, имя может быть пустым, длиной в 64 килобайта или содержать управляющие символы, которые испортят терминал получателям. Любое поле, пришедшее от клиента, нужно проверять — это относится не только к чатам.

Клиент в одной комнате. В настоящих чатах человек состоит сразу в нескольких, и это меняет структуру данных: вместо поля `room` — множество комнат, а в сообщении появляется указание, куда именно оно адресовано. В IRC для этого служит команда `PRIVMSG #канал :текст`.

Ничего не сохраняется. Перезапустили сервер — комнаты пусты, история потеряна. Историей займёмся в следующей главе.

## Главные правила главы

1. Две связанные структуры данных — цена быстрых операций в обе стороны; согласовывать их приходится вручную.
2. Состояние клиента — автомат; сервер обязан отвергать сообщения, недопустимые в текущем состоянии.
3. Не полагайтесь на порядок сообщений от клиента: сервер должен выживать при любой последовательности.
4. При выходе из комнаты порядок действий строгий: скопировать имя, удалить участника, разослать, очистить поле.
5. Опустевшие комнаты надо удалять, иначе они копятся навсегда.
6. При обрыве соединения `leave_room` вызывается до удаления клиента, иначе в комнате остаётся призрак.
7. Вывод из нескольких потоков в один терминал защищают мьютексом — иначе строки перемешиваются.
8. Разбудить поток, спящий в `recv`, можно через `shutdown`; закрывать дескриптор до `join` нельзя.

## Упражнения

1. Соберите чат и проверьте изоляцию комнат: три клиента, двое в одной комнате, третий в другой. Убедитесь, что третий не видит чужих сообщений.

2. Отправьте `Message` до `Join` и `Join` до `Hello`. Какие уведомления пришли? Найдите в коде проверки, которые их выдали.

3. Уберите удаление пустых комнат и добавьте служебную команду, печатающую размер `rooms`. Повходите и повыходите десяток раз — что происходит с числом комнат?

4. Поменяйте местами `leave_room` и `clients.erase` при отключении. Подключите двух клиентов в одну комнату, одного убейте резко и посмотрите, что происходит при следующей рассылке.

5. Сделайте, чтобы `broadcast_room` кодировал кадр один раз, а не для каждого получателя. Замерьте разницу на комнате из пятидесяти клиентов.

6. Добавьте команды `/who` (список участников комнаты) и `/list` (список комнат). Первая — обход множества, вторая — обход отображения.

7. (Сложнее) Ограничьте размер буфера отправки: если он превысил мегабайт, отключайте клиента с уведомлением. Проверьте, подключившись клиентом, который не читает данные вовсе.

8. (Сложнее) Поддержите участие в нескольких комнатах: замените поле `room` на множество, добавьте в сообщение указание комнаты. Продумайте, что произойдёт со старыми клиентами, которые про это не знают.

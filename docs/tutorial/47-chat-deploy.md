# Глава 47. Сборка, упаковка и итоги Части V

Чат работает — на нашей машине, из каталога с исходниками, запущенный руками. Между этим состоянием и «работает у людей» лежит ещё одна работа, о которой в учебниках говорят редко.

В этой главе разберёмся, что мешает просто скопировать бинарник на другую машину, чем статическая сборка отличается от динамической, почему статически собрать программу с glibc не так просто, как кажется, и как упаковать сервер в контейнер размером в несколько мегабайт. И подведём итоги всей Части V.

## Почему бинарник не переносится

Скопируем собранный сервер на другую машину — и, скорее всего, получим отказ запускаться. Причина в том, что программа собрана динамически: сама она содержит только свой код, а всё остальное берёт из библиотек системы.

Посмотреть, от чего зависит программа, можно системными средствами — `ldd` на Linux, `otool -L` на macOS:

```bash
$ otool -L build/rooms_chat_server
build/rooms_chat_server:
	/usr/lib/libc++.1.dylib (compatibility version 1.0.0, current version 2100.43.0)
	/usr/lib/libSystem.B.dylib (compatibility version 1.0.0, current version 1356.0.0)
```

Две зависимости: стандартная библиотека C++ и системная библиотека C. На чужой машине их может не оказаться вовсе или оказаться другая версия, несовместимая по внутреннему устройству.

Именно отсюда растёт знаменитая жалоба «у меня работает». Программа, собранная на свежей Ubuntu, не запустится на старой CentOS, потому что там другая версия glibc, и наоборот — собранная на старой обычно запускается на новой, потому что совместимость поддерживают в одну сторону.

Наш сервер в динамической сборке занимает 310 килобайт — это почти чистый наш код. Всё остальное берётся снаружи.

## Статическая сборка

Альтернатива — вкомпилировать библиотеки внутрь:

```bash
$ g++ -static -static-libstdc++ -static-libgcc ...
```

Тогда бинарник становится самодостаточным: скопировал и запустил, ничего не требуется. Размер вырастает до нескольких мегабайт, но зависимостей нет.

У подхода есть и обратная сторона, о которой стоит помнить. Обновление библиотеки с исправленной уязвимостью больше не приходит из системы — программу надо пересобирать и раскладывать заново. Для сервера, живущего в контейнере, это нормально: его и так пересобирают на каждый выпуск. Для программы, установленной у пользователей, — уже вопрос.

### Что не так со статическим glibc

На Linux попытка собрать статически даёт неожиданное:

```
warning: Using 'getaddrinfo' in statically linked applications requires
at runtime the shared libraries from the glibc version used for linking
```

Предупреждение, а не ошибка: программа соберётся и в большинстве случаев даже заработает. Но не всегда.

Причина в устройстве glibc. Разрешение имён устроено через подключаемые модули: как искать имя — в файле `/etc/hosts`, через DNS, через LDAP — решается настройкой, и соответствующий модуль подгружается на ходу. Подгрузка означает динамическую загрузку, а её невозможно вкомпилировать заранее: набор модулей известен только на целевой машине.

Итог: статически собранная программа с glibc работает, пока не понадобится разрешить имя. А нашему клиенту оно нужно — `getaddrinfo` вызывается при подключении.

Обойти это можно тремя способами. Не разрешать имена вовсе, работая только с числовыми адресами, — годится для сервера, но не для клиента. Собирать с другой реализацией стандартной библиотеки C. Или не собирать статически, а класть программу вместе с нужными библиотеками — так делают контейнеры.

### musl

Вторая реализация, о которой речь, — musl. Написана с нуля, компактнее glibc, лицензия свободнее, и главное — рассчитана на статическую сборку: разрешение имён в ней встроено, никаких подгружаемых модулей.

Дистрибутив, построенный на musl, — Alpine Linux, самый популярный выбор для контейнеров именно по этой причине. Там статическая сборка получается честной:

```bash
# внутри alpine
$ apk add build-base
$ g++ -static -static-libstdc++ -static-libgcc -O2 -std=c++11 ... -o server
$ file server
server: ELF 64-bit LSB executable, statically linked, ...
```

Расплата — мелкие несовместимости. musl строже относится к нарушениям стандарта, у неё меньше расширений GNU, и программы, привыкшие к особенностям glibc, иногда требуют правок. Ещё у musl заметно медленнее стандартный распределитель памяти, что бьёт по программам, активно выделяющим память.

## Контейнер

Многоступенчатая сборка решает противоречие «для сборки нужен компилятор, а в готовом образе он не нужен»:

```dockerfile
# Многоступенчатый Dockerfile для chat-server.
# Stage 1: builder на alpine с musl — компилируем статически.
# Stage 2: scratch (пустой образ) + только бинарь.
# Итог: < 5 MB образ, никаких зависимостей.

FROM alpine:3.19 AS builder
RUN apk add --no-cache build-base make
WORKDIR /src
COPY . .
RUN make MODE=release CXX=g++ \
    CXXFLAGS="-std=c++11 -O2 -DNDEBUG -static -static-libstdc++ -static-libgcc -pthread -Iinclude -MMD -MP" \
    LDFLAGS="-static -pthread"

FROM scratch
COPY --from=builder /src/build/rooms_chat_server /chat-server
EXPOSE 9001
ENTRYPOINT ["/chat-server", "9001"]
```

Первая ступень — полноценная система с компилятором, около полугигабайта. В ней собирается статический бинарник.

Вторая ступень начинается с `scratch` — совершенно пустого образа. В него копируется единственный файл: наш сервер. Ни оболочки, ни утилит, ни библиотек.

Итоговый образ — размер бинарника плюс несколько килобайт метаданных. Кроме размера это даёт безопасность: в контейнере, где нет ни оболочки, ни `cat`, злоумышленнику, нашедшему уязвимость, буквально нечем воспользоваться. Тот же принцип лежит в основе образов `distroless` от Google.

Расплата — отлаживать такой контейнер нечем: `docker exec` не запустит оболочку, потому что её нет. Отлаживают либо на промежуточном образе, либо подключая отладочный контейнер к тому же пространству имён.

```bash
$ docker build -t my-chat .
$ docker images
my-chat    latest    abc123    5.2MB

$ docker run -p 9001:9001 my-chat
Rooms chat-server слушает на :9001
```

Строка `EXPOSE 9001` — только документация; настоящий проброс делает `-p 9001:9001` при запуске. Сервер внутри контейнера обязан слушать `0.0.0.0`, а не `127.0.0.1`, иначе снаружи до него не достучаться, — у нас так и есть, `INADDR_ANY` из главы 40.

### Чего в нашем контейнере не хватает

Сервер работает от имени администратора — в `scratch` других пользователей просто нет. Правильно добавить непривилегированного пользователя и указать `USER`.

Нет проверки живости: оркестратор не знает, работает сервер или завис. Обычно для этого добавляют `HEALTHCHECK` или отдельную ручку состояния.

Нет обработки сигнала завершения. Docker при остановке шлёт SIGTERM и через десять секунд добивает SIGKILL. Наш сервер не ловит SIGTERM, значит, его всегда убивают жёстко — и история сообщений теряет последние записи. Как это чинится, мы разбирали в главе 28: обработчик выставляет флаг, цикл его проверяет.

## Что построено в Части V

Восемь глав назад мы не умели передать по сети ни байта. Сейчас в `demo-chat/` лежит около полутора тысяч строк:

| Файл | Что делает |
|------|-----------|
| `echo_server.cpp`, `echo_client.cpp` | сокеты: `socket`, `bind`, `listen`, `accept`, `connect` |
| `threaded_chat_server.cpp` | поток на клиента, мьютекс на общий список |
| `atomic_demo.cpp` | гонка данных и три способа её устранить |
| `reactor_chat_server.cpp` | цикл событий на `poll`, неблокирующие сокеты |
| `protocol.cpp` | двоичный протокол с префиксом длины |
| `rooms_chat_server.cpp` | комнаты поверх реактора и протокола |
| `chat_client.cpp` | клиент с двумя потоками, понимающий протокол |
| `history.cpp` | журнал сообщений на диске |
| `xor_demo.cpp` | почему самодельное шифрование не работает |
| `tests/test_protocol.cpp` | 25 проверок протокола и истории |

Три архитектуры одной задачи — последовательная, многопоточная и событийная — на одном и том же примере. Это, пожалуй, главное, что стоит унести из части: выбор между ними определяется не модой, а числом соединений и характером работы.

## Чему научила эта часть

Что TCP — поток байтов, а не сообщений, и любой протокол поверх него обязан сам размечать границы. Что `recv` и `send` обрабатывают сколько успели, а не сколько попросили. Что закрытие соединения — это ноль от `recv`, а не ошибка.

Что общие данные в многопоточной программе должны быть защищены — без исключений; что гонку данных находит не внимательность, а ThreadSanitizer; что атомарная переменная годится для счётчика и не годится для структуры.

Что цикл событий заменяет тысячи спящих потоков одним и требует за это вывернуть код наизнанку, хранить состояние явно и никогда не блокироваться.

Что в протоколе нужны версия, тип и предел на размер, а разбор должен различать «данных мало» и «данные испорчены».

И что любая длина, пришедшая извне, проверяется до того, как под неё выделяют память, — эта мысль повторилась в части трижды, в трёх разных местах, и это не совпадение.

## Главные правила Части V

1. Сокет — файловый дескриптор; сетевой код работает теми же приёмами, что файловый, плюс несколько своих.
2. Границы сообщений размечает протокол: разделителем, фиксированным размером или префиксом длины.
3. Данные, доступные нескольким потокам, защищают всегда; счётчику хватает атомарной переменной, структуре нужен мьютекс.
4. Поток на соединение прост и хорош до сотен клиентов; дальше нужен цикл событий.
5. В цикле событий нельзя блокироваться и нельзя делать ничего долгого — иначе встают все клиенты.
6. Каждому клиенту нужен собственный буфер отправки, потому что `send` может отправить часть.
7. Любое поле, пришедшее по сети, проверяется: длина, версия, тип, содержимое.
8. Криптографию не пишут сами — берут TLS или проверенную библиотеку.

## Упражнения

1. Посмотрите зависимости своих бинарников через `ldd` или `otool -L`. Соберите сервер статически и сравните размер и список зависимостей.

2. Соберите образ по нашему `Dockerfile` (понадобится Docker и Linux или Docker Desktop). Проверьте размер и запустите сервер в контейнере, подключившись клиентом снаружи.

3. Добавьте в образ непривилегированного пользователя и укажите `USER`. Убедитесь, что сервер по-прежнему может занять порт 9001 (и объясните, почему не смог бы занять 80-й).

4. Научите сервер аккуратно завершаться по SIGTERM: обработчик выставляет флаг, цикл `poll` получает тайм-аут и проверяет флаг, при завершении закрываются все соединения. Проверьте через `docker stop`.

5. Добавьте предел на размер буфера отправки и отключение зависших клиентов — то, чего нам не хватало в главе 45.

6. Соберите сервер с `-fsanitize=address` и погоняйте под нагрузкой (сотня клиентов, тысячи сообщений). Нашлось ли что-нибудь?

7. (Сложнее) Сделайте нагрузочный клиент: подключает N соединений, каждое шлёт сообщение каждые M миллисекунд, считает задержку между отправкой и получением. Сравните три сервера — многопоточный, реактор и комнатный — на 500 соединениях.

8. (Сложнее) Замените `poll` на `epoll` (Linux) или `kqueue` (macOS) в комнатном сервере и повторите нагрузочный тест. Где разница стала заметной?

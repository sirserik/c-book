# Глава 33. Страничный файл и LRU-кэш

В прошлой главе мы научились писать и читать байты в буфер. Сейчас — следующий уровень: файл базы данных как **массив страниц** фиксированного размера, с **кэшем** в памяти. Это базовая инфраструктура **любой настоящей СУБД** — PostgreSQL, MySQL, SQLite, ClickHouse. Без неё было бы катастрофически медленно.

К концу главы у нас работает `PageManager`: открывает файл, разбивает на страницы по 4 KiB, читает/пишет страницы через кэш, синхронизирует на диск через `fsync`.

## Зачем страницы

Альтернатива страницам: «база данных как набор записей произвольного размера». Каждая запись на своём смещении в файле. Чтобы добавить запись — пишем на следующее свободное место. Чтобы удалить — оставляем «дыру».

Проблемы такого подхода:
1. **Фрагментация**: после многих delete файл превращается в «швейцарский сыр».
2. **Размер записи**: некоторые большие, некоторые маленькие. Поиск свободного места — задача.
3. **Кэш**: что кэшировать? Записи разного размера сложнее держать в LRU.
4. **Диск работает блоками**: даже если читаешь 1 байт — ОС всё равно прочтёт целый блок (обычно 4 KB).

**Страничный подход**:
- Файл делится на **страницы** одинакового размера (обычно 4 KB).
- Каждая страница имеет **id** — индекс в файле.
- Внутри страницы — что угодно (записи, узлы дерева, метаданные).
- Все IO — целыми страницами.

Преимущества:
- **Совместимость с ОС**: размер страницы СУБД = размер блока диска = размер страницы памяти. Никаких лишних чтений.
- **Простой кэш**: страницы все одного размера, легко иметь LRU.
- **Атомарность**: запись 4 KB гарантированно атомарна на современных дисках (страница записывается целиком или не записывается).
- **Простой алгоритм allocate**: новая страница — `page_count`, инкремент.

## PAGE_SIZE = 4096

Почему именно 4 KiB?

- **Размер страницы памяти** в большинстве ОС — 4 KB. Ядро управляет памятью страницами по 4 KB. Если ваша страница совпадает — `mmap` и virtual memory работают эффективно.
- **Размер блока файловой системы** — обычно 4 KB (ext4, APFS, NTFS). Меньшая запись — всё равно округлится до блока.
- **Размер страницы SSD** — 4 KB или 16 KB. Запись меньше страницы — write amplification.

Некоторые СУБД используют 8 KB или 16 KB (PostgreSQL по умолчанию 8 KB, MySQL InnoDB — 16 KB). Это компромисс: больше страница = больше данных за один IO, но больше overhead на маленькие операции.

Мы — 4 KB. Стандарт для учебной задачи.

## Адресация страниц

```
Файл: 0123456789...
       page0  page1  page2  ...
       ↑      ↑      ↑
       0      4096   8192   ...
```

Page 0 — байты 0..4095. Page 1 — байты 4096..8191. И так далее. Адрес страницы в файле:

```cpp
off_t offset = static_cast<off_t>(page_id) * PAGE_SIZE;
```

`page_id` имеет тип `PageId` — у нас `uint32_t`. Это поддерживает до 4 миллиардов страниц = 16 TB на 4 KB страницах. Достаточно.

Если файл «закончился» (например, попросили читать страницу 100, а в файле только 10) — это **ошибка**. У нас `read_page` проверяет `pid < page_count_`.

## pread / pwrite

POSIX даёт две системные вызовы для IO по конкретному смещению:

```cpp
ssize_t pread(int fd, void* buf, size_t count, off_t offset);
ssize_t pwrite(int fd, const void* buf, size_t count, off_t offset);
```

Их преимущество перед `read`/`write` + `lseek`:

1. **Атомарны** для многопоточных приложений. `read`/`write` + `lseek` — это две операции; между ними другой поток может изменить позицию.
2. **Не меняют файловую позицию**. После `pwrite` cursor где был.

Для нашей СУБД это пока не критично (мы однопоточные), но привычка `pread`/`pwrite` правильная.

Возвращаемое значение — число реально записанных/прочитанных байт. Может быть **меньше** запрошенного (short read/write). Цикл обязателен:

```cpp
ssize_t written = 0;
while (written < PAGE_SIZE) {
    ssize_t n = pwrite(fd, buf + written, PAGE_SIZE - written, off + written);
    if (n < 0) {
        if (errno == EINTR) continue;   // сигнал
        throw PageError(...);
    }
    written += n;
}
```

`EINTR` (interrupted) — прерывание сигналом, повторяем. Это та же история, что в `mycat` (глава 31).

## Кэш — зачем

Каждый pread — это **системный вызов** + потенциальное обращение к диску. Время:
- Если страница в page cache ОС — ~микросекунда.
- Если на SSD — ~100 микросекунд.
- Если на HDD — ~10 миллисекунд.

При активной работе с одной и той же страницей миллион раз — это много. Решение — **кэш в нашей программе**: держим часто используемые страницы в памяти.

ОС тоже имеет page cache. Но:
- ОС-кэш — глобальный, разделяется всеми программами. Может вытеснить наши страницы.
- Наш кэш — **знает специфику нашего workflow** (B+tree часто посещает корень).
- Между ОС-кэшем и пользовательским кодом есть syscall — небесплатно.

Поэтому свой кэш — не дублирование, а ускорение.

## LRU как стратегия

Что вытеснять, когда кэш заполнен?

Самый частый подход — **LRU** (Least Recently Used): «выбросить ту страницу, которую дольше всего не трогали». Гипотеза: если страница не нужна давно, скорее всего и дальше не понадобится.

Альтернативы:
- **FIFO**: вытесняем самую старую (по времени попадания в кэш).
- **LFU**: вытесняем самую редко используемую.
- **Random**: случайно.

LRU — золотая середина. Хорошо для большинства реальных workload'ов. PostgreSQL использует усовершенствованный LRU («clock sweep»), MySQL — LRU с защищённой/непривилегированной половиной. Мы — простой LRU.

### Реализация LRU

Нужно:
1. Быстро найти страницу по id — `unordered_map`.
2. Быстро понять, что трогаем сейчас — переместить в «начало». Это `list` + переустановка указателя.

Связка `list + map`:

```cpp
std::list<PageId> lru_;                       // фронт = недавнее
std::unordered_map<PageId, std::pair<Entry, LruIter>> cache_;
```

`cache_` мапит page_id в (содержимое страницы + итератор на её позицию в LRU). При обращении:

```cpp
void PageManager::touch(PageId pid) {
    auto it = cache_.find(pid);
    if (it == cache_.end()) return;
    lru_.erase(it->second.second);
    lru_.push_front(pid);
    it->second.second = lru_.begin();
}
```

`lru_.erase(iterator)` — O(1) для list. `push_front` — O(1). Поиск в map — O(1). Итого touch — **O(1)**, что важно для горячих путей.

При вытеснении:

```cpp
void PageManager::evict_one_if_full() {
    if (cache_.size() < cache_size_) return;
    PageId victim = lru_.back();   // самая старая
    auto it = cache_.find(victim);
    flush_entry(victim, it->second.first);   // если dirty — записать
    lru_.pop_back();
    cache_.erase(it);
}
```

Берём с хвоста LRU (самую старую), сбрасываем на диск (если она грязная), удаляем из map.

## Dirty pages

Когда мы пишем в страницу через кэш, мы **не** идём на диск сразу. Помечаем `dirty = true` и пишем только в кэш. Когда страница выкидывается из кэша **или** при `sync()` — пишем на диск.

```cpp
void PageManager::write_page(PageId pid, const Page& page) {
    Entry& e = load_into_cache(pid);
    e.page = page;
    e.dirty = true;
}
```

Это **write-back** стратегия — пишем «когда удобно». Альтернатива — **write-through** (сразу на диск). Write-back быстрее для частых обновлений одной страницы (один диск-IO вместо ста).

Цена: если программа упадёт до flush'а — данные потеряются. Защита — **журнал** (WAL, глава 35). Каждое изменение сначала пишется в WAL, потом в страницу. После краша WAL переигрываем.

## fsync — durability

Записали через `pwrite` 4 KB на диск. Готово? **Нет**.

ОС держит **свой** буфер записи. Запись из ОС в буфер диска — мгновенно. Запись из буфера в флэш — асинхронно. Если в этот момент пропадёт питание — данные потеряются, хотя `pwrite` уже вернул.

`fsync(fd)` — заставить ОС сбросить **все** свои буферы для этого файла на физический диск. Только после `fsync` можно сказать «данные точно на диске».

`fsync` дорогой — миллисекунды, иногда десятки. Делать его на каждый `pwrite` сильно тормозит. Стратегия: **периодические fsync** или **fsync только на commit** (после транзакции).

В нашем `sync()`:

```cpp
void PageManager::sync() {
    for (auto& kv : cache_) {
        flush_entry(kv.first, kv.second.first);
    }
    if (::fsync(fd_) < 0) {
        throw PageError(...);
    }
}
```

Сначала сбрасываем все dirty страницы через `pwrite`. Потом `fsync`. Теперь данные гарантированно на диске.

В деструкторе PageManager — тоже sync. Но **глотаем** исключения: деструктор бросать не должен. Если sync упал — в лучшем случае данные на диске недополнены. Решение «правильное» — отдельный явный `close()` метод, который пользователь вызывает и проверяет результат. Мы упрощаем.

`fdatasync` — оптимизированный вариант: сбрасывает данные, но не метаданные (mtime, size). Если вам нужен только sync содержимого — `fdatasync` чуть быстрее.

## Класс PageManager

`include/page_manager.h`:

```cpp
class PageManager {
public:
    PageManager(const std::string& path, std::size_t cache_size = 64);
    ~PageManager();

    PageManager(const PageManager&) = delete;
    PageManager& operator=(const PageManager&) = delete;

    Page read_page(PageId pid);
    void write_page(PageId pid, const Page& page);
    PageId allocate_page();
    PageId page_count() const { return page_count_; }
    void sync();

private:
    struct Entry {
        Page page;
        bool dirty = false;
    };

    int fd_;
    PageId page_count_;
    std::size_t cache_size_;

    std::list<PageId> lru_;
    std::unordered_map<PageId, std::pair<Entry, LruIter>> cache_;

    void evict_one_if_full();
    void flush_entry(PageId pid, Entry& e);
    Entry& load_into_cache(PageId pid);
    void touch(PageId pid);
};
```

Запрет копирования через `= delete` — `PageManager` владеет файловым дескриптором, копировать его (= иметь два владельца fd) приведёт к проблемам.

### Открытие файла

```cpp
PageManager::PageManager(const std::string& path, std::size_t cache_size)
    : fd_(-1), page_count_(0), cache_size_(cache_size) {
    fd_ = ::open(path.c_str(), O_RDWR | O_CREAT, 0644);
    if (fd_ < 0) {
        throw PageError("не открыт: " + path + ": " + std::strerror(errno));
    }
    struct stat st;
    if (::fstat(fd_, &st) < 0) {
        ::close(fd_);
        throw PageError(std::string("fstat: ") + std::strerror(errno));
    }
    if (st.st_size % PAGE_SIZE != 0) {
        ::close(fd_);
        throw PageError("файл не выровнен по PAGE_SIZE");
    }
    page_count_ = static_cast<PageId>(st.st_size / PAGE_SIZE);
}
```

Открываем (создаём при отсутствии), читаем размер через `fstat`, проверяем, что он кратен `PAGE_SIZE` (иначе файл повреждён). Количество страниц = `size / PAGE_SIZE`.

### Загрузка страницы

```cpp
PageManager::Entry& PageManager::load_into_cache(PageId pid) {
    auto it = cache_.find(pid);
    if (it != cache_.end()) {
        touch(pid);
        return it->second.first;
    }

    evict_one_if_full();

    Entry e;
    e.page = make_page();
    e.dirty = false;

    off_t off = static_cast<off_t>(pid) * static_cast<off_t>(PAGE_SIZE);
    // pread в цикле с обработкой short read и EINTR
    // ...

    lru_.push_front(pid);
    auto inserted = cache_.emplace(pid, std::make_pair(std::move(e), lru_.begin()));
    return inserted.first->second.first;
}
```

Если страница есть в кэше — `touch` и вернуть. Если нет — `evict_one_if_full` (освободить место), потом загрузить с диска, потом добавить в map+list.

`make_page()` — функция из `include/page.h`, создаёт `vector<unsigned char>(PAGE_SIZE, 0)`.

### Выделение новой страницы

```cpp
PageId PageManager::allocate_page() {
    PageId new_id = page_count_;
    page_count_++;

    Entry e;
    e.page = make_page();
    e.dirty = true;     // новая = dirty, чтобы записаться при sync

    evict_one_if_full();
    lru_.push_front(new_id);
    cache_.emplace(new_id, std::make_pair(std::move(e), lru_.begin()));
    return new_id;
}
```

Просто инкрементируем счётчик, добавляем пустую (нулевую) страницу в кэш, помечаем dirty. При следующем `sync()` или `evict` — страница появится в файле.

Это **lazy** allocate — файл расширяется только при flush. Альтернатива — сразу делать `ftruncate(fd, new_size)`. Мы лениво.

## Cache size: сколько страниц держать

В моём демо — 2 (`PageManager pm(path, 2)`). Поэтому при работе с 3 страницами кэш постоянно вытесняет одну. Это специально для теста.

В реальной СУБД — гораздо больше. PostgreSQL по умолчанию ~16 тысяч страниц (shared_buffers 128 MB / 8 KB). MySQL InnoDB по умолчанию буфер 128 MB.

Чем больше кэш — тем меньше дисковых IO. Но и больше памяти.

В нашей мини-СУБД кэш — параметр конструктора. По умолчанию 64 страницы = 256 KB. Маленький, но достаточный для учебной работы.

## Тонкости и неприятности

### Page tearing

При записи 4 KB на диск может произойти **page tearing** — потеря питания на середине записи. На SSD обычно записи 4 KB атомарны на уровне controller'а, но не гарантировано на всех уровнях.

Защита — WAL (глава 35): сначала пишем full image страницы в журнал. При восстановлении после краха — берём данные из журнала.

PostgreSQL называет это «full page writes» — каждое первое изменение страницы в checkpoint пишет всю страницу в WAL. Защита от page tearing.

### Write amplification

SSD имеет страницы 4-16 KB и блоки стираемые 128 KB - 4 MB. Любая запись 4 KB на «грязный» блок требует:
1. Прочитать весь блок (4 MB).
2. Стереть.
3. Записать обратно с изменением.

Это **write amplification** — реальная запись больше логической. Сокращает время жизни SSD.

Хорошие СУБД учитывают этот эффект — пишут большими порциями (`sequential writes`), редко делают `fsync`, используют SSD-friendly алгоритмы.

### O_DIRECT

Линукс предоставляет флаг `O_DIRECT` при `open`, который **обходит page cache ОС**. Чтения и записи идут напрямую между программой и диском.

Зачем? Если у вас свой большой кэш — ОС-кэш только тратит память. Также убирается двойное копирование (ОС → кэш ОС → кэш программы).

Мы не используем `O_DIRECT` — это требует выровненной памяти, выровненных смещений, и осторожности. Современные NVMe настолько быстры, что page cache ОС редко мешает.

## Главные правила главы

1. **Страницы фиксированного размера** — основа всех СУБД. 4 KB стандарт.
2. **`pread`/`pwrite`** вместо `read`+`lseek`/`write`+`lseek` — атомарно, проще.
3. **LRU-кэш** с `list + unordered_map` — O(1) операции.
4. **`dirty` flag** + write-back — пишем на диск только при evict/sync.
5. **`fsync` для durability**. Без него запись может потеряться при крахе.
6. **`fsync` дорог** — не на каждый write. Группируйте.
7. **`O_RDWR | O_CREAT`** для открытия — открываем или создаём.
8. **Запрещайте копирование** для классов с fd через `= delete`.

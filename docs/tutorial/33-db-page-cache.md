# Глава 33. Страничный файл и кэш

В прошлой главе мы научились превращать числа в байты. Теперь надо решить, как эти байты лежат в файле и как база с ними работает.

Ответ, к которому за полвека пришли все — PostgreSQL, MySQL, SQLite, ClickHouse, — одинаков: файл базы данных считается **массивом страниц** одинакового размера, обычно по четыре килобайта. Не потоком записей переменной длины, а именно массивом блоков с номерами. Поверх этого массива живёт кэш в памяти, потому что обращение к диску в тысячи раз дороже обращения к оперативной памяти.

К концу главы у нас будет `PageManager` — компонент, на котором стоит вся Часть IV. Он открывает файл, выдаёт страницы по номеру, держит недавно использованные в памяти, помечает изменённые и по команде сбрасывает всё на диск.

## Почему страницы, а не записи

Представим, что база хранит записи как есть, каждую по своему смещению, вплотную друг к другу. Первая беда обнаружится при удалении: на месте записи остаётся дыра, а дыры надо где-то учитывать и как-то переиспользовать, причём дыра размером 40 байт не подойдёт для записи в 50. Вторая беда — при изменении: если запись выросла на байт, её больше нельзя оставить на месте, надо переносить и править все ссылки на неё.

Со страницами всё проще. Файл нарезан на равные куски, каждый кусок имеет номер, и любой кусок можно прочитать или записать целиком, зная только номер. Пустое место внутри страницы — забота самой страницы, а не всего файла. Ссылка на данные становится парой «номер страницы, смещение внутри» и не ломается при перекладывании соседей.

Есть и вторая причина, поважнее удобства. Диск физически работает блоками: даже если попросить один байт, устройство прочитает целый сектор, а файловая система — целый блок. Читать меньше блока бессмысленно, читать не кратно блоку — значит трогать лишний блок. Раз всё равно платим за блок, будем и работать блоками.

### Почему 4096

Число не случайное и совпадает сразу с несколькими другими.

Страница виртуальной памяти на x86 и ARM — четыре килобайта. Блок в ext4, APFS, NTFS по умолчанию — четыре килобайта. Размер страницы по умолчанию в SQLite — тоже четыре, в PostgreSQL — восемь. Мы это уже видели своими глазами в прошлой главе: в заголовке настоящего файла SQLite по смещению 16 лежало `10 00`, то есть 4096.

Совпадение полезное. Когда размер страницы базы кратен блоку файловой системы, запись страницы — это запись целых блоков, без чтения соседних. Если бы страница была, скажем, 3000 байт, то запись первой страницы задела бы часть второго блока, и файловой системе пришлось бы сначала прочитать этот блок, вставить в него кусок и записать обратно. Такое чтение-перед-записью — известный источник тормозов.

Размер побольше выгоден при последовательном чтении: меньше обращений на тот же объём. Размер поменьше выгоден при случайном доступе: не тратим канал на данные, которые не нужны. Четыре килобайта — компромисс, устоявшийся десятилетиями.

Объявляем всё это в `include/page.h`:

```cpp
#ifndef DB_PAGE_H
#define DB_PAGE_H

#include <cstddef>
#include <cstdint>
#include <vector>

namespace db {

// Размер страницы — 4 KiB. Совпадает с размером страницы памяти в большинстве ОС
// и размером блока в большинстве файловых систем. Чтение/запись страницы — это
// один блок IO, без частичных операций.
constexpr std::size_t PAGE_SIZE = 4096;

// Адрес страницы — индекс в файле. Файл рассматривается как массив страниц:
// страница 0 это байты 0..4095, страница 1 — 4096..8191, и так далее.
using PageId = std::uint32_t;

// Страница — буфер из 4 KiB байтов. Используем vector, а не array, чтобы можно
// было std::move без копий.
using Page = std::vector<unsigned char>;

inline Page make_page() {
    return Page(PAGE_SIZE, 0);
}

}  // namespace db

#endif
```

Адрес страницы — 32-битное беззнаковое число, и это ограничивает базу четырьмя миллиардами страниц, то есть шестнадцатью терабайтами. Для учебной базы с запасом; в настоящих системах номер страницы обычно 64-битный или составной — номер файла плюс номер страницы внутри.

Выбор `std::vector` вместо `std::array<unsigned char, 4096>` сделан ради перемещения. Массив фиксированного размера всегда копируется целиком — четыре килобайта на каждую передачу; вектор при перемещении отдаёт указатель, и копирования не происходит вовсе. Это прямое применение того, о чём шла речь в главе 19.

## Адресация: страница номер N

Перевод номера страницы в смещение в файле — умножение:

```
смещение = pid * PAGE_SIZE
```

Страница 0 занимает байты 0–4095, страница 1 — 4096–8191, страница 7 начинается с 28672. Обратный перевод — деление.

Важная мелочь: умножать надо в достаточно широком типе. `PageId` у нас 32-битный, и `pid * PAGE_SIZE` при большом `pid` переполнится ещё до того, как результат попадёт в 64-битную переменную. Поэтому в коде везде стоит явное приведение:

```cpp
off_t off = static_cast<off_t>(pid) * static_cast<off_t>(PAGE_SIZE);
```

`off_t` — тип смещения в файле, на 64-битных системах он 64-битный. Ошибка «переполнение при вычислении смещения» относится к тем, которые не проявляются в тестах и вылезают на большом файле у пользователя.

## pread и pwrite

Обычные `read` и `write` работают с текущей позицией в файле, которую надо предварительно выставить вызовом `lseek`:

```cpp
lseek(fd, offset, SEEK_SET);
read(fd, buf, PAGE_SIZE);
```

Для страничного доступа это неудобно и опасно. Во-первых, два системных вызова вместо одного. Во-вторых, позиция — общее состояние дескриптора: если тот же дескриптор используется в другом потоке, он сдвинет позицию между вашими `lseek` и `read`, и вы прочитаете не то. Мы это свойство наблюдали в главе 27, когда родитель и ребёнок делили позицию в файле после `fork`.

POSIX даёт пару, свободную от обеих проблем:

```cpp
ssize_t pread(int fd, void* buf, size_t count, off_t offset);
ssize_t pwrite(int fd, const void* buf, size_t count, off_t offset);
```

Смещение передаётся аргументом, позиция дескриптора не трогается вообще. Один вызов, никакого общего состояния, безопасно из нескольких потоков.

Как и обычные `read` с `write`, они могут обработать меньше запрошенного и прерваться сигналом, поэтому вызываются в цикле — том самом, который мы написали в главе 31 для `mycat`:

```cpp
ssize_t written = 0;
while (written < static_cast<ssize_t>(PAGE_SIZE)) {
    ssize_t n = ::pwrite(fd_, e.page.data() + written,
                         PAGE_SIZE - written, off + written);
    if (n < 0) {
        if (errno == EINTR) continue;
        throw PageError(std::string("pwrite: ") + std::strerror(errno));
    }
    ++stats_.disk_writes;
    written += n;
}
```

## Зачем кэш

Числа, которые стоит держать в голове. Обращение к оперативной памяти — около 100 наносекунд. Чтение блока с SSD — около 100 микросекунд, то есть в тысячу раз дольше. Позиционирование головки жёсткого диска — около 10 миллисекунд, в сто тысяч раз дольше.

Значит, всё, что можно не читать с диска, читать не нужно. Кэш страниц в памяти делает ровно это: держит недавно использованные страницы под рукой и отдаёт их без обращения к диску.

Работает это благодаря локальности обращений. В базе данных они распределены крайне неравномерно: верхние узлы индекса читаются при каждом запросе, метаданные — постоянно, а какая-нибудь страница с данными за позапрошлый год — раз в год. Даже маленький кэш ловит большинство обращений, потому что горячих страниц немного.

Кэш ограничен по размеру, значит, при заполнении надо кого-то выселять. Стратегий много, самая известная — вытеснять ту страницу, к которой дольше всего не обращались; её называют LRU, least recently used. Идея простая: если страницу не трогали дольше всех, вероятно, и дальше не тронут.

### Структура данных для LRU

Нужны две операции, обе за постоянное время: найти страницу по номеру и переместить страницу в «самые свежие». Ни хеш-таблица, ни список поодиночке этого не дают, а вместе — дают.

Держим двусвязный список номеров страниц: в начале самая свежая, в конце самая старая. И хеш-таблицу из номера страницы в пару «данные плюс итератор на позицию в списке».

```cpp
using LruList = std::list<PageId>;
using LruIter = LruList::iterator;

LruList lru_;   // front = самая свежая
std::unordered_map<PageId, std::pair<Entry, LruIter>> cache_;
```

Обращение к странице — переносим её узел в начало списка:

```cpp
void PageManager::touch(PageId pid) {
    auto it = cache_.find(pid);
    if (it == cache_.end()) return;
    lru_.erase(it->second.second);
    lru_.push_front(pid);
    it->second.second = lru_.begin();
}
```

Вытеснение — берём с конца списка:

```cpp
void PageManager::evict_one_if_full() {
    if (cache_.size() < cache_size_) return;
    // Жертва — самый старый элемент (хвост LRU).
    PageId victim = lru_.back();
    auto it = cache_.find(victim);
    flush_entry(victim, it->second.first);
    ++stats_.evictions;
    lru_.pop_back();
    cache_.erase(it);
}
```

Именно ради этого сочетания выбран `std::list`, а не `std::vector`: у списка есть свойство, которого нет у большинства контейнеров, — итератор на элемент остаётся действительным после вставок и удалений где угодно ещё. Поэтому итератор можно хранить в хеш-таблице. У `std::vector` при первой же вставке всё бы протухло.

Заметьте, что `erase` плюс `push_front` в `touch` — это не перевыделение памяти, а перевешивание указателей: узел списка остаётся на месте, меняются связи. Правда, `std::list::splice` сделал бы то же самое одной операцией и без переприсваивания итератора; это упражнение в конце главы.

## Грязные страницы

Если бы страницы только читались, кэш был бы просто копией диска и выбрасывался бы без последствий. Но их изменяют, и изменённая в памяти страница отличается от той, что на диске. Такую страницу называют грязной.

Правило простое: грязную страницу нельзя выбросить, не записав. Поэтому у каждой записи в кэше есть флаг:

```cpp
struct Entry {
    Page page;
    bool dirty = false;
};
```

`write_page` ставит флаг, `flush_entry` при записи снимает:

```cpp
void PageManager::flush_entry(PageId pid, Entry& e) {
    if (!e.dirty) return;
    // ... pwrite в цикле ...
    e.dirty = false;
}
```

Отложенная запись — не просто оптимизация, а серьёзный выигрыш. Если страницу изменили десять раз подряд, на диск уйдёт одна запись вместо десяти. В базе данных, где верхний узел индекса меняется при каждой вставке, разница огромна.

Плата за это — окно, в котором изменения существуют только в памяти. Что случится при внезапном выключении питания, разбирается в главе 35, где мы напишем журнал.

## fsync: когда данные действительно на диске

Здесь легко попасть в ловушку. Вызов `pwrite` вернул успех — значит ли это, что данные на диске?

Нет. Он значит, что данные скопированы в кэш ядра. Когда именно ядро запишет их на устройство, решает оно само, обычно в пределах десятков секунд. Если в этот промежуток выключить питание, данные пропадут, хотя программа была уверена, что записала их.

Заставить ядро довести дело до конца можно вызовом `fsync`:

```cpp
void PageManager::sync() {
    // 1) сбросить все dirty-страницы.
    for (auto& kv : cache_) {
        flush_entry(kv.first, kv.second.first);
    }
    // 2) fsync — заставить ядро записать данные с буферов на диск.
    if (::fsync(fd_) < 0) {
        throw PageError(std::string("fsync: ") + std::strerror(errno));
    }
}
```

Он возвращается только тогда, когда устройство подтвердило запись. Стоит это дорого — миллисекунды, — поэтому вызывать его на каждую страницу нельзя, а нужно в моменты, когда важна сохранность: при контрольной точке, при закрытии базы, после записи в журнал.

Есть родственник `fdatasync`, который сбрасывает только содержимое, не трогая метаданные вроде времени изменения. Он чуть быстрее и обычно достаточен, если размер файла не менялся.

Отдельно предупрежу про честность самих устройств. У диска есть собственный кэш записи, и некоторые дешёвые накопители подтверждают запись, когда данные ещё лежат в нём. На таком железе `fsync` не спасает; лечится это отключением кэша записи или использованием устройств с защитой от потери питания. Знать об этом стоит хотя бы потому, что рано или поздно вы услышите фразу «база потеряла подтверждённую транзакцию».

В деструкторе `PageManager` тоже стоит `sync`, но с проглатыванием исключений:

```cpp
PageManager::~PageManager() {
    if (fd_ >= 0) {
        // На деструкторе пытаемся синхронизироваться. Исключения проглатываем —
        // в деструкторе их бросать нельзя.
        try { sync(); } catch (...) {}
        ::close(fd_);
    }
}
```

Бросать из деструктора нельзя — если это случится во время раскрутки стека из-за другого исключения, программа немедленно завершится через `std::terminate` (глава 22). Поэтому в деструкторе остаётся только попытка. Правильное решение для важных данных — явный метод закрытия, который возвращает ошибку и который вызывающий обязан проверить; деструктор тогда становится страховкой на случай, если про метод забыли.

## Класс PageManager

Соберём всё вместе. Заголовок `include/page_manager.h`:

```cpp
class PageManager {
public:
    // Открыть файл (создаст, если не существует). cache_size — сколько страниц
    // держать в памяти.
    PageManager(const std::string& path, std::size_t cache_size = 64);
    ~PageManager();

    // Запрет копирования.
    PageManager(const PageManager&) = delete;
    PageManager& operator=(const PageManager&) = delete;

    Page read_page(PageId pid);
    void write_page(PageId pid, const Page& page);
    PageId allocate_page();
    PageId page_count() const { return page_count_; }
    void sync();

    // Счётчики для наблюдения за кэшем.
    struct Stats {
        long long hits = 0;        // страница была в кэше
        long long misses = 0;      // пришлось читать с диска
        long long evictions = 0;   // вытеснено из кэша
        long long disk_reads = 0;  // вызовов pread
        long long disk_writes = 0; // вызовов pwrite
    };
    const Stats& stats() const { return stats_; }
    void reset_stats() { stats_ = Stats(); }

private:
    struct Entry {
        Page page;
        bool dirty = false;
    };

    using LruList = std::list<PageId>;
    using LruIter = LruList::iterator;

    int fd_;
    PageId page_count_;
    std::size_t cache_size_;
    Stats stats_;

    LruList lru_;
    std::unordered_map<PageId, std::pair<Entry, LruIter>> cache_;

    void evict_one_if_full();
    void flush_entry(PageId pid, Entry& e);
    Entry& load_into_cache(PageId pid);
    void touch(PageId pid);
};
```

Копирование запрещено через `= delete` — приём из главы 18. `PageManager` владеет файловым дескриптором, и второй владелец того же дескриптора означал бы двойное закрытие. Это тот случай, когда запрет копирования не ограничение, а описание сути объекта.

Счётчики в открытой части класса — не украшение. Кэш трудно обсуждать умозрительно, и возможность спросить «сколько раз ты попал» превращает догадки в измерения. В главе 39 мы будем смотреть на них при настройке размера кэша.

### Открытие

```cpp
PageManager::PageManager(const std::string& path, std::size_t cache_size)
    : fd_(-1), page_count_(0), cache_size_(cache_size) {
    fd_ = ::open(path.c_str(), O_RDWR | O_CREAT, 0644);
    if (fd_ < 0) {
        throw PageError("не открыт: " + path + ": " + std::strerror(errno));
    }
    struct stat st;
    if (::fstat(fd_, &st) < 0) {
        ::close(fd_);
        throw PageError(std::string("fstat: ") + std::strerror(errno));
    }
    if (st.st_size % PAGE_SIZE != 0) {
        ::close(fd_);
        throw PageError("файл не выровнен по PAGE_SIZE");
    }
    page_count_ = static_cast<PageId>(st.st_size / PAGE_SIZE);
}
```

Количество страниц нигде не хранится — оно вычисляется из размера файла. Так меньше состояния, которое может рассинхронизироваться: файл сам себя описывает.

Проверка кратности размера — дешёвая защита от чужого или обрезанного файла. Обратите внимание на порядок в ветках ошибок: сначала закрываем дескриптор, потом бросаем исключение. Пропустить `close` здесь — классическая утечка, потому что деструктор объекта, конструктор которого бросил, не вызывается.

`fstat` вместо `stat` — потому что дескриптор у нас уже есть, и спрашивать про файл по имени было бы и лишней работой, и гонкой: между `open` и `stat` файл могли подменить.

### Чтение и запись

```cpp
Page PageManager::read_page(PageId pid) {
    if (pid >= page_count_) {
        throw PageError("страница вне диапазона: " + std::to_string(pid));
    }
    Entry& e = load_into_cache(pid);
    return e.page;  // copy
}

void PageManager::write_page(PageId pid, const Page& page) {
    if (pid >= page_count_) {
        throw PageError("страница вне диапазона: " + std::to_string(pid));
    }
    if (page.size() != PAGE_SIZE) {
        throw PageError("неправильный размер page");
    }
    Entry& e = load_into_cache(pid);
    e.page = page;
    e.dirty = true;
}
```

`read_page` возвращает **копию** страницы — четыре килобайта на каждый вызов. Это осознанное упрощение, и в настоящей базе так не делают: там возвращают указатель на страницу в кэше вместе с механизмом закрепления (pin), который запрещает вытеснять страницу, пока на неё кто-то смотрит. Мы платим копированием за то, что не нужно думать о времени жизни: страница, полученная из `read_page`, остаётся действительной, даже если её оригинал вытеснили. В главе 39 мы увидим, во что это обходится по времени.

Проверка `pid >= page_count_` превращает обращение за границу в исключение вместо чтения мусора. За такие проверки на границах компонентов платят наносекундами, а получают часы сэкономленной отладки.

### Загрузка в кэш

```cpp
PageManager::Entry& PageManager::load_into_cache(PageId pid) {
    auto it = cache_.find(pid);
    if (it != cache_.end()) {
        ++stats_.hits;
        touch(pid);
        return it->second.first;
    }
    ++stats_.misses;

    evict_one_if_full();

    Entry e;
    e.page = make_page();
    e.dirty = false;

    off_t off = static_cast<off_t>(pid) * static_cast<off_t>(PAGE_SIZE);
    ssize_t read_total = 0;
    while (read_total < static_cast<ssize_t>(PAGE_SIZE)) {
        ssize_t n = ::pread(fd_, e.page.data() + read_total,
                            PAGE_SIZE - read_total, off + read_total);
        if (n < 0) {
            if (errno == EINTR) continue;
            throw PageError(std::string("pread: ") + std::strerror(errno));
        }
        if (n == 0) {
            // Дочитали до конца файла — остальное оставляем нулями.
            break;
        }
        ++stats_.disk_reads;
        read_total += n;
    }

    lru_.push_front(pid);
    auto inserted = cache_.emplace(pid, std::make_pair(std::move(e), lru_.begin()));
    return inserted.first->second.first;
}
```

Ветка с `n == 0` заслуживает объяснения. Ноль от `pread` означает, что мы читаем за концом файла. Так бывает штатно: страницу выделили в памяти, ещё не сбросили на диск, а кто-то её читает. Файл до неё не дорос, читать нечего — и мы оставляем страницу нулевой, что как раз и есть её содержимое.

Возвращается ссылка на запись **внутри** хеш-таблицы. Это безопасно ровно до следующей операции, которая может вытеснить эту страницу, — и именно поэтому `read_page` тут же делает копию. У `std::unordered_map` ссылки на элементы переживают вставки, в отличие от итераторов, но не переживают удаление самого элемента.

### Выделение страницы

```cpp
PageId PageManager::allocate_page() {
    PageId new_id = page_count_;
    page_count_++;

    // Расширяем файл, чтобы он действительно содержал эту страницу.
    Entry e;
    e.page = make_page();
    e.dirty = true;

    evict_one_if_full();
    lru_.push_front(new_id);
    cache_.emplace(new_id, std::make_pair(std::move(e), lru_.begin()));
    return new_id;
}
```

Новая страница создаётся сразу грязной, хотя в ней одни нули. Иначе она никогда бы не попала на диск, файл не вырос бы, и `page_count_` при следующем открытии оказался бы меньше — база потеряла бы страницы.

Свободные страницы мы не переиспользуем: номера всегда растут. В настоящей базе есть список свободных страниц (freelist), куда попадают освобождённые при удалении данных, и `allocate_page` сначала смотрит туда. Нам это не нужно, потому что удаление данных мы не реализуем; в упражнениях есть задание сделать freelist.

## Кэш в работе

Посмотрим на всё это в действии — программа `utils/page_demo.cpp` записывает страницы, переоткрывает файл и гоняет разные образцы обращений:

```bash
$ ./build/page_demo
=== Запись трёх страниц ===
page_count = 3, размер файла будет 12288 байт
после записи: попаданий 3, промахов 0, вытеснено 0, pread 0, pwrite 3

=== Переоткрытие файла ===
page_count восстановлен из размера файла: 3
  страница 0: page 0 payload................
  страница 1: page 1 payload................
  страница 2: page 2 payload................
три первых чтения: попаданий 0, промахов 3, вытеснено 0, pread 3, pwrite 0
ещё 30 чтений: попаданий 30, промахов 0, вытеснено 0, pread 0, pwrite 0
```

Три записи — три попадания в кэш (страницы только что выделены и лежат в памяти) и ни одного чтения с диска. После `sync` — три вызова `pwrite`. При переоткрытии первые три чтения промахиваются, а следующие тридцать попадают все: страницы уже в памяти, диск не потревожен ни разу.

Теперь интереснее — кэш на четыре страницы при шестидесяти трёх используемых:

```
=== Кэш меньше рабочего набора ===
обход по кругу: попаданий 0, промахов 189, вытеснено 189, pread 189, pwrite 0
горячие 4 страницы: попаданий 196, промахов 4, вытеснено 4, pread 4, pwrite 0
```

Первая строка — полный провал: 189 обращений, 189 промахов, ноль попаданий. Кэш не помог совсем. Вторая строка — почти идеал: 196 попаданий из 200.

Разница только в образце обращений, и она объясняет главную слабость LRU. При обходе по кругу к моменту, когда мы вернёмся к первой странице, её уже вытеснили — как раз потому, что к ней дольше всех не обращались. Кэш работает точно наоборот, чем нужно. Это явление называют вымыванием кэша последовательным чтением, и настоящие базы борются с ним отдельно: PostgreSQL для больших последовательных чтений выделяет крошечное кольцо буферов, чтобы такое чтение не выбрасывало из кэша всё полезное.

Вторая строка показывает случай, ради которого кэш и существует: небольшой горячий набор, который целиком помещается в память. Именно так выглядит доступ к верхним узлам индекса.

## Сколько страниц держать

Наш кэш по умолчанию — 64 страницы, то есть 256 килобайт. Мало по меркам настоящей базы, но нам хватает.

Общее правило: кэш должен вмещать горячий набор — те страницы, к которым обращаются постоянно. Для индекса это верхние уровни дерева; при миллионе записей и ветвлении в сотню верхних уровней всего два-три, и это десятки страниц. Промахи станут заметны, если кэш меньше этого.

Настоящие базы отдают кэшу существенную долю оперативной памяти: в PostgreSQL параметр `shared_buffers` обычно ставят около четверти памяти машины, в MySQL InnoDB буферный пул нередко доводят до трёх четвертей. Спорить с этими цифрами бессмысленно без измерений — а измерения начинаются с тех самых счётчиков попаданий и промахов, которые мы завели.

## Что здесь упрощено

Честный список, чтобы вы не приняли учебный код за образец промышленного.

Мы возвращаем копию страницы вместо указателя с закреплением — просто, но копирует четыре килобайта на каждое чтение. Мы не переиспользуем освобождённые страницы. У нас нет ни блокировок, ни атомарности: `PageManager` рассчитан на один поток, и попытка работать с ним из двух потоков сломает и кэш, и список LRU. Наконец, при вытеснении грязной страницы мы пишем её сразу и синхронно, тогда как настоящие базы делают это фоновым процессом, чтобы запрос не ждал диска.

Есть и опасность, о которой стоит знать заранее: разрыв страницы. Если питание пропадёт посреди записи четырёх килобайт, на диске может оказаться половина новой страницы и половина старой. Для SSD запись сектора обычно атомарна, но целая страница из нескольких секторов — уже нет. PostgreSQL решает это записью полного образа страницы в журнал при первом изменении после контрольной точки, MySQL — двойной записью в отдельную область. Наш ответ будет проще и тоже рабочий: журнал операций, из которого дерево восстанавливается заново. Это глава 35.

## Главные правила главы

1. База данных работает с файлом как с массивом страниц одинакового размера, а не как с потоком записей.
2. Размер страницы выбирают кратным блоку файловой системы; 4096 — устоявшийся выбор.
3. Смещение считают в достаточно широком типе: `static_cast<off_t>(pid) * PAGE_SIZE`.
4. `pread` и `pwrite` не трогают позицию дескриптора — это один вызов вместо двух и безопасность при многопоточности.
5. LRU строится на паре «двусвязный список плюс хеш-таблица»; итераторы `std::list` не портятся при вставках и удалениях.
6. Изменённую страницу помечают грязной; выбросить её без записи нельзя.
7. Успешный `pwrite` не означает, что данные на диске; гарантию даёт только `fsync`.
8. Последовательный обход большого файла сводит пользу LRU к нулю — это надо учитывать, а не удивляться.

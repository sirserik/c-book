# Глава 43. Цикл событий

Сервер на потоках работает, но мы знаем его пределы: стек на каждое соединение, переключения контекста, состязание за мьютекс при рассылке. На сотне клиентов это незаметно, на десяти тысячах — уже нет.

В этой главе построим тот же чат другим способом: один поток, который спрашивает у ядра «на каких сокетах что-то произошло» и обрабатывает только их. Такую схему называют циклом событий или реактором, и на ней работают nginx, Redis, Node.js и почти всё, что держит много соединений.

Заодно узнаем, что такое неблокирующий режим, зачем каждому клиенту собственный буфер отправки и почему при переходе на события код выворачивается наизнанку.

## Почему потоков не хватает

Сравним два наших сервера на ста подключённых клиентах — просто посмотрим, что показывает система:

```
сервер на потоках:  потоков 102, память 1.7 МБ
реактор:            потоков 2,   память 1.0 МБ
```

Сто два потока против двух. Память пока отличается несильно, потому что стеки выделены виртуально и почти не тронуты, — но на десяти тысячах клиентов разница станет решающей: адресное пространство под стеки, память ядра под структуры потоков, а главное — планировщик, который вынужден раскладывать десять тысяч потоков по восьми ядрам.

Ещё одна причина, менее очевидная: в чате потоки почти всё время спят. Клиент пишет сообщение раз в минуту, а поток занят соединением постоянно. Мы платим за поток, а работы у него на доли процента.

Идея цикла событий отсюда и растёт: раз потоки всё равно ждут, пусть ждёт один — сразу за всех.

## poll

Системный вызов, который умеет ждать сразу на многих дескрипторах, называется `poll`:

```cpp
#include <poll.h>

struct pollfd {
    int   fd;         // за каким дескриптором следим
    short events;     // чего ждём: POLLIN, POLLOUT
    short revents;    // что произошло — заполняет ядро
};

int poll(struct pollfd fds[], nfds_t nfds, int timeout);
```

Программа готовит массив: для каждого сокета — номер и набор интересующих событий. `poll` засыпает, пока хоть на одном что-нибудь не случится, и возвращает количество готовых дескрипторов, проставив в `revents` то, что произошло.

Флаги, которые нам нужны: `POLLIN` — есть данные для чтения (или соединение закрыто), `POLLOUT` — можно писать без блокировки, `POLLHUP` — собеседник отключился, `POLLERR` — ошибка на сокете. Первые два ставим мы, вторые два ядро выставляет само, о них просить не нужно.

Тайм-аут — в миллисекундах; `-1` означает «ждать бесконечно», `0` — «посмотреть и сразу вернуться».

Есть три родственника, и разница между ними важна для больших нагрузок. `select` — самый старый, ограничен 1024 дескрипторами и неудобен. `poll` — без ограничения на число, но каждый вызов передаёт ядру весь массив целиком, а ядро проходит по нему линейно; при десяти тысячах сокетов это десять тысяч проверок на каждое событие. `epoll` на Linux и `kqueue` на macOS и BSD решают эту проблему: список отслеживаемых дескрипторов хранится в ядре и меняется отдельными вызовами, а при пробуждении отдаются только готовые.

Мы берём `poll`, потому что он работает и на Linux, и на macOS, а идея у всех трёх одна. Переход на `epoll` в упражнениях.

## Неблокирующий режим

Цикл событий работает только с неблокирующими сокетами, и это принципиально.

Представьте: `poll` сказал, что на сокете есть данные, мы делаем `recv` и читаем всё, что пришло. Данных было мало, а буфер большой — и `recv` в блокирующем режиме уснёт, ожидая продолжения. Один клиент остановит весь сервер.

Перевод в неблокирующий режим:

```cpp
void set_nonblocking(int fd) {
    int flags = ::fcntl(fd, F_GETFL, 0);
    ::fcntl(fd, F_SETFL, flags | O_NONBLOCK);
}
```

Сначала читаем текущие флаги, потом добавляем свой — именно добавляем, а не назначаем. Написать `fcntl(fd, F_SETFL, O_NONBLOCK)` — значит стереть все остальные флаги, и это распространённая ошибка.

После этого поведение вызовов меняется: если данных нет, `recv` не ждёт, а сразу возвращает `-1` с `errno` равным `EAGAIN` (то же самое, что `EWOULDBLOCK` — два имени одного значения). Аналогично `send` при переполненном буфере отправки и `accept` при отсутствии ожидающих соединений.

Отсюда правило: **`EAGAIN` — не ошибка, а сообщение «пока ничего нет»**. Оно повторяется в коде постоянно:

```cpp
ssize_t r = ::recv(fd, buf, sizeof(buf), 0);
if (r < 0) {
    if (errno == EAGAIN || errno == EWOULDBLOCK) break;   // всё прочитали
    if (errno == EINTR) continue;                          // сигнал, повторим
    gone = true; break;                                    // настоящая ошибка
}
```

Три ветки на каждый вызов. Многословно, но каждая нужна.

## Состояние клиента

В потоковом сервере состояние разговора хранилось в локальных переменных обработчика: имя лежало в `name`, накопитель — в `acc`, а место, где мы находимся, — в счётчике команд. Всё это исчезает, когда обработчиков больше нет.

Значит, состояние надо хранить явно:

```cpp
struct ClientState {
    int fd;
    std::string name;
    std::string recv_buf;   // буфер для частичных recv
    std::string send_buf;   // что мы хотим послать (пока не отправлено)
};

std::unordered_map<int, ClientState> clients;
```

Отображение из дескриптора в состояние — типичная для реакторов структура: событие приносит номер дескриптора, по нему находим, с кем имеем дело.

Буфер приёма нужен по той же причине, что и раньше: сообщение может прийти по частям.

А вот буфер отправки — новинка, и он появляется именно из-за неблокирующего режима. Раньше мы просто звали `send` и ждали, пока он отправит. Теперь `send` может отправить половину и вернуть `EAGAIN` — буфер сокета переполнен, клиент не успевает читать. Блокироваться нельзя, значит, остаток надо сохранить и попробовать позже:

```cpp
void broadcast(std::unordered_map<int, ClientState>& clients,
               int from_fd, const std::string& msg) {
    for (auto& kv : clients) {
        if (kv.first == from_fd) continue;
        kv.second.send_buf += msg;
    }
}
```

Обратите внимание, что рассылка теперь **ничего не отправляет**. Она только раскладывает сообщение по буферам, а отправкой займётся цикл, когда ядро скажет, что сокет готов принимать. Это и есть переворот, о котором я говорил: код перестаёт делать вещи и начинает планировать их.

## Цикл

```cpp
while (true) {
    // Собираем массив pollfd на эту итерацию.
    std::vector<pollfd> pfds;
    pfds.reserve(clients.size() + 1);
    pfds.push_back({srv, POLLIN, 0});
    for (const auto& kv : clients) {
        short events = POLLIN;
        if (!kv.second.send_buf.empty()) events |= POLLOUT;
        pfds.push_back({kv.first, events, 0});
    }

    int n = ::poll(pfds.data(), pfds.size(), -1 /*ms, infinite*/);
    if (n < 0) {
        if (errno == EINTR) continue;
        std::cerr << "poll: " << std::strerror(errno) << "\n";
        break;
    }
    ...
}
```

Массив собирается заново на каждой итерации — расточительно, но наглядно. В настоящем сервере его держат постоянным и правят точечно, а с `epoll` вопрос отпадает сам: список живёт в ядре.

Ключевая строка — условие про `POLLOUT`. Просить готовность к записи надо **только тогда, когда есть что писать**. Иначе `poll` будет просыпаться непрерывно: свободное место в буфере отправки есть почти всегда, и цикл превратится в бесконечную прокрутку с полной загрузкой ядра. Это классическая ошибка новичков в реакторах, и её легко заметить по стопроцентной загрузке процессора на пустом сервере.

### Новые соединения

```cpp
if (pfds[0].revents & POLLIN) {
    while (true) {
        int c = ::accept(srv, nullptr, nullptr);
        if (c < 0) {
            if (errno == EAGAIN || errno == EWOULDBLOCK) break;
            if (errno == EINTR) continue;
            break;
        }
        set_nonblocking(c);

        ClientState st;
        st.fd = c;
        st.name = "user_" + std::to_string(next_id++);
        clients.emplace(c, std::move(st));
        broadcast(clients, c, "* " + clients[c].name + " вошёл\n");
        clients[c].send_buf += "Привет, " + clients[c].name + "\n";
    }
}
```

Принимаем в цикле, пока `accept` не скажет `EAGAIN`. Причина в том, что за одно пробуждение могло прийти несколько соединений, а `poll` сообщает лишь факт готовности, не количество. Приняв одно и вернувшись в `poll`, мы бы разобрали очередь по одному за круг — работало бы, но медленнее.

Слушающий сокет тоже переведён в неблокирующий режим — иначе `accept` в этом цикле однажды заснёт.

Заметьте, что счётчик `next_id` здесь — обычный `int`, и никакой гонки нет: поток один. Это первая приятная особенность реактора — исчезает целый класс ошибок.

### Чтение

```cpp
if (re & POLLIN) {
    char buf[1024];
    bool gone = false;
    while (true) {
        ssize_t r = ::recv(fd, buf, sizeof(buf), 0);
        if (r == 0) { gone = true; break; }
        if (r < 0) {
            if (errno == EAGAIN || errno == EWOULDBLOCK) break;
            if (errno == EINTR) continue;
            gone = true; break;
        }
        s.recv_buf.append(buf, static_cast<std::size_t>(r));
    }
    // Парсим сообщения по \n
    std::size_t pos;
    while ((pos = s.recv_buf.find('\n')) != std::string::npos) {
        std::string line = s.recv_buf.substr(0, pos);
        s.recv_buf.erase(0, pos + 1);
        if (line == "/quit") { gone = true; break; }
        std::string out = "<" + s.name + "> " + line + "\n";
        broadcast(clients, fd, out);
    }
    if (gone) {
        std::string bye = "* " + s.name + " вышел\n";
        ::close(fd);
        clients.erase(it);
        broadcast(clients, -1, bye);
        continue;
    }
}
```

Читаем тоже в цикле до `EAGAIN` — по той же причине, что и принимаем.

Ноль от `recv` означает, что клиент закрыл соединение. Обратите внимание на порядок при отключении: сначала запоминаем прощальное сообщение в локальную переменную, потом закрываем сокет, удаляем клиента и только затем рассылаем. Если бы мы рассылали до удаления, ушедший клиент получил бы собственное прощание в буфер отправки, которого уже не существует.

### Запись и ловушка с висящей ссылкой

```cpp
// Можно писать. Осторожно: если отправка сорвалась, клиента надо
// удалить — и после этого ссылка s указывает в никуда, поэтому
// выходим сразу, а не продолжаем работать с ней.
if ((re & POLLOUT) && !s.send_buf.empty()) {
    bool dropped = false;
    while (!s.send_buf.empty()) {
        ssize_t w = ::send(fd, s.send_buf.data(), s.send_buf.size(), MSG_NOSIGNAL);
        if (w < 0) {
            if (errno == EAGAIN || errno == EWOULDBLOCK) break;
            if (errno == EINTR) continue;
            std::cout << "[server] " << s.name << ": send: "
                      << std::strerror(errno) << "\n";
            ::close(fd);
            clients.erase(it);
            dropped = true;
            break;
        }
        s.send_buf.erase(0, static_cast<std::size_t>(w));
    }
    if (dropped) continue;
}

// Хост-отключение/ошибка
if (re & (POLLHUP | POLLERR | POLLNVAL)) {
    std::cout << "[server] " << s.name << " (hup/err)\n";
    ::close(fd);
    clients.erase(it);
}
```

Здесь была настоящая ошибка, и стоит рассказать о ней подробно, потому что она характерна для такого кода.

В первой версии после неудачной отправки клиент удалялся, но цикл не прерывался — а условие цикла читает `s.send_buf`, где `s` — ссылка на удалённый элемент. Обращение к освобождённой памяти в чистом виде. Хуже того, дальше управление доходило до проверки `POLLHUP`, которая печатала `s.name`, — второе обращение к тому же трупу.

Ошибка не проявлялась в обычной работе: неудачная отправка случается редко, и надо было специально ронять клиента посреди рассылки. Именно такие ошибки — редкие, зависящие от времени, ведущие к порче памяти — и делают серверный код сложным.

Лечится флагом `dropped` и немедленным выходом. Более надёжный подход — не удалять клиентов сразу, а помечать их и вычищать в конце итерации цикла: тогда никакие ссылки не протухают в середине обработки. Так делают в настоящих реакторах, и это упражнение в конце главы.

Флаг `MSG_NOSIGNAL` в `send` — та же защита от SIGPIPE, что в главе 41. На macOS, кстати, этого флага нет (там вместо него настройка сокета `SO_NOSIGPIPE`), но заголовки его определяют, и код собирается.

## Чем приходится платить

Реактор решает проблему масштаба, но забирает взамен несколько вещей.

Код становится сложнее. Сравните два обработчика: в потоковой версии логика читается сверху вниз — поздоровались, читаем, разбираем, отвечаем. В реакторе она разорвана на куски, между которыми возврат в цикл, а связь между кусками держится на структуре состояния. Это та же разница, что между обычным кодом и цепочкой обратных вызовов.

Одна долгая операция останавливает всех. Если в обработке сообщения окажется запрос к базе данных на сто миллисекунд, все клиенты будут ждать эти сто миллисекунд. В потоковой версии ждал бы только один. Отсюда правило реакторов: **в цикле событий не должно быть ничего долгого** — ни синхронного ввода-вывода, ни тяжёлых вычислений, ни ожидания замков.

Не используются ядра. Один поток — одно ядро, как бы ни была мощна машина. Промышленное решение — несколько реакторов, по одному на ядро, каждый со своим набором соединений: так устроены nginx с его рабочими процессами и Node.js с модулем кластера.

## Как это выглядит у взрослых

Наш цикл — учебный, но идея в промышленных серверах ровно та же, отличается техника.

Вместо `poll` берут `epoll` (Linux) или `kqueue` (BSD, macOS): список наблюдаемых дескрипторов живёт в ядре, а при пробуждении отдаются только готовые. Разница видна на тысячах соединений, где `poll` тратит время на обход всего массива.

Реакторов заводят несколько — по числу ядер, и распределяют соединения между ними. Иногда с помощью `SO_REUSEPORT`, о котором шла речь в главе 40: несколько процессов слушают один порт, а ядро само раскладывает подключения.

Тяжёлую работу выносят в отдельный пул потоков: реактор принимает запрос, отдаёт его рабочему потоку и возвращается к событиям, а результат отправляет, когда работа закончится.

И почти всегда берут готовую библиотеку — libuv (на ней стоит Node.js), Boost.Asio, libevent. Писать цикл событий руками имеет смысл ровно один раз — чтобы понять, как он устроен.

Стоит упомянуть и направление, в котором всё это движется. В Linux с 2019 года есть `io_uring` — интерфейс, где программа и ядро общаются через две кольцевые очереди в разделяемой памяти, почти без системных вызовов. А в C++20 появились сопрограммы, позволяющие писать асинхронный код в привычном линейном виде: `co_await` вместо разрыва на обратные вызовы. Об обоих — коротко в главе 51.

## Главные правила главы

1. Цикл событий заменяет много спящих потоков одним, который ждёт сразу за всех.
2. Реактор работает только с неблокирующими сокетами; `EAGAIN` в нём означает «пока ничего нет», а не ошибку.
3. Флаги дескриптора меняют чтением и добавлением бита, а не назначением — иначе сотрутся остальные.
4. Состояние разговора приходится хранить явно, потому что стека обработчика больше нет.
5. Буфер отправки у каждого клиента обязателен: `send` может отправить часть и вернуть `EAGAIN`.
6. `POLLOUT` просят только при непустом буфере отправки, иначе цикл крутится вхолостую на полной загрузке.
7. Принимать и читать надо в цикле до `EAGAIN`: событие говорит о готовности, но не о количестве.
8. Удаление клиента посреди обработки оставляет висящую ссылку — либо выходите сразу, либо откладывайте удаление на конец итерации.

## Упражнения

1. Запустите оба сервера и подключите к каждому по сотне клиентов (`for i in $(seq 100); do sleep 30 | nc localhost ПОРТ & done`). Сравните число потоков (`ps -M PID`) и потребление памяти.

2. Уберите условие `if (!kv.second.send_buf.empty())` — просите `POLLOUT` всегда. Запустите сервер с одним клиентом и посмотрите загрузку процессора через `top`. Объясните результат.

3. Уберите `set_nonblocking(c)` для клиентских сокетов. Подключите двух клиентов и заставьте одного молчать посреди отправки. Что произойдёт со вторым?

4. Замените в `set_nonblocking` добавление флага на назначение (`F_SETFL, O_NONBLOCK`). Проверьте, что сокет всё ещё работает, и объясните, какие флаги вы при этом потеряли.

5. Переделайте удаление клиентов на отложенное: собирайте дескрипторы на удаление в вектор и вычищайте в конце итерации. Убедитесь, что ссылки больше не протухают.

6. Добавьте тайм-аут в `poll` (например, тысячу миллисекунд) и раз в секунду отключайте клиентов, молчавших дольше минуты. Понадобится хранить время последней активности в состоянии клиента.

7. (Сложнее) Перепишите цикл на `epoll` (Linux) или `kqueue` (macOS). Сравните код: что стало проще, что сложнее. Замерьте разницу на тысяче соединений.

8. (Сложнее) Сделайте несколько реакторов: главный поток принимает соединения и раздаёт их по очереди рабочим потокам, у каждого из которых свой цикл `poll`. Продумайте, как передать дескриптор в чужой цикл, не разбудив его насильно.

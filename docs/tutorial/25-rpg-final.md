## Зачем юнит-тесты

Программа из 1600 строк уже достаточно большая, чтобы случайные изменения ломали неожиданные вещи. Вы правите `Inventory::take`, а тут ломается `cmd_drop`. Юнит-тесты — **первая линия защиты** от регрессий.

Хороший тест:
- Покрывает один сценарий (одна функция, один аспект).
- Запускается за миллисекунды.
- Не зависит от других тестов.
- Чётко говорит, что прошло и что упало.

Юнит-тесты пишутся **на ту же кодовую базу**, ловят баги до того, как они доберутся до пользователя, и заодно служат документацией: «вот так этот класс используется».

## GoogleTest vs свой простой framework

Стандартный фреймворк тестирования C++ — **GoogleTest**. Он мощный (макросы `EXPECT_EQ`, фикстуры, параметризованные тесты), но требует подключения внешней зависимости.

Для нашего учебного проекта возьмём **свой минимальный test-runner**. Это:
- Никаких внешних зависимостей.
- Видна вся логика подсчёта.
- Достаточно для нашего масштаба.

В реальном проекте на нескольких десятках тысяч строк — GoogleTest или Catch2. Идея та же, просто фреймворк удобнее.

## Свой test-framework

`tests/test_framework.h`:

```cpp
#ifndef RPG_TEST_FRAMEWORK_H
#define RPG_TEST_FRAMEWORK_H

#include <iostream>
#include <sstream>
#include <string>

namespace test {

struct Stats {
    int total = 0;
    int passed = 0;

    int report(const std::string& suite) const {
        std::cout << "[" << suite << "] " << passed << "/" << total
                  << " прошло\n";
        return (passed == total) ? 0 : 1;
    }
};

}  // namespace test

#define CHECK(stats, cond)                                                  \
    do {                                                                    \
        (stats).total++;                                                    \
        if (cond) {                                                         \
            (stats).passed++;                                               \
        } else {                                                            \
            std::cerr << "FAIL " << __FILE__ << ":" << __LINE__              \
                      << " — " #cond << "\n";                                \
        }                                                                   \
    } while (0)

#define CHECK_EQ(stats, a, b)                                               \
    do {                                                                    \
        (stats).total++;                                                    \
        auto&& _a = (a);                                                    \
        auto&& _b = (b);                                                    \
        if (_a == _b) {                                                     \
            (stats).passed++;                                               \
        } else {                                                            \
            std::ostringstream _ss;                                         \
            _ss << "FAIL " << __FILE__ << ":" << __LINE__                    \
                << " — " #a " == " #b " (got " << _a << " vs " << _b << ")"; \
            std::cerr << _ss.str() << "\n";                                  \
        }                                                                   \
    } while (0)

#endif
```

Разбор макросов.

**`do { ... } while (0)`** — стандартный приём, чтобы макрос вёл себя как одна инструкция. Без этого `if (cond) CHECK(...);` сломался бы — `do/while(0)` фиксирует «один блок, требующий `;` после».

**`#cond`** — **stringification**: имя выражения превращается в строку. `CHECK(s, x > 5)` напечатает `"x > 5"`.

**`__FILE__` и `__LINE__`** — макросы препроцессора, подставляют имя файла и номер строки.

**`auto&& _a = (a);`** — захват выражения в локальную ссылку, чтобы вычислить **один раз** (выражение могло иметь побочные эффекты — например, `++i`).

Это не идеальный фреймворк (нет фикстур, параметризации), но достаточный.

## Юнит-тесты модулей

`tests/test_units.cpp`. Каждая функция — отдельная группа тестов:

```cpp
void test_player(test::Stats& s) {
    Player p("Alice", 50);
    CHECK_EQ(s, p.name(), std::string("Alice"));
    CHECK_EQ(s, p.hp(), 50);
    CHECK(s, p.alive());

    p.take_damage(20);
    CHECK_EQ(s, p.hp(), 30);
    p.heal(100);             // не выше max
    CHECK_EQ(s, p.hp(), 50);
    p.take_damage(1000);      // не ниже 0
    CHECK_EQ(s, p.hp(), 0);
    CHECK(s, !p.alive());
}
```

Проверяем: конструктор работает, ограничения работают (heal не превысит max, damage не загонит в минус), `alive()` правильно меняется.

```cpp
void test_player_validation(test::Stats& s) {
    bool empty_caught = false;
    try { Player p("", 10); }
    catch (const ValidationError&) { empty_caught = true; }
    CHECK(s, empty_caught);

    bool neg_caught = false;
    try { Player p("ok", -1); }
    catch (const ValidationError&) { neg_caught = true; }
    CHECK(s, neg_caught);
}
```

Проверяем валидацию: пустое имя и отрицательный hp бросают исключение. Это **обратная сторона**: показываем, что баги (поломки) тоже работают как ожидаешь.

```cpp
void test_inventory(test::Stats& s) {
    Inventory inv;
    CHECK(s, inv.empty());

    inv.add(make_unique<Weapon>("меч", 5, 8));
    inv.add(make_unique<Armor>("шлем", 3, 4));
    CHECK_EQ(s, inv.items().size(), static_cast<std::size_t>(2));
    CHECK_EQ(s, inv.total_weight(), 8);

    auto taken = inv.take("меч");
    CHECK(s, static_cast<bool>(taken));
    CHECK_EQ(s, taken->name(), std::string("меч"));
    CHECK_EQ(s, inv.items().size(), static_cast<std::size_t>(1));

    auto miss = inv.take("щит");
    CHECK(s, !miss);

    inv.clear();
    CHECK(s, inv.empty());
}
```

Полный жизненный цикл инвентаря: пустой → добавили → проверили → взяли → проверили → попытались взять несуществующее → проверили → очистили.

`static_cast<std::size_t>(2)` — для подавления `-Wsign-compare`: `size()` возвращает `size_t` (unsigned), а `2` — это `int` (signed). С строгими флагами компилятор требует, чтобы оба были одного знака.

### Парсер и save/load

```cpp
void test_world_parser(test::Stats& s) {
    std::string source =
        "location start\n"
        "name Старт\n"
        "desc Тут начало.\n"
        "exit east finish\n"
        "item weapon кинжал 2 4\n"
        "\n"
        "location finish\n"
        "name Финиш\n"
        "desc Конец.\n";
    std::istringstream in(source);
    World w = parse_world(in);
    CHECK_EQ(s, w.size(), static_cast<std::size_t>(2));

    const Location* start = w.find("start");
    CHECK(s, start != nullptr);
    CHECK_EQ(s, start->name(), std::string("Старт"));
    CHECK_EQ(s, start->exit("east"), std::string("finish"));
    CHECK_EQ(s, start->items().items().size(), static_cast<std::size_t>(1));
}
```

Парсер тестируем **на строке**, не на файле. Так быстрее и тест не зависит от внешних файлов. `parse_world` принимает `std::istream&` — через `std::istringstream` подаём строку.

```cpp
void test_save_load_roundtrip(test::Stats& s) {
    World w;
    Location loc("home", "Дом", "Тут уютно.");
    w.add(std::move(loc));

    Player p("Hero", 100);
    p.take_damage(30);
    p.inventory().add(make_unique<Consumable>("яблоко", 1, 5));

    std::string path = "/tmp/rpg_test_save.sav";
    save::write(path, p, w, "home");

    // Восстанавливаем в другой Player/World
    Player p2("Other", 50);
    World w2;
    Location loc2("home", "Дом", "Тут уютно.");
    w2.add(std::move(loc2));
    std::string cur;
    save::read(path, p2, w2, cur);

    CHECK_EQ(s, p2.name(), std::string("Hero"));
    CHECK_EQ(s, p2.hp(), 70);
    CHECK_EQ(s, p2.max_hp(), 100);
    CHECK_EQ(s, cur, std::string("home"));
    CHECK_EQ(s, p2.inventory().items().size(), static_cast<std::size_t>(1));
}
```

**Roundtrip тест**: записали → прочли → проверили совпадение. Если что-то сломали в сериализации — тест упадёт.

## Сборка на нескольких платформах

`Makefile` мы заточили под GCC/Clang с Unix-инструментами. Это работает:
- **macOS** — clang/g++ из Xcode Command Line Tools (глава 6).
- **Linux** — gcc из `build-essential`.
- **Windows + WSL2** — Linux-окружение в Windows.

Что **не работает** на нативном Windows (без WSL):
- `mkdir -p` — на Windows это другое.
- `rm -rf` — на cmd.exe нет `rm`.
- Возможно проблемы с UTF-8 в исходниках (MSVC требует особых флагов).

Решений несколько:

**1. Использовать CMake** вместо Makefile. CMake генерирует Visual Studio проекты на Windows, Makefile на Unix, Ninja-файлы — везде.

```cmake
cmake_minimum_required(VERSION 3.10)
project(rpg CXX)
set(CMAKE_CXX_STANDARD 11)

add_executable(rpg
    src/main.cpp
    src/game.cpp
    src/commands.cpp
    src/item.cpp
    src/inventory.cpp
    src/location.cpp
    src/player.cpp
    src/world.cpp
    src/world_parser.cpp
    src/save_manager.cpp
)
target_include_directories(rpg PRIVATE include)
target_compile_options(rpg PRIVATE -Wall -Wextra)
```

Команда:
```bash
$ cmake -B build
$ cmake --build build
```

Получаете `build/rpg` независимо от платформы.

**2. WSL2 на Windows.** Простейший вариант: пользователь на Windows ставит WSL2, дальше всё как на Linux.

**3. Условные правила в Makefile.** Можно усложнить наш Makefile, чтобы он автоопределял ОС:

```makefile
ifeq ($(OS),Windows_NT)
    MKDIR := mkdir
    RM    := rmdir /S /Q
else
    MKDIR := mkdir -p
    RM    := rm -rf
endif
```

— и так далее. Возможно, но рассыпает простоту.

Для учебной книги — **простой Makefile + рекомендация WSL на Windows**. На реальном проекте перешли бы на CMake.

## Что покрыли в C++

Полезно перечислить, что именно из языка пошло в дело — не в виде списка тем из оглавления, а по месту применения.

Из основ работает всё, что было в Части I. Типы и переменные — в каждой строке. Ветвления и циклы, в том числе цикл по диапазону, — в обходах инвентаря и выходов из локации. Разные способы передачи параметров: по значению там, где объект дешёвый, по константной ссылке для чтения, по значению с последующим перемещением для передачи владения. Память на стеке и в куче с освобождением по правилу RAII. Строки и потоки ввода-вывода — в парсере мира и в сохранении. Контейнеры `vector` и `unordered_map` — в инвентаре и в мире. Алгоритмы `find_if`, `sort` и `replace`.

Из продвинутого в проекте задействовано почти всё, о чём шла речь в Части II. Классы с инкапсуляцией — `Player`, `Location`, `World`, `Inventory`, `Item`. Списки инициализации в конструкторах и правильная расстановка `const` у методов и параметров. Наследование с виртуальными методами, `override`, `final`, виртуальным деструктором и чистыми виртуальными функциями — иерархия предметов. Запрет копирования через `= delete` там, где объект владеет уникальным ресурсом. Умные указатели `std::unique_ptr<Item>` в инвентаре и перемещение вместо копирования при передаче предметов. Шаблоны — `EventBus<T>` и наш собственный `make_unique<T>` с переменным числом аргументов и совершенной передачей. Лямбды с захватами и `std::function` в реестре команд. Исключения со своей иерархией и строгой гарантией безопасности в загрузке сохранения. Разбор текстовых файлов, сериализация в файл и обратно, контрольная сумма для проверки целостности. И пространства имён, которыми всё это разложено по местам.

Список выглядит внушительно, но суть не в количестве. Суть в том, что каждая из этих вещей появилась не сама по себе, а потому что понадобилась: виртуальный деструктор — когда предметы стали храниться по указателю на базу, перемещение — когда предмет понадобилось передать из локации игроку, исключения — когда обнаружилось, что ошибку загрузки некуда возвращать. Этого достаточно, чтобы читать почти любой C++-проект из открытых источников; незнакомые места останутся, но словарь у вас уже есть.

## Что осталось «за кадром»

Игру можно расширять, и дизайн для этого готов. Перечислю направления — не как список задач, а чтобы показать, куда именно ложится каждое расширение в уже существующей архитектуре.

Бой требует нового класса `Enemy` с очками здоровья и уроном, команды `attack` в реестре команд и обработки смерти — игрока или врага. Класс предметов трогать не придётся: оружие уже знает свой урон, а `dynamic_cast` из главы 17 позволит найти оружие в инвентаре.

Задания — это состояние, которого у нас пока нет: у игрока появляется список взятых заданий, а у локаций — персонажи, которые их выдают. Проверка выполнения удобно ложится на шину событий: подписались на событие «предмет подобран» и сверяем с условием задания.

Несколько персонажей означают, что сохранение перестаёт быть одним файлом. Формат менять не придётся — достаточно завести каталог на игрока, и как раз пригодится версия формата, которую мы заложили в главе 24.

Шина событий сейчас используется в одном месте. С ней можно сделать журнал всего урона, систему достижений, звуковые эффекты — всё это подписчики, о которых издатель ничего не знает. Это и есть польза от разделения, ради которого она затевалась.

Оформление в терминале — библиотека `ncurses` на Unix или `PDCurses` на Windows: псевдо-окна, цвета, карта мира в виде рисунка из символов. Настоящая графика — SDL2 или SFML — тоже возможна, но это уже другая книга.

Сетевая игра — несколько игроков в одном мире через TCP. После Части V навыков для этого хватит; правда, придётся решать вопросы, которых нет в одиночной игре: одновременные действия, согласование состояния, что делать при обрыве связи.

Ни одно из этих расширений не требует ломать существующее — новые классы добавляются рядом, новые команды регистрируются в реестре, новые подписчики появляются у шины. Это и есть проверка архитектуры на прочность.

## Если бы это шло в работу

Учебный проект и рабочий отличаются не кодом, а обвязкой. Вот чего в нашем не хватает, если бы его пришлось выпускать всерьёз.

Сборка через CMake вместо Makefile — чтобы собиралось на трёх системах без правок. Тесты на готовом фреймворке вроде GoogleTest или Catch2 — со внятными сообщениями и запуском по маске. Непрерывная интеграция, которая на каждый коммит собирает проект на Linux, macOS и Windows и прогоняет тесты; без неё тесты рано или поздно перестают запускать.

Единый стиль кода, поддерживаемый `clang-format`, чтобы споры о расстановке скобок закончились раз и навсегда. Статический анализ `clang-tidy`, который находит подозрительные места до запуска. Санитайзеры адресов и неопределённого поведения в отладочной сборке.

Для парсеров — фаззинг: автоматическая подача случайного мусора в `world_parser` и загрузчик сохранений, чтобы найти падения, до которых не додумался бы ни один тест. Наш разбор мира к такому обращению, скорее всего, не готов, и это стоило бы проверить.

Плюс измерение покрытия тестами, документация в исходниках для `doxygen` и нормальное журналирование вместо печати в поток вывода.

Каждый пункт — от получаса до дня работы, а вместе они превращают «работает у меня» в «работает у всех». Для учебного проекта мы сделали разумный минимум: тесты, разделение на модули, обработка ошибок, версия формата.

В Части V сделаем сетевой чат: сокеты, потоки, цикл событий, свой двоичный протокол. Часть VI, короткая, покажет, что добавили к языку стандарты после C++11.

Каждая часть — отдельный проект в своей папке: `demo-shell/`, `demo-db/`, `demo-chat/`. Структура везде та же, что в RPG: заголовки в `include/`, реализации в `src/`, проверки в `tests/`, сборка одним `make`.

## Главные правила главы

1. Тесты нужны не ради процента покрытия, а ради возможности менять код и сразу узнавать, что сломалось.
2. Один класс — один тестовый файл; свалка из всех проверок в одном месте перестаёт читаться на третьей сотне строк.
3. Проверка «записал, прочитал, сравнил» — самый ценный вид теста для любой сериализации.
4. Тесты, которые не запускаются автоматически, живут ровно до тех пор, пока о них помнят.
5. Makefile хорош для учёбы, CMake — для проекта, который собирают на разных системах.
6. Санитайзеры адресов и неопределённого поведения должны быть включены в отладочной сборке, а не откладываться на потом.
7. Хорошая архитектура проверяется добавлением новой возможности: если для этого не пришлось трогать старое — она хорошая.
8. Цель — не запомнить синтаксис, а научиться разбирать задачу; синтаксис доучивается по справочнику.

## Маленькое упражнение

1. Запустите `make tests && ./build/tests/test_units`. Все 37 прошли?

2. Поломайте одну строку в `Player::heal` (например, уберите ограничение по max_hp). Запустите тесты — увидите fail.

3. Добавьте тест для команды `cmd_take`: создайте `Game`, имитируйте ввод (это сложно для CLI; можно через `Game::cmd_take(...)` напрямую через friend или public метод для теста).

4. Установите CMake (`brew install cmake` или `apt install cmake`). Напишите `CMakeLists.txt` по примеру выше. Соберите через `cmake -B build && cmake --build build`.

5. Реализуйте класс `Enemy` (имя, hp, damage). Добавьте поддержку в `world.txt`: `enemy гоблин 10 3` — кладёт врага в локацию. В `cmd_look` показывайте врагов.

6. Реализуйте команду `attack <enemy>` — пошаговый бой. Используйте `dynamic_cast` для определения «оружия» в инвентаре игрока.

7. (Сложнее) Добавьте `EventBus<DamageEvent>` в `Game`. Подпишите логгер в `register_commands`. В команде `attack` публикуйте события — увидите, как декаплинг работает.

8. (Сложнее) Прогоните игру под **AddressSanitizer**:
   ```bash
   make CXXFLAGS="-std=c++11 -Wall -fsanitize=address -g"
   ```
   Если ASan находит проблему — это серьёзный сигнал. Чистая программа не должна ничего давать.

# Глава 7. Как программа становится исполняемым файлом

В главе 6 мы написали `hello.cpp`, скомпилировали и запустили. И вскользь упомянули, что компиляция идёт в четыре стадии: препроцессинг → компиляция → ассемблирование → линковка. В этой главе разбираем каждую стадию подробно. Что именно происходит, какие файлы появляются на каждом шаге, как выглядят их «потроха», что такое объектный файл, что такое символ, в чём разница между статической и динамической линковкой, и как программа лежит в памяти процесса.

Эта тема — фундамент, на котором всё дальнейшее построено. Без понимания, что компиляция многоступенчатая, и что «ошибка компиляции» отличается от «ошибки линковки», вы будете тонуть в сообщениях gcc/clang ближе к проектам. Поэтому глава длинная, но я постараюсь обойтись без лишней теории — будем смотреть на реальные файлы и команды.

## Подопытная программа

Чтобы было что разбирать, заведём чуть более интересный пример, чем простой hello. Сделаем программу из двух файлов: главного `main.cpp` и вспомогательного `math.cpp` с функцией сложения.

Создайте папку и три файла.

`math.h`:
```cpp
#ifndef MATH_H
#define MATH_H

int add(int a, int b);

#endif
```

`math.cpp`:
```cpp
#include "math.h"

int add(int a, int b) {
    return a + b;
}
```

`main.cpp`:
```cpp
#include <iostream>
#include "math.h"

int main() {
    int x = add(2, 3);
    std::cout << "2 + 3 = " << x << std::endl;
    return 0;
}
```

Три файла. Я их буду использовать на протяжении всей главы. Кратко скажу, что тут происходит — детали разберём по ходу.

В `math.h` лежит **объявление** функции `add` — обещание, что где-то есть функция с таким именем, принимающая два `int` и возвращающая `int`. Сам код функции тут не написан.

`#ifndef MATH_H ... #define MATH_H ... #endif` — это **защита от двойного включения** (include guard). Если этот заголовочный файл случайно попадёт в перевод дважды (например, его подключают два других файла, которые в свою очередь подключаются обоим), компилятор увидит, что `MATH_H` уже определён, и пропустит содержимое второй раз. Без этой защиты получим ошибку «redefinition of `add`». Подробнее про препроцессор — ниже.

В `math.cpp` лежит **определение** функции — собственно её код. Тут она `return a + b`.

В `main.cpp` функция `add` используется. Чтобы компилятор знал, что такая функция существует и что она принимает/возвращает, в начале файла подключаем `math.h` (через `#include "math.h"`). А определение функции живёт в `math.cpp` и попадёт в программу через линковку.

Это классическое разделение в C/C++: **заголовочный файл (`.h`)** — объявления, чтобы все знали, что есть такая функция; **исходный файл (`.cpp`)** — определения, реальные тела функций.

Соберём программу одной командой и убедимся, что работает:

```bash
$ g++ -std=c++11 main.cpp math.cpp -o program
$ ./program
2 + 3 = 5
```

Прекрасно. Теперь — препарируем процесс.

## Стадия 1: препроцессор

Препроцессор — это первая стадия компиляции. Программа, отвечающая за неё, исторически называется `cpp` (C Pre-Processor; не путать с C++!). Что она делает?

**Препроцессор работает с текстом.** Он не понимает C++. Он не знает, что такое функция, что такое класс, что такое тип `int`. Для него файл `main.cpp` — это просто последовательность символов. Он ищет строчки, начинающиеся с `#`, и применяет к ним свои правила.

Самое частое — `#include`. Когда препроцессор видит `#include <iostream>`, он буквально берёт содержимое файла `iostream` из стандартной библиотеки и **вставляет его прямо в это место**. Текстуально, без анализа.

Также препроцессор обрабатывает:
- `#define X Y` — макросы. После этой строки везде в файле `X` будет заменяться на `Y`.
- `#ifdef`, `#ifndef`, `#endif` — условная компиляция. Куски кода включаются или исключаются в зависимости от того, определён ли тот или иной макрос.
- `#pragma` — указания компилятору (нестандартные расширения).
- Комментарии (хоть и не через `#`) — препроцессор их удаляет.

После работы препроцессора на выходе — один большой «развёрнутый» файл, в котором все `#include` подставлены, макросы развёрнуты, комментарии удалены.

### Посмотрим своими глазами

GCC и Clang позволяют остановиться после препроцессора, флаг `-E`:

```bash
$ g++ -std=c++11 -E main.cpp -o main.i
$ wc -l main.i
40826 main.i
```

40 тысяч строк! Из наших 9 строк! Что произошло?

Откройте `main.i` любым редактором. Сверху увидите содержимое `iostream`, потом всех других файлов, которые `iostream` тянет за собой (а тянет он много — около сорока тысяч строк). А внизу, среди этой простыни, найдёте знакомое:

```cpp
int add(int a, int b);

int main() {
    int x = add(2, 3);
    std::cout << "2 + 3 = " << x << std::endl;
    return 0;
}
```

Это и есть наш код. Заметили: `#include <iostream>` исчез — на его месте теперь буквально содержимое iostream. `#include "math.h"` тоже исчез — на его месте `int add(int a, int b);`.

### Макросы

Препроцессор может ещё определять и подставлять **макросы**. Пример:

`main.cpp`:
```cpp
#include <iostream>

#define PI 3.14159
#define SQUARE(x) ((x) * (x))

int main() {
    std::cout << "Pi = " << PI << std::endl;
    std::cout << "5 squared = " << SQUARE(5) << std::endl;
    return 0;
}
```

После препроцессора код превращается в:

```cpp
int main() {
    std::cout << "Pi = " << 3.14159 << std::endl;
    std::cout << "5 squared = " << ((5) * (5)) << std::endl;
    return 0;
}
```

Каждое упоминание `PI` буквально заменилось на `3.14159`. Каждое упоминание `SQUARE(x)` развернулось в выражение `((x) * (x))`.

В C макросы были основным способом «не повторяться». В C++ макросы остаются, но их использование сократилось — вместо них есть `constexpr`-константы, `inline`-функции, шаблоны. Они почти всегда лучше макросов, потому что:

- Макрос — это текстовая замена; в нём нет понятия «тип». Если написать `SQUARE("hello")` — препроцессор просто подставит и оставит компилятору разбираться. Компилятор скажет «нельзя умножить строку на строку», но указание ошибки будет на сгенерированной строке, а не на той, где вы написали `SQUARE`.
- Макросы не видны отладчику.
- Макросы не уважают границы пространств имён.

Тем не менее макросы остаются: include guard (`#ifndef MATH_H` в нашем `math.h`) — это макрос. Условная компиляция (`#ifdef __APPLE__` — «выполнять этот блок только на macOS») — макросы. Платформенно-зависимый код часто полагается на макросы.

### Условная компиляция

Допустим, мы хотим, чтобы наш код по-разному работал на Linux и на macOS:

```cpp
#include <iostream>

int main() {
#ifdef __APPLE__
    std::cout << "Running on macOS\n";
#elif defined(__linux__)
    std::cout << "Running on Linux\n";
#elif defined(_WIN32)
    std::cout << "Running on Windows\n";
#else
    std::cout << "Running on something else\n";
#endif
    return 0;
}
```

Эти `__APPLE__`, `__linux__`, `_WIN32` — макросы, которые компилятор сам определяет в зависимости от того, на какой системе он работает. Препроцессор смотрит, что определено, и оставляет в коде только подходящий блок.

После препроцессора на macOS у вас в файле будет:

```cpp
int main() {
    std::cout << "Running on macOS\n";
    return 0;
}
```

Никаких других веток нет — препроцессор их выкинул. Это **условная компиляция**. На больших проектах ей пользуются часто, чтобы единый код собирался под разные платформы.

### Include guard детальнее

Раз про `#ifndef MATH_H` уже несколько раз говорили, разберём окончательно.

Допустим, у нас три файла:

`a.h`:
```cpp
struct Point { int x; int y; };
```

`b.h`:
```cpp
#include "a.h"
void draw(Point p);
```

`main.cpp`:
```cpp
#include "a.h"
#include "b.h"

int main() {
    Point p{1, 2};
    draw(p);
    return 0;
}
```

После препроцессора `main.cpp` превратится в:

```cpp
struct Point { int x; int y; };    // из a.h, через прямой include
struct Point { int x; int y; };    // из a.h, через b.h
void draw(Point p);                 // из b.h
                                    // (main.cpp дальше)
int main() {
    Point p{1, 2};
    draw(p);
    return 0;
}
```

`Point` объявлен дважды! Компилятор ругнётся: «redefinition of `struct Point`». Это и есть проблема двойного включения.

Решается стандартной защитой:

`a.h`:
```cpp
#ifndef A_H
#define A_H

struct Point { int x; int y; };

#endif
```

Теперь, когда `a.h` подключается первый раз, `A_H` не определён, препроцессор заходит внутрь, определяет `A_H` и оставляет объявление `Point`. Когда `a.h` подключается второй раз (через `b.h`), `A_H` уже определён — препроцессор пропускает весь блок до `#endif`. `Point` объявлен ровно один раз.

В современном коде защиту иногда заменяют на `#pragma once`:

```cpp
#pragma once

struct Point { int x; int y; };
```

Это нестандартное расширение, но его поддерживают все основные компиляторы. Удобнее (одна строка вместо трёх), но менее портабельно.

### Что выучить про препроцессор

- Препроцессор работает с текстом, до компилятора.
- `#include <header>` — буквально подставляет содержимое.
- `#include "header.h"` — то же, но в первую очередь ищет в папке исходника.
- `#define` создаёт макрос. Старайтесь избегать макросов; для констант используйте `constexpr`, для функций — `inline` или шаблоны.
- Каждый `.h`-файл должен иметь защиту от двойного включения (`#ifndef`/`#define`/`#endif` или `#pragma once`).
- Платформенно-зависимый код пишут через `#ifdef`.

## Стадия 2: собственно компиляция

После препроцессора мы получили развёрнутый текст. Теперь **компилятор** (в узком смысле — программа `cc1plus` внутри g++) превращает его в **ассемблерный код** для целевой архитектуры.

Здесь происходит самое интересное:

1. **Лексический анализ.** Текст разбивается на «токены»: `int`, `main`, `(`, `)`, `{`, и так далее.
2. **Синтаксический анализ.** Из токенов строится **AST** (abstract syntax tree) — дерево, отражающее структуру программы. Узел «функция main» с дочерним узлом «тело», в теле — узел «вызов функции add», и так далее.
3. **Семантический анализ.** Компилятор проверяет, что всё имеет смысл: типы совместимы, имена существуют, функции вызываются с правильным числом аргументов.
4. **Оптимизация.** Компилятор смотрит на код и переписывает его так, чтобы он делал то же самое, но эффективнее. Например, `int x = 2 + 3;` он сразу заменит на `int x = 5;` — это называется constant folding.
5. **Генерация кода.** AST превращается в ассемблерные инструкции под нужную архитектуру.

Если на любой из стадий компилятор найдёт проблему — это **ошибка компиляции**. Например, «`add` is not declared in this scope» — на стадии семантического анализа.

Остановимся после компилятора:

```bash
$ g++ -std=c++11 -S main.cpp -o main.s
$ wc -l main.s
80 main.s
```

Откройте `main.s` — это ассемблер для вашей архитектуры. На Mac M3 (ARM64) выглядит примерно так:

```asm
_main:
    sub sp, sp, #48
    stp x29, x30, [sp, #32]
    add x29, sp, #32
    mov w8, #2
    str w8, [sp, #8]
    mov w8, #3
    str w8, [sp, #4]
    ldr w0, [sp, #8]
    ldr w1, [sp, #4]
    bl _Z3addii
    ...
```

Под x86-64 (Intel/AMD) другой синтаксис, но смысл тот же. Каждая строка — одна инструкция.

Что тут особенно интересно: строчка `bl _Z3addii`. `bl` — это «branch with link», то есть вызов функции на ARM64. А `_Z3addii` — это имя функции `add`, преобразованное компилятором.

«Зачем имя так искорёжено?», — справедливый вопрос. Это называется **name mangling**.

### Манглинг имён

В C функции называются буквально так, как вы их написали: `add` — это `add`. Это удобно, но непригодно для C++, где функции могут быть **перегружены**:

```cpp
int add(int a, int b);
double add(double a, double b);
int add(int a, int b, int c);
```

Три разные функции, все называются `add`. Как линкер их отличит? Никак, если имена одинаковые.

Поэтому компилятор C++ «кодирует» в имя функции типы её параметров. На GCC/Clang используется схема Itanium ABI:
- `_Z3addii` = функция `add` с двумя `int` (`i` = int).
- `_Z3adddd` = функция `add` с двумя `double` (`d` = double).
- `_Z3addiii` = функция `add` с тремя `int`.

Линкер видит эти разные имена и спокойно различает.

На MSVC (Microsoft) используется другая схема манглинга, со своими правилами.

Чтобы посмотреть «человеческое» имя из «искорёженного», есть утилита `c++filt`:

```bash
$ echo "_Z3addii" | c++filt
add(int, int)
```

Очень полезно, когда вы видите в сообщении об ошибке «undefined reference to `_Z6lambda...`».

Иногда нужно отключить манглинг — например, при экспорте функций для C-кода. Для этого пишут `extern "C"`:

```cpp
extern "C" int my_function(int x);
```

В этом случае компилятор имени `my_function` не трогает — линкер видит её как `my_function`. Это используется при создании библиотек, чтобы их могли использовать программы на других языках.

### Что выучить про компиляцию

- Компилятор разбирает текст, проверяет смысл, и генерирует ассемблер.
- Ошибки компиляции — несовместимые типы, неизвестные имена, синтаксические ошибки.
- C++-имена кодируются (mangle) для поддержки перегрузки.
- Узнать «реальное» имя — через `c++filt`.

## Стадия 3: ассемблирование

После компилятора у нас текстовый ассемблерный файл. Теперь его надо превратить в **машинный код**. Этим занимается **ассемблер** (программа `as`).

Ассемблер — простая программа. Она берёт ассемблерный текст и для каждой инструкции находит её бинарный опкод. На выходе — **объектный файл**.

```bash
$ g++ -std=c++11 -c main.cpp -o main.o
$ file main.o
main.o: Mach-O 64-bit object x86_64
# или, на ARM64 Mac:
main.o: Mach-O 64-bit object arm64
# на Linux:
main.o: ELF 64-bit LSB relocatable, x86-64, ...
```

Это уже бинарный файл. Прочитать как текст не получится — увидите кракозябры. Но есть утилиты для просмотра.

### Внутри объектного файла

Объектный файл — это **не** просто массив машинных инструкций. Это структурированный формат, в котором есть:

1. **Секция кода (.text)** — собственно машинный код функций.
2. **Секция данных (.data)** — глобальные и статические переменные с начальным значением.
3. **Секция BSS (.bss)** — глобальные и статические переменные без начального значения (обнуляются автоматически при загрузке).
4. **Секция read-only (.rodata)** — константы, строковые литералы.
5. **Таблица символов** — список всех функций и переменных, которые объявлены в этом файле.
6. **Таблица релокаций** — список «дырок», где нужно подставить адреса других функций/переменных при линковке.

На разных платформах форматы разные:
- **Linux** — ELF (Executable and Linkable Format).
- **macOS** — Mach-O.
- **Windows** — COFF/PE (Portable Executable).

Все они идейно похожи: секции, символы, релокации.

### Смотрим на символы

Утилита `nm` показывает символы внутри объектного файла:

```bash
$ nm main.o
                 U __ZSt4cout
                 U __ZSt4endl
                 U __Z3addii
0000000000000000 T _main
                 U __ZNSolsEi
                 U __ZNSolsEPKc
```

Буква перед именем (`U`, `T`, и так далее) — это тип символа:
- `T` (text) — символ определён в этом файле, в секции кода. У нас `_main` — определён.
- `U` (undefined) — символ нужен, но не определён здесь. Например, `__Z3addii` — это `add(int, int)`, и наш `main.o` ждёт, что она будет где-то определена.
- `D` (data) — определён в секции данных (глобальная переменная с инициализацией).
- `B` (bss) — определён в секции BSS (глобальная переменная без инициализации).
- `R` (rodata) — определён в read-only секции (константа).

Теперь сделаем `math.o`:

```bash
$ g++ -std=c++11 -c math.cpp -o math.o
$ nm math.o
0000000000000000 T __Z3addii
```

Видим: `__Z3addii` (то есть `add(int, int)`) **определён** в `math.o` (`T`). А в `main.o` он был **не определён** (`U`).

Это и есть основа линковки. У одного объектного файла есть «дырка» — символ, нужный, но не определённый. У другого этот же символ есть в готовом виде. Линкер их соединит.

### Утилита `objdump`

`objdump` показывает содержимое объектного файла подробнее. Например:

```bash
$ objdump -d main.o | head -30
main.o:	file format mach-o-x86-64

Disassembly of section __TEXT,__text:

_main:
       0:	push    %rbp
       1:	mov     %rsp, %rbp
       4:	sub     $0x20, %rsp
       8:	movl    $0x0, -0x4(%rbp)
       f:	movl    $0x2, %edi
      14:	movl    $0x3, %esi
      19:	callq   0x1e <_main+0x1e>
      1e:	...
```

Это уже почти то же самое, что в `.s`-файле, только с числовыми смещениями. `callq 0x1e` — это вызов функции по смещению `0x1e`. Сейчас оно ссылается само на себя (компилятор не знал куда указать). Линкер потом подставит правильный адрес.

## Стадия 4: линковка

Самая интересная стадия. У нас есть два объектных файла: `main.o` и `math.o`. Линкер их соединит, разрешит все «дырки», и получит финальный исполняемый файл.

```bash
$ g++ main.o math.o -o program
$ ./program
2 + 3 = 5
```

Или, что то же самое, одной командой:

```bash
$ g++ main.cpp math.cpp -o program
```

Под капотом происходит:

1. Линкер читает все объектные файлы.
2. Собирает таблицу всех символов: какие определены где.
3. Для каждого символа `U` в каком-то файле ищет, где этот символ `T` (определён) — в других объектных файлах или в библиотеках.
4. Соединяет секции: все `.text` склеиваются в одну, все `.data` — в одну, и так далее.
5. Корректирует все ссылки: где была «дырка» с именем — подставляет реальный адрес.
6. Получается готовый исполняемый файл.

### А стандартная библиотека?

Замечу: в `main.o` были «undefined» символы вроде `__ZSt4cout` (это `std::cout`). Откуда они придут?

Из **стандартной библиотеки**. Когда вы вызываете `g++`, он автоматически добавляет в линковку стандартную библиотеку C++ (libstdc++ на Linux, libc++ на macOS). Туда зашит код `std::cout`, `std::endl`, всех контейнеров, и так далее.

Если бы вы делали линковку вручную через `ld` (а не через `g++` как обёртку), вам пришлось бы явно указывать эти библиотеки. Поэтому-то и используют `g++` как обёртку — он знает, какие библиотеки нужно подцепить.

### Сообщения об ошибках линковки

Самые частые ошибки этой стадии:

**`undefined reference to <symbol>`**

Линкер нашёл «дырку», но не нашёл, чем её заполнить. Возможные причины:
- Забыли скомпилировать нужный .cpp файл. Например, написали `g++ main.cpp -o program` без `math.cpp` — `add` неоткуда взять.
- Объявили функцию, но не написали её тело.
- Не подключили нужную внешнюю библиотеку (флаг `-l`).
- Перепутали манглинг (например, `extern "C"` где надо/не надо).

**`multiple definition of <symbol>`**

Два или больше определений одной функции. Линкер не знает, какое выбрать. Часто случается, когда определение функции случайно попадает в заголовочный файл, который подключается из нескольких `.cpp`-файлов.

Пример. Если бы мы в `math.h` написали не объявление, а определение:

```cpp
// math.h
#ifndef MATH_H
#define MATH_H

int add(int a, int b) {    // ОШИБКА — определение в заголовке!
    return a + b;
}

#endif
```

И этот заголовок подключился бы в `main.cpp` и `math.cpp` — после препроцессинга в обоих файлах оказался бы код `add`. После компиляции — два определения в двух `.o`. Линкер: «multiple definition».

Решение: в заголовках — только объявления. Определения — в `.cpp`. (Исключение: шаблоны и `inline`-функции должны быть полностью в заголовках, об этом в главе 20.)

### Статическая и динамическая линковка

Линковка бывает двух видов.

**Статическая линковка.** Все нужные функции из библиотек **копируются прямо в исполняемый файл**. Получается «жирный» бинарь, который работает сам по себе: библиотеки больше не нужны.

Плюсы:
- Можно запустить на любом компьютере (нужной версии ОС/архитектуры) без необходимости иметь установленные библиотеки.
- Не зависит от версий библиотек в системе.

Минусы:
- Большой размер бинарника.
- Если в библиотеке нашли уязвимость — нужно пересобрать программу, чтобы обновить.

**Динамическая линковка.** Линкер только записывает в исполняемый файл «здесь надо подгрузить такую-то библиотеку, и оттуда взять такую-то функцию». Сама библиотека лежит отдельным файлом и подгружается операционной системой при запуске программы.

Файлы динамических библиотек:
- `*.so` (Shared Object) на Linux.
- `*.dylib` на macOS.
- `*.dll` (Dynamic Link Library) на Windows.

Плюсы:
- Маленький размер бинарника.
- Можно обновить библиотеку в системе — и все программы, использующие её, автоматически получат свежую версию.
- Память экономится: если 50 программ используют libc — она в памяти один раз, не 50.

Минусы:
- Нужно, чтобы библиотеки требуемых версий были в системе.
- Знаменитый «DLL hell» — программа жаждет версию X.Y, а в системе X.Z, и не работает.

По умолчанию компиляторы используют **динамическую линковку для стандартной библиотеки и системных библиотек**, и **статическую для ваших объектных файлов**. То есть `main.o` + `math.o` слипаются в один бинарник, а libstdc++ подгружается во время запуска.

Узнать, какие динамические библиотеки нужны программе:

```bash
$ ldd ./program   # на Linux
linux-vdso.so.1 (0x00007fff...)
libstdc++.so.6 => /lib/x86_64-linux-gnu/libstdc++.so.6
libm.so.6 => /lib/x86_64-linux-gnu/libm.so.6
libgcc_s.so.1 => /lib/x86_64-linux-gnu/libgcc_s.so.1
libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6
/lib64/ld-linux-x86-64.so.2 (0x00007f...)

$ otool -L ./program   # на macOS
./program:
    /usr/lib/libc++.1.dylib
    /usr/lib/libSystem.B.dylib
```

Чтобы собрать статически (всё внутрь бинарника):

```bash
$ g++ -static main.cpp math.cpp -o program
```

После этого `ldd program` покажет «not a dynamic executable». Размер бинаря вырастет в десятки раз (с ~30 KB до ~2-5 MB), потому что вся стандартная библиотека теперь внутри. На macOS полностью статическая линковка не поддерживается (Apple использует dyld и не разрешает статически линковать libc) — там можно только частично.

Статическую сборку часто используют для Docker-контейнеров минимального размера (образ `scratch` + статический бинарь), для подачи бинаря на сервер без установки зависимостей, для embedded-устройств.

### Что выучить про линковку

- Линковка склеивает несколько `.o` файлов и библиотек в один исполняемый файл.
- «Undefined reference» — линкер не нашёл нужный символ. Проверьте, что нужный `.cpp` тоже компилируется и подключается.
- «Multiple definition» — символ определён в нескольких местах. В заголовках только объявления, не определения.
- Динамическая линковка — библиотеки подгружаются при запуске; статическая — копируются в бинарник.
- `ldd` / `otool -L` показывают, от каких библиотек зависит бинарник.

## Memory layout: что где лежит в памяти процесса

Программа собрана, бинарник готов. Запускаем — что происходит в памяти?

Операционная система создаёт **процесс** (вспомните главу 1) и **отображает виртуальное адресное пространство процесса** на физическую память. В этом адресном пространстве у программы есть несколько ключевых областей.

Если идти от низких адресов к высоким (типичная картина на Linux x86-64):

### .text (код)

В самом низу — секция **.text**. Это машинный код вашей программы: функции `main`, `add`, всё, что вы написали. Эта секция помечена как **read-only** и **executable**: процессор может её исполнять, но никто не может в неё писать. Если программа попытается записать в код — получит segfault (нарушение защиты памяти).

Это защита от того, чтобы программа случайно (или вирусно) не модифицировала собственный код во время работы.

### .rodata (константы)

Чуть выше — секция **.rodata** (read-only data). Здесь лежат:
- Строковые литералы: `"Hello, world!"`, `"2 + 3 = "`.
- `const`-константы с фиксированными значениями.
- Виртуальные таблицы классов (vtable) — про них в главе 17.

Эта секция тоже read-only. Если вы возьмёте указатель на строковый литерал и попытаетесь через него что-то записать — segfault.

```cpp
char* p = (char*)"hello";
p[0] = 'H';   // segfault!
```

### .data (инициализированные глобальные)

**.data** — глобальные и `static`-переменные с **ненулевым** начальным значением.

```cpp
int counter = 5;          // окажется в .data
static int max_size = 100; // тоже в .data
```

Эта секция read-write. Программа может изменять эти переменные во время работы.

### .bss (неинициализированные глобальные)

**.bss** — глобальные и `static`-переменные **без** начального значения (или с явным `= 0`). Они автоматически зануляются при загрузке.

```cpp
int errors;        // окажется в .bss, значение 0
int counters[1000]; // .bss, все нули
```

Почему отдельная секция? Потому что .bss занимает в бинарнике ровно ноль байт — там просто записано «у меня нужно столько-то нулей». Заполнение нулями делает уже ОС, при загрузке. Экономия места на диске.

### Куча (heap)

Дальше идёт **куча** (heap). Это область, из которой программа **динамически выделяет** память во время работы. Когда вы пишете `new int` или `malloc(100)`, ОС выделяет вам кусок из кучи. Когда вы вернёте через `delete` или `free`, кусок возвращается.

Куча растёт вверх (от низких адресов к высоким) по мере роста потребностей программы. Размер ограничен либо настройками ОС, либо физической памятью.

Куча — это про **долгоживущие** объекты. Например, дерево комнат в нашем RPG-проекте будет жить в куче, потому что оно должно существовать на протяжении всей игры, а не «пока выполняется одна функция».

### Mmap-области

Где-то посередине между кучей и стеком (на современных ОС) живут **отображённые в память** регионы. Сюда подгружаются динамические библиотеки (`libstdc++.so`, `libc.so`). Сюда же попадают большие выделения через `mmap` (например, когда вы запрашиваете у ОС 100 MB одним куском).

Это нюанс — для понимания общей картины можно пропустить.

### Стек (stack)

В самой верхней части адресного пространства — **стек**. Растёт вниз, в сторону кучи.

Стек — это **локальные переменные функций**, аргументы вызовов, адреса возврата. Когда вы вызываете функцию, на стек кладётся:
- адрес, куда вернуться после функции (return address);
- значения аргументов;
- место под локальные переменные.

Когда функция возвращается — этот «кадр стека» (stack frame) убирается, и стек уменьшается.

Стек — это про **короткоживущие** объекты. Локальная переменная `int x = 5;` внутри `main` — на стеке. Когда `main` закончится — `x` исчезнет автоматически.

```cpp
void foo() {
    int local = 42;    // на стеке
}                      // local исчезает здесь
```

### Картинка целиком

Адреса в типичном Linux-процессе x86-64 (упрощённо):

```
Высокие адреса
+-----------------------+
|       Stack           |  ← растёт вниз
|         ↓             |
|                       |
|       ...             |
|                       |
|  Mmap'd libraries     |
|       ...             |
|                       |
|         ↑             |
|       Heap            |  ← растёт вверх
+-----------------------+
|       .bss            |
+-----------------------+
|       .data           |
+-----------------------+
|       .rodata         |
+-----------------------+
|       .text           |
+-----------------------+
Низкие адреса
```

Между стеком и кучей — большое пустое пространство, в которое они оба могут расти. Если стек дойдёт до кучи (или наоборот) — программа упадёт с переполнением.

### Утилита `size`

Чтобы увидеть размеры секций бинарника:

```bash
$ size program
__TEXT	__DATA	__OBJC	others	dec	hex
8192	4096	0	4295106560	4295119248	1000ff850
```

На Linux:

```bash
$ size program
   text    data     bss     dec     hex filename
   1820     608      24    2452     994 program
```

`text` — размер кода (.text + .rodata). `data` — инициализированных переменных. `bss` — неинициализированных (но в файле они не лежат, только размер).

### Стек: размер и переполнение

Размер стека по умолчанию — на Linux обычно **8 MB**, на macOS — **8 MB** для главного потока и **512 KB** для дополнительных потоков, на Windows — **1 MB**. Можно изменить:

```bash
$ ulimit -s 16384   # установить 16 MB
```

Стек кончается при глубокой рекурсии:

```cpp
void recur() {
    int big_array[10000]; // 40 KB на каждом вызове
    recur();
}
```

Эта функция вызывает себя бесконечно, каждый раз кладя на стек 40 KB. Через 200 вызовов стек кончится → **stack overflow** → программа упадёт.

Куча кончается сложнее — обычно вы упрётесь в физическую память раньше, чем в ограничение на размер кучи. На 64-битной системе виртуального пространства хватит на петабайты, а физического — на 16-64 GB обычно.

В Главе 11 «Память — стек, куча, RAII» эти штуки разберём подробно с C++-примерами.

## Полная картина: что происходит при сборке

Соберём весь процесс в одну схему. Команда `g++ main.cpp math.cpp -o program` выполняет:

1. **Препроцессор**: каждый `.cpp` файл проходит через cpp. Подставляются include'ы, разворачиваются макросы. На выходе — два развёрнутых файла (промежуточно, в памяти).

2. **Компилятор**: каждый развёрнутый файл проходит через cc1plus. Получается ассемблер. (Промежуточно.)

3. **Ассемблер**: каждый ассемблерный файл проходит через as. Получаются `main.o` и `math.o` (могут быть и не сохранены физически, если делаем одной командой).

4. **Линкер**: все объектные файлы плюс стандартная библиотека → исполняемый файл `program`.

Чтобы увидеть это в подробностях, есть флаг `-v` («verbose»):

```bash
$ g++ -v main.cpp math.cpp -o program
... много вывода ...
```

Увидите все запускаемые программы с их аргументами. Полезно, когда что-то не собирается и непонятно почему.

## Один важный нюанс: единицы трансляции

В C++ есть понятие **translation unit** (единица трансляции). Это **один .cpp-файл вместе со всеми include'ами**, развёрнутый препроцессором.

Каждый `.cpp`-файл — отдельная translation unit. Они компилируются независимо. Это значит:
- Изменения в одной TU не требуют пересборки остальных. Если поправили `math.cpp` — `main.cpp` пересобирать не надо, только новый `math.o` слинковать с старым `main.o`.
- Декларации, которые видны только внутри одной TU (через `static` или unnamed namespace), не видны другим.

Это основа **incremental builds**: на больших проектах системы сборки (Make, CMake, Bazel, ...) пересобирают только те TU, чьи зависимости изменились. На моём ноутбуке Lirotech компилируется с нуля 8 минут; инкрементно — 5 секунд.

Подробнее — в главе 15 (Дизайн проекта RPG) с Makefile.

## Маленькое упражнение

Заведите папку, создайте три файла из начала главы (`math.h`, `math.cpp`, `main.cpp`). Дальше:

1. Скомпилируйте каждый `.cpp` отдельно (флаг `-c`):
   ```bash
   $ g++ -std=c++11 -c main.cpp
   $ g++ -std=c++11 -c math.cpp
   ```
2. Посмотрите символы в каждом:
   ```bash
   $ nm main.o
   $ nm math.o
   ```
   Найдите символ `add` в обоих. В одном он должен быть `U` (нужен), в другом `T` (определён).
3. Слинкуйте:
   ```bash
   $ g++ main.o math.o -o program
   ```
4. Запустите.

Теперь нарочно сломайте линковку:

5. Скомпилируйте только `main.cpp`:
   ```bash
   $ g++ -std=c++11 main.cpp -o broken
   ```
   Что увидите? Изучите сообщение об ошибке.

6. В `main.cpp` замените `add(2, 3)` на `multiply(2, 3)`. Скомпилируйте только `main.cpp`:
   ```bash
   $ g++ -std=c++11 -c main.cpp
   ```
   Что произойдёт и почему? Это ошибка компиляции или линковки?

7. Посмотрите ассемблер:
   ```bash
   $ g++ -std=c++11 -S main.cpp -o main.s
   $ less main.s
   ```
   Найдите место вызова `add`. Обратите внимание на манглинг имени.

8. (Опционально) Посмотрите вывод препроцессора:
   ```bash
   $ g++ -std=c++11 -E main.cpp | wc -l
   ```
   Сколько строк? Откройте `g++ -E main.cpp -o main.i` и просмотрите. Найдите в конце своё `int main()`.

Эти упражнения покажут «вживую» все понятия главы. Если что-то не получается — перечитайте соответствующий раздел.

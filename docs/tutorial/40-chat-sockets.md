# Глава 40. Сокеты

Начинается Часть V, и в ней восемь глав мы будем писать сетевой чат. Сервер, клиент, свой двоичный протокол, комнаты, многопоточность, цикл событий, шифрование и упаковка в контейнер. Лежать всё это будет в `demo-chat/`.

Главной темой части станет одновременность. В Части III мы разговаривали с операционной системой, в Части IV боролись за корректность на диске — а здесь появится десяток клиентов, которые обращаются к серверу когда им вздумается, и данные, к которым обращаются сразу несколько потоков.

Но начнём с основы: как две программы вообще передают друг другу байты. Интерфейс для этого придумали в Беркли в начале восьмидесятых, назвали сокетами, и с тех пор он почти не изменился — тот же код работает на Linux, macOS, BSD и, с косметическими правками, на Windows.

К концу главы у нас будет работающий эхо-сервер и клиент к нему.

## Что такое сокет

Сокет — это конечная точка соединения, и в программе он выглядит как файловый дескриптор. То самое небольшое целое число из главы 27, только за ним стоит не файл, а сетевое соединение.

Отсюда следует приятное: с сокетом работают те же вызовы, что и с файлом. `read` и `write` на сокете работают, `close` закрывает его, `dup2` подменяет — можно, например, направить в сокет стандартный вывод запускаемой программы, и она будет отвечать по сети, ничего об этом не подозревая. Ровно так устроен классический `inetd`.

Отдельные вызовы `recv` и `send` существуют потому, что у них есть четвёртый аргумент — флаги, которых у `read` и `write` нет. Мы им воспользуемся: флаг `MSG_NOSIGNAL` в главе 43 спасёт сервер от смерти.

## TCP и UDP

Прежде чем создавать сокет, надо выбрать вид.

TCP даёт поток байтов с гарантиями: что отправлено, то и придёт, в том же порядке, без потерь и дубликатов. Достигается это подтверждениями, повторными отправками и нумерацией — всё внутри ядра, программе видна только чистая труба. Плата — установление соединения тремя пакетами, задержка при потерях (потерянный кусок ждут, а следующие за ним данные лежат в очереди) и состояние на обеих сторонах.

UDP отправляет отдельные пакеты и ничего не обещает: пакет может потеряться, продублироваться, прийти не в том порядке. Зато никакого соединения, никакой задержки на подтверждения — отправил и забыл.

Для чата нужен TCP: терять сообщения нельзя, порядок важен, объёмы маленькие. UDP выбирают там, где свежесть данных важнее полноты, — голос, видео, игры, где потерянный кадр проще пропустить, чем ждать.

Есть третий вариант, который стоит держать в голове: поверх UDP делают собственные протоколы с нужным набором гарантий. Так устроен QUIC, на котором работает HTTP/3, — ему понадобилось избавиться от блокировки очереди, которую TCP навязывает по своей природе.

## Порядок вызовов

У сервера и клиента разные последовательности, и их полезно видеть рядом.

```
   Сервер                              Клиент

   socket()   создать сокет            socket()
   bind()     занять адрес и порт
   listen()   начать слушать
   accept()   ждать клиента     ◄────  connect()   подключиться
   recv/send  общаться          ◄───►  send/recv
   close()                             close()
```

Ключевое отличие в `accept`: он не принимает данные, а порождает **новый** сокет — отдельный на каждое соединение. Слушающий сокет продолжает слушать, а разговор идёт через новый. Это сбивает с толку при первом знакомстве, зато объясняет, как один сервер работает с сотней клиентов.

## Создание сокета

```cpp
int srv = ::socket(AF_INET, SOCK_STREAM, 0);
if (srv < 0) {
    std::cerr << "socket: " << std::strerror(errno) << "\n";
    return 1;
}
```

Первый аргумент — семейство адресов: `AF_INET` для IPv4, `AF_INET6` для IPv6, `AF_UNIX` для сокетов внутри одной машины, работающих через файловую систему. Второй — тип: `SOCK_STREAM` для TCP, `SOCK_DGRAM` для UDP. Третий — протокол внутри типа; ноль означает «выбери сам», и для пары `AF_INET` плюс `SOCK_STREAM` это всегда TCP.

Двойное двоеточие перед именем — `::socket` — указывает глобальную область видимости. Привычка полезная: в программе может оказаться свой `socket` в пространстве имён проекта, и без уточнения компилятор выберет его.

## Адрес

Адрес для IPv4 описывается структурой `sockaddr_in`:

```cpp
sockaddr_in addr;
std::memset(&addr, 0, sizeof(addr));
addr.sin_family = AF_INET;
addr.sin_port = htons(static_cast<std::uint16_t>(port));
addr.sin_addr.s_addr = htonl(INADDR_ANY);
```

Обнуление через `memset` обязательно: в структуре есть поле `sin_zero`, оставшееся от древних времён, и мусор в нём приводит к трудноуловимым ошибкам.

`htons` и `htonl` — те самые преобразователи порядка байтов из главы 32. В сети принят порядок старшим байтом вперёд, и номер порта с адресом обязаны быть записаны именно так. Забыть `htons` — классическая ошибка: сервер запускается, но слушает не тот порт. Порт 9001 без преобразования превращается в 10531.

`INADDR_ANY` означает «все адреса машины»: сервер примет соединение и через сетевую карту, и через локальную петлю. Альтернатива — `INADDR_LOOPBACK`, тогда достучаться можно будет только с этой же машины. Для отладки второе безопаснее.

Дальше начинается самое неприятное в этом интерфейсе — приведение типов:

```cpp
::bind(srv, reinterpret_cast<sockaddr*>(&addr), sizeof(addr));
```

Функции принимают указатель на `sockaddr` — обобщённую структуру, а мы передаём `sockaddr_in`, специфичную для IPv4. Для IPv6 передавали бы `sockaddr_in6`. Это способ сделать полиморфизм в языке C, где его нет: все структуры начинаются с одинакового поля семейства, по которому ядро понимает, что ему дали.

С точки зрения C++ такое приведение — нарушение правил о совместимости типов (глава 32), но здесь оно узаконено самим стандартом POSIX, и другого способа просто нет.

## bind, listen, accept

```cpp
if (::bind(srv, reinterpret_cast<sockaddr*>(&addr), sizeof(addr)) < 0) {
    std::cerr << "bind: " << std::strerror(errno) << "\n";
    ::close(srv);
    return 1;
}

if (::listen(srv, 16) < 0) {
    std::cerr << "listen: " << std::strerror(errno) << "\n";
    ::close(srv);
    return 1;
}
```

`bind` закрепляет за сокетом адрес и порт. Самая частая ошибка здесь — `EADDRINUSE`, «адрес уже используется»; о ней отдельный разговор ниже.

Порты меньше 1024 — привилегированные: занять их может только процесс с правами администратора. Поэтому веб-сервер запускается от `root`, занимает 80-й порт и сразу сбрасывает права. Мы берём 9001 — свободный и непривилегированный.

`listen` переводит сокет в режим ожидания соединений. Второй аргумент — длина очереди уже установленных, но ещё не принятых соединений. Если очередь переполнена, новые попытки подключения ядро отвергает. Шестнадцать — разумно для учебного сервера; у нагруженных значение доводят до тысяч.

```cpp
sockaddr_in cli;
socklen_t cli_len = sizeof(cli);
int c = ::accept(srv, reinterpret_cast<sockaddr*>(&cli), &cli_len);
if (c < 0) {
    if (errno == EINTR) continue;
    std::cerr << "accept: " << std::strerror(errno) << "\n";
    break;
}
```

`accept` блокирует выполнение, пока кто-нибудь не подключится, и возвращает новый дескриптор для разговора с этим клиентом. Заодно он заполняет структуру адресом клиента — отсюда и второй с третьим аргументы.

Третий аргумент — указатель на длину, и это ещё одна особенность интерфейса. На входе он говорит, сколько места в структуре, на выходе — сколько ядро записало. Такой параметр называют «значение-результат», и в сокетном интерфейсе их несколько.

Проверка на `EINTR` знакома по главе 28: блокирующий вызов может прерваться сигналом, и это не ошибка, а повод повторить.

Адрес клиента печатаем человекочитаемо:

```cpp
char ip[INET_ADDRSTRLEN] = {0};
::inet_ntop(AF_INET, &cli.sin_addr, ip, sizeof(ip));
std::cout << "Клиент " << ip << ":" << ntohs(cli.sin_port) << " подключён\n";
```

`inet_ntop` переводит двоичный адрес в строку вида `192.168.1.5`; `INET_ADDRSTRLEN` — константа с достаточным размером буфера. Обратное преобразование делает `inet_pton`. Старые функции `inet_ntoa` и `inet_addr` встречаются в примерах из девяностых, но у них нет поддержки IPv6 и есть проблемы с многопоточностью — не используйте.

## Обмен данными

```cpp
char buf[1024];
while (true) {
    ssize_t n = ::recv(c, buf, sizeof(buf), 0);
    if (n == 0) { std::cout << "клиент отключился\n"; break; }
    if (n < 0) {
        if (errno == EINTR) continue;
        std::cerr << "recv: " << std::strerror(errno) << "\n";
        break;
    }
    ssize_t sent = 0;
    while (sent < n) {
        ssize_t s = ::send(c, buf + sent, n - sent, 0);
        if (s < 0) {
            if (errno == EINTR) continue;
            break;
        }
        sent += s;
    }
}
```

Три исхода `recv` те же, что у `read` в главе 31, но со своими значениями. Ноль означает, что собеседник закрыл соединение, — это не ошибка, а нормальное завершение. Отрицательное — ошибка, и `EINTR` среди них особая. Положительное — сколько байт пришло, и оно почти никогда не равно запрошенному.

Отправка обёрнута в цикл по той же причине, что и запись в файл: `send` вправе отправить меньше, чем попросили, если буфер отправки заполнен. Не проверять его результат — значит терять хвосты сообщений при высокой нагрузке, а это ошибка, которая не воспроизводится в тестах и вылезает в бою.

### TCP — поток, а не сообщения

Здесь скрыто самое важное свойство TCP, и его лучше увидеть, чем прочитать. Клиент отправляет три сообщения по двенадцать байт тремя вызовами `send`, а сервер делает один `recv`:

```cpp
::send(fd, "ПЕРВОЕ", 12, 0);
::send(fd, "ВТОРОЕ", 12, 0);
::send(fd, "ТРЕТЬЕ", 12, 0);
```

```bash
$ ./stream
три вызова send по 12 байт → один recv вернул 36 байт:
  "ПЕРВОЕВТОРОЕТРЕТЬЕ"
```

Границы сообщений исчезли. TCP не знает, что вы считаете сообщением, — он передаёт поток байтов и вправе склеивать их и разрезать как угодно. Три отправки могут прийти одним куском, одна отправка — тремя кусками.

Из этого следует, что **любой протокол поверх TCP обязан сам размечать границы сообщений**. Способов три: разделитель (например, перевод строки, как в HTTP и SMTP), префикс длины (как в нашем формате из главы 32) или фиксированный размер. Наш эхо-сервер работает без разметки только потому, что ему всё равно: что пришло, то и отправил обратно.

В главе 44 мы напишем протокол с префиксом длины и накопителем — и заодно поймём, почему эта задача сложнее, чем кажется.

## Клиент

У клиента вместо `bind` и `listen` один вызов `connect`, но перед ним — разрешение имени:

```cpp
addrinfo hints;
std::memset(&hints, 0, sizeof(hints));
hints.ai_family = AF_UNSPEC;     // и IPv4, и IPv6
hints.ai_socktype = SOCK_STREAM;

addrinfo* res = nullptr;
int rc = ::getaddrinfo(host, port, &hints, &res);
if (rc != 0) {
    std::cerr << "getaddrinfo: " << ::gai_strerror(rc) << "\n";
    return 1;
}

int fd = -1;
for (addrinfo* p = res; p; p = p->ai_next) {
    fd = ::socket(p->ai_family, p->ai_socktype, p->ai_protocol);
    if (fd < 0) continue;
    if (::connect(fd, p->ai_addr, p->ai_addrlen) == 0) break;
    ::close(fd);
    fd = -1;
}
::freeaddrinfo(res);
```

`getaddrinfo` — единственная правильная функция для превращения имени в адрес. Она умеет и доменные имена, и цифровые адреса, и IPv4, и IPv6, и имена служб (`"http"` вместо `"80"`).

Возвращает она **список** адресов, и перебор этого списка — не формальность. У домена может быть несколько адресов, часть из них может не отвечать, IPv6 может быть настроен, но не работать. Правильный клиент пробует все по очереди — именно так делают браузеры, только они ещё и параллельно.

Ошибки `getaddrinfo` расшифровываются не через `strerror`, а через `gai_strerror`: у неё собственный набор кодов.

`freeaddrinfo` обязателен — список выделен в куче. Здесь напрашивается умный указатель со своим удалителем (глава 18); в учебном коде оставлено как есть, но в настоящем проекте стоит обернуть.

Дальше клиент читает строки со стандартного ввода, отправляет и печатает ответ:

```cpp
std::string line;
while (true) {
    std::cout << "> ";
    std::cout.flush();
    if (!std::getline(std::cin, line)) break;
    if (line.empty()) break;
    line += '\n';
    // ... send в цикле ...
    char buf[1024];
    ssize_t n = ::recv(fd, buf, sizeof(buf), 0);
    if (n <= 0) {
        std::cerr << "сервер закрыл соединение\n";
        break;
    }
    std::cout << "<- " << std::string(buf, n);
}
```

Обратите внимание: клиент отправляет запрос и сразу ждёт ответ. Для эха годится, для чата — нет: там сообщения приходят когда угодно, а не в ответ на наши. Как быть с этим, разберёмся в главе 41, где появится второй поток.

## TIME_WAIT и SO_REUSEADDR

Остался вызов, который я до сих пор не объяснил:

```cpp
int yes = 1;
if (::setsockopt(srv, SOL_SOCKET, SO_REUSEADDR, &yes, sizeof(yes)) < 0) { ... }
```

Без него сервер, который только что работал и был остановлен, при перезапуске получает `bind: Address already in use` — хотя никто порт не занимает. Проверим на опыте: программа поднимает сервер, принимает соединение, закрывается и сразу пытается занять порт снова.

```bash
$ ./twait
без SO_REUSEADDR: повторный bind: Address already in use
$ ./twait reuse
с SO_REUSEADDR:  повторный bind сразу удался
```

Причина — состояние TIME_WAIT. Сторона, закрывшая соединение первой, держит его в этом состоянии около минуты (на macOS и Linux — от 30 до 120 секунд в зависимости от настроек). Нужно это затем, чтобы опоздавшие пакеты старого соединения не были приняты новым, случайно занявшим ту же пару адресов и портов. Пока соединение в TIME_WAIT, его порт считается занятым.

`SO_REUSEADDR` говорит ядру: «разреши занять порт, даже если на нём висят соединения в TIME_WAIT». Это ровно то, что нужно серверу при перезапуске.

Заодно развеем распространённое заблуждение. Многие думают, что `SO_REUSEADDR` позволяет двум серверам слушать один порт. Не позволяет:

```bash
$ ./reuse 9188
без SO_REUSEADDR: bind удался
без SO_REUSEADDR: bind не удался — Address already in use
с SO_REUSEADDR:  bind не удался — Address already in use
```

Первый занял порт, и второй не может занять его ни с флагом, ни без. Для нескольких процессов на одном порту существует другой флаг — `SO_REUSEPORT`, — и он появился гораздо позже, для распределения нагрузки между процессами. Не путайте их.

## Чего наш сервер не умеет

Один клиент за раз. Пока идёт разговор с одним, остальные ждут в очереди `listen`. Это следующая глава.

Ничего, кроме эха. Никакого протокола, никаких имён, никакой рассылки — всё впереди.

Не переживает разрыв. Если клиент исчез без закрытия соединения — выдернули кабель, уснул ноутбук, — сервер узнает об этом не скоро: TCP обнаружит обрыв только при попытке отправки, а если ничего не отправлять, соединение может висеть часами. Лечится это либо своими сообщениями «я жив» на уровне протокола, либо флагом `SO_KEEPALIVE`, включающим проверки на уровне TCP (правда, по умолчанию первая проверка происходит через два часа).

Не ограничивает никого и ни в чём. Клиент может отправить гигабайт в одном сообщении, открыть тысячу соединений, вообще ничего не отправлять и держать соединение занятым. Все три случая для настоящего сервера — поводы для защиты.

## Главные правила главы

1. Сокет — это файловый дескриптор; с ним работают те же `read`, `write` и `close`, а `recv` и `send` добавляют флаги.
2. TCP даёт надёжный поток байтов, UDP — ненадёжные отдельные пакеты; выбор делается по тому, что важнее — полнота или свежесть.
3. `accept` возвращает новый сокет; слушающий продолжает слушать.
4. Номер порта и адрес записываются в сетевом порядке байтов — `htons` и `htonl` обязательны.
5. TCP не хранит границ сообщений: разметку обязан обеспечивать протокол поверх него.
6. `recv` и `send` обрабатывают меньше запрошенного; оба зовут в цикле, ноль от `recv` означает закрытие соединения.
7. Имя в адрес переводит `getaddrinfo`, и перебирать надо весь возвращённый список.
8. `SO_REUSEADDR` снимает запрет на занятие порта, оставшегося в TIME_WAIT, но не позволяет двум серверам слушать один порт.

2. Подключите к серверу двух клиентов одновременно. Что происходит со вторым? Посмотрите состояние соединений через `netstat -an | grep 9001` и найдите очередь.

3. Уберите `SO_REUSEADDR`, пересоберите, запустите сервер, подключитесь клиентом, остановите сервер и сразу запустите снова. Сколько времени порт остаётся занятым на вашей системе?

4. Повторите опыт со склейкой сообщений: отправьте три коротких сообщения подряд и посмотрите, сколько байт вернёт один `recv`. Затем вставьте паузу в полсекунды между отправками — изменится ли результат?

5. Замените в сервере `recv` и `send` на `read` и `write` и убедитесь, что всё работает. Какие возможности вы при этом потеряли?

6. Сделайте так, чтобы сервер печатал длину каждого полученного куска. Отправьте клиентом строку в сто килобайт (например, `python3 -c "print('x'*100000)" | nc localhost 9001`) и посмотрите, на сколько кусков она разбилась.

7. (Сложнее) Добавьте серверу таймаут на бездействующего клиента через `setsockopt` с `SO_RCVTIMEO`. Проверьте, что `recv` возвращает `-1` с `errno == EAGAIN` по истечении времени.

8. (Сложнее) Перепишите клиент так, чтобы он работал и с IPv6: уберите привязку к `AF_INET` там, где она осталась, и проверьте подключение к `::1`. Что придётся поменять в сервере, чтобы он слушал оба протокола?

## Что дальше

Глава 41 — многопоточность. Наш сервер обслуживает одного клиента за раз, и это никуда не годится для чата. Заведём по потоку на соединение, познакомимся с `std::thread`, увидим первую гонку данных своими глазами и научимся защищать общие данные мьютексом. А заодно поймём, почему модель «поток на соединение» проста, удобна и плохо масштабируется.

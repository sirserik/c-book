# Глава 42. Атомарные операции

В прошлой главе мы спасли счётчик имён одним словом — заменили `int` на `std::atomic<int>`. Работает, но объяснения это не заменяет: что именно происходит при `counter++` из двух потоков, почему атомарная переменная быстрее мьютекса и что такое пресловутая модель памяти, о которой все говорят с придыханием.

Разберёмся. Материала здесь на целую книгу, но практической пользы — на одну главу и одно правило, которого хватает в девяти случаях из десяти.

## Почему ++ теряет половину

Возьмём самый простой возможный код: два потока, каждый увеличивает общий счётчик миллион раз.

```cpp
int counter = 0;
std::thread a([&] { for (int i = 0; i < ITER; ++i) ++counter; });
std::thread b([&] { for (int i = 0; i < ITER; ++i) ++counter; });
a.join(); b.join();
```

Ожидаем два миллиона. Получаем:

```
Без защиты:        counter=1032826 (ожидалось 2000000), 6.4 ms
```

Половина прибавлений исчезла. Не «немного разошлось», а именно половина.

Причина в том, что `++counter` — не одна операция, а три. Процессор читает значение из памяти в регистр, прибавляет единицу, записывает обратно. Между чтением и записью может вклиниться другой поток:

```
поток A: читает 100
поток B: читает 100          ← оба видят одно и то же
поток A: пишет 101
поток B: пишет 101           ← прибавление A потерялось
```

Два прибавления, результат один. Чем чаще потоки попадают в это окно, тем больше теряется — при плотном цикле почти всегда.

Обратите внимание и на время: небезопасная версия отработала за шесть миллисекунд. Запомним это число, оно понадобится для сравнения.

## Мьютекс: правильно и дорого

Самое очевидное решение — замок из прошлой главы:

```cpp
std::mutex m;
auto work = [&] {
    for (int i = 0; i < ITER; ++i) {
        std::lock_guard<std::mutex> lock(m);
        ++counter;
    }
};
```

```
Mutex:             counter=2000000, 97.2 ms
```

Ответ верный, но время выросло в пятнадцать раз. И это на операции, которая сама по себе занимает наносекунду.

Дорого обходится не сам замок — в неоспариваемом случае он стоит десятки наносекунд. Дорого обходится состязание: когда второй поток приходит к закрытому замку, он засыпает, а это системный вызов, переключение контекста и последующее пробуждение. При миллионе прибавлений столкновения происходят постоянно.

## Атомарная переменная

Мьютекс — универсальный инструмент: он защищает произвольный кусок кода любой длины. Но нам нужно защитить одну-единственную операцию, и для этого у процессора есть встроенная поддержка.

```cpp
std::atomic<int> counter(0);
auto work = [&] { for (int i = 0; i < ITER; ++i) ++counter; };
```

```
atomic (seq_cst):  counter=2000000, 42.2 ms
```

Верно и вдвое быстрее мьютекса. Причём заметьте: медленнее незащищённой версии всё равно в семь раз — атомарность не бесплатна, просто дешевле замка.

Что происходит внутри, видно в ассемблере. Соберём с оптимизацией и посмотрим, во что превратился `fetch_add`:

```asm
inc_seq:
    lock  inc  dword ptr [rip + a]
```

Одна инструкция с приставкой `lock`. Она заставляет процессор выполнить чтение, изменение и запись как единое целое: на время операции строка кэша захватывается в исключительное владение, и другие ядра не могут её тронуть. Никакого засыпания, никаких системных вызовов — только задержка на согласование кэшей между ядрами.

Отсюда и разница в цене. Мьютекс при столкновении уходит в ядро, атомарная операция остаётся в пользовательском коде.

### Что умеет std::atomic

Кроме привычных `++` и `--` у атомарной переменной есть именованные операции:

```cpp
counter.fetch_add(1);          // прибавить и вернуть прежнее значение
counter.fetch_sub(1);
counter.load();                // прочитать
counter.store(42);             // записать
counter.exchange(99);          // записать и вернуть прежнее
```

И главная из них, на которой строится всё остальное:

```cpp
int expected = 5;
if (counter.compare_exchange_strong(expected, 10)) {
    // было 5, стало 10
} else {
    // не было 5; в expected теперь лежит фактическое значение
}
```

«Сравнить и обменять» — атомарная проверка с условной записью. На ней строятся все алгоритмы без блокировок: прочитали значение, вычислили новое, попытались записать, если никто не вмешался; вмешались — повторили.

```cpp
// Атомарно умножить на два — операции fetch_mul не существует.
int old = counter.load();
while (!counter.compare_exchange_weak(old, old * 2)) {
    // old обновилось фактическим значением, пробуем снова
}
```

Слабая версия `compare_exchange_weak` вправе иногда «промахнуться» без причины, зато на некоторых процессорах дешевле; поскольку она всё равно вызывается в цикле, ложный промах безвреден. Сильная версия нужна там, где цикла нет.

Важно понимать границу применимости: атомарной может быть одна переменная, но не связка из двух. Если нужно согласованно поменять счётчик и список, атомарные переменные не помогут — нужен мьютекс.

## Модель памяти и одно правило

Теперь та часть, вокруг которой ходят легенды.

Проблема в том, что и компилятор, и процессор переставляют операции. Компилятор — при оптимизации, процессор — при выполнении, чтобы не простаивать в ожидании памяти. В однопоточной программе это незаметно: перестановка не меняет наблюдаемый результат. В многопоточной — меняет, потому что другой поток видит промежуточные состояния.

Классический пример:

```cpp
// Поток A                     // Поток B
data = 42;                     if (ready) {
ready = true;                      use(data);   // а точно ли 42?
                               }
```

Ничто не мешает процессору сделать запись `ready` раньше записи `data` — они не связаны между собой. Поток B увидит поднятый флаг и мусор в данных.

Атомарные операции решают и это: у каждой из них есть параметр упорядочивания, который говорит, что можно, а что нельзя переставлять вокруг неё. Вариантов в C++11 шесть, и разбирать их все здесь ни к чему. Достаточно знать три.

`memory_order_seq_cst` — по умолчанию. Самый строгий: все атомарные операции всех потоков выстраиваются в единый глобальный порядок, и ничего вокруг них не переставляется. Именно поэтому пример выше починится сам, если `ready` сделать атомарным.

`memory_order_relaxed` — самый слабый: гарантируется только атомарность самой операции, никаких обещаний про порядок. Годится для счётчиков, которые ни с чем не синхронизируют, — например, для сбора статистики.

`memory_order_acquire` и `memory_order_release` — пара для передачи данных между потоками: писатель делает `store(..., release)`, читатель `load(..., acquire)`, и всё, что писатель сделал **до** своей записи, гарантированно видно читателю **после** его чтения. Это дешевле полного порядка и достаточно почти всегда.

Правило, которого хватает большинству: **берите умолчание**. `seq_cst` рассуждается проще всего, ошибиться в нём нельзя, а разница в цене на практике редко заметна.

### Насколько редко — измерим

Наш демо-стенд сравнивает `seq_cst` и `relaxed` на том же миллионе прибавлений:

```
atomic (seq_cst):  counter=2000000, 42.2 ms
atomic (relaxed):  counter=2000000, 44.2 ms
```

Разницы нет вовсе — расслабленная версия даже чуть медленнее, что укладывается в разброс измерений.

Объяснение — в ассемблере. Обе версии компилируются в одну и ту же инструкцию:

```asm
inc_seq:      lock inc dword ptr [rip + a]
inc_relaxed:  lock inc dword ptr [rip + a]
```

Дело в том, что у x86 сильная модель памяти: процессор сам почти ничего не переставляет, и большинство гарантий получается бесплатно. Разница между режимами проявляется на ARM, где модель слабая, — и там `relaxed` действительно дешевле.

Но не для всех операций. Посмотрим на запись:

```asm
store_seq:  xchg dword ptr [rip + a], edi     ; неявно атомарна и ставит барьер
store_rlx:  mov  dword ptr [rip + a], edi     ; обычная запись
```

Здесь разница есть даже на x86: строгая запись превращается в `xchg`, которая дороже обычного `mov`. А вот чтение в обоих режимах — обычный `mov`.

Вывод практический: чтобы рассуждать о цене упорядочивания, надо смотреть на конкретную операцию и конкретный процессор. И ещё раз — если вы не пишете структуру данных без блокировок, оставьте умолчание.

## Ложное разделение

Есть у атомарных операций неочевидная ловушка, о которой стоит знать, потому что она бьёт по производительности незаметно.

Процессор работает с памятью не байтами, а строками кэша — обычно по 64 байта. Если две атомарные переменные попали в одну строку, то ядра, работающие с разными переменными, всё равно дерутся за одну строку кэша. Это называют ложным разделением: логически данные независимы, физически — нет.

```cpp
struct Counters {
    std::atomic<long> a;   // эти две переменные почти наверняка
    std::atomic<long> b;   // окажутся в одной строке кэша
};
```

Лечится выравниванием — тем самым `alignas` из главы 32:

```cpp
struct Counters {
    alignas(64) std::atomic<long> a;
    alignas(64) std::atomic<long> b;
};
```

Структура станет вдвое больше, зато ядра перестанут мешать друг другу. В C++17 для этого появилась константа `std::hardware_destructive_interference_size` — размер строки кэша, узнанный у компилятора.

Замечать такое стоит только тогда, когда счётчики действительно горячие и обновляются миллионы раз в секунду. В остальных случаях выравнивание — преждевременная оптимизация.

## Что выбрать

Короткая таблица, которой хватает для принятия решения:

| Задача | Инструмент |
|--------|-----------|
| Счётчик, флаг, одна переменная | `std::atomic` |
| Несколько связанных переменных | `std::mutex` |
| Структура данных (список, отображение) | `std::mutex` |
| Много читателей, редкие записи | `std::shared_mutex` (C++17) |
| Один пишет, один читает, порядок важен | атомарный флаг с `release`/`acquire` |
| Очередь задач между потоками | мьютекс плюс `condition_variable` |

Отдельно стоит сказать про соблазн написать структуру данных без блокировок. Выглядит это заманчиво — очередь на атомарных операциях, никаких замков, — а на практике оказывается одной из самых сложных областей программирования. Там ждут проблема ABA (значение вернулось к прежнему, но объект уже другой), сложности с освобождением памяти (когда безопасно удалить узел, на который может смотреть другой поток) и почти полная невозможность проверить корректность тестами.

Практический совет: начинайте с мьютекса. Если измерения покажут, что он мешает, — сначала уменьшайте область блокировки, потом смотрите в сторону `shared_mutex`, и только потом, с очень большой осторожностью, в сторону структур без блокировок. И берите готовую библиотеку, а не пишите свою.

## В нашем сервере

Атомарная переменная у нас ровно одна:

```cpp
// Счётчик имён. Его увеличивают потоки-обработчики, значит, обычный int
// здесь — гонка данных: два клиента, подключившиеся одновременно, могли бы
// получить одно имя. atomic делает инкремент неделимым (глава 42).
std::atomic<int> g_next_id(1);
...
std::string name = "user_" + std::to_string(g_next_id.fetch_add(1));
```

Это ровно тот случай из таблицы: одна независимая переменная, никакой связи с другими данными. Мьютекс здесь был бы избыточен, а `fetch_add` возвращает прежнее значение — то самое, которое нам и нужно для имени.

Список клиентов, наоборот, защищён мьютексом, и правильно: изменение списка — это не одна операция над одной переменной, а перестройка структуры.

## Главные правила главы

1. `counter++` — это чтение, прибавление и запись; из двух потоков теряется значительная часть прибавлений.
2. Атомарная операция выполняется процессором как единое целое — одной инструкцией с приставкой `lock` на x86.
3. Атомарная переменная вдвое быстрее мьютекса на счётчике, потому что не уходит в ядро при столкновении.
4. Атомарной может быть одна переменная, но не связка из нескольких — там нужен мьютекс.
5. `compare_exchange` — основа всех алгоритмов без блокировок: прочитал, вычислил, попытался записать, повторил при неудаче.
6. По умолчанию берите `seq_cst`; расслабленные режимы дают выигрыш не везде и требуют внимательности.
7. На x86 `relaxed` и `seq_cst` для прибавления компилируются в одну инструкцию, а для записи — в разные; проверять надо конкретную операцию.
8. Две горячие атомарные переменные в одной строке кэша мешают друг другу; лечится `alignas(64)`.

## Упражнения

1. Запустите `./build/atomic_demo` несколько раз. Насколько отличается потерянная доля прибавлений от запуска к запуску? Объясните разброс.

2. Уменьшите число итераций до тысячи и запустите снова. Пропала ли гонка? Сделайте вывод о том, можно ли доверять отсутствию ошибки в тесте.

3. Посмотрите ассемблер сами: соберите маленький файл с `fetch_add` в двух режимах через `g++ -O2 -S -masm=intel` и найдите инструкции. Затем то же самое для `store` и `load`.

4. Замените в демо `++counter` на `counter.fetch_add(1, std::memory_order_relaxed)` и замерьте. Есть ли разница на вашей машине? А если запустить на телефоне или Raspberry Pi?

5. Реализуйте атомарное умножение на два через `compare_exchange_weak` в цикле. Проверьте на двух потоках, что результат совпадает с ожидаемым.

6. Соберите демо с `-fsanitize=thread` и убедитесь, что детектор находит гонку в первом варианте и молчит в трёх остальных.

7. (Сложнее) Воспроизведите ложное разделение: два потока увеличивают два счётчика в одной структуре, замерьте время; добавьте `alignas(64)` и замерьте снова. Какой выигрыш?

8. (Сложнее) Напишите очередь «один писатель, один читатель» на двух атомарных индексах и кольцевом буфере. Проверьте, что ни одно сообщение не теряется и не дублируется на миллионе передач.

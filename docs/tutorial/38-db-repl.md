# Глава 38. Оболочка базы данных

Движок готов, язык есть. Не хватает того, через что с базой общается человек, — оболочки.

Все клиенты баз данных устроены одинаково: `psql`, `mysql`, `sqlite3` — это циклы «прочитать, выполнить, напечатать». Внешне просто, но в деталях набирается работа: запрос может занимать несколько строк, служебные команды должны отличаться от запросов, история должна переживать выход, а ошибка в запросе не должна ронять программу.

В этой главе доведём `mydb` до состояния, в котором им приятно пользоваться. И заодно разберём, почему разбор пользовательского ввода — задача, не сводящаяся к разбору языка.

## Цикл

Скелет знаком по оболочке из главы 26:

```cpp
while (true) {
    std::cout << (first_line ? "mydb> " : "  ... ");
    std::cout.flush();

    std::string line;
    if (!std::getline(std::cin, line)) {
        std::cout << "\n";
        break;
    }
    ...
}
```

Два вида приглашения — `mydb>` для начала команды и `  ...` для продолжения — это соглашение всех клиентов баз. Увидев `...`, пользователь понимает, что программа ждёт продолжения, а не зависла.

`flush` после приглашения обязателен по той же причине, что и в оболочке: приглашение не заканчивается переводом строки и без сброса буфера осталось бы невидимым.

Проверка `!std::getline(...)` ловит конец ввода — Ctrl+D в терминале или конец файла, если команды поданы конвейером. Именно она позволяет пользоваться базой из скриптов:

```bash
$ printf 'INSERT INTO items VALUES (1, 10);\nSELECT * FROM items;\n' | ./build/mydb
```

## Многострочный ввод

Первое настоящее отличие от оболочки: команда SQL не заканчивается на переводе строки. Запрос может занимать десяток строк, и признаком конца служит точка с запятой.

Отсюда накопитель: строки складываются в буфер, пока в нём не появится `;`.

```cpp
if (!buffer.empty()) buffer += " ";
buffer += t;
first_line = false;

// В строке может быть несколько команд: `INSERT ...; SELECT ...;`.
// Выполняем ВСЕ завершённые, а незавершённый хвост оставляем в буфере
// до следующей строки.
while (true) {
    std::size_t semi = buffer.find(';');
    if (semi == std::string::npos) break;

    std::string stmt = buffer.substr(0, semi + 1);
    buffer = trim(buffer.substr(semi + 1));

    try {
        db.execute(stmt, std::cout);
    } catch (const std::exception& e) {
        std::cout << "Error: " << e.what() << "\n";
    }
    history_add(trim(stmt));
}

first_line = buffer.empty();
```

Строки склеиваются через пробел, а не через перевод строки: для нашего лексера это одно и то же, зато в историю команда попадает одной строкой.

Внутренний цикл — результат исправления ошибки, о которой стоит рассказать подробно, потому что она поучительна.

### Ошибка, которую нашла проверка вручную

В первой версии вместо цикла стояла одна проверка: нашли точку с запятой — выполнили команду, остаток положили обратно в буфер, читаем следующую строку. Выглядит разумно и работает, пока в строке одна команда.

А вот что получалось, если написать две:

```
mydb> INSERT INTO items VALUES (1, 10); INSERT INTO items VALUES (2, 20);
1 строка
  ... 
```

Первая команда выполнилась, вторая осталась в буфере, приглашение сменилось на `...` — и всё, программа ждёт продолжения того, что уже полное. Хуже того, служебные команды перестают работать: они распознаются только в начале ввода, а буфер не пуст. Набранный `.exit` уходит в накопитель, и выйти из программы можно только через Ctrl+D.

Именно так это и выглядело при проверке: три служебные команды подряд провалились в никуда, и сессия не завершилась.

Исправление — обрабатывать буфер, пока в нём есть завершённые команды. Три строки разницы, а поведение меняется принципиально.

Урок здесь не про цикл. Урок про то, что интерактивные программы нужно проверять сценариями, а не по одной команде. Ошибка не проявлялась, пока команды вводились по одной, — то есть ровно в том режиме, в котором обычно и проверяют, дописав функцию.

### Чего не умеет наш поиск точки с запятой

Мы ищем `;` обычным `find`, не глядя на контекст. Для нашего диалекта этого достаточно: строк в языке нет, а значит, точка с запятой не может оказаться внутри данных.

Как только появятся строковые литералы, всё сломается:

```sql
INSERT INTO t VALUES ('привет; пока');
```

Здесь `;` внутри кавычек, а наш разбор оборвёт команду посередине. Правильное решение — искать разделитель тем же лексером, который разбирает язык: он про кавычки знает. Клиенты настоящих баз так и делают, причём `psql` умеет ещё и вложенные `$$`-блоки для функций.

Это тот случай, когда простое решение годится ровно до определённого момента, и важно понимать, до какого именно.

## Служебные команды

Команды, которые адресованы не базе, а клиенту, принято отличать по точке в начале — так сделано в `sqlite3`, а в `psql` для этого служит обратная косая черта:

```cpp
bool handle_meta(const std::string& cmd, db::Database& db) {
    std::string c = trim(cmd);
    if (c == ".quit" || c == ".exit") return false;
    if (c == ".help") { show_help(); return true; }
    if (c == ".history") { show_history(); return true; }
    if (c == ".checkpoint") {
        db.checkpoint();
        std::cout << "(checkpoint done)\n";
        return true;
    }
    std::cout << "Неизвестная meta-команда: " << c << " (.help для справки)\n";
    return true;
}
```

Возвращаемое значение означает «продолжать ли работу»: `false` только у команд выхода. Такой способ выхода из вложенной функции чище, чем `std::exit`, — он позволяет циклу выйти нормально и выполнить всё, что положено при завершении: контрольную точку и сохранение истории.

Обратите внимание, что распознаются служебные команды **только в начале ввода**:

```cpp
if (first_line && !t.empty() && t[0] == '.') {
    if (!handle_meta(t, db)) break;
    continue;
}
```

Условие `first_line` защищает от неверного толкования: если пользователь набирает многострочный запрос и одна из строк начинается с точки, это часть запроса, а не команда клиенту.

Справка по `.help` — не украшение. Программа, которая не может рассказать о себе, вынуждает лезть в исходники:

```
mydb> .help
Meta-команды:
  .help        справка
  .history     показать историю
  .checkpoint  принудительный sync на диск
  .quit/.exit  выход

SQL:
  CREATE TABLE <name> (<col> INT [PRIMARY KEY], <col> INT);
  CREATE INDEX <name> ON <table>(<column>);
  INSERT INTO <name> VALUES (<n>, <n>);
  SELECT <cols>|* FROM <name> [WHERE <col> <op> <n>];
  EXPLAIN SELECT ...;

Команды многострочные, завершаются `;`.
```

## Комментарии

SQL-комментарий начинается с двух дефисов и идёт до конца строки. Убираем его до всякого разбора:

```cpp
// Удалить SQL-комментарии: «-- до конца строки».
std::string strip_comment(const std::string& s) {
    auto pos = s.find("--");
    if (pos == std::string::npos) return s;
    return s.substr(0, pos);
}
```

Четыре строки, и у них тот же изъян, что у поиска точки с запятой: два дефиса внутри строкового литерала обрежут команду. И то же оправдание — строк в нашем языке нет.

Блочные комментарии `/* ... */` мы не поддерживаем: они могут занимать несколько строк, и для них потребовалось бы состояние «мы внутри комментария», переживающее переход к следующей строке. Это упражнение в конце главы.

## История

Устроена так же, как в оболочке из главы 30: список строк в памяти, файл в домашней папке, загрузка при старте и сохранение при выходе.

```cpp
// Сколько команд помним. Без ограничения файл истории растёт вечно.
const std::size_t kHistoryLimit = 1000;

void history_add(const std::string& q) {
    if (q.empty()) return;
    if (!g_history.empty() && g_history.back() == q) return;
    g_history.push_back(q);
    if (g_history.size() > kHistoryLimit) {
        g_history.erase(g_history.begin(),
                        g_history.begin() +
                            static_cast<long>(g_history.size() - kHistoryLimit));
    }
}
```

Ограничение появилось не из теоретических соображений. Пока я гонял примеры к этим главам, файл истории дорос до двух с лишним тысяч строк, и `.history` начал выдавать простыню на весь экран. Тысяча последних команд — разумный предел, столько же по умолчанию держит `bash`.

Обрезание сделано одним вызовом `erase` с диапазоном, а не циклом удалений с начала. Разница принципиальна: `erase` с диапазоном сдвигает хвост один раз, а тысяча одиночных удалений сдвинула бы его тысячу раз. Это общее правило работы с `std::vector`: удаляйте диапазоном.

В историю попадает разобранная команда, а не введённая строка, — то есть если пользователь написал две команды в одной строке, в истории их будет две:

```
mydb> INSERT INTO items VALUES (1, 10); INSERT INTO items VALUES (2, 20);
1 строка
1 строка
mydb> .history
  1  INSERT INTO items VALUES (1, 10);
  2  INSERT INTO items VALUES (2, 20);
  3  SELECT * FROM items;
```

Так удобнее для повторного использования: каждая запись истории — самостоятельная команда.

## Ошибки не должны ронять программу

Пожалуй, главное требование к интерактивной программе. Опечатка в запросе — обычное дело, и клиент, падающий от неё, никуда не годится.

```cpp
try {
    db.execute(stmt, std::cout);
} catch (const std::exception& e) {
    std::cout << "Error: " << e.what() << "\n";
}
```

Ловим `std::exception` — общего предка и `SqlError`, и `PageError`, и `WALError`. Это тот случай, когда широкий захват уместен: на верхнем уровне цикла нас интересует не вид ошибки, а факт, что команда не выполнилась.

```
mydb> SELECT * FROM other;
Error: SQL: неизвестная таблица: other
mydb> INSERT INTO items VALUES (1, 2, 3);
Error: SQL: ожидается 2 значения
mydb> SELECT * FROM items;
id       | value
---------+---------
1        | 10
(1 строка)
```

После двух ошибок база продолжает работать как ни в чём не бывало.

Ошибка при открытии базы обрабатывается отдельно и до цикла — там продолжать нечего:

```cpp
std::unique_ptr<db::Database> db_ptr;
try {
    db_ptr.reset(new db::Database(dir));
} catch (const std::exception& e) {
    std::cerr << "Не удалось открыть базу в " << dir << ": " << e.what() << "\n";
    return 1;
}
db::Database& db = *db_ptr;
```

Указатель здесь нужен из-за `try`: объект, созданный внутри блока, за его пределами не виден, а ссылку на него хочется иметь во всей функции. Разыменование сразу после — способ дальше писать `db.execute(...)`, а не `db_ptr->execute(...)`.

Возврат `1` из `main` — не мелочь: по нему скрипт, вызвавший базу, узнает, что дело не пошло.

## Завершение

При штатном выходе нужно прибраться:

```cpp
db.checkpoint();
history_save();
return 0;
```

Порядок важен и здесь: сначала данные, потом история. Если что-то пойдёт не так, потерять историю команд неприятно, а потерять данные — недопустимо.

Слово «штатном» здесь ключевое. Выход по `.exit` или Ctrl+D сюда попадает, а вот `kill -9` — нет, и в этом случае данные спасает журнал (глава 35).

## Как это работает целиком

```bash
$ ./build/mydb /tmp/demo
mydb REPL — таблица 'items(id INT PRIMARY KEY, value INT)' по умолчанию.
Open: /tmp/demo
.help для справки, .quit для выхода.

mydb> SELECT *
  ...   FROM items
  ...   WHERE id > 0;
id       | value
---------+---------
(0 строк)
mydb> INSERT INTO items VALUES (1, 10); INSERT INTO items VALUES (2, 20);
1 строка
1 строка
mydb> SELECT * FROM items; -- комментарий в конце
id       | value
---------+---------
1        | 10
2        | 20
(2 строки)
mydb> .checkpoint
(checkpoint done)
mydb> .exit
```

Работают многострочный ввод, несколько команд в строке, комментарии и служебные команды.

## Чего не хватает

Стрелки вверх и вниз не листают историю — по той же причине, что и в оболочке из главы 30: для этого нужен сырой режим терминала и разбор управляющих последовательностей. Подключение библиотеки `readline` или `libedit` даёт это в три строки, и такое упражнение есть в конце главы.

Нет автодополнения имён таблиц и ключевых слов, нет подсветки синтаксиса, нет постраничного вывода длинных результатов (в `psql` для этого запускается внешний `less`), нет вывода в форматах CSV и JSON, нет выполнения файла со скриптом.

Всё это — обвязка вокруг того же цикла, и ни одна из этих возможностей не меняет устройства программы. Именно поэтому клиенты баз данных выглядят так похоже: внутри у них одно и то же.

## Главные правила главы

1. Интерактивная программа читает по строкам, но команда может занимать несколько строк — нужен накопитель и признак завершённости.
2. Обрабатывать надо все завершённые команды в накопителе, а не первую: иначе остаток блокирует ввод.
3. Служебные команды клиента отличают приставкой и распознают только в начале ввода.
4. Ошибка выполнения не должна прерывать цикл; ошибка открытия базы, наоборот, должна прекращать работу с ненулевым кодом возврата.
5. Поиск разделителя без учёта кавычек работает ровно до появления строковых литералов в языке.
6. У истории должен быть предел, иначе файл растёт бесконечно; обрезайте диапазоном, а не по одному элементу.
7. Приглашение без перевода строки требует явного `flush`.
8. При штатном завершении сначала сохраняют данные, потом всё остальное.

## Упражнения

1. Соберите базу и проверьте все режимы: многострочный запрос, две команды в одной строке, комментарий, служебные команды, ошибочный запрос. Убедитесь, что после ошибки клиент продолжает работать.

2. Верните старое поведение — замените внутренний цикл на одну проверку — и воспроизведите ошибку с двумя командами в строке. Опишите, что при этом происходит с приглашением и служебными командами.

3. Добавьте служебную команду `.tables`, печатающую имя таблицы и список её колонок, и `.indexes` — список индексов с колонками. Данные для этого уже есть в каталоге из главы 37.

4. Добавьте `.read <файл>`: прочитать файл и выполнить все команды из него. Учтите, что в файле могут быть комментарии и многострочные запросы.

5. Сделайте вывод результата в формате CSV по служебной команде `.mode csv`. Заголовок — имена колонок через запятую, дальше строки.

6. Добавьте поддержку блочных комментариев `/* ... */`, в том числе многострочных. Понадобится флаг «мы внутри комментария», переживающий переход к следующей строке.

7. (Сложнее) Замените поиск точки с запятой на поиск через лексер: добавьте в него режим «найти конец команды», понимающий кавычки. Проверьте на запросе с точкой с запятой внутри строкового литерала (строки придётся сначала добавить в язык).

8. (Сложнее) Подключите `libedit` и получите стрелки, поиск по Ctrl+R и редактирование строки. Не забудьте отдавать историю библиотеке через `add_history` и освобождать строку, которую возвращает `readline`.

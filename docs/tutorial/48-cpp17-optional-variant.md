# Глава 48. C++17: optional, variant, структурные привязки

Всю книгу мы держались C++11. Причина была практическая: этот стандарт понимает любой компилятор старше 2013 года, и код из книги соберётся у школьника на старом ноутбуке и на сервере с древним дистрибутивом.

Но с 2011 года вышли ещё три стандарта, и кое-что в них не просто удобнее — оно меняет способ писать код. Часть VI — короткая, четыре главы — про то, что появилось и как оно относится к уже написанному нами.

Начнём с четырёх возможностей C++17, которые встречаются чаще всего. Все примеры лежат в `demo-cpp17/` и собираются с `-std=c++17`.

## std::optional: значение или ничего

Задача старая как мир: функция ищет что-то и может не найти. Как об этом сообщить?

Способ первый — особое значение. Так делает `find_age_oldstyle` в нашем демо:

```cpp
int find_age_oldstyle(const std::string& name) {
    if (name == "Alice") return 30;
    return -1;  // «не найден» — но что если возраст реально -1?
}
```

Работает, пока особое значение невозможно в данных. Возраст `-1` невозможен, а вот баланс счёта — вполне, и температура тоже. Такие функции ломаются не сразу, а когда в данных появляется то самое значение.

Способ второй — вернуть признак отдельно: `bool find(const std::string&, int& out)`. Мы так делали в `BPlusTree::find` в главе 34. Честно, но неуклюже: результат приходится объявлять заранее, а функцию нельзя использовать в выражении.

Способ третий — исключение. Годится, когда «не нашли» — исключительная ситуация, и не годится, когда это обычный ход дела.

C++17 даёт четвёртый:

```cpp
std::optional<int> find_age(const std::string& name) {
    static const std::unordered_map<std::string, int> ages = {
        {"Alice", 30}, {"Bob", 25}
    };
    auto it = ages.find(name);
    if (it == ages.end()) return std::nullopt;
    return it->second;
}
```

Тип возвращаемого значения сам говорит: значение может быть, а может не быть. Ни особых значений, ни выходных параметров.

Пользоваться удобно:

```cpp
auto a = find_age("Alice");
if (a.has_value()) {
    std::cout << "Alice: " << *a << "\n";
}

// Сокращение: optional в bool-контексте.
if (auto b = find_age("Charlie")) {
    std::cout << "Charlie: " << *b << "\n";
} else {
    std::cout << "Charlie не найден\n";
}

// value_or — значение по умолчанию.
int c_age = find_age("Charlie").value_or(0);
```

Проверка через `if (auto b = ...)` объявляет переменную прямо в условии и ограничивает её областью видимости `if` — это тоже подарок C++17, раньше так было можно только в цикле `for`.

Отличие `*` от `.value()` существенно. Оператор разыменования не проверяет наличие значения: обращение к пустому `optional` — неопределённое поведение, как разыменование нулевого указателя. Метод `value()` проверяет и бросает исключение:

```cpp
try {
    std::cout << find_age("ghost").value() << "\n";  // бросит bad_optional_access
} catch (const std::bad_optional_access&) {
    std::cout << "bad_optional_access поймали\n";
}
```

Правило простое: `*` — когда наличие уже проверено, `value()` — когда хочется гарантию.

Есть тонкость с перемещением, о которой легко забыть:

```cpp
std::optional<std::string> name = "Hello";
std::string taken = std::move(*name);
// *name теперь moved-from, но optional всё ещё has_value.
name.reset();
```

Перемещение забирает содержимое строки, но не делает `optional` пустым — он по-прежнему считает, что значение есть, просто значение это теперь пустая строка. Чтобы действительно опустошить, нужен `reset()`. Ошибка распространённая: переместили и думают, что `has_value()` вернёт `false`.

Важно понимать, что `optional` хранит значение внутри себя, а не в куче — никаких выделений памяти. Он занимает размер типа плюс флаг наличия плюс выравнивание.

## std::variant: одно из нескольких

Второй тип решает другую задачу: значение может быть одного из нескольких типов.

В C++11 для этого писали объединение с тегом:

```cpp
struct Item {
    enum Kind { Weapon, Armor, Potion } kind;
    union {
        int damage;
        int defense;
        int heal;
    };
};
```

Компактно и опасно: ничто не мешает записать `damage`, а прочитать `heal`. Компилятор не проверит, а объединение с нетривиальными типами (той же `std::string`) потребует ручного вызова конструкторов и деструкторов.

Второй способ — иерархия классов с виртуальными функциями. Именно так устроены предметы нашей RPG в главе 17. Способ хороший, но требует выделения в куче и указателя на каждый объект.

`std::variant` даёт третий путь — типобезопасное объединение:

```cpp
using Item = std::variant<Weapon, Armor, Potion>;

std::vector<Item> items = { Weapon{8}, Armor{4}, Potion{15} };
```

Значения лежат по значению, без кучи, а тип отслеживается внутри. Прочитать не тот тип нельзя — попытка кончится исключением или ошибкой компиляции.

Разбирают `variant` двумя способами. Первый — спросить, что внутри:

```cpp
if (std::holds_alternative<Weapon>(item)) {
    std::cout << "weapon dmg " << std::get<Weapon>(item).damage << "\n";
}
```

Второй, более идиоматичный, — посетитель:

```cpp
std::visit([](const auto& x) {
    using T = std::decay_t<decltype(x)>;
    if constexpr (std::is_same_v<T, Weapon>) {
        std::cout << "Weapon, dmg=" << x.damage << "\n";
    } else if constexpr (std::is_same_v<T, Armor>) {
        std::cout << "Armor, def=" << x.defense << "\n";
    } else {
        std::cout << "Potion, heal=" << x.heal << "\n";
    }
}, item);
```

```
=== std::visit + if constexpr ===
Weapon, dmg=8
Armor, def=4
Potion, heal=15
```

`std::visit` вызывает переданную функцию с фактически хранящимся значением. Если функция — обобщённая лямбда (с `auto` в параметре), компилятор порождает по версии на каждый возможный тип, а `if constexpr` выбирает нужную ветку на этапе компиляции.

Главное преимущество перед иерархией классов — проверка полноты. Если добавить в `variant` четвёртый тип и забыть обработать его в посетителе, компилятор скажет об этом. С виртуальными функциями забытая реализация обнаружилась бы только во время работы.

Когда что выбирать? Иерархия классов лучше, когда набор типов открыт (кто угодно может добавить свой) и когда объекты крупные. `variant` лучше, когда набор типов закрыт и известен заранее, а объекты мелкие: нет выделений памяти, нет косвенности, полнота проверяется компилятором.

Размер `variant` — размер самого большого из типов плюс тег. Это стоит помнить: `std::variant<char, std::array<char, 1000>>` займёт килобайт независимо от того, что в нём лежит.

## Структурные привязки

Мелочь, которая ощутимо меняет читаемость. Было:

```cpp
auto result = m.insert({"Carol", 40});
if (result.second) {
    std::cout << "вставили " << result.first->first << "\n";
}
```

Что такое `second`? Что такое `first->first`? Приходится помнить.

Стало:

```cpp
auto [it, inserted] = m.insert({"Carol", 40});
if (inserted) {
    std::cout << "вставили " << it->first << "\n";
}
```

Имена вместо номеров. Работает с парами, кортежами, структурами и массивами фиксированного размера:

```cpp
auto [id, name, score] = std::make_tuple(42, "Alice", 5.7);
auto [x, y] = point;                  // структура из двух полей
```

Особенно заметен выигрыш в циклах по отображениям:

```cpp
for (const auto& [name, age] : ages) {
    std::cout << name << " = " << age << "\n";
}
```

```
Alice = 30
Bob = 25
Carol = 40
```

Вместо `kv.first` и `kv.second` — осмысленные имена. Наш код по всей книге пестрит обращениями к `kv.first`, и в C++17 каждое из них стало бы читаемее.

Ограничение: имена в привязке нельзя пропустить — если из трёх полей нужно одно, объявить придётся все три. Неиспользованные переменные вызовут предупреждение компилятора; в C++17 для этого есть атрибут `[[maybe_unused]]`.

## if constexpr

Ветвление, которое разрешается при компиляции. Ветка, не выбранная условием, не просто не выполняется — она вообще не компилируется:

```cpp
template <typename T>
void describe(const T& value) {
    if constexpr (std::is_integral_v<T>) {
        std::cout << "integer: " << value << " (×2 = " << value * 2 << ")\n";
    } else if constexpr (std::is_floating_point_v<T>) {
        std::cout << "float: " << value << " (sqrt = " << std::sqrt(value) << ")\n";
    } else if constexpr (std::is_same_v<T, std::string>) {
        std::cout << "string: '" << value << "' (size " << value.size() << ")\n";
    } else {
        std::cout << "other type\n";
    }
}
```

```
integer: 42 (×2 = 84)
float: 3.14 (sqrt = 1.772)
string: 'hello' (size 5)
other type
```

Почему это важно, видно на строке: `value.size()` есть у `std::string`, но нет у `int`. С обычным `if` шаблон, вызванный с `int`, не скомпилировался бы — компилятор проверяет обе ветки, даже недостижимую. С `if constexpr` невыбранная ветка исключается из компиляции целиком.

До C++17 то же самое делали через специализацию шаблонов или хитрости с подстановкой типов — техника под названием SFINAE, читать которую было мучением. `if constexpr` заменяет её обычным `if`, и это одно из тех улучшений, ради которых стоит переходить на новый стандарт.

## Что бы изменилось в нашем коде

Пройдёмся по книге и посмотрим, где C++17 сделал бы код лучше.

`BPlusTree::find` из главы 34 возвращает `bool` и пишет результат в выходной параметр:

```cpp
bool find(std::int64_t key, std::int64_t& out_value) const;

// вызов
std::int64_t v = 0;
if (tree.find(42, v)) { ... }
```

С `optional` это стало бы:

```cpp
std::optional<std::int64_t> find(std::int64_t key) const;

// вызов
if (auto v = tree.find(42)) { ... }
```

`chat::try_decode` из главы 44 возвращает `bool` и заполняет два выходных параметра. Просится `std::optional<Frame>`, где `Frame` — структура с типом и данными.

Разбор SQL из главы 36 хранит все виды команд в одной структуре с полями «на все случаи». Идеальный кандидат на `std::variant<CreateStatement, InsertStatement, SelectStatement>` с посетителем вместо `switch` — и компилятор проследит, чтобы ни один вид не забыли.

Обходы отображений — а их в книге десятки — стали бы читаемее со структурными привязками.

Значит ли это, что книгу надо было писать на C++17? Нет. Совместимость со старыми компиляторами тоже чего-то стоит, и понимание того, что `optional` делает под капотом, приходит именно от опыта с выходными параметрами. Но когда вы начнёте свой проект и никто не заставляет держаться старого стандарта — берите новый.

## Что ещё есть в C++17

Коротко о том, что не поместилось в отдельные разделы.

`std::any` — хранилище значения любого типа с проверкой при извлечении. Нужен реже, чем кажется: почти всегда набор типов известен, и `variant` подходит лучше.

`std::string_view` — невладеющая ссылка на строку. Ему посвящена целая глава 50, потому что вокруг него есть тонкости.

`std::filesystem` — работа с путями и файлами вместо системных вызовов. Это глава 49.

Встроенные переменные (`inline`) — способ объявить переменную в заголовке, не нарушая правило одного определения. Мелочь, но избавляет от возни с отдельным файлом ради одной константы.

Гарантированное устранение копий при возврате временного объекта — стандарт теперь требует то, что компиляторы и так делали. Заодно это позволяет возвращать по значению объекты, которые нельзя ни копировать, ни перемещать.

Параллельные алгоритмы — про них будет разговор в главе 50, и разговор невесёлый.

## Главные правила главы

1. `std::optional` заменяет особые значения и выходные параметры: тип сам сообщает, что значения может не быть.
2. `*` не проверяет наличие, `value()` проверяет и бросает исключение — выбирайте осознанно.
3. Перемещение из `optional` не делает его пустым; для этого есть `reset()`.
4. `std::variant` — типобезопасное объединение; в отличие от иерархии классов не требует кучи, а компилятор проверяет полноту разбора.
5. Размер `variant` определяется самым большим из вариантов.
6. Структурные привязки убирают `first`/`second` и делают циклы по отображениям читаемыми.
7. `if constexpr` исключает невыбранную ветку из компиляции — это заменяет громоздкие приёмы работы с шаблонами.
8. Переходить на новый стандарт стоит тогда, когда компиляторы целевых систем его поддерживают; в остальном ограничения бывают только внешние.

## Упражнения

1. Соберите `demo-cpp17` (`cd demo-cpp17 && make`) и запустите все демонстрации. Разберитесь в выводе каждой.

2. Обратитесь к пустому `optional` через `*` вместо `value()`. Соберите с `-fsanitize=undefined` и посмотрите, что скажет детектор.

3. Добавьте в `variant` из демо четвёртый тип и не обрабатывайте его в посетителе. Какую ошибку выдаст компилятор?

4. Перепишите `BPlusTree::find` из главы 34 на `std::optional`. Что изменилось в коде вызывающей стороны?

5. Замените в любом файле книги обход отображения на структурные привязки. Сравните читаемость.

6. Напишите шаблон `print_size`, который для контейнеров печатает `size()`, для чисел — `sizeof`, а для остальных типов сообщает, что не знает. Используйте `if constexpr`.

7. (Сложнее) Перепишите `Statement` из главы 36 на `std::variant` с посетителем. Проверьте, что забытый вид команды теперь ловится компилятором.

8. (Сложнее) Реализуйте свой упрощённый `optional<T>` без выделения памяти: хранилище через `alignas` и `std::aligned_storage`, размещающее создание через placement new, деструктор, копирование и перемещение. Это упражнение показывает, сколько работы прячется за простым типом.

## Что дальше

Глава 49 — `std::filesystem`. Всю книгу мы работали с файлами через системные вызовы: `open`, `stat`, `mkdir`, `opendir`. В C++17 появилась библиотека, делающая то же самое переносимо и без возни с `errno`. Разберём, как она устроена, чем `path` лучше `std::string`, почему у каждой функции есть две версии — с исключением и с кодом ошибки, — и где эта библиотека всё-таки не поможет.

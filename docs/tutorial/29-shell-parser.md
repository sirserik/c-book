# Глава 29. Парсер командной строки

Наш токенизатор до сих пор состоял из четырёх строк: положили строку в `istringstream` и вычерпали слова оператором `>>`. Для `ls -1 | wc -l` этого хватало, но стоит появиться кавычкам — и всё рассыпается:

```
myshell$ sh -c "exit 42"
42": -c: line 0: unexpected EOF while looking for matching `"'
[exit 2]
```

Строка развалилась на четыре слова: `sh`, `-c`, `"exit`, `42"`. Кавычки остались внутри слов, а пробел между ними разрезал аргумент пополам.

В этой главе напишем настоящий токенизатор — с двойными и одинарными кавычками, с экранированием обратным слэшем, — и научим оболочку понимать перенаправления `>`, `>>`, `<`, `2>`, `2>>` и `2>&1`. Заодно у структуры `Command`, заведённой в главе 27, наконец появится второе поле, а в проекте — первые тесты.

Задача эта родственна разбору мира в главе 23, но требовательнее: там формат придумывали мы сами и могли сделать его удобным, здесь синтаксис задан сорока годами традиции, и отступать от него нельзя — пользователь ждёт, что `echo "a b"` сработает точно так же, как в `bash`.

## Что должно получиться

Возьмём строку:

```
grep "hello world" file.txt > result.txt 2>&1
```

Разобрать её нужно так: команда `grep` с аргументами `grep`, `hello world` и `file.txt`, плюс два перенаправления — вывод в `result.txt` и поток ошибок туда же, куда вывод. Кавычки при этом должны исчезнуть: программа `grep` получит аргумент `hello world` без них, ведь кавычки — синтаксис оболочки, а не часть данных.

Структуры для этого уже почти готовы. Дополним `include/pipeline.h`:

```cpp
struct Redirect {
    enum Type {
        Input,        // < file
        Output,       // > file
        Append,       // >> file
        ErrOutput,    // 2> file
        ErrAppend,    // 2>> file
        ErrToOut,     // 2>&1 (без файла)
    };
    Type type;
    std::string target;  // имя файла; пусто для ErrToOut
};

struct Command {
    std::vector<std::string> argv;
    std::vector<Redirect> redirects;
};

struct Pipeline {
    std::vector<Command> commands;

    bool empty() const { return commands.empty(); }
    std::size_t size() const { return commands.size(); }
};
```

`Redirect` — тип и цель. `ErrToOut` единственный обходится без цели: `2>&1` не открывает файл, а связывает один дескриптор с другим.

Порядок перенаправлений хранится в `vector` не случайно. Как увидим ближе к концу главы, `> out 2>&1` и `2>&1 > out` дают разный результат, и единственный способ воспроизвести поведение `bash` — применять их строго в том порядке, в каком они написаны.

## Две ступени разбора

Разбор традиционно делят на две независимые ступени.

Токенизатор (его же называют лексером) работает с символами и ничего не знает про команды. Его дело — понять, где кончается одно слово и начинается другое, снять кавычки, обработать экранирование и выделить служебные символы в отдельные токены. На выходе — плоский список строк.

Парсер работает уже с токенами и ничего не знает про кавычки. Его дело — увидеть в списке структуру: разбить по `|` на команды, отделить перенаправления от аргументов, проверить, что после `>` действительно стоит имя файла.

Разделение стоит держать в голове, потому что оно окупается сразу. Каждая ступень получается небольшой и проверяемой отдельно; ошибка «незакрытая кавычка» рождается в токенизаторе, ошибка «редирект без файла» — в парсере, и по тексту сообщения сразу понятно, куда смотреть. Ровно так же устроены настоящие компиляторы, только там между лексером и парсером стоит ещё грамматика посерьёзнее.

## Токенизатор

Требований к нему шесть.

Пробелы и табуляции разделяют слова — но только вне кавычек. Двойные кавычки `"..."` собирают всё внутри в одно слово, при этом обратный слэш внутри них экранирует четыре символа: `"`, `\`, `$` и обратную кавычку. Одинарные кавычки `'...'` берут содержимое буквально, без единого исключения — внутри них не работает даже экранирование. Обратный слэш вне кавычек экранирует любой следующий символ. Служебные `|`, `<`, `>`, `>>` становятся отдельными токенами, даже если написаны вплотную к слову. И, наконец, `2>`, `2>>`, `2>&1` тоже отдельные токены, но распознаются только в начале слова — иначе `file2.txt` развалилось бы на куски.

Всё это естественно ложится на конечный автомат с тремя состояниями: «обычный текст», «внутри двойных кавычек», «внутри одинарных». Переписываем `src/exec_runner.cpp` целиком:

```cpp
#include "exec_runner.h"

#include <stdexcept>
#include <string>
#include <vector>

namespace shell {

namespace {

// Распознать на позиции i спец-токен. Возвращает длину поглощённых символов
// и сам токен. 0 — не спец.
std::size_t match_special(const std::string& s, std::size_t i, std::string& out) {
    if (i >= s.size()) return 0;
    char c = s[i];

    if (c == '|') { out = "|"; return 1; }
    if (c == '<') { out = "<"; return 1; }
    if (c == '>') {
        if (i + 1 < s.size() && s[i + 1] == '>') { out = ">>"; return 2; }
        out = ">"; return 1;
    }
    return 0;
}

}  // namespace

std::vector<std::string> tokenize(const std::string& line) {
    std::vector<std::string> tokens;
    std::string current;
    bool in_dq = false;   // double quote
    bool in_sq = false;   // single quote

    auto flush = [&]() {
        if (!current.empty()) {
            tokens.push_back(std::move(current));
            current.clear();
        }
    };

    for (std::size_t i = 0; i < line.size(); ++i) {
        char c = line[i];

        if (in_sq) {
            if (c == '\'') in_sq = false;
            else current += c;
            continue;
        }

        if (in_dq) {
            if (c == '"') {
                in_dq = false;
            } else if (c == '\\' && i + 1 < line.size() &&
                       (line[i + 1] == '"' || line[i + 1] == '\\' ||
                        line[i + 1] == '$' || line[i + 1] == '`')) {
                current += line[++i];
            } else {
                current += c;
            }
            continue;
        }

        // Вне кавычек.
        if (c == '\'') { in_sq = true; continue; }
        if (c == '"')  { in_dq = true; continue; }

        if (c == '\\' && i + 1 < line.size()) {
            current += line[++i];
            continue;
        }

        if (c == ' ' || c == '\t') {
            flush();
            continue;
        }

        // 2>, 2>>, 2>&1 — только в начале слова.
        if (current.empty() && c == '2' && i + 1 < line.size() && line[i + 1] == '>') {
            if (i + 3 < line.size() &&
                line[i + 2] == '&' && line[i + 3] == '1') {
                tokens.push_back("2>&1");
                i += 3;
                continue;
            }
            if (i + 2 < line.size() && line[i + 2] == '>') {
                tokens.push_back("2>>");
                i += 2;
                continue;
            }
            tokens.push_back("2>");
            i += 1;
            continue;
        }

        std::string spec;
        std::size_t consumed = match_special(line, i, spec);
        if (consumed > 0) {
            flush();
            tokens.push_back(spec);
            i += consumed - 1;
            continue;
        }

        current += c;
    }

    if (in_sq || in_dq) {
        throw std::runtime_error("незакрытая кавычка");
    }

    flush();
    return tokens;
}

}  // namespace shell
```

Разберём по частям.

Лямбда `flush` сбрасывает накопленное слово в список токенов и очищает накопитель. Условие `if (!current.empty())` избавляет нас от пустых токенов при двойных пробелах: строка `ls   -l` даст два слова, а не четыре. У этой мелочи есть побочный эффект, о котором скажу ниже, — `echo ""` теряет пустой аргумент.

Ветка `in_sq` — самая простая во всём коде, и это отражает суть одинарных кавычек. Внутри них нет ничего, кроме символов: закрывающая кавычка заканчивает режим, всё остальное копируется как есть. Поэтому вставить одинарную кавычку внутрь одинарных кавычек невозможно в принципе — ни в нашей оболочке, ни в `bash`. Классический обход выглядит пугающе: `'don'\''t'` — закрыли кавычку, поставили экранированный апостроф, открыли снова.

Ветка `in_dq` сложнее ровно на одно правило: обратный слэш экранирует, но лишь четыре символа. Это не наша прихоть, а поведение `bash`: внутри двойных кавычек `\n` остаётся двумя символами, слэшем и буквой, а вот `\"` превращается в кавычку. Смысл в том, что внутри двойных кавычек специальными остаются только `$`, обратная кавычка и сама кавычка — экранировать имеет смысл лишь их.

Дальше идёт обычный режим. Кавычки включают соответствующее состояние и в слово не попадают. Обратный слэш забирает следующий символ буквально — так работает `echo a\ b`, дающий одно слово `a b`. Пробел и табуляция завершают слово.

Отдельного внимания заслуживает условие `current.empty()` перед разбором `2>`. Без него строка `cat file2.txt` распалась бы на `cat`, `file`, `2>`, `.txt` — токенизатор увидел бы двойку с угловой скобкой в середине имени файла и радостно принял бы её за перенаправление. Проверка «накопитель пуст» означает «мы в начале слова», и этого достаточно. В `bash`, кстати, правило то же самое, только там оно сформулировано через понятие «номер дескриптора перед оператором».

Функция `match_special` возвращает не токен, а число поглощённых символов — так вызывающий код узнаёт, на сколько сдвинуть позицию. Для `>>` это два символа, для `>` один. В цикле пишем `i += consumed - 1`, потому что `++i` в заголовке `for` добавит недостающую единицу. Такие смещения — обычный источник ошибок «на единицу», и тесты, которые мы сейчас напишем, ловят их первыми.

Незакрытая кавычка в конце строки — синтаксическая ошибка, и мы бросаем исключение. `bash` в этой ситуации ведёт себя дружелюбнее: печатает вторичное приглашение `>` и ждёт продолжения, собирая многострочную команду. Нам такое поведение стоило бы переделки цикла REPL, и я его сознательно не делаю — зато в конце главы есть упражнение.

## Тесты токенизатора

Токенизатор — идеальный кандидат для юнит-тестов: чистая функция, строка на входе, вектор строк на выходе, никаких системных вызовов. Наш `Makefile` из главы 26 уже умеет собирать тесты (цель `tests`), но каталог `tests/` до сих пор пустовал. Создадим `tests/test_tokenize.cpp`:

```cpp
#include "exec_runner.h"
#include "pipeline.h"

#include <iostream>
#include <stdexcept>
#include <string>
#include <vector>

namespace {

int failures = 0;
int checks = 0;

std::string join(const std::vector<std::string>& v) {
    std::string r;
    for (std::size_t i = 0; i < v.size(); ++i) {
        if (i) r += " | ";
        r += "[" + v[i] + "]";
    }
    return r;
}

void expect_tokens(const std::string& line,
                   const std::vector<std::string>& expected) {
    ++checks;
    std::vector<std::string> got = shell::tokenize(line);
    if (got != expected) {
        ++failures;
        std::cout << "FAIL  tokenize(\"" << line << "\")\n"
                  << "  ждали:  " << join(expected) << "\n"
                  << "  выдало: " << join(got) << "\n";
    }
}

void expect_throw(const std::string& line) {
    ++checks;
    try {
        shell::tokenize(line);
        ++failures;
        std::cout << "FAIL  tokenize(\"" << line << "\") — ждали исключение\n";
    } catch (const std::runtime_error&) {
        // как и задумано
    }
}

}  // namespace
```

Никакого фреймворка — та же самодельная схема, что в тестах RPG из главы 25: счётчик проверок, счётчик провалов, понятное сообщение при расхождении. Сравнение векторов строк работает само: `operator==` для `std::vector` сравнивает поэлементно, а для `std::string` — посимвольно.

Сами проверки:

```cpp
int main() {
    // Простые слова.
    expect_tokens("echo hello", {"echo", "hello"});
    expect_tokens("  ls   -l  ", {"ls", "-l"});
    expect_tokens("", {});

    // Кавычки.
    expect_tokens("echo \"hello world\"", {"echo", "hello world"});
    expect_tokens("echo 'hello world'", {"echo", "hello world"});
    expect_tokens("echo 'one \"two\"'", {"echo", "one \"two\""});
    expect_tokens("echo \"a'b\"", {"echo", "a'b"});
    expect_tokens("echo \"\"", {"echo"});          // пустое слово теряется

    // Escape.
    expect_tokens("echo a\\ b", {"echo", "a b"});
    expect_tokens("echo \"a\\\"b\"", {"echo", "a\"b"});
    expect_tokens("echo 'a\\b'", {"echo", "a\\b"});  // внутри '' escape не работает

    // Спец-токены.
    expect_tokens("ls | wc", {"ls", "|", "wc"});
    expect_tokens("ls|wc", {"ls", "|", "wc"});
    expect_tokens("cmd > file.txt", {"cmd", ">", "file.txt"});
    expect_tokens("cmd >> file.txt", {"cmd", ">>", "file.txt"});
    expect_tokens("cmd < in.txt", {"cmd", "<", "in.txt"});
    expect_tokens("cmd 2> err.txt", {"cmd", "2>", "err.txt"});
    expect_tokens("cmd 2>> err.txt", {"cmd", "2>>", "err.txt"});
    expect_tokens("cmd 2>&1", {"cmd", "2>&1"});

    // Цифра 2 в середине слова — не редирект.
    expect_tokens("cat file2.txt", {"cat", "file2.txt"});

    // Незакрытые кавычки.
    expect_throw("echo \"no end");
    expect_throw("echo 'no end");
    ...
```

Обратите внимание на двойное экранирование в строковых литералах C++. Чтобы проверить пользовательский ввод `echo "hello world"`, в исходнике надо написать `"echo \"hello world\""`; чтобы проверить `echo a\ b` — написать `"echo a\\ b"`. Первый слой экранирования съедает компилятор C++, второй — наш токенизатор. Путаться тут нормально, и лучший способ не запутаться — держать в голове, что именно увидит пользователь.

Три теста заслуживают отдельного слова.

`expect_tokens("ls|wc", {"ls", "|", "wc"})` подтверждает, что теперь вертикальная черта не нуждается в пробелах. В главе 27 наивный токенизатор этого не умел, и я обещал, что ограничение исчезнет, — вот оно и исчезло, само собой, потому что `match_special` разрезает слово в любом месте.

`expect_tokens("cat file2.txt", {"cat", "file2.txt"})` — тот самый случай, ради которого написано условие `current.empty()`. Уберите его — и тест немедленно покраснеет.

`expect_tokens("echo \"\"", {"echo"})` фиксирует известное расхождение с `bash`. Настоящая оболочка передала бы `echo` пустой аргумент, и вывелась бы пустая строка; у нас пустое слово теряется в `flush`. Тест написан не для того, чтобы одобрить это поведение, а чтобы оно было зафиксировано: если однажды вы почините пустые аргументы, тест напомнит о себе и его нужно будет обновить. Тесты, описывающие текущие ограничения, полезны не меньше тестов, описывающих правильную работу.

g++ ... build/tests/test_tokenize.o build/builtins.o build/exec_runner.o \

## Парсер

Токены есть, пора собирать из них структуру. Работа делится на две функции: внешняя режет список по `|`, внутренняя разбирает один кусок.

```cpp
Pipeline parse_pipeline(const std::string& line) {
    Pipeline p;
    auto tokens = tokenize(line);
    if (tokens.empty()) return p;

    // Разбиваем по `|` на сегменты, каждый — Command.
    auto seg_start = tokens.begin();
    for (auto it = tokens.begin(); it != tokens.end(); ++it) {
        if (*it == "|") {
            if (seg_start == it) {
                throw std::runtime_error("пустая команда перед '|'");
            }
            p.commands.push_back(parse_command(seg_start, it));
            seg_start = it + 1;
        }
    }
    if (seg_start != tokens.end()) {
        p.commands.push_back(parse_command(seg_start, tokens.end()));
    } else {
        throw std::runtime_error("пустая команда после '|'");
    }

    // Проверка: каждая команда имеет хотя бы один аргумент.
    for (const auto& cmd : p.commands) {
        if (cmd.argv.empty()) {
            throw std::runtime_error("команда без названия");
        }
    }
    return p;
}
```

Сегменты задаются парой итераторов — от `seg_start` до найденной черты. Такой способ передачи диапазона привычен по алгоритмам STL из главы 14 и избавляет от копирования кусков вектора.

Три проверки покрывают все способы ошибиться с чертой. `seg_start == it` означает, что между началом сегмента и чертой ничего нет, — так ловится `| ls` и `ls || wc` (две черты подряд). Условие `seg_start != tokens.end()` после цикла проверяет, что за последней чертой что-то есть, — так ловится `ls |`. И финальный проход по командам ловит случай, когда токены есть, а имени команды нет: `> out.txt` состоит из двух токенов, но запускать нечего.

Последняя проверка нужна ещё и потому, что `parse_command` спокойно возвращает команду без `argv`, если ей достались одни перенаправления. Разделение обязанностей здесь такое: `parse_command` разбирает то, что видит, а осмысленность целого проверяет `parse_pipeline`.

Теперь разбор одной команды:

```cpp
bool is_redirect_token(const std::string& t) {
    return t == "<" || t == ">" || t == ">>" ||
           t == "2>" || t == "2>>" || t == "2>&1";
}

Redirect::Type redirect_type_for(const std::string& t) {
    if (t == "<")    return Redirect::Input;
    if (t == ">")    return Redirect::Output;
    if (t == ">>")   return Redirect::Append;
    if (t == "2>")   return Redirect::ErrOutput;
    if (t == "2>>")  return Redirect::ErrAppend;
    if (t == "2>&1") return Redirect::ErrToOut;
    throw std::runtime_error("не редирект: " + t);
}

Command parse_command(std::vector<std::string>::iterator begin,
                      std::vector<std::string>::iterator end) {
    Command cmd;
    for (auto it = begin; it != end; ++it) {
        if (is_redirect_token(*it)) {
            Redirect r;
            r.type = redirect_type_for(*it);
            if (r.type == Redirect::ErrToOut) {
                // 2>&1 — без аргумента-файла
            } else {
                if (it + 1 == end || is_redirect_token(*(it + 1)) || *(it + 1) == "|") {
                    throw std::runtime_error("редирект '" + *it + "' без файла");
                }
                ++it;
                r.target = *it;
            }
            cmd.redirects.push_back(std::move(r));
        } else {
            cmd.argv.push_back(*it);
        }
    }
    return cmd;
}
```

Логика простая: встретили служебный токен — значит, началось перенаправление, и следующий токен (кроме случая `2>&1`) должен быть именем файла. Всё остальное — аргументы.

Проверка перед `++it` разбирает три способа написать перенаправление без файла: строка кончилась (`ls >`), дальше идёт другое перенаправление (`ls > > x`), дальше идёт черта (`ls > | wc`). Без неё `++it` шагнул бы за конец диапазона — и мы получили бы чтение чужой памяти вместо внятного сообщения об ошибке.

Важная деталь: перенаправления вынимаются из потока аргументов, а не остаются в нём. Команда `ls -l > out.txt` даст `argv` из двух элементов, `ls` и `-l`; про файл знает только `Redirect`. Программе `ls` о перенаправлении знать незачем, для неё вывод как шёл в дескриптор 1, так и идёт.

## Применение перенаправлений

Разбор закончен, пора выполнять. Перенаправления применяются в ребёнке, после `fork` и до `exec`, — в том самом промежутке, ради которого в Unix и разделили создание процесса на два шага.

```cpp
// Применить редиректы в текущем процессе (вызывается в ребёнке).
// При ошибке завершается с _exit.
void apply_redirects(const std::vector<Redirect>& redirects) {
    for (const auto& r : redirects) {
        switch (r.type) {
            case Redirect::Input: {
                int fd = open(r.target.c_str(), O_RDONLY);
                if (fd < 0) {
                    std::cerr << r.target << ": " << std::strerror(errno) << "\n";
                    _exit(1);
                }
                dup2(fd, STDIN_FILENO);
                close(fd);
                break;
            }
            case Redirect::Output: {
                int fd = open(r.target.c_str(),
                              O_WRONLY | O_CREAT | O_TRUNC, 0644);
                if (fd < 0) {
                    std::cerr << r.target << ": " << std::strerror(errno) << "\n";
                    _exit(1);
                }
                dup2(fd, STDOUT_FILENO);
                close(fd);
                break;
            }
            case Redirect::Append: {
                int fd = open(r.target.c_str(),
                              O_WRONLY | O_CREAT | O_APPEND, 0644);
                if (fd < 0) {
                    std::cerr << r.target << ": " << std::strerror(errno) << "\n";
                    _exit(1);
                }
                dup2(fd, STDOUT_FILENO);
                close(fd);
                break;
            }
            case Redirect::ErrOutput: {
                int fd = open(r.target.c_str(),
                              O_WRONLY | O_CREAT | O_TRUNC, 0644);
                if (fd < 0) {
                    std::cerr << r.target << ": " << std::strerror(errno) << "\n";
                    _exit(1);
                }
                dup2(fd, STDERR_FILENO);
                close(fd);
                break;
            }
            case Redirect::ErrAppend: {
                int fd = open(r.target.c_str(),
                              O_WRONLY | O_CREAT | O_APPEND, 0644);
                if (fd < 0) {
                    std::cerr << r.target << ": " << std::strerror(errno) << "\n";
                    _exit(1);
                }
                dup2(fd, STDERR_FILENO);
                close(fd);
                break;
            }
            case Redirect::ErrToOut: {
                // stderr → туда же, куда stdout сейчас идёт.
                dup2(STDOUT_FILENO, STDERR_FILENO);
                break;
            }
        }
    }
}
```

Код повторяется, и это осознанный выбор: пять почти одинаковых веток читаются легче, чем одна с тремя флагами-параметрами. Если такое повторение вас смущает, вынесите открытие в маленькую функцию `open_or_die(target, flags)` — это упражнение в конце главы.

Каждая ветка делает одно и то же в три шага: открыть файл с нужными флагами, `dup2` на нужный стандартный дескриптор, закрыть оригинал. Порядок последних двух действий важен, и мы разбирали его в главе 27: сначала дублируем, потом закрываем.

Флаги `open` стоит запомнить, они встречаются постоянно. `O_RDONLY` — только чтение, для `<`. Комбинация `O_WRONLY | O_CREAT | O_TRUNC` — только запись, создать, если файла нет, обрезать до нуля, если есть; это `>`. Комбинация `O_WRONLY | O_CREAT | O_APPEND` — то же самое, но каждая запись идёт в конец файла; это `>>`. Флаг `O_APPEND` не просто ставит позицию в конец при открытии — он делает это атомарно перед каждой записью, поэтому два процесса, дописывающих в один лог, не затирают строки друг друга.

Третий аргумент `0644` — права доступа для нового файла, в восьмеричной записи: владельцу чтение и запись, остальным только чтение. Ноль в начале и означает восьмеричную систему. Права из этого числа реальный файл получит не целиком: ядро вычтет из них маску `umask` процесса, о которой шла речь в главе 5. При обычной маске `022` из `0644` получится `0644`, а вот `0666` превратится в `0644`.

Ошибка открытия обрабатывается жёстко — сообщение и `_exit(1)`. Мягче нельзя: мы уже в ребёнке, отступать некуда, а запускать программу с неперенаправленным выводом было бы хуже, чем не запускать вовсе. Именно так ведёт себя `bash`: `cat < nosuchfile` не выполняет `cat` вообще.

Ветка `ErrToOut` вообще не открывает файлов — `dup2(STDOUT_FILENO, STDERR_FILENO)` направляет поток ошибок туда же, куда в этот момент направлен вывод. Слова «в этот момент» здесь — самое главное.

## Порядок перенаправлений решает всё

Возьмём программу, которая пишет в оба потока:

```cpp
#include <iostream>
int main() {
    std::cout << "это stdout\n";
    std::cerr << "это stderr\n";
    return 0;
}
```

И запустим её в нашей оболочке двумя способами:

```
myshell$ /tmp/errout > /tmp/o1.txt 2>&1
myshell$ /tmp/errout 2>&1 > /tmp/o2.txt
это stderr
```

```bash
$ cat /tmp/o1.txt
это stdout
это stderr
$ cat /tmp/o2.txt
это stdout
```

В первом случае в файле оба потока. Во втором — только вывод, а ошибка осталась на экране, хотя написано, казалось бы, то же самое.

Разгадка в порядке применения. В первом случае сначала `>` подменяет дескриптор 1 файлом, а затем `2>&1` копирует дескриптор 1 — уже указывающий на файл — в дескриптор 2. Оба потока в файле.

Во втором случае сначала `2>&1` копирует дескриптор 1 — а он в этот момент ещё указывает на терминал — в дескриптор 2. Ошибки прибиты к терминалу. И только потом `>` перенаправляет дескриптор 1 в файл; дескриптора 2 это уже не касается, он давно скопирован.

Это самый известный подвох `bash`, и запоминается он одной фразой: `2>&1` копирует то, куда дескриптор указывает **сейчас**, а не создаёт вечную связь. Отсюда правило: `> file 2>&1` отправляет в файл всё, а `2>&1 > file` — только вывод.

Наша оболочка воспроизводит это поведение бесплатно, потому что хранит перенаправления в векторе по порядку и применяет их подряд. Стоило бы нам, скажем, отсортировать их или сложить в `map` по типу — и совместимость с `bash` сломалась бы.

## Перенаправления вместе с конвейером

Что будет, если у команды есть и черта, и перенаправление?

```
myshell$ ls Makefile > /tmp/o3.txt | wc -l
       0
```

```bash
$ cat /tmp/o3.txt
Makefile
```

Вывод `ls` ушёл в файл, а `wc` не получил ничего и насчитал ноль строк. Так и должно быть: побеждает то, что применено последним, а порядок в нашем коде задан явно:

```cpp
if (pid == 0) {
    restore_default_signal_handlers();

    if (i > 0) {
        dup2(pipes[i - 1][0], STDIN_FILENO);
    }
    if (i < n - 1) {
        dup2(pipes[i][1], STDOUT_FILENO);
    }
    close_all_pipes(pipes);

    // Редиректы применяются ПОСЛЕ pipe-dup2, поэтому они «победнее».
    // То есть `cmd > file | other` — stdout cmd идёт в file, не в pipe.
    apply_redirects(p.commands[i].redirects);

    auto argv = to_c_argv(p.commands[i].argv);
    execvp(argv[0], argv.data());
    std::cerr << "exec '" << argv[0] << "' failed: "
              << std::strerror(errno) << "\n";
    _exit(127);
}
```

Сначала конвейер, потом перенаправления — значит, перенаправление затирает конвейер. `bash` ведёт себя точно так же, и `wc` в нём тоже напечатает ноль. Заодно обратите внимание, что `wc` не завис: пишущий конец канала закрыт всеми, кто его держал, поэтому конец данных наступил сразу.

## Чего парсер не умеет

Настоящая оболочка умеет намного больше, и честнее перечислить пропущенное, чем делать вид, что его не существует. Ни одну из этих возможностей мы реализовывать не будем — но каждая упирается в понятную работу, а не в магию.

Последовательности `;`, `&&` и `||` требуют ещё одного уровня разбора: сейчас вершина нашего дерева — конвейер, а нужна цепочка конвейеров со связками между ними. Работы примерно на одну функцию `parse_sequence` и небольшой цикл выполнения, который смотрит на код возврата предыдущего конвейера.

Подстановка переменных `$HOME` живёт в токенизаторе: увидели `$`, собрали имя, вызвали `getenv`, подставили значение. Тонкость в том, что подстановка работает вне кавычек и внутри двойных, но не внутри одинарных, — как раз то различие, ради которого в нашем автомате уже есть три состояния.

Раскрытие шаблонов `*.cpp` делается после токенизации и до запуска: каждое слово с `*`, `?` или `[...]` разворачивается в список подходящих имён файлов. Руками это писать не нужно, в POSIX есть функция `glob` из `<glob.h>`.

Пустой аргумент `echo ""` теряется — про это мы уже говорили, и лечится оно флагом «слово было в кавычках, сбрось его даже пустым».

Многострочный ввод (незакрытая кавычка, вложенный документ `<< EOF`) требует переделки цикла REPL: оболочка должна понимать, что команда не закончилась, и запрашивать продолжение.

Фоновый запуск `&` вообще не про парсер — распознать амперсанд легко, а вот дальше нужны список задач, обработчик SIGCHLD и команды `jobs`, `fg`, `bg`. Это управление задачами, о котором шла речь в конце главы 28.

## Три ступени, если посмотреть сверху

Если отойти на шаг, наша оболочка выглядит так:

```
строка от пользователя
        ↓  tokenize        — состояния: текст, "…", '…', escape
   список токенов
        ↓  parse_pipeline  — режет по '|', проверяет структуру
        ↓  parse_command   — отделяет редиректы от аргументов
      Pipeline
        ↓  run_pipeline    — fork, dup2, exec, waitpid
     результат
```

Это в миниатюре та же схема, по которой устроен любой компилятор или интерпретатор: лексер превращает текст в токены, парсер — токены в дерево, исполнитель обходит дерево и что-то делает. В `gcc` между второй и третьей ступенью помещаются ещё оптимизации, а в Python дерево сначала превращается в байт-код, но каркас узнаётся сразу.

Именно поэтому имеет смысл писать парсеры руками хотя бы раз. Дальше вы будете брать готовые библиотеки — но уже понимая, что внутри.

## Главные правила главы

1. Лексер и парсер разделяют: первый знает про символы и кавычки, второй — про структуру команды.
2. Токенизатор с кавычками — это конечный автомат; состояний ровно столько, сколько видов кавычек, плюс обычный режим.
3. Значение символа зависит от позиции: `2>` в начале слова — перенаправление, в середине — часть имени.
4. Проверяйте границы перед тем, как заглянуть в следующий токен, иначе выйдете за конец диапазона.
5. Перенаправления применяются в ребёнке между `fork` и `exec`, строго в порядке написания.
6. `2>&1` копирует текущее назначение дескриптора, поэтому `> f 2>&1` и `2>&1 > f` дают разный результат.
7. Ошибка открытия файла в ребёнке означает `_exit`, а не запуск программы с неперенаправленным выводом.
8. Чистая функция вроде токенизатора обязана быть покрыта тестами — это дёшево и окупается сразу.

## Упражнения

1. Соберите оболочку и тесты (`make && make tests && ./build/tests/test_tokenize`). Проверьте вручную: `echo "Привет, мир"`, `echo it\'s`, `echo 'внутри "двойные"'`, `cat < Makefile | head -3`.

2. Уберите условие `current.empty()` из разбора `2>`, пересоберите тесты. Какой тест упал и что он теперь выдаёт? Верните условие обратно.

3. Напишите программу `errout`, печатающую строку в `stdout` и строку в `stderr`. Запустите её в оболочке четырьмя способами: `> f`, `2> f`, `> f 2>&1`, `2>&1 > f`. Для каждого объясните, что оказалось в файле и что на экране.

4. Добавьте перенаправление `&>` (весь вывод в файл, сокращение для `> f 2>&1`). Понадобится новый токен в `match_special`, новый тип в `Redirect` и новая ветка в `apply_redirects`.

5. Вынесите повторяющееся открытие файла из `apply_redirects` в функцию `int open_or_die(const std::string& path, int flags)`. Проверьте, что все тесты по-прежнему проходят и оболочка ведёт себя как раньше.

6. Реализуйте подстановку `$VAR` и `${VAR}` в токенизаторе. Внутри одинарных кавычек подстановки быть не должно. Добавьте тесты: `echo $HOME`, `echo "$HOME/x"`, `echo '$HOME'`.

7. (Сложнее) Реализуйте `;`, `&&` и `||`. Заведите структуру `Sequence` со списком конвейеров и связок, разберите её в `parse_sequence`, а в `main` выполняйте с учётом кодов возврата.

8. (Сложнее) Сделайте многострочный ввод: если `tokenize` бросил «незакрытая кавычка», оболочка печатает вторичное приглашение `> `, читает следующую строку, склеивает через `\n` и пробует разобрать снова.

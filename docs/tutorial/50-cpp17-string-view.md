# Глава 50. string_view и параллельные алгоритмы

Две темы, объединённые общим свойством: обе выглядят как бесплатное ускорение, и обе требуют понимания, что происходит внутри.

Первая — `std::string_view`, способ смотреть на чужую строку без копирования. Он действительно ускоряет разбор текста, и он же приносит с собой новый класс ошибок, которых в C++ раньше не было.

Вторая — параллельные алгоритмы, обещающие ускорение сортировки одним лишним параметром. С ними история поучительнее: сначала о том, что они дают, потом о том, почему на моей машине они не работают вовсе.

## Проблема копирования строк

Всякий раз, когда мы разбирали текст в этой книге, мы копировали куски строки. Токенизатор командной строки из главы 29 копирует каждое слово. Лексер SQL из главы 36 копирует каждый токен. Разбор мира RPG в главе 23 копирует каждое поле.

Каждая копия — выделение памяти в куче (если строка длиннее пятнадцати-двадцати символов) и пересылка байтов. Для строки, которая нужна только на время проверки, это чистая трата.

Обойти проблему можно было и раньше — парой «указатель плюс длина», — но такая пара неудобна: её надо передавать двумя аргументами, ей нельзя пользоваться как строкой, у неё нет методов.

`std::string_view` — это и есть указатель с длиной, но с интерфейсом строки:

```cpp
std::string_view sv = "какая-то строка";
sv.size();
sv.find(' ');
sv.substr(5, 3);
sv == "какая-то строка";
```

Всё как у `std::string`, кроме одного: `string_view` **не владеет** данными. Он смотрит на чужую память и обязан умереть раньше неё.

## Сколько выигрывает

Проверим на разборе текста в миллион слов. Две реализации разбиения на слова, отличающиеся только типом результата:

```cpp
std::vector<std::string> split_copy(const std::string& s);
std::vector<std::string_view> split_view(const std::string& s);
```

```
std::string:      20 мс (1000000 слов)
std::string_view: 10 мс (1000000 слов)
```

Вдвое быстрее. Выигрыш взялся из отсутствия выделений памяти: копирующая версия делает миллион выделений и миллион освобождений, версия с представлением — ни одного.

Выигрыш был бы ещё заметнее на длинных словах: короткие строки помещаются внутрь объекта `std::string` без обращения к куче (это называют оптимизацией коротких строк), и для них копирование почти бесплатно. Наши слова как раз короткие — отсюда «всего» вдвое.

Есть и второй выигрыш, менее очевидный. `substr` у `std::string` создаёт новую строку, у `string_view` — просто сдвигает указатель и длину:

```
=== срез не аллоцирует ===
исходная строка не тронута, срез = [move]
```

Значит, разбор текста можно строить целиком на срезах, не создавая ни одной новой строки, пока результат действительно не понадобится сохранить.

## Опасность, которой раньше не было

За удобство приходится платить, и плата — новый вид ошибок.

```cpp
std::string make_name() { return "Александра"; }

std::string_view bad = make_name();
std::cout << "после смерти строки: '" << bad << "'\n";
```

Временная строка, которую вернула функция, уничтожается в конце строки с инициализацией. `string_view` продолжает смотреть на освобождённую память. Результат:

```
после смерти строки: '���  �?��< ��f'
живая строка:        'Александра'
```

Мусор вместо имени — и это в лучшем случае; в худшем программа упадёт или отдаст чужие данные наружу.

К счастью, компиляторы такие случаи знают:

```
warning: object backing the pointer will be destroyed at the end of
the full-expression [-Wdangling-gsl]
```

А детектор адресов ловит обращение точно:

```
ERROR: AddressSanitizer: stack-use-after-scope
READ of size 20 ...
    #6 0x0001098569f1 in main dangling.cpp:11
```

Отсюда правила, которые надо соблюдать буквально.

Никогда не возвращайте `string_view` на локальную строку — она умрёт раньше. Никогда не сохраняйте `string_view` в поле объекта, если не уверены, что строка переживёт объект. Никогда не создавайте `string_view` из временного значения — той самой функции, возвращающей строку.

А вот где `string_view` уместен: параметр функции, которая только читает строку и не сохраняет её. Это, пожалуй, главное его применение:

```cpp
void log(std::string_view message);      // берёт и string, и литерал, и срез
bool starts_with(std::string_view s, std::string_view prefix);
```

Такая функция принимает без копирования и `std::string`, и строковый литерал, и кусок другой строки. Раньше для этого приходилось делать две перегрузки — для `const std::string&` и для `const char*`.

## Ещё одна тонкость: нулевой байт

`std::string_view` не обязан заканчиваться нулевым байтом, потому что он может смотреть на середину другой строки.

Отсюда следует запрет: у него нет метода `c_str()`, и передавать его в функции языка C нельзя:

```cpp
void open_file(std::string_view path) {
    // ::open(path.data(), ...);   // ОШИБКА: data() может не иметь \0 в конце
    std::string tmp(path);         // придётся скопировать
    ::open(tmp.c_str(), O_RDONLY);
}
```

Метод `data()` существует, но возвращает указатель на начало без гарантии завершающего нуля. Использовать его вместе с `size()` — правильно, использовать как строку C — ошибка, которая проявится на срезе.

Именно поэтому для путей в главе 49 существует отдельный тип `std::filesystem::path`, а не `string_view`: пути в конце концов уходят в системные вызовы, которым нужен нулевой байт.

## Где он пригодился бы нам

Токенизатор командной строки из главы 29 возвращает `std::vector<std::string>` — каждый токен копируется. С представлениями копий не было бы вовсе, а строка команды всё равно жива до конца разбора.

Лексер SQL из главы 36 копирует текст каждого токена в поле структуры. То же самое.

Разбор пути в `builtin_type` из главы 30 режет переменную `PATH` через `substr` — это выделение памяти на каждый каталог. С `string_view` разбор был бы без единого выделения; я даже упоминал это в той главе.

Общее правило: если строка живёт дольше, чем разбор, и результат разбора не переживает исходную строку — берите представления. Если результат надо сохранить надолго — копируйте.

## Параллельные алгоритмы

Вторая тема главы обещает большее за меньшее. В C++17 у алгоритмов появился первый параметр — политика выполнения:

```cpp
#include <execution>

std::sort(std::execution::par, v.begin(), v.end());
std::for_each(std::execution::par_unseq, v.begin(), v.end(), heavy_work);
```

Политик четыре. `seq` — последовательно, как обычно. `par` — параллельно на нескольких потоках. `par_unseq` — параллельно и с векторизацией, то есть с использованием команд, обрабатывающих несколько значений сразу. `unseq` (появилась в C++20) — только векторизация.

Идея прекрасна: одна строка, и алгоритм использует все ядра. Библиотека сама разбивает работу, создаёт потоки, собирает результат.

### Что нужно понимать до применения

Требования к переданной функции строже, чем кажется. Она не должна иметь состояния, не должна обращаться к общим данным без защиты, не должна бросать исключения (при исключении в параллельном алгоритме вызывается `std::terminate`, а не раскрутка стека). Иными словами, всё, о чём говорилось в главах 41 и 42, здесь ложится на вас.

Выигрыш есть не всегда. Разбиение работы и синхронизация стоят времени; на массиве из тысячи чисел параллельная сортировка окажется медленнее обычной. Порог начинается где-то с десятков тысяч элементов и сильно зависит от того, насколько дорога операция над одним элементом.

И порядок обхода перестаёт быть определённым. `std::for_each` с политикой `par` может обойти элементы в любом порядке; полагаться на последовательность нельзя.

### А теперь неприятное

Всё вышесказанное — теория, и вот почему.

```bash
$ g++ -std=c++17 exec_test.cpp -o exec_test
error: no member named 'par' in namespace 'std::execution'
```

Заголовок `<execution>` есть, а политик в нём нет. Реализация libc++, которая поставляется с Apple Clang, параллельные алгоритмы не поддерживает — точнее, поддерживает частично и только в свежих версиях, собранных особым образом.

С GCC на Linux ситуация другая, но тоже не безоблачная: там параллельные алгоритмы работают, если установлена библиотека Intel TBB, и линковать надо с `-ltbb`. Без неё код соберётся, но выполнится последовательно.

Отсюда практический вывод, который важнее самих алгоритмов: **наличие возможности в стандарте не означает её наличия у вас**. Между принятием стандарта и появлением рабочей реализации проходят годы, а на некоторых платформах не появляется вовсе.

Поэтому я не стал писать демонстрацию параллельных алгоритмов — она не собралась бы на моей машине, а печатать в книге непроверенный код нечестно. Если они вам нужны, проверьте доступность на своей платформе и сравните с альтернативами: пул потоков, написанный руками, даёт больше контроля, а библиотеки вроде TBB — больше возможностей.

## Главные правила главы

1. `string_view` — указатель плюс длина с интерфейсом строки; он не владеет данными.
2. Разбор текста на представлениях вдвое быстрее, потому что не делает выделений памяти.
3. `substr` у представления не выделяет память, а сдвигает границы.
4. Представление обязано умереть раньше строки, на которую смотрит; временные значения — источник висящих ссылок.
5. Компилятор предупреждает о таких ошибках (`-Wdangling-gsl`), а детектор адресов ловит их точно.
6. У представления нет `c_str()` и нет гарантии завершающего нуля — в функции языка C его передавать нельзя.
7. Лучшее применение — параметр функции, которая только читает строку.
8. Параллельные алгоритмы есть в стандарте, но не везде в реализациях; проверяйте доступность до того, как рассчитывать на них.

## Упражнения

1. Соберите и запустите `./build/string_view_demo`. Разберитесь, где в нём происходит копирование, а где нет.

2. Повторите замер разбиения на слова на своей машине. Затем удлините слова до пятидесяти символов и повторите — как изменилось соотношение и почему?

3. Воспроизведите висящую ссылку: создайте `string_view` из временной строки. Соберите с предупреждениями, потом с `-fsanitize=address` и сравните, что скажет каждый инструмент.

4. Перепишите `tokenize` из главы 29 на `std::string_view`. Что придётся изменить в вызывающем коде и почему нельзя просто поменять тип?

5. Напишите функцию `bool has_extension(std::string_view path, std::string_view ext)` без единого выделения памяти. Проверьте на пути без расширения и на имени вроде `.gitignore`.

6. Проверьте на своей машине, доступны ли параллельные алгоритмы: соберите пример с `std::execution::par`. Если не собирается — найдите в документации своего компилятора, что для этого нужно.

7. (Сложнее) Замерьте параллельную и обычную сортировку на массивах в тысячу, сто тысяч и десять миллионов элементов (если параллельные алгоритмы доступны). Найдите порог, начиная с которого параллельная версия выигрывает.

8. (Сложнее) Напишите свой параллельный `for_each` на пуле потоков: разбейте диапазон на части по числу ядер, обработайте каждую в своём потоке, дождитесь всех. Сравните с последовательной версией на тяжёлой операции.

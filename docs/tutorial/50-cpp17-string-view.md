# Глава 50. std::string_view и параллельные алгоритмы

Ещё две новинки C++17, которые стоят отдельного разговора. Первая — **`std::string_view`** — встречается в реальном коде постоянно, и именно её не хватало нашим парсерам в RPG, shell и DB: мы рубили строки на токены и каждый раз создавали новый `std::string`, то есть новую аллокацию на кучу. Вторая — **параллельные алгоритмы** — это `std::sort`, `std::for_each` и компания, которым одним аргументом говоришь «выполняйся на всех ядрах».

С `string_view` мы разберёмся подробно, с демо и переписыванием токенизатора. С параллельными алгоритмами — обзорно: к ним есть важная оговорка про поддержку компиляторами, о которой я честно скажу ниже.

## std::string_view — строка, которой не владеют

Вспомните, что такое `std::string`: он **владеет** буфером символов на куче. Создал строку — выделилась память; скопировал строку — выделилась ещё раз; вышел из области видимости — освободилась. Это надёжно, но не бесплатно.

Теперь представьте парсер. На входе одна большая строка:

```cpp
std::string line = "move north quickly";
```

Мы хотим разбить её на слова. Классический способ:

```cpp
std::vector<std::string> tokenize(const std::string& line) {
    std::vector<std::string> tokens;
    // ... режем по пробелам, каждый кусок копируем в новый std::string
    tokens.push_back(line.substr(start, len));   // ← аллокация на каждый токен!
}
```

`line.substr(...)` возвращает **новый** `std::string` — отдельный буфер на куче. Три слова — три аллокации. А ведь символы уже лежат в памяти, в исходной `line`. Зачем их копировать?

`std::string_view` — это **указатель плюс длина**, и больше ничего:

```cpp
#include <string_view>

std::string_view sv = "hello world";
// внутри: const char* ptr → 'h', std::size_t size = 11
```

Он не владеет символами, не копирует их, не аллоцирует память. Он просто **смотрит** на чужие символы. Отсюда название — «view», вид, окно.

### Что умеет string_view

Почти весь интерфейс `std::string`, только для чтения:

```cpp
std::string_view sv = "hello world";

sv.size();              // 11
sv.empty();             // false
sv[0];                  // 'h'
sv.front();             // 'h'
sv.back();              // 'd'
sv.substr(0, 5);        // "hello" — это тоже string_view, НЕ копия!
sv.find("world");       // 6
sv == "hello world";    // сравнение работает
```

Главная магия — `substr`. У `std::string` он делает копию. У `string_view` — возвращает **другой view** на тот же буфер: просто сдвигает указатель и меняет длину. Ноль аллокаций.

Есть и две специфичные операции — подрезать концы без копий:

```cpp
sv.remove_prefix(2);    // сдвинуть начало на 2 символа вправо
sv.remove_suffix(3);    // отрезать 3 символа с конца
```

Это меняет сам `sv` (его указатель и длину), исходные символы не трогаются.

### Главная ловушка: view не продлевает жизнь

`string_view` не владеет данными — значит, символы, на которые он смотрит, **обязаны его пережить**. Иначе получите указатель на освобождённую память (мы это называли *dangling* в главе 11).

Классическая ошибка:

```cpp
std::string_view bad() {
    std::string local = "временная строка";
    return local;        // ← возвращаем view на локальную строку!
}                        //   local умирает здесь, view смотрит в никуда
```

Компилируется без ошибок, а при использовании — UB. Правило простое: **не храните `string_view` дольше, чем живёт строка-источник**. Как параметр функции и короткоживущая локальная переменная — идеально. Как поле класса, переживающее источник, — опасно.

Второй нюанс: `string_view` **не гарантирует нуль-терминатор**. Обычный C-string заканчивается `'\0'`, и функции вроде `printf("%s")` или `fopen` на это рассчитывают. А `string_view` — это кусок чужого буфера, после него может стоять что угодно. Поэтому нельзя писать `some_c_api(sv.data())` — передастся указатель, но без длины C-функция прочитает за границу. Если нужен настоящий C-string, придётся скопировать: `std::string(sv).c_str()`.

### Параметр функции: string_view вместо const std::string&

Долгие годы каноном для «принять строку только на чтение» был `const std::string&`. У него есть скрытая цена:

```cpp
void process(const std::string& s);

process("literal");        // создаётся временный std::string — аллокация!
process(some_char_buffer); // тоже временный std::string
```

Литерал `"literal"` — это `const char[8]`, не `std::string`. Чтобы связать его с `const std::string&`, компилятор молча создаёт временный `std::string` — с аллокацией. А `string_view` принимает и литерал, и `std::string`, и кусок буфера **без единой копии**:

```cpp
void process(std::string_view s);   // современный канон для read-only строк

process("literal");        // ноль аллокаций — view на литерал
process(my_string);        // ноль аллокаций — view на буфер std::string
process(my_string.substr(2, 4));  // тут substr строки всё ещё копирует, осторожно
```

Правило: **для строкового параметра, который вы только читаете, берите `std::string_view` по значению** (он маленький — указатель и размер, копировать дёшево).

## Демо: токенизатор без копий

`utils/string_view_demo.cpp` переписывает наш парсер на `string_view`:

```cpp
#include <iostream>
#include <string>
#include <string_view>
#include <vector>

std::vector<std::string_view> tokenize(std::string_view line) {
    std::vector<std::string_view> tokens;
    std::size_t i = 0;
    while (i < line.size()) {
        while (i < line.size() && line[i] == ' ') ++i;   // пропустить пробелы
        if (i >= line.size()) break;
        std::size_t start = i;
        while (i < line.size() && line[i] != ' ') ++i;
        tokens.push_back(line.substr(start, i - start)); // срез, не копия
    }
    return tokens;
}

bool starts_with(std::string_view s, std::string_view prefix) {
    return s.size() >= prefix.size() &&
           s.substr(0, prefix.size()) == prefix;
}

int main() {
    std::string command = "  move   north   quickly  ";

    for (std::string_view tok : tokenize(command)) {
        std::cout << "[" << tok << "] (len=" << tok.size() << ")\n";
    }

    std::cout << std::boolalpha
              << starts_with("move north", "move") << "\n"   // true
              << starts_with("go east", "move") << "\n";      // false
}
```

Запуск:

```
[move] (len=4)
[north] (len=5)
[quickly] (len=7)

true
false
```

Сравните с версией на `std::string`: при трёх токенах раньше было три аллокации на кучу, теперь — **ноль**. На горячем пути парсера (миллион строк лога) это ощутимая разница. И при этом сам `vector<string_view>` хранит лишь пары «указатель + длина», смотрящие в исходную `command`.

### Где в наших проектах

- **demo-shell** (глава 29): `tokenize` рубит командную строку. Сейчас он копирует каждый токен в `std::string`. На `string_view` — режет без копий, а в `std::string` превращает только то, что реально уйдёт в `execvp`.
- **demo-db** (глава 36): мини-SQL парсер разбирает запрос на слова. То же самое — слова это срезы исходного запроса.
- **demo-rpg** (глава 23): парсер мира из `world.txt` бьёт строки на ключ и значение. `string_view` для ключа избавит от лишних строк.

Важная оговорка для всех трёх: пока живёт исходная строка-запрос, view-токены валидны. Как только функция вернула управление и строка умерла — токены протухли. Поэтому `string_view` тут идеален как **временный** инструмент внутри одного разбора, а не как способ хранить токены «на потом».

## Параллельные алгоритмы

C++17 добавил алгоритмам из `<algorithm>` и `<numeric>` необязательный первый аргумент — **политику выполнения** (execution policy). Одним словом вы говорите «можешь параллелить»:

```cpp
#include <algorithm>
#include <execution>
#include <vector>

std::vector<int> data = /* миллион чисел */;

std::sort(std::execution::seq, data.begin(), data.end());        // как обычно, один поток
std::sort(std::execution::par, data.begin(), data.end());        // на всех ядрах
std::sort(std::execution::par_unseq, data.begin(), data.end());  // ядра + векторизация (SIMD)
```

Три политики:

- **`seq`** — последовательно, как всегда. То же, что без аргумента.
- **`par`** — параллельно: библиотека сама раскидывает работу по потокам пула. Вы не пишете ни `std::thread`, ни мьютексов — всё внутри.
- **`par_unseq`** — параллельно **и** с разрешением переставлять/векторизовать операции (SIMD). Самая агрессивная; ваша функция-предикат не должна при этом блокироваться или менять общее состояние.

Работает не только `sort`. Параллельные перегрузки получили десятки алгоритмов: `for_each`, `transform`, `count_if`, `reduce` (параллельный аналог `accumulate`), `transform_reduce` и другие.

```cpp
// Сумма миллиона элементов на всех ядрах:
long total = std::reduce(std::execution::par, data.begin(), data.end(), 0L);
```

Почему `reduce`, а не привычный `accumulate`? Потому что `accumulate` обязан складывать **строго слева направо** — это последовательный контракт, параллелить его нельзя. `reduce` не гарантирует порядок, поэтому может разбить диапазон на куски, сложить их на разных ядрах и объединить. Цена свободы: операция должна быть ассоциативной (для сложения чисел — да; для вычитания или конкатенации строк — порядок важен, будут сюрпризы).

### Когда это выгодно — и когда нет

Параллелизм не бесплатен: раскидать работу по потокам и собрать результат стоит времени. Выигрыш появляется, только когда работы **много**:

- Маленький массив (сотни элементов) — `par` будет **медленнее** `seq` из-за накладных расходов на потоки.
- Большой массив (сотни тысяч, миллионы) и тяжёлая операция на каждом элементе — вот где `par` окупается, иногда в разы.

Как и везде с производительностью (глава 14): не угадывайте — **измеряйте**. Замените `seq` на `par`, прогоните бенчмарк на реальных данных, сравните.

### Честная оговорка про поддержку

А теперь то, о чём многие туториалы умалчивают. Параллельные алгоритмы есть в **стандарте** C++17, но в **реализациях** — неравномерно:

- **MSVC** — поддерживает с Visual Studio 2017 15.7, из коробки.
- **GCC** — поддерживает с версии 9, но требует слинковаться с библиотекой Intel **TBB** (`-ltbb`); без неё `<execution>` либо не найдётся, либо `par` молча выполнится последовательно.
- **Apple Clang / libc++** (то, что стоит на macOS по умолчанию) — **на момент написания не поставляет** параллельные политики: `std::execution::par` просто не существует, код не скомпилируется.

Поэтому в нашем `demo-cpp17` параллельного демо нет — на типичном маке книги он бы не собрался, а я обещал, что весь код в книге собирается. Если хотите попробовать вживую — поставьте GCC и соберите с `-ltbb`, либо запустите под MSVC на Windows. Сам же приём — «добавь политику первым аргументом» — выучить полезно уже сейчас: переносимость подтянется, а в C++20 у `std::reduce`/`transform_reduce` появятся ещё и удобные ranges-обёртки (о ranges — в следующей, финальной главе).

## Главные правила главы

1. **`string_view` — это указатель + длина**, без владения и без аллокации.
2. **`substr` у view не копирует** — возвращает другой view на тот же буфер.
3. **View не продлевает жизнь источника** — не храните его дольше, чем живёт строка.
4. **Нет гарантии нуль-терминатора** — не передавайте `sv.data()` в C-API, ждущий C-string.
5. **Read-only строковый параметр — берите `std::string_view` по значению**, не `const std::string&`.
6. **Параллельные алгоритмы — политика первым аргументом**: `seq` / `par` / `par_unseq`.
7. **`reduce` вместо `accumulate`** для параллельной свёртки; операция должна быть ассоциативной.
8. **`par` окупается только на больших объёмах** — на малых медленнее; всегда измеряйте.

## Маленькое упражнение

1. Соберите и запустите `./build/string_view_demo`. Добавьте в `command` табы (`\t`) и научите `tokenize` считать их разделителями.

3. Реализуйте `trim(std::string_view)` — отрезает пробелы с обоих концов через `remove_prefix`/`remove_suffix`, без единой копии.

4. Перепишите `tokenize` из demo-shell (глава 29) на `string_view`, а в `std::string` превращайте только финальные аргументы для `execvp`. Замерьте, изменилось ли число аллокаций (например, через переопределённый `operator new` со счётчиком).

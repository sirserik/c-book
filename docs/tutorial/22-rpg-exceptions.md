# Глава 22. Исключения и exception safety

Исключения — механизм сигнализации об ошибках в C++. Они мощные и удобные, но имеют свою цену и кучу подводных камней. Эта глава — детальный разбор: как работают `throw/try/catch`, что такое stack unwinding, какие бывают гарантии безопасности при исключениях, и почему некоторые большие проекты (Google, ядро Chrome, LLVM) исключения **отключают**.

В коде добавим иерархию ошибок (`GameError → ValidationError, WorldError`), научимся ловить исключения в `main`, и проверим валидацию через них.

## Зачем исключения

В функции что-то пошло не так. Файл не открылся. Память не выделилась. Параметр невалидный. Как сообщить об ошибке вызывающему?

**Подход 1: возвращаемое значение.**

```cpp
int divide(int a, int b, int& result) {
    if (b == 0) return -1;   // код ошибки
    result = a / b;
    return 0;
}

int r;
if (divide(10, 0, r) != 0) {
    std::cerr << "ошибка\n";
}
```

Проблемы:
- Возвращаемое значение «занято» под код ошибки — реальный результат через out-параметр.
- Каждый вызов нужно проверять. Забыли — баг.
- Глубоко в стеке вызовов ошибка должна **«всплыть»** через все промежуточные функции — каждая проверяет, каждая возвращает.

**Подход 2: глобальная переменная `errno` (C-стиль).**

```cpp
double d = std::strtod("not a number", nullptr);
if (errno == ERANGE) { ... }
```

Те же проблемы плюс **глобальное состояние**, плохо с потоками.

**Подход 3: исключения.**

```cpp
int divide(int a, int b) {
    if (b == 0) throw std::invalid_argument("division by zero");
    return a / b;
}

try {
    int r = divide(10, 0);
} catch (const std::exception& e) {
    std::cerr << "ошибка: " << e.what() << "\n";
}
```

Преимущества:
- **Возвращаемое значение свободно** — для результата.
- **Нельзя случайно проигнорировать** — необработанное исключение валит программу.
- **Автоматическое распространение** — пробивает все уровни стека.

Недостатки тоже есть, разберём.

## throw, try, catch

Базовый синтаксис:

```cpp
try {
    // код, который может бросить
    do_something();
} catch (const SpecificException& e) {
    // ловим конкретный тип
} catch (const std::exception& e) {
    // ловим базу всех стандартных
} catch (...) {
    // ловим всё, что осталось (плохой стиль, но иногда нужно)
}
```

**Бросить** исключение — `throw expression`:

```cpp
throw std::runtime_error("что-то пошло не так");
throw std::invalid_argument("плохой параметр");
throw 42;     // да, можно бросить int — но не надо
```

`throw` ищет ближайший `try` в стеке вызовов, у которого есть подходящий `catch`. Если найден — управление прыгает туда, и **все локальные переменные** между `throw` и `catch` уничтожаются по обычным правилам (вызываются деструкторы). Это и есть **stack unwinding**.

Если ни одного подходящего `catch` нет — программа вызывает `std::terminate`, что обычно приводит к падению с сообщением вроде `terminate called after throwing an instance of 'std::runtime_error'`.

### Ловите по ссылке, не по значению

```cpp
catch (std::exception e) { ... }       // ПЛОХО: копия
catch (const std::exception& e) { ... } // ХОРОШО: ссылка
```

Если ловим по значению — исключение копируется. Хуже того: если оно полиморфное (бросили `std::runtime_error`, ловите как `std::exception`), при копировании происходит **slicing** (помните из главы 17). Теряются дополнительные данные.

Ссылка избегает копии и slicing. **Всегда ловите по `const T&`**.

### Несколько catch

Можно ловить разные типы:

```cpp
try {
    risky();
} catch (const std::invalid_argument& e) {
    // плохие параметры
} catch (const std::runtime_error& e) {
    // что-то сломалось в рантайме
} catch (const std::exception& e) {
    // все остальные стандартные
} catch (...) {
    // вообще всё (последняя линия защиты)
}
```

Проверяются **сверху вниз**, срабатывает первый подходящий. Полиморфизм: `const std::exception&` поймает любой потомок, поэтому ставьте конкретные типы **выше** общих, иначе общий перехватит всё.

`catch (...)` — без типа — ловит **любое** исключение. Удобно для логирования и продолжения работы, но информации никакой (даже `e.what()` нельзя). Использовать редко.

### Rethrow

Внутри `catch` можно «передать дальше»:

```cpp
try {
    risky();
} catch (const std::exception& e) {
    log("ошибка: ", e.what());
    throw;   // та же ошибка летит дальше
}
```

`throw;` без аргументов — повторно бросает текущее исключение. Можно и новое:

```cpp
catch (const std::runtime_error& e) {
    throw std::runtime_error("обёрнуто: " + std::string(e.what()));
}
```

Это иногда нужно для добавления контекста.

## std::exception и иерархия

В стандартной библиотеке есть **базовый класс** `std::exception` с методом `what()`:

```cpp
class std::exception {
public:
    virtual const char* what() const noexcept;
    virtual ~exception();
};
```

От него наследуются:

- `std::logic_error` — программная ошибка (что-то, что **программист должен был** избежать):
  - `std::invalid_argument`
  - `std::out_of_range`
  - `std::length_error`
  - `std::domain_error`
- `std::runtime_error` — внешняя ошибка (что-то, что **программа не могла** предвидеть):
  - `std::range_error`
  - `std::overflow_error`
  - `std::underflow_error`
  - `std::system_error`
- `std::bad_alloc` — не выделилась память (бросается `new`).
- `std::bad_cast` — неудачный `dynamic_cast` к ссылке.

Эта иерархия даёт **тип-безопасное** ловление. Если ловите `std::out_of_range` — точно знаете, что это «индекс за границей». Если ловите `std::exception` — поймает что угодно стандартное.

Свои ошибки лучше **наследовать** от подходящих стандартных. Тогда любой код, ловящий `std::exception`, поймает и ваши.

## Свои типы исключений

В нашем проекте сделаем три:

```cpp
// include/errors.h
class GameError : public std::runtime_error {
public:
    explicit GameError(const std::string& msg)
        : std::runtime_error(msg) {}
};

class ValidationError : public GameError {
public:
    explicit ValidationError(const std::string& msg)
        : GameError("ValidationError: " + msg) {}
};

class WorldError : public GameError {
public:
    explicit WorldError(const std::string& msg)
        : GameError("WorldError: " + msg) {}
};
```

- `GameError` — корень нашей иерархии. Кто-то ловит **все** наши ошибки одним `catch (const GameError&)`.
- `ValidationError` — невалидный ввод (пустое имя, отрицательный HP).
- `WorldError` — состояние мира неправильное (локация не найдена).

`explicit` у конструктора — запрещает неявную конверсию из `std::string`. Без него можно было бы случайно сделать `throw "some text"` (точнее, не совсем, но всё же).

### Базовый тип runtime_error

Я наследую от `std::runtime_error`, потому что:

1. Это стандартный класс. Любой код, ловящий `std::exception` или `std::runtime_error`, поймает мою ошибку.
2. У него уже есть конструктор от `std::string` и реализация `what()`. Не надо переписывать.

Альтернатива — наследовать прямо от `std::exception` и самим реализовывать `what()`. Сложнее, без явных плюсов.

## Применяем: валидация в Player

В `src/player.cpp`:

```cpp
Player::Player(std::string name, int max_hp)
    : name_(std::move(name)),
      max_hp_(max_hp),
      hp_(max_hp) {
    if (name_.empty()) {
        throw ValidationError("имя игрока не может быть пустым");
    }
    if (max_hp <= 0) {
        throw ValidationError("max_hp должен быть положительным");
    }
}
```

**Важно**: проверяем после инициализации. К моменту `throw` поля уже инициализированы. Это нормально — при выходе из конструктора через исключение поля корректно уничтожатся (их деструкторы вызовутся).

Что произойдёт, если `Player p("", 100)`:

1. Конструктор вызывается.
2. `name_` инициализируется пустой строкой через move.
3. `max_hp_` и `hp_` = 100.
4. Проверка: `name_.empty()` истина.
5. `throw ValidationError(...)` — исключение полетело.
6. Stack unwinding: `name_` уничтожается (вызывается `~std::string()`), `max_hp_`/`hp_` — тривиально.
7. Объект `p` **никогда не создан**. Его как будто не было.
8. Исключение летит к ближайшему `catch`.

Это **критично важное свойство**: если конструктор бросил, объекта нет. Нельзя получить «полусоздан» объект. RAII работает безопасно.

## Главный try/catch в main

Чтобы не падать с ужасным сообщением `terminate after throwing...`, оборачиваем `main`:

```cpp
int main() {
    try {
        rpg::Game game;
        return game.run();
    } catch (const rpg::GameError& e) {
        std::cerr << "Игра не запустилась: " << e.what() << "\n";
        return 1;
    } catch (const std::exception& e) {
        std::cerr << "Неожиданная ошибка: " << e.what() << "\n";
        return 2;
    } catch (...) {
        std::cerr << "Неизвестная ошибка\n";
        return 3;
    }
}
```

Три уровня:

1. **Наши ошибки** — выводим как «ожидаемые», возвращаем 1.
2. **Стандартные ошибки** — как «неожиданные», возвращаем 2.
3. **Что-то совсем странное** — возвращаем 3.

Это **best practice**: ваш `main` должен быть единой точкой обработки всех исключений. Внутри программы — бросайте свободно; в `main` ловите и форматируйте для пользователя.

## Stack unwinding под капотом

Когда `throw` срабатывает, среда выполнения C++ делает примерно следующее:

1. **Создаёт объект исключения** в специальной памяти (не на стеке вызвавшего, потому что стек будет очищаться).
2. **Идёт вверх по стеку**, проверяя для каждого кадра: есть ли в нём активный `try` с подходящим `catch`?
3. Для каждого пройденного кадра **вызывает деструкторы** локальных переменных. Это и есть unwinding.
4. Когда найден подходящий `catch` — управление переходит туда.

Этим механизмом пользуется **RAII** (глава 11). Все RAII-объекты в stack frame получают свой деструктор бесплатно, даже когда исключение разрушает выполнение.

```cpp
void foo() {
    std::ofstream f("output.txt");   // RAII: файл откроется
    risky_operation();                // бросает исключение
    f << "это не запишется";          // эта строка не выполнится
    // ~f вызывается АВТОМАТИЧЕСКИ во время unwinding — файл корректно закроется
}
```

В C-стиле пришлось бы оборачивать в try/catch и закрывать вручную. С C++-RAII — само.

## noexcept — обещание не бросать

Функция, помеченная `noexcept`, обещает не бросать исключений:

```cpp
void safe_thing() noexcept {
    // не бросает
}
```

Если **всё-таки бросит** — программа вызывает `std::terminate` (как при необработанном). То есть `noexcept` это **строгое** обещание; нарушение фатально.

Зачем `noexcept`:

- **Документация**. Программист видит «эта функция гарантированно не бросит».
- **Оптимизация**. Компилятор может не генерировать stack-unwinding-таблицу для этой функции — экономия места.
- **Move-семантика**: `std::vector` использует move-конструктор только если он `noexcept` (см. главу 19).
- **Деструкторы должны быть noexcept**. В C++11 деструкторы **неявно** `noexcept`, если не сказали иначе. Это правильно — бросать из деструктора почти всегда баг.

Ставьте `noexcept` на:
- Деструкторы (хотя автоматически).
- Move-конструкторы и move-присваивание.
- Простые геттеры, не делающие ничего сложного.

**Не ставьте** `noexcept` на функции, которые могут позвать аллокацию памяти (`new`, `std::vector::push_back`) — они могут бросить `std::bad_alloc`.

## Exception safety — три уровня гарантий

Когда функция бросает, что с **состоянием программы**? Этот вопрос изучили глубоко, выделили три уровня.

### Уровень 1: basic guarantee — слабая

После исключения программа **в валидном состоянии**, нет утечек ресурсов, инвариантов не нарушено. Но конкретное содержимое может быть «частично применённым» — то есть какие-то изменения сделаны, какие-то нет.

Пример. Функция, добавляющая элементы в два контейнера:

```cpp
void add_to_both(std::vector<int>& a, std::vector<int>& b, int v) {
    a.push_back(v);
    b.push_back(v);   // если эта строка бросит — a уже изменён, b нет
}
```

Basic guarantee: оба вектора целы, утечек нет, но программа **не может предположить**, что обе вставки сделаны.

### Уровень 2: strong guarantee — сильная

Либо операция полностью успешна, либо состояние **точно как было**. «Транзакционность» — всё или ничего.

```cpp
// Сильная гарантия:
void add_to_both(std::vector<int>& a, std::vector<int>& b, int v) {
    std::vector<int> a_new = a;   // копия
    a_new.push_back(v);
    
    std::vector<int> b_new = b;
    b_new.push_back(v);
    
    // Если до сюда дошли — операции прошли. Теперь атомарно меняем.
    a.swap(a_new);   // swap у vector — noexcept
    b.swap(b_new);
}
```

Если любая из вставок бросает — оригиналы `a` и `b` нетронуты. Это потому, что мы делали копию, и только в конце атомарно меняли.

Это **copy-and-swap идиома** — частый паттерн для сильной гарантии.

### Уровень 3: nothrow guarantee — без бросков

Функция **гарантированно не бросает**. Например, деструкторы, простые геттеры, перемещения. Идеал.

```cpp
void operator=(const T& other) noexcept { ... }
```

### Какая гарантия предпочтительна

- Деструкторы — **nothrow** (иначе ад при stack unwinding — что делать с исключением во время unwinding?).
- Move-операции — **nothrow** (для оптимизации STL).
- Простые методы (getters, etc) — **nothrow** где возможно.
- Сложные методы — хотя бы **basic**, лучше **strong** через copy-and-swap.

В нашей RPG большая часть кода имеет basic guarantee. Это часто достаточно, особенно с RAII.

## Copy-and-swap идиома детально

Классический пример: оператор присваивания с сильной гарантией.

```cpp
class Buffer {
public:
    Buffer(const Buffer& other);   // copy ctor
    ~Buffer();
    
    // Простая copy-and-swap
    Buffer& operator=(Buffer other) {  // принимаем по значению — компилятор сам копирует
        swap(*this, other);             // меняемся местами с временной
        return *this;
    }
    
    friend void swap(Buffer& a, Buffer& b) noexcept {
        using std::swap;
        swap(a.data_, b.data_);
        swap(a.size_, b.size_);
    }

private:
    int* data_;
    std::size_t size_;
};
```

Что происходит:
1. Параметр `other` создаётся как **копия** аргумента. Если копирование бросит — `*this` нетронут.
2. `swap` (без `std::`, для нахождения через ADL — argument-dependent lookup) меняет внутренности. Он `noexcept`, не бросает.
3. В конце `other` уничтожается, забирая с собой **бывшие данные `*this`**.

Если бы кому-то пришло на ум присваивать самому себе (`a = a`), сначала бы скопировался `a` в `other`, потом swap, потом `other` уничтожился. Всё корректно.

Это **исключительно элегантный** паттерн. Использует RAII (`other` уничтожается сама), move-семантику (передача параметра), и одну операцию `swap` с гарантией `noexcept`. Сильная гарантия за дёшево.

## Цена исключений

«Цена» — спорный вопрос. Зависит от ABI и оптимизаций.

**На «happy path»** (нет исключений):
- Современные ABI (Itanium, Microsoft x64) реализуют «zero-cost exception handling» — никакого оверхеда, пока исключение не бросилось. Стек-таблицы лежат в памяти, но не выполняются.
- Совсем нулевой? Не совсем. Компилятор не может агрессивно оптимизировать функции, которые могут бросать.

**Когда исключение полетело**:
- Дорого. Поиск catch'а, unwinding, вызов деструкторов — десятки микросекунд.
- Поэтому не используйте исключения для **обычного управления потоком** (например, выход из цикла). Только для **ошибочных** ситуаций.

В обычном коде overhead исключений не виден. В код горячих циклов и реал-тайм-систем — заметен.

## Почему отключают исключения

Несколько громких проектов отключают `-fno-exceptions`:

- **Google C++ Style Guide** — отключает в основном legacy-причинам (старый код Google не знал исключений, плюс есть проблемы с интеграцией с C-кодом).
- **Embedded** — overhead неприемлем, плюс таблицы исключений жрут память.
- **Game engines** — стабильность fps критична, нельзя «зависать» на исключении.
- **LLVM/Clang** — отключены, ошибки через `llvm::Error`-тип.

При `-fno-exceptions`:
- `throw` → ошибка компиляции (или `abort()`).
- Любой код стандартной библиотеки, который может бросить — заменяется на `abort()` или возврат специального значения.
- Используются альтернативные механизмы: коды ошибок, `std::expected` (C++23), Result-типы.

В нашей книге исключения используем — это идиоматический C++ для приложений. Но знайте, что в индустрии бывает по-разному.

## Когда что выбирать: исключение vs код ошибки vs assert

Грубая модель:

- **`assert`** для ошибок программиста, которые **никогда не должны** случаться в правильной программе. Деление на ноль в коде, который должен это исключать. Пустой указатель там, где гарантированно не пустой. В release-сборке `assert` отключается.
- **Возврат `bool`/`std::optional`/код ошибки** для **ожидаемых** «безуспешных» исходов, которые не считаются ошибкой. Например, «не нашли элемент». Тут исключение — overkill.
- **Исключения** для **реальных ошибок**, которые **должен поймать вышестоящий код**. Файл не открылся, память не выделилась, параметр невалиден.

В нашей RPG:
- `Inventory::take` возвращает `nullptr` при отсутствии — это не ошибка, а нормальная ситуация.
- `Player(empty_name, ...)` бросает — это программистская ошибка.
- `World::find` возвращает `nullptr` — не ошибка, а «нет такой».

## Главные правила главы

1. **Ловите по `const T&`** — не по значению, не по указателю.
2. **Бросайте конкретные типы**, наследованные от `std::runtime_error` или `std::logic_error`.
3. **Главный `try/catch` в `main`** — единая точка форматирования ошибок.
4. **Деструкторы и move — `noexcept`.** Без исключений.
5. **`assert` для невозможных ситуаций**, исключение для реальных ошибок.
6. **`copy-and-swap`** для сильной гарантии оператора присваивания.
7. **Не используйте исключения для управления потоком** — они дорогие при бросании.
8. **`-fno-exceptions`** — реальная опция в некоторых проектах. Подумайте, как ваш код переживёт это.

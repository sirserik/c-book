# Глава 11. Память — стек, куча, RAII

Это самая важная глава Части I. После неё вы поймёте, почему C++ устроен именно так — со ссылками, указателями, конструкторами, деструкторами. Поймёте, откуда берутся «утечки памяти», «висячие указатели», «двойное освобождение» — и как современный C++ их предотвращает. Без этого знания дальше можно писать только маленькие игрушки; на больших программах вы будете натыкаться на загадочные крэши и недоумевать.

Главное на эту главу: **в C++ программист сам отвечает за память**. В Python, Java, JavaScript есть сборщик мусора — он сам находит ненужные объекты и удаляет. В C++ — нет. Если вы взяли память — вы её и возвращаете. Если забыли — утечка. Если вернули дважды — крэш. Если используете после возврата — UB.

Этой ручной работой можно было бы заняться лично, но за десятилетия C++ выработал паттерн **RAII**, который перекладывает работу на компилятор. RAII — главное изобретение C++, отличающее его от C. Об этом и поговорим.

## Освежим картинку из главы 7

В главе 7 я показывал layout памяти процесса:

```
Высокие адреса
+-----------------------+
|       Stack           |  ← локальные переменные
|         ↓             |
|                       |
|  Mmap'd libraries     |
|                       |
|         ↑             |
|       Heap            |  ← динамически выделяемая
+-----------------------+
|       .bss            |  ← глобальные неинициализированные
|       .data           |  ← глобальные инициализированные
|       .rodata         |  ← константы
|       .text           |  ← код
+-----------------------+
Низкие адреса
```

Из всех областей в этой главе нас интересуют две — **стек** и **куча**. Глобальные данные (`.data`, `.bss`) — это редкость в хорошем C++-коде, серьёзный разговор о них не нужен. Код (`.text`, `.rodata`) — read-only, программа в них не пишет.

Стек и куча — два главных места жизни данных. Различия в одной фразе: **стек — автоматически, куча — вручную**.

## Стек: подробности

Каждая функция при вызове **получает кусок стека** — называется **stack frame** (кадр стека). В этом кадре лежат:
- Параметры функции.
- Локальные переменные.
- Адрес возврата (куда прыгать после `return`).
- Сохранённые регистры (если нужно).

Когда функция возвращается — её кадр **исчезает**. Локальные переменные, которые в нём лежали, перестают существовать. Если у переменной был деструктор (об этом ниже) — он вызывается прямо в момент исчезновения кадра.

Пример:

```cpp
void foo() {
    int x = 5;
    int y = 10;
    // x и y лежат в кадре foo
    // адреса близкие: &x и &y отличаются на несколько байт
}
// после возврата кадр исчезает, x и y больше нет

int main() {
    foo();   // создаётся кадр foo, потом исчезает
    foo();   // снова создаётся новый кадр на тех же адресах, потом исчезает
}
```

Если бы внутри `foo` была переменная, которую мы хотели использовать после `foo` — её бы не было. Кадр уничтожается.

### Стек растёт «вниз»

По соглашению почти всех современных архитектур стек **растёт от высоких адресов к низким**. Когда вы вызываете функцию, указатель стека (`rsp` на x86-64, `sp` на ARM64) **уменьшается** на размер кадра. Когда функция возвращается — увеличивается обратно.

Это особенность исторически такая. С точки зрения программы это неважно — стек просто «есть».

### Стек ограничен

Размер стека по умолчанию:
- **Linux**: 8 MB (можно изменить через `ulimit -s`).
- **macOS**: 8 MB для главного потока, 512 KB для дополнительных.
- **Windows**: 1 MB.

Если кадры функций займут больше — **stack overflow**, программа упадёт. Это бывает в двух случаях.

**1. Слишком глубокая рекурсия** (про это в главе 10).

```cpp
int recurse(int n) {
    return recurse(n + 1);   // бесконечная рекурсия
}
// упадёт где-то на 100-200 тысячах вызовов
```

**2. Огромные локальные переменные**.

```cpp
void bad() {
    int big_array[10'000'000];   // 40 MB на стеке!
    // ...
}
```

40 MB не помещается ни в 8 MB, ни в 1 MB. Программа упадёт ещё до выполнения тела функции. Решение — переместить такой массив в **кучу** (об этом ниже).

### Преимущества стека

- **Бесплатное создание и уничтожение.** Никаких системных вызовов, никакого поиска свободного места. Просто перемещение указателя стека на N байт. Это **одна инструкция процессора**.
- **Автоматическое управление.** Программист не думает, когда освобождать — это делается само при выходе из функции.
- **Кэш-дружелюбность.** Локальные переменные функции близки в памяти, скорее всего попадают в одну кэш-линию.
- **Безопасность.** Нет утечек, нет двойного освобождения. Стек сам знает свою жизнь.

### Недостатки стека

- **Размер ограничен.** Большие массивы туда нельзя.
- **Размер фиксирован на этапе компиляции.** Нельзя сказать «создай мне массив размером N, где N — переменная». В стандартном C++ — нельзя. (В C99 разрешены VLA — массивы переменной длины, и GCC поддерживает их как расширение для C++. Но в стандартном C++ — нет.)
- **Жизнь привязана к функции.** Если нужно, чтобы объект пережил функцию — на стеке нельзя.

## Куча: подробности

Куча — большая область памяти, из которой программа может выделять кусочки **во время работы**. Размер выделения определяется в рантайме. Жизнь куска **не привязана** к функции — он живёт, пока вы его явно не вернёте.

В C++ есть два уровня работы с кучей:
- **Низкий**: оператор `new`, оператор `delete`. Аналоги `malloc`/`free` из C.
- **Высокий**: smart pointers (`std::unique_ptr`, `std::shared_ptr`) и стандартные контейнеры (`std::vector`, `std::string`, ...). Они сами зовут `new`/`delete` внутри, программисту думать не надо.

В современном коде используют высокий уровень. Низкий — для понимания, как это работает, и для редких случаев. Я разберу низкий уровень детально (это нужно понимать), а потом покажу высокий и объясню, почему он лучше.

### new — выделение

Чтобы выделить из кучи память для одного объекта:

```cpp
int* p = new int;          // выделить место для int, p — адрес
*p = 42;                   // положить 42
std::cout << *p << "\n";   // напечатать 42
```

Что произошло:

1. Оператор `new` пошёл к ОС (через библиотеку: `malloc` → `mmap`/`brk`) и попросил «дай мне 4 байта» (размер `int`).
2. ОС нашла свободный кусок в куче и вернула его адрес.
3. Этот адрес положили в `p` (тип `int*`).
4. Теперь `*p` — это значение по этому адресу. Записали 42.

С инициализацией значения сразу при создании:

```cpp
int* p = new int(42);     // выделить и положить 42
int* q = new int{42};     // то же, через uniform initialization (C++11)
```

Для классов это вызывает соответствующий конструктор — об этом в главе 16.

### delete — возврат

Когда объект больше не нужен — обязательно верните память:

```cpp
delete p;
```

Это говорит: «я закончил с памятью по адресу `p`, верни её в общий пул». ОС/менеджер памяти помечает кусок как свободный, и его смогут переиспользовать следующие `new`.

После `delete` указатель **становится опасным**. Адрес тот же, но память уже не «наша». Использовать `*p` после `delete p` — UB:

```cpp
int* p = new int(42);
delete p;
*p = 0;          // UB! Память уже не наша
delete p;        // UB! Двойное освобождение
```

Хорошая привычка — после `delete` присвоить указатель `nullptr`:

```cpp
delete p;
p = nullptr;     // теперь *p вызовет крэш сразу, а не UB
delete p;        // delete nullptr — безопасно, ничего не делает
```

### new[] и delete[] — массивы

Чтобы выделить **массив** объектов:

```cpp
int* arr = new int[100];      // массив из 100 int
arr[0] = 1;
arr[99] = 100;

delete[] arr;                   // вернуть, ВНИМАНИЕ — delete[], не delete
```

**Никогда не путайте `delete` и `delete[]`**:
- `new int` → `delete` (одиночный).
- `new int[N]` → `delete[]` (массив).

Если перепутать — UB. Самое противное: на простых типах (`int`, `float`) это часто «работает», но протекает память. На сложных типах с деструкторами (`std::string[]`) — крэш.

### Размер можно вычислять в рантайме

В отличие от стека, размер на куче **может быть переменным**:

```cpp
int n;
std::cin >> n;
int* arr = new int[n];   // OK! n может быть любым

for (int i = 0; i < n; ++i) {
    arr[i] = i * i;
}

delete[] arr;
```

Это то, чего не сделать на стеке стандартным C++. Куча — единственный способ.

## Утечки памяти

Утечка — это когда вы выделили память через `new`, но **никогда не освободили** через `delete`. Память остаётся занятой, но программа её больше не видит — потеряна.

```cpp
void leak() {
    int* p = new int(42);
    // забыли delete
}

int main() {
    for (int i = 0; i < 1'000'000; ++i) {
        leak();
    }
    // программа потребляет ~4 MB лишней памяти
}
```

Один пропуск `delete` в коде, который выполняется миллион раз — миллион утечек. Программа толстеет, начинает занимать гигабайты, ОС начинает свапиться, всё тормозит, в худшем случае — OOM-killer убивает программу.

### Когда утечки нестрашны

Парадокс: иногда утечки **не имеют значения**.

- Если программа **выполняется секунду и закрывается** — ОС всё равно освободит её память при выходе. Утечка в `main` в маленькой утилите — никому не вредит.
- Если программа выделила что-то и удерживает до самого конца (а конец близок) — тоже не страшно.

Опасны утечки в **долгоживущих** процессах: серверы, демоны, мобильные приложения. Там каждая утечка остаётся навсегда, и через месяц работы — гигабайты лишнего.

### Пять способов утечь память

Я набрал из практики пять типичных:

**1. Забыл `delete`.**

```cpp
void process() {
    int* p = new int(42);
    use(p);
    // нет delete
}
```

**2. Исключение между `new` и `delete`.**

```cpp
void process() {
    int* p = new int(42);
    might_throw();      // исключение!
    delete p;           // не выполнится
}
```

**3. Ранний `return`.**

```cpp
int* find_or_create() {
    int* p = new int(42);
    if (some_condition) {
        return p;       // вернули, вызывающий должен delete
    }
    if (other_condition) {
        return nullptr; // ОЙ: p потеряно
    }
    return p;
}
```

**4. Перезапись указателя.**

```cpp
int* p = new int(42);
p = new int(43);        // адрес 42-го объекта потерян, утечка
delete p;               // удаляет только 43-й
```

**5. Циклы между shared_ptr** — про это в главе 18. Сейчас просто упомяну: даже с smart pointers можно утечь, если структура объектов закольцованная.

### Висячие указатели

Обратная проблема: `delete`-нули объект, но указатель остался. Использование такого указателя — UB.

```cpp
int* p = new int(42);
int* q = p;          // q тоже указывает туда

delete p;            // память освобождена
p = nullptr;

*q = 0;              // q — висячий указатель! UB!
```

Сложнее с возвратом из функции:

```cpp
int* make_int() {
    int x = 42;
    return &x;       // !!! &x — адрес локальной переменной
}

int main() {
    int* p = make_int();   // p висячий: x уничтожен
    *p = 0;                // UB
}
```

Современные компиляторы это ловят (`-Wreturn-local-addr`), но не всегда.

### Двойное освобождение

```cpp
int* p = new int(42);
delete p;
delete p;            // UB: второе освобождение
```

Что произойдёт — зависит от рантайма. На glibc вы получите красивое сообщение «double free or corruption». На других — UB, может быть SEGFAULT, может быть тихая катастрофа.

### Использование после освобождения (UAF)

```cpp
int* p = new int(42);
delete p;
std::cout << *p;     // UB: use-after-free
```

Это золотая жила багов безопасности — большинство уязвимостей в браузерах и ядрах ОС в 2010-2020-х годах связаны с UAF.

## Проблема: слишком много ручной работы

Получается, программисту нужно:
- Помнить о каждом `new` — где он, кто делает `delete`.
- Освобождать на всех путях выхода из функции (включая исключения).
- Не использовать указатель после `delete`.
- Не освобождать дважды.

На больших программах это нереально. Поэтому в C — постоянная борьба с утечками. В C++ нашли решение.

## RAII — главный паттерн C++

**RAII** — Resource Acquisition Is Initialization, «получение ресурса есть инициализация». Идея, кажущаяся простой, но меняющая всё:

> **Привязать жизнь ресурса к жизни объекта на стеке.**

Когда объект создаётся (на стеке) — он **захватывает** ресурс. Когда объект уничтожается (выходит из области видимости) — он **освобождает** ресурс.

Стек уничтожает объекты автоматически. Значит, ресурс автоматически освобождается. Никаких ручных `delete`. Никаких ошибок «забыл освободить».

Это работает для любого ресурса, не только памяти: файлов, мьютексов, сокетов, окон, чего угодно.

### Конструктор и деструктор

Чтобы это работало, у объекта должно быть два специальных метода:

- **Конструктор** — выполняется при создании объекта.
- **Деструктор** — выполняется при уничтожении.

Подробно про эти штуки в главе 16 на проекте RPG. Сейчас — лёгкий обзор.

Простой пример. Класс, который сам управляет одним динамически выделенным `int`:

```cpp
class IntHolder {
public:
    // Конструктор: создаём объект, выделяем int
    IntHolder(int value) {
        ptr_ = new int(value);
        std::cout << "Created at " << ptr_ << "\n";
    }
    
    // Деструктор: освобождаем
    ~IntHolder() {
        std::cout << "Destroying at " << ptr_ << "\n";
        delete ptr_;
    }
    
    int get() const { return *ptr_; }
    void set(int v) { *ptr_ = v; }
    
private:
    int* ptr_;
};

int main() {
    IntHolder a(42);
    IntHolder b(100);
    std::cout << a.get() << " " << b.get() << "\n";
}   // здесь автоматически вызываются деструкторы a и b
```

Вывод:

```
Created at 0x600003a04020
Created at 0x600003a04030
42 100
Destroying at 0x600003a04030
Destroying at 0x600003a04020
```

Заметили: я не написал ни одного `delete` в `main`. Память освобождается **сама**, потому что деструктор `IntHolder` это делает, и деструктор вызывается автоматически при выходе из `main`. Деструкторы вызываются в **обратном порядке создания** — это гарантия языка, и она важна, когда объекты зависят друг от друга.

Это и есть RAII в чистом виде. Объект на стеке владеет ресурсом на куче, и его деструктор разруливает уборку.

### Почему RAII работает с исключениями

Главная сила RAII — она устойчива к исключениям.

```cpp
void might_throw();

void process() {
    IntHolder x(42);
    might_throw();    // если выкинет исключение — деструктор x всё равно вызовется!
}
```

При возникновении исключения C++ выполняет **stack unwinding** (раскрутка стека): по очереди вызываются деструкторы всех объектов в текущем кадре, потом в кадре функции выше, и так далее до места, где исключение поймают. Утечек нет.

Сравните с прямой работой через `new`/`delete`:

```cpp
void process() {
    int* p = new int(42);
    might_throw();    // утечка! delete не выполнится
    delete p;
}
```

Утечка. Можно обернуть в `try/catch`, но громоздко. RAII делает это автоматически.

## Стандартные RAII-обёртки

В стандартной библиотеке десятки RAII-объектов. Самые частые:

- **`std::vector<T>`** — массив, который сам управляет памятью. Растёт по мере добавления, сам освобождает в деструкторе.
- **`std::string`** — строка, аналогично.
- **`std::ifstream` / `std::ofstream`** — файлы, открываемые в конструкторе и закрываемые в деструкторе.
- **`std::lock_guard`** — берёт мьютекс в конструкторе, отпускает в деструкторе (про потоки в главе 41).
- **`std::unique_ptr<T>`** — умный указатель, владеющий объектом и удаляющий его в деструкторе.
- **`std::shared_ptr<T>`** — умный указатель с подсчётом ссылок (`std::shared_ptr`).

С этими штуками вы **почти никогда не пишете `new`/`delete` сами**. Они делают это за вас.

### Пример: вектор вместо ручного массива

Так делать **не** надо:

```cpp
int* arr = new int[1000];
// ...использование...
delete[] arr;    // надо помнить!
```

Так — надо:

```cpp
std::vector<int> arr(1000);
// ...использование... 
// arr автоматически освободится
```

Короче, безопаснее, и нет потенциальной утечки.

### Пример: файл вместо `fopen`

Так делать **не** надо (C-стиль):

```cpp
FILE* f = fopen("data.txt", "r");
if (f == nullptr) return;
// ...использование...
fclose(f);   // надо помнить!
```

Так — надо:

```cpp
#include <fstream>

std::ifstream f("data.txt");
if (!f.is_open()) return;
// ...использование...
// f автоматически закроется
```

Меньше кода, нет вероятности забыть `fclose`.

## smart pointers — предварительно

Раз стандартные контейнеры обёртки идут с готовой RAII-логикой, может, и для голого указателя кто-то сделал? Да, и это **smart pointers**.

В C++11 их три:

- **`std::unique_ptr<T>`** — единоличный владелец. Только один указатель на объект; при уничтожении — удаляет.
- **`std::shared_ptr<T>`** — совладельцы. Объект живёт, пока есть хоть один `shared_ptr` на него; уничтожается, когда последний пропадает.
- **`std::weak_ptr<T>`** — наблюдатель, не владеет. Нужен против циклических ссылок `shared_ptr`.

Они подробно разбираются в главе 18 на проекте RPG. Сейчас — лёгкое знакомство.

```cpp
#include <memory>

void use_unique() {
    std::unique_ptr<int> p(new int(42));
    std::cout << *p << "\n";
    // p автоматически удалит int
}

void use_shared() {
    std::shared_ptr<int> p(new int(42));
    auto q = p;             // оба указывают на тот же объект
    std::cout << *p << " " << *q << "\n";
    // объект удалится, когда оба p и q уничтожатся
}
```

В современном C++ почти **весь** код, имеющий дело с памятью на куче — это контейнеры и smart pointers. Ручной `new`/`delete` — крайне редкая экзотика, обычно только в реализации низкоуровневых структур данных или интерфейсах к C-API.

В C++14 добавили `std::make_unique`, в C++11 его нет — поэтому в нашей C++11-базе будем писать `std::unique_ptr<T>(new T(...))` или сделаем свой шим. Подробнее в главе 18.

## Стек или куча — что выбрать

После всех этих описаний — простое правило:

**По умолчанию — стек. Куча — только если есть конкретная причина.**

Причины брать кучу:

1. **Размер заранее неизвестен.** Массив `n` элементов, где `n` ввёл пользователь.
2. **Объект должен пережить функцию.** Создаём в одной функции, отдаём наружу.
3. **Объект слишком большой для стека.** Например, видеобуфер 10 MB.
4. **Полиморфизм через базовый класс.** Передаём `Item*`, реальный объект — `Weapon` или `Armor`. Об этом в главе 17.

Во всех остальных случаях — стек. Локальная переменная, маленький массив, маленькая структура — на стеке. Это и быстрее, и безопаснее.

### Конкретные примеры

```cpp
// Стек:
int x = 42;
double pi = 3.14;
std::vector<int> v = {1, 2, 3};
std::string name = "Alice";
Player player(100, "Hero");

// Куча (через RAII обёртки):
std::vector<int> big_array(1'000'000);   // вектор сам хранит данные на куче
std::unique_ptr<Player> hero(new Player(100, "Hero"));  // когда нужен полиморфизм
auto enemies = std::vector<std::unique_ptr<Enemy>>{};   // массив указателей на разные типы врагов
```

В каждой строке стек хранит **управляющую часть** (указатель + размер для вектора, указатель для unique_ptr). А содержимое — на куче. Деструкторы стеков-управляющих частей освобождают кучу. Это и есть RAII в действии.

## Инструменты для борьбы с проблемами памяти

Несмотря на RAII, иногда что-то протекает или указывает не туда. Есть инструменты, которые помогают находить эти баги.

### AddressSanitizer (ASan)

Встроен в clang и gcc. Скомпилируйте программу с `-fsanitize=address`:

```bash
$ g++ -std=c++11 -fsanitize=address -g program.cpp -o program
$ ./program
```

ASan вставит проверки в каждое обращение к памяти. Если будет:
- Использование после освобождения,
- Двойное освобождение,
- Выход за границы массива,
- Утечка,

— программа упадёт с красивым отчётом, какая строка кода виновата.

ASan чуть замедляет программу (раза в 2), но для отладки незаменим. **Всегда** запускайте тесты под ASan.

### Valgrind

Раньше (до ASan) самым популярным был **Valgrind** — внешняя программа, эмулирующая выполнение и проверяющая все обращения к памяти. Сейчас на Linux:

```bash
$ valgrind --leak-check=full ./program
```

Точнее ASan, но в 50 раз медленнее. На macOS работает плохо. Раньше — стандарт; сейчас ASan чаще.

### LeakSanitizer (LSan)

Часть ASan. Включается флагом `-fsanitize=leak`. Просто проверяет утечки, не остальные ошибки. Полезно для CI.

## Большой пример: классический ресурс

Соберём пример, который ясно показывает разницу C-стиля и C++-стиля. Класс «лог-файл»: открывает файл, пишет в него, закрывает.

### C-стиль (без RAII)

```cpp
class LogFile_BAD {
public:
    LogFile_BAD(const std::string& filename) {
        f_ = std::fopen(filename.c_str(), "w");
    }
    
    void close() {
        if (f_ != nullptr) {
            std::fclose(f_);
            f_ = nullptr;
        }
    }
    
    void write(const std::string& message) {
        if (f_ != nullptr) {
            std::fprintf(f_, "%s\n", message.c_str());
        }
    }
    
private:
    FILE* f_;
};

void use_bad() {
    LogFile_BAD log("test.log");
    log.write("hello");
    log.close();          // программист ОБЯЗАН вспомнить close
}
```

Проблема: что если программист забудет `close()`? Или между `write` и `close` будет ранний `return`, или исключение? Файл останется открытым, дескриптор утечёт. На длинной программе можно исчерпать лимит ОС на открытые файлы.

### C++-стиль (с RAII)

```cpp
class LogFile {
public:
    LogFile(const std::string& filename) {
        f_ = std::fopen(filename.c_str(), "w");
        if (f_ == nullptr) {
            throw std::runtime_error("cannot open " + filename);
        }
    }
    
    ~LogFile() {
        if (f_ != nullptr) {
            std::fclose(f_);
        }
    }
    
    void write(const std::string& message) {
        std::fprintf(f_, "%s\n", message.c_str());
    }
    
    // Запрещаем копирование (об этом в главе 16)
    LogFile(const LogFile&) = delete;
    LogFile& operator=(const LogFile&) = delete;
    
private:
    FILE* f_ = nullptr;
};

void use_good() {
    LogFile log("test.log");
    log.write("hello");
    // close не нужен! Деструктор сделает это сам.
}
```

Этот код **физически не может** забыть закрыть файл. Что бы ни случилось — исключение, ранний return, нормальный выход — деструктор сработает и `fclose` будет вызван. Это и есть сила RAII.

Конструкции `= delete` запрещают копирование объекта. Иначе можно было бы сделать копию `LogFile`, и при уничтожении обоих копий случился бы двойной `fclose`. Об этом подробно в главе 16 (rule of five).

### Вариант со стандартной библиотекой

Ещё короче — `std::ofstream` уже RAII:

```cpp
#include <fstream>

void use_modern() {
    std::ofstream log("test.log");
    log << "hello\n";
    // ничего больше не надо
}
```

Стандартная библиотека уже использует RAII для большинства ресурсов. Поэтому **в реальной работе вы редко пишете деструкторы сами** — обычно завернуть в готовый `vector`/`string`/`fstream`/`unique_ptr` достаточно.

## Когда нужно писать свой деструктор

Когда стандартные обёртки не подходят. Например:

- Работа с C-API, где нужно вызвать специфическую очистку (`SDL_FreeSurface`, `curl_easy_cleanup`, и так далее).
- Свой контейнер с особой логикой.
- Объект, владеющий несколькими ресурсами сразу.

Правило **rule of five** — если у класса есть нетривиальный деструктор, ему **скорее всего** нужны:
- Конструктор копирования,
- Оператор присваивания при копировании,
- Конструктор перемещения,
- Оператор присваивания при перемещении.

— или явно запретить все эти операции через `= delete`.

Об этом в главе 16. Сейчас просто запомните, что свой деструктор тянет за собой много работы — поэтому **избегайте писать свой деструктор**, если можно обойтись стандартной обёрткой.

## Главные правила этой главы

1. **По умолчанию — переменная на стеке.** Только если нужна гибкость или объект должен пережить функцию — куча.

2. **На куче — через RAII-обёртки.** `std::vector`, `std::string`, `std::unique_ptr`, `std::shared_ptr`. **Не** через сырой `new`/`delete`.

3. **Каждый ресурс — в одном объекте.** Если класс владеет несколькими ресурсами — оберните каждый в свою RAII-обёртку, не пишите общий деструктор.

4. **`new` без `delete` или со «свободным» указателем — звоночек.** Используйте `std::unique_ptr` или поместите в контейнер.

5. **Запускайте тесты под ASan.** Многие баги памяти он находит мгновенно.

6. **Помните про двойной `delete` и UAF.** Они выглядят страшнее, чем «легко исправимые опечатки» — это часто эксплуатируемые уязвимости.

## Маленькое упражнение

1. Напишите класс `IntArray`, который владеет динамическим массивом `int`:
   - конструктор `IntArray(size_t n)` выделяет `new int[n]`.
   - деструктор `~IntArray()` делает `delete[]`.
   - метод `at(size_t i)` возвращает `int&` на элемент.
   
   Запустите программу, создающую `IntArray`, заполняющую его, и убедитесь, что деструктор зовётся.

2. Скомпилируйте программу из пункта 1 с `-fsanitize=address`. Запустите. Должно работать без жалоб.

3. Намеренно сломайте: уберите `delete[]` из деструктора. Скомпилируйте под ASan, запустите. ASan должен сказать про утечку.

4. Намеренно сломайте: вернитесь к рабочей версии, но в `main` после уничтожения `IntArray` попытайтесь обратиться к освобождённой памяти через сохранённый указатель. ASan должен сказать про use-after-free.

5. Напишите программу:
   ```cpp
   void deep(int n) {
       int x = n;
       deep(n + 1);
       (void)x;   // чтобы компилятор не выкинул
   }
   ```
   Запустите `deep(0)`. Программа должна упасть через секунды. Если есть `ulimit -s 1024` — упадёт быстрее.

6. (Опционально, важно). Перепишите упражнение 1 через `std::unique_ptr<int[]>` (использует `delete[]` под капотом):
   ```cpp
   std::unique_ptr<int[]> arr(new int[100]);
   ```
   Никакого пользовательского деструктора. Память по-прежнему освобождается. Это и есть современный C++.

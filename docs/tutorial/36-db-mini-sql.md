# Глава 36. Мини-SQL

Хранилище готово: страницы, дерево, журнал. Но чтобы вставить строку, пользователю пришлось бы писать на C++ и знать про `BPlusTree::insert`. Между человеком и хранилищем не хватает языка.

В этой главе напишем свой диалект SQL — маленький, но настоящий: `CREATE TABLE`, `INSERT`, `SELECT` с условием, `CREATE INDEX` и `EXPLAIN`. После этого с базой можно будет разговаривать так:

```sql
SELECT * FROM items WHERE value > 250;
```

Разбор устроен так же, как токенизатор командной строки из главы 29: сначала лексер режет текст на токены, потом парсер собирает из токенов дерево. Разница в том, что грамматика здесь заметно богаче, и разбирать её будем методом рекурсивного спуска — тем самым, которым устроено большинство компиляторов.

Это четвёртый разбор в книге: мир RPG в главе 23, сохранение в главе 24, командная строка в главе 29 и теперь SQL. К этому моменту схема должна быть уже знакомой, и в главе будет больше внимания к тому, что отличает язык запросов от остальных.

## Зачем вообще язык

Вызов `tree.insert(1, 100)` — это императивный интерфейс: вы говорите, **что делать**, и знаете, с какой структурой данных работаете. Если завтра дерево заменят на хеш-таблицу, весь код, который им пользовался, придётся переписать.

SQL устроен наоборот. Запрос описывает, **что нужно получить**, и молчит о том, как это делать:

```sql
SELECT * FROM items WHERE value > 250;
```

Ни слова о деревьях, индексах и порядке обхода. Решение о способе выполнения принимает база — и может решить по-разному в зависимости от того, есть ли индекс и сколько строк в таблице. Именно это разделение и сделало реляционные базы тем, чем они стали: запросы, написанные в семидесятых, работают на движках, о которых их авторы не подозревали.

Обратная сторона — планировщик может ошибиться, и тогда запрос, работавший миллисекунду, начинает работать минуту. Отсюда команда `EXPLAIN`, показывающая выбранный план; мы её тоже сделаем, в следующей главе.

## Что поддерживаем

Грамматика нашего диалекта умещается в несколько строк:

```
CREATE TABLE <имя> (<колонка> INT [PRIMARY KEY], <колонка> INT)
CREATE INDEX <имя> ON <таблица> (<колонка>)
INSERT INTO <таблица> VALUES (<число>, <число>)
[EXPLAIN] SELECT <колонки> | * FROM <таблица> [WHERE <колонка> <оператор> <число>]
```

Операторы сравнения — все шесть: `=`, `!=`, `<`, `<=`, `>`, `>=`.

Чего нет, тоже стоит проговорить сразу: нет `DELETE` и `UPDATE` (в дереве нет удаления, глава 34), нет соединения таблиц, нет `AND` и `OR` в условии, нет строковых колонок, нет `ORDER BY`, `GROUP BY` и `LIMIT`. Таблица в базе одна, колонок в ней ровно две, обе целые.

Такое подмножество выглядит скромно, но его хватает, чтобы показать всю схему целиком: от текста запроса до обращения к дереву. Каждая недостающая возможность — это либо ещё одна ветка в парсере, либо ещё один способ выполнения, а каркас остаётся тем же.

## Три ступени

Обработка запроса проходит те же три ступени, что и обработка команды в оболочке:

```
текст запроса
     ↓  лексер      — режет на токены, узнаёт ключевые слова и числа
  токены
     ↓  парсер      — собирает Statement по правилам грамматики
 Statement
     ↓  исполнитель — обращается к дереву и журналу, печатает результат
  результат
```

Разделение даёт то же, что и раньше: каждая ступень проверяема отдельно, а сообщения об ошибках получаются осмысленными — лексер жалуется на неизвестный символ, парсер на неожиданный токен, исполнитель на неизвестную таблицу.

## Лексер

Токен у нас — пара из типа и текста:

```cpp
struct Token {
    enum Type {
        kIdent,    // имя таблицы/колонки
        kKeyword,  // CREATE, TABLE, INSERT, INTO, ...
        kNumber,
        kStar,     // *
        kComma,
        kLParen,
        kRParen,
        kOp,       // =, <, >, <=, >=, !=
        kSemi,
        kEnd
    };
    Type type;
    std::string text;
};
```

Тип `kEnd` — не настоящий токен, а метка конца, которую лексер дописывает в конец списка. С ней парсер может всегда смотреть на `peek()` без проверки на выход за границу — приём, экономящий десяток проверок.

Сам разбор — цикл по символам:

```cpp
std::vector<Token> tokenize(const std::string& s) {
    std::vector<Token> out;
    std::size_t i = 0;
    while (i < s.size()) {
        char c = s[i];
        if (std::isspace(static_cast<unsigned char>(c))) { ++i; continue; }

        if (c == '(') { out.push_back({Token::kLParen, "("}); ++i; continue; }
        if (c == ')') { out.push_back({Token::kRParen, ")"}); ++i; continue; }
        if (c == ',') { out.push_back({Token::kComma,  ","}); ++i; continue; }
        if (c == ';') { out.push_back({Token::kSemi,   ";"}); ++i; continue; }
        if (c == '*') { out.push_back({Token::kStar,   "*"}); ++i; continue; }

        if (c == '=' || c == '<' || c == '>' || c == '!') {
            std::string op(1, c);
            if (i + 1 < s.size() && s[i + 1] == '=') { op += '='; i += 2; }
            else { ++i; }
            if (op != "=" && op != "<" && op != ">" && op != "<=" && op != ">=" && op != "!=") {
                throw SqlError("плохой оператор: " + op);
            }
            out.push_back({Token::kOp, op});
            continue;
        }

        if (std::isdigit(static_cast<unsigned char>(c)) ||
            (c == '-' && i + 1 < s.size() && std::isdigit(static_cast<unsigned char>(s[i + 1])))) {
            std::size_t j = i;
            if (c == '-') ++j;
            while (j < s.size() && std::isdigit(static_cast<unsigned char>(s[j]))) ++j;
            out.push_back({Token::kNumber, s.substr(i, j - i)});
            i = j;
            continue;
        }

        if (std::isalpha(static_cast<unsigned char>(c)) || c == '_') {
            std::size_t j = i;
            while (j < s.size() && (std::isalnum(static_cast<unsigned char>(s[j])) || s[j] == '_')) ++j;
            std::string text = s.substr(i, j - i);
            std::string upper = to_upper(text);
            if (is_keyword(upper)) {
                out.push_back({Token::kKeyword, upper});
            } else {
                out.push_back({Token::kIdent, text});
            }
            i = j;
            continue;
        }

        throw SqlError(std::string("неизвестный символ: '") + c + "'");
    }
    out.push_back({Token::kEnd, ""});
    return out;
}
```

Разберём места, где принимались решения.

Односимвольные знаки разбираются первыми и без затей. Операторы сравнения требуют заглядывания вперёд: увидев `<`, надо проверить, не идёт ли следом `=`. Это тот же приём, что при разборе `>>` в командной строке.

Отрицательные числа распознаются по минусу перед цифрой. Решение спорное: в настоящем SQL минус — это оператор, и `value - 5` должно разбираться как три токена. У нас арифметики нет вовсе, поэтому минус может означать только знак числа, и лексер сразу приклеивает его. Как только появится сложение, это придётся переделать.

Ключевые слова отличаются от имён проверкой по списку:

```cpp
bool is_keyword(const std::string& u) {
    static const std::vector<std::string> kw = {
        "CREATE", "TABLE", "INT", "PRIMARY", "KEY",
        "INDEX", "ON",
        "INSERT", "INTO", "VALUES",
        "SELECT", "FROM", "WHERE",
        "EXPLAIN",
    };
    for (const auto& k : kw) if (u == k) return true;
    return false;
}
```

Сравнение идёт по версии в верхнем регистре — поэтому `select`, `Select` и `SELECT` работают одинаково, как и положено в SQL. А вот имена таблиц и колонок сохраняются как есть: в тексте токена лежит исходное написание, и `items` не превращается в `ITEMS`. Это соответствует поведению большинства баз, где ключевые слова регистронезависимы, а имена — как повезёт (в PostgreSQL они приводятся к нижнему регистру, в MySQL зависят от файловой системы).

Список из четырнадцати слов перебирается линейно. Для четырнадцати это быстрее хеш-таблицы: сравнение коротких строк стоит наносекунды, а хеширование — тоже наносекунды, но с накладными расходами. Когда слов станет сто, стоит взять `std::unordered_set`.

Приведение `static_cast<unsigned char>` перед `isspace`, `isdigit` и `isalpha` обязательно, и это одна из самых известных ловушек стандартной библиотеки C. Эти функции принимают `int`, и передавать в них отрицательное значение — неопределённое поведение. А `char` на x86 знаковый, и любой байт русского текста в UTF-8 отрицателен. Забыть приведение — значит получить падение или мусор на первом же запросе с кириллицей в имени.

## Парсер

Разбор идёт методом рекурсивного спуска: на каждое правило грамматики — своя функция, которая читает токены слева направо и при необходимости зовёт другие функции. Состояние — позиция в списке токенов:

```cpp
struct Parser {
    const std::vector<Token>& tokens;
    std::size_t pos = 0;

    const Token& peek() const { return tokens[pos]; }
    Token consume() { return tokens[pos++]; }

    Token expect(Token::Type t) {
        if (peek().type != t) {
            throw SqlError("ожидался токен, получено '" + peek().text + "'");
        }
        return consume();
    }

    Token expect_keyword(const std::string& kw) {
        if (peek().type != Token::kKeyword || peek().text != kw) {
            throw SqlError("ожидалось '" + kw + "', получено '" + peek().text + "'");
        }
        return consume();
    }
    ...
};
```

Три метода — `peek`, `consume`, `expect` — составляют весь инструментарий. `peek` смотрит, не сдвигаясь; `consume` берёт и сдвигается; `expect` берёт, если тип совпал, и бросает исключение, если нет. Дальше вся грамматика выражается через них.

Точка входа выбирает разбор по первому слову:

```cpp
Statement parse() {
    if (peek().type != Token::kKeyword) {
        throw SqlError("ожидался keyword");
    }
    if (peek().text == "EXPLAIN") {
        consume();
        Statement st = parse_select();
        st.is_explain = true;
        return st;
    }
    const std::string& kw = peek().text;
    if (kw == "CREATE") return parse_create();
    if (kw == "INSERT") return parse_insert();
    if (kw == "SELECT") return parse_select();
    throw SqlError("неизвестный statement: " + kw);
}
```

`EXPLAIN` обрабатывается как приставка: съели слово, разобрали обычный `SELECT`, поставили флаг. Так же он устроен и в настоящих базах — это не отдельная команда, а модификатор.

Разбор вставки — самая простая из функций и хорошо показывает стиль:

```cpp
Statement parse_insert() {
    Statement st;
    st.kind = Statement::kInsert;
    expect_keyword("INSERT");
    expect_keyword("INTO");
    st.table = expect(Token::kIdent).text;
    expect_keyword("VALUES");
    expect(Token::kLParen);
    while (true) {
        st.values.push_back(parse_number());
        if (peek().type == Token::kComma) { consume(); continue; }
        break;
    }
    expect(Token::kRParen);
    if (peek().type == Token::kSemi) consume();
    return st;
}
```

Функция читается как сама грамматика: `INSERT`, `INTO`, имя, `VALUES`, скобка, числа через запятую, закрывающая скобка. В этом и состоит удобство рекурсивного спуска — код совпадает с описанием языка, и по нему видно, что именно принимается.

Цикл по списку значений — типичный образец «элемент, потом пока есть запятая — ещё элемент». Он не позволяет ни пустого списка, ни висящей запятой, и это правильно: `VALUES ()` и `VALUES (1,)` должны быть ошибками.

Точка с запятой в конце необязательна — мы её съедаем, если она есть. В REPL завершающая точка с запятой обязательна по другой причине: по ней он понимает, что команда закончилась и её пора выполнять (глава 38).

Разбор выборки чуть сложнее из-за необязательных частей:

```cpp
Statement parse_select() {
    Statement st;
    st.kind = Statement::kSelect;
    expect_keyword("SELECT");
    if (peek().type == Token::kStar) {
        consume();
        st.select_columns.push_back("*");
    } else {
        while (true) {
            st.select_columns.push_back(expect(Token::kIdent).text);
            if (peek().type == Token::kComma) { consume(); continue; }
            break;
        }
    }
    expect_keyword("FROM");
    st.table = expect(Token::kIdent).text;
    if (peek().type == Token::kKeyword && peek().text == "WHERE") {
        consume();
        st.has_where = true;
        st.where_col = expect(Token::kIdent).text;
        st.where_op = expect(Token::kOp).text;
        st.where_val = parse_number();
    }
    if (peek().type == Token::kSemi) consume();
    return st;
}
```

Необязательные части разбираются по одной схеме: заглянули через `peek`, и если там ожидаемое слово — разобрали, иначе прошли мимо. Флаг `has_where` нужен, потому что отсутствие условия и условие «всегда истинно» — разные вещи для планировщика.

Условие у нас предельно жёсткое: колонка, оператор, число. Ни `5 > value`, ни `value > other_column`, ни скобок. Полноценное выражение потребовало бы разбора с приоритетами операций — того самого, что пишут для калькуляторов, — и дерева выражений вместо трёх полей. Это большое, но полезное упражнение, оно есть в конце главы.

### Дерево разбора

Результат — одна структура на все виды команд:

```cpp
struct Statement {
    enum Kind { kCreate, kCreateIndex, kInsert, kSelect };
    Kind kind = kSelect;

    bool is_explain = false;
    std::string table;

    // CREATE TABLE: список (имя_колонки, тип).
    // CREATE INDEX: только колонки[0].first = имя индексируемой колонки.
    std::vector<std::pair<std::string, std::string>> columns;
    std::string index_name;

    // INSERT: значения по позициям.
    std::vector<std::int64_t> values;

    // SELECT: какие колонки (или "*"), плюс опциональное WHERE.
    std::vector<std::string> select_columns;
    bool has_where = false;
    std::string where_col;
    std::string where_op;
    std::int64_t where_val = 0;
};
```

Одна структура с полями на все случаи — решение спорное, и стоит объяснить его честно. Правильнее была бы иерархия классов с общим предком (`CreateStatement`, `InsertStatement`, `SelectStatement`) и виртуальным методом выполнения — ровно то, что мы делали для предметов RPG в главе 17. Или, если бы у нас был C++17, — `std::variant`, о котором пойдёт речь в главе 48.

Но для четырёх видов команд с десятком полей иерархия добавила бы больше кода, чем сэкономила. Цена такого решения — половина полей в каждом конкретном разборе не используется, и об этом приходится помнить. Как только видов станет десять, а полей полсотни, надо переделывать.

Обратите внимание на комментарии над полями: они объясняют, какое поле для какого вида команды осмысленно. В структуре без иерархии это единственный способ не запутаться, и пренебрегать им нельзя.

### Проверка конца

Последний штрих в точке входа:

```cpp
Statement parse_sql(const std::string& sql) {
    auto tokens = tokenize(sql);
    Parser p(tokens);
    Statement st = p.parse();
    if (p.peek().type != Token::kEnd) {
        throw SqlError("лишние токены после statement: '" + p.peek().text + "'");
    }
    return st;
}
```

Проверка на `kEnd` ловит запросы вроде `SELECT * FROM items garbage` — разбор успешно завершился, но токены не кончились. Без неё лишний текст молча игнорировался бы, а опечатки превращались бы в неправильные запросы.

## Исполнитель

Разобранная команда попадает в `Database::execute`:

```cpp
void Database::execute(const std::string& sql, std::ostream& out) {
    Statement st = parse_sql(sql);
    switch (st.kind) {
        case Statement::kCreate:      execute_create(st, out);       break;
        case Statement::kCreateIndex: execute_create_index(st, out); break;
        case Statement::kInsert:      execute_insert(st, out);       break;
        case Statement::kSelect:      execute_select(st, out);       break;
    }
}
```

Обратите внимание на `switch` без `default`. При таком написании компилятор с `-Wall` предупредит, если в перечисление добавят новый вид, а ветку забудут. С `default:` предупреждения не будет — и новый вид тихо провалится в него. Это общее правило для `switch` по перечислению: не пишите `default`, если хотите, чтобы компилятор помогал.

Вывод идёт в `std::ostream&`, а не в `std::cout` напрямую. Разница проявляется в тестах: туда можно передать `std::ostringstream` и проверить результат строкой, что мы и делаем:

```cpp
std::ostringstream sel;
d.execute("SELECT * FROM items WHERE value = 100", sel);
check(sel.str().find("(2 строки)") != std::string::npos, ...);
```

Привязка к `std::cout` внутри библиотечного кода — частая ошибка, из-за которой потом невозможно ни протестировать, ни перенаправить вывод.

### Создание таблицы

```cpp
void Database::execute_create(const Statement& st, std::ostream& out) {
    if (st.columns.size() != 2) {
        throw SqlError("мини-СУБД поддерживает таблицы только из 2 колонок");
    }
    table_name_ = st.table;
    col_names_ = {st.columns[0].first, st.columns[1].first};
    out << "OK (table '" << table_name_ << "')\n";
}
```

Вся команда сводится к запоминанию имён. Ни новых файлов, ни схемы на диске: таблица у нас всегда одна, а её структура зашита в код — первая колонка становится ключом дерева, вторая значением.

Отсюда следует неприятная особенность, о которой лучше сказать прямо: имена колонок не сохраняются между запусками. Создали таблицу с колонками `sku` и `price`, закрыли базу, открыли — и колонки снова зовутся `id` и `value`, потому что так написано в конструкторе. Данные при этом на месте.

Чтобы это исправить, нужна системная таблица — место, где база хранит собственную схему. В настоящих СУБД это `pg_catalog` в PostgreSQL или `sqlite_master` в SQLite, и устроены они как обычные таблицы, только заполняет их сам движок. Нам хватило бы одной страницы с именами; это упражнение в конце главы.

### Вставка

```cpp
void Database::execute_insert(const Statement& st, std::ostream& out) {
    if (st.table != table_name_) throw SqlError("неизвестная таблица: " + st.table);
    if (st.values.size() != 2) throw SqlError("ожидается 2 значения");

    std::int64_t id = st.values[0];
    std::int64_t value = st.values[1];

    wal_->log_insert(id, value);
    tree_->insert(id, value);

    for (auto& kv : indexes_) {
        const std::string& col = kv.first;
        std::int64_t key = (col == col_names_[0]) ? id : value;
        kv.second.wal->log_insert(key, id);
        kv.second.tree->insert_dup(key, id);
    }

    out << "1 строка\n";
}
```

Порядок здесь ровно тот, что мы обсуждали в главе 35: сначала журнал, потом дерево. Поменяйте местами — и авария между двумя строками потеряет запись.

Каждый вторичный индекс — отдельное дерево со своим журналом, и вставка обновляет их все. Это и есть цена индексов, о которой всегда говорят: чтение ускоряется, запись замедляется. Три индекса — четыре дерева и четыре записи в журналы на каждую строку. Подробнее об этом в следующей главе.

Заметьте `insert_dup` вместо `insert` для индексов — та самая правка из главы 34, без которой строки с одинаковым значением затирали бы друг друга.

### Выборка

```cpp
bool Database::matches_where(const Statement& st,
                             std::int64_t id, std::int64_t value) const {
    if (!st.has_where) return true;
    std::int64_t left = (st.where_col == col_names_[0]) ? id : value;
    const auto r = st.where_val;
    const auto& op = st.where_op;
    if (op == "=")  return left == r;
    if (op == "!=") return left != r;
    if (op == "<")  return left <  r;
    if (op == "<=") return left <= r;
    if (op == ">")  return left >  r;
    if (op == ">=") return left >= r;
    throw SqlError("неизвестный оператор: " + op);
}
```

Проверка условия для одной строки. Сравнение операторов строками — не самое быстрое решение: на каждой строке таблицы выполняется до шести сравнений коротких строк. Правильнее было бы превратить оператор в перечисление ещё в парсере, и на большой таблице это дало бы заметную разницу. Для учебной базы оставлено как есть, но приём общий: **разбор должен превращать текст в числа один раз, а не заставлять исполнителя разбирать его снова на каждой строке**.

Самый простой способ выполнения — обойти всё дерево и отфильтровать:

```cpp
void Database::run_full_scan(const Statement& st, const std::vector<std::string>& cols,
                             std::ostream& out) {
    int rows = 0;
    tree_->scan([&](std::int64_t id, std::int64_t value) {
        if (!matches_where(st, id, value)) return;
        for (std::size_t i = 0; i < cols.size(); ++i) {
            if (i) out << " | ";
            std::int64_t cell = (cols[i] == col_names_[0]) ? id : value;
            out << std::setw(8) << std::left << cell;
        }
        out << "\n";
        ++rows;
    });
    print_row_count(rows, out);
}
```

Это полный перебор — тот самый, от которого нас должен спасать индекс. В следующей главе появятся ещё три способа выполнения и планировщик, который между ними выбирает.

Согласование числительных вынесено в отдельную функцию — мелочь, но приятная:

```cpp
// Согласование числительного: 1 строка, 2-4 строки, 5+ строк.
void print_row_count(int rows, std::ostream& out) {
    int last_two = rows % 100;
    int last = rows % 10;
    const char* word = "строк";
    if (last == 1 && last_two != 11) word = "строка";
    else if (last >= 2 && last <= 4 && (last_two < 12 || last_two > 14)) word = "строки";
    out << "(" << rows << " " << word << ")\n";
}
```

Правило русского языка требует смотреть на две последние цифры: 21 строка, но 11 строк; 22 строки, но 12 строк. Такую функцию стоит написать один раз и носить с собой из проекта в проект.

## Тесты разбора

Парсер — чистая функция от строки к структуре, и тестировать его так же удобно, как токенизатор оболочки:

```cpp
db::Statement s = db::parse_sql("CREATE TABLE items (id INT PRIMARY KEY, value INT)");
check(s.kind == db::Statement::kCreate, "CREATE TABLE распознан");
check_eq(s.table, std::string("items"), "имя таблицы");
check_eq(s.columns.size(), static_cast<std::size_t>(2), "две колонки");

s = db::parse_sql("select * from items where value >= -5");
check(s.kind == db::Statement::kSelect, "SELECT в нижнем регистре распознан");
check(s.has_where, "WHERE распознан");
check_eq(s.where_op, std::string(">="), "оператор >=");
check_eq(s.where_val, static_cast<std::int64_t>(-5), "отрицательное число");
```

Отдельно проверяется, что плохой ввод отвергается, а не разбирается как попало:

```cpp
const char* bad[] = {
    "SELECT",
    "INSERT INTO items VALUES (1",
    "SELECT * FROM items WHERE",
    "DROP TABLE items",
};
for (...) {
    bool threw = false;
    try { db::parse_sql(bad[i]); } catch (const db::SqlError&) { threw = true; }
    check(threw, std::string("плохой SQL отвергается: ") + bad[i]);
}
```

Тесты на отрицательные случаи в парсерах важнее положительных. Разбор правильного запроса вы проверите руками при первом же запуске, а вот что делает программа с обрубком `SELECT * FROM items WHERE` — узнаете, только если специально спросите. Ответ должен быть «внятная ошибка», а не «падение» и не «молча принял».

## Главные правила главы

1. Язык запросов отделяет «что нужно» от «как получить» — благодаря этому движок можно менять, не трогая запросы.
2. Схема разбора одна и та же для любого языка: лексер, парсер, исполнитель; каждая ступень проверяется отдельно.
3. Метка конца в списке токенов избавляет парсер от проверок на выход за границу.
4. Рекурсивный спуск пишется так, что код повторяет грамматику; это его главное достоинство.
5. Ключевые слова в SQL регистронезависимы, имена — нет; сравнивайте по приведённой копии, храните исходное написание.
6. Перед `isalpha` и роднёй обязательно приводите символ к `unsigned char`, иначе кириллица даст неопределённое поведение.
7. После разбора проверьте, что токены кончились, — иначе лишний текст молча пропадёт.
8. Разбор должен превращать текст в числа и перечисления один раз; исполнитель не должен разбирать строки на каждой записи.

## Упражнения

1. Соберите базу и повторите сессию из главы. Затем проверьте разные написания: `SeLeCt`, лишние пробелы, отсутствие точки с запятой, точку с запятой в середине.

2. Сделайте сообщение об ошибке для неизвестной команды понятнее: `DROP TABLE items` должно давать «неизвестная команда: DROP», а не «ожидался keyword». Подсказка — проверьте тип первого токена и его текст.

3. Добавьте в сообщения об ошибках позицию в строке: лексер знает смещение, достаточно донести его до токена. Проверьте на `SELECT * FROM items WHERE value >> 5`.

4. Замените строковый оператор в `Statement` на перечисление, разбираемое в парсере. Убедитесь, что тесты проходят, и объясните, где именно это ускорит выполнение.

5. Добавьте `ORDER BY <колонка> [DESC]`. Для колонки-ключа сортировка бесплатна (дерево уже отдаёт по возрастанию), для второй колонки придётся собрать строки и отсортировать.

6. Добавьте `LIMIT <число>`. Важно, чтобы обход прекращался по достижении предела, а не отбрасывал лишнее после сбора всего.

7. (Сложнее) Сделайте системную таблицу: заведите страницу, где хранятся имя таблицы и имена колонок, пишите её при `CREATE TABLE` и читайте при открытии базы. Проверьте, что после перезапуска колонки называются так, как их создали.

8. (Сложнее) Поддержите `AND` и `OR` в условии. Понадобится дерево выражений вместо трёх полей и разбор с приоритетами: `OR` слабее `AND`, скобки сильнее всего. Начните с грамматики на бумаге.

## Что дальше

Глава 37 — вторичные индексы и планировщик. Сейчас любой запрос с условием выполняется полным перебором: даже `WHERE id = 42` честно обходит всё дерево, хотя ключ у нас именно `id`. Научим базу выбирать способ выполнения — по первичному ключу, по вторичному индексу, диапазонным сканированием индекса или полным перебором, — и покажем выбранный план по команде `EXPLAIN`. А заодно измерим, во сколько раз индекс ускоряет чтение и на сколько замедляет запись.

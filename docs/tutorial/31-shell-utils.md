# Глава 31. Свои cat, wc, grep и head

Мы написали оболочку, которая умеет соединять чужие программы. Осталось написать программы, которые она будет соединять.

В этой главе сделаем четыре классические утилиты Unix — `cat`, `wc`, `grep` и `head`. Не игрушечные подобия, а рабочие: они читают стандартный ввод, принимают файлы аргументами, соблюдают соглашения о кодах возврата и без проблем встают в цепочку рядом с системными. Назовём их `mycat`, `mywc`, `mygrep` и `myhead`, чтобы не путались с настоящими.

Смысл упражнения не в том, чтобы заменить `/bin/cat`. Смысл в том, что программа-фильтр — самая частая форма командной утилиты вообще. Прочитать поток, что-то с ним сделать, отдать дальше. Написав их, вы получите шаблон, по которому дальше пишется любая своя утилита: конвертер логов, обработчик выгрузки, генератор отчёта.

Заодно разберёмся с вещами, которые в прикладном коде обычно проходят мимо: почему `read` может вернуть меньше запрошенного, как считать символы в UTF-8, не разбирая кодировку целиком, и почему `std::regex` в шесть раз медленнее системного `grep`.

## Модель фильтра

У всех четырёх утилит одинаковый каркас, и он же — общее соглашение Unix.

Если аргументов нет, программа читает стандартный ввод. Это важнейшее правило: именно оно позволяет ставить утилиту в середину конвейера, где никакого файла нет, а есть только канал. Если аргументы есть, они считаются именами файлов, и каждый обрабатывается по очереди. Отдельный аргумент `-` означает «здесь читай стандартный ввод», что позволяет смешивать файлы и поток: `mycat header.txt - footer.txt`.

Результат всегда идёт в стандартный вывод, ошибки — в поток ошибок. Разделение не формальность: благодаря ему `mygrep foo *.log > found.txt` кладёт в файл только найденные строки, а жалобы на нечитаемые файлы остаются на экране.

Код возврата — ноль при успехе, ненулевой при неудаче, и у каждой утилиты свои оттенки. У `grep` их три, и мы к этому вернёмся.

## mycat

Начнём с самой простой. Задача — прочитать источник и без изменений вывалить его в стандартный вывод.

```cpp
// mycat — простая копия Unix-утилиты cat.
// Читает файлы (или stdin), пишет в stdout.
// Поддержка: один или несколько файлов, "-" как stdin.

#include <cerrno>
#include <cstring>
#include <iostream>
#include <string>
#include <vector>

#include <fcntl.h>
#include <unistd.h>

namespace {

// Скопировать всё из fd в stdout. Возвращает 0 при успехе, 1 при ошибке.
int cat_fd(int fd, const std::string& name) {
    char buf[4096];
    while (true) {
        ssize_t n = read(fd, buf, sizeof(buf));
        if (n == 0) return 0;            // EOF
        if (n < 0) {
            if (errno == EINTR) continue;  // прервало сигналом — попробуем снова
            std::cerr << "mycat: " << name << ": " << std::strerror(errno) << "\n";
            return 1;
        }
        // Записываем всё, что прочитали (с учётом short writes).
        ssize_t written = 0;
        while (written < n) {
            ssize_t m = write(STDOUT_FILENO, buf + written, n - written);
            if (m < 0) {
                if (errno == EINTR) continue;
                std::cerr << "mycat: write: " << std::strerror(errno) << "\n";
                return 1;
            }
            written += m;
        }
    }
}

}  // namespace

int main(int argc, char* argv[]) {
    if (argc < 2) {
        return cat_fd(STDIN_FILENO, "<stdin>");
    }

    int rc = 0;
    for (int i = 1; i < argc; ++i) {
        std::string name = argv[i];
        if (name == "-") {
            if (cat_fd(STDIN_FILENO, "<stdin>") != 0) rc = 1;
            continue;
        }
        int fd = open(name.c_str(), O_RDONLY);
        if (fd < 0) {
            std::cerr << "mycat: " << name << ": " << std::strerror(errno) << "\n";
            rc = 1;
            continue;
        }
        if (cat_fd(fd, name) != 0) rc = 1;
        close(fd);
    }
    return rc;
}
```

Сорок строк, и почти все они — про обработку ошибок. Так и должно быть в системном коде: полезное действие занимает две строки, остальное — честная реакция на то, что может пойти не так.

Разберём внутренний цикл, потому что он важнее, чем кажется.

`read` возвращает три разных вида ответа, и все три надо различать. Ноль означает конец данных — файл кончился или собеседник закрыл канал. Отрицательное значение означает ошибку, и тут есть особый случай: `EINTR` говорит, что вызов прервал сигнал (глава 28), и это не настоящая ошибка — надо просто повторить. Положительное значение — количество прочитанных байт, и оно **может быть меньше** размера буфера, даже если данные ещё не кончились. Для файла на диске такое почти не случается, а вот при чтении из канала или сокета — постоянно: сколько успело прийти, столько и вернули.

Ровно та же история с `write`, и здесь она опаснее, потому что о ней чаще забывают. Вызов имеет право записать меньше, чем попросили, — например, если буфер канала заполнился наполовину. Если не проверять возвращённое значение, программа молча потеряет хвост данных. Поэтому запись обёрнута в цикл со счётчиком `written`, который двигает указатель и уменьшает остаток, пока не отдаст всё.

Возьмите этот цикл за образец. В Части V, когда мы будем писать сетевой код, он повторится почти дословно — там короткие чтения и записи станут не редкостью, а нормой.

Размер буфера в четыре килобайта выбран не наугад: это типичный размер страницы памяти и блока файловой системы. Меньше — больше системных вызовов на тот же объём; больше — заметного выигрыша уже не даёт, а память тратится.

В `main` стоит обратить внимание на две мелочи. Ошибка на одном файле не прекращает обработку остальных, но запоминается в `rc` — так ведёт себя настоящий `cat`. И имя файла хранится в `std::string`, а не в `const char*`, чтобы не думать о времени жизни, — `argv` живёт до конца программы, но привычка полезная.

### Так read или ifstream?

В главе 12 мы читали файлы через `<fstream>`, а тут вдруг сырые системные вызовы. Есть ли смысл?

Я измерил на файле в 16 мегабайт, при прогретом кэше, все варианты собраны с `-O2`:

```
mycat (read/write, буфер 4 КБ):   0.01 с
ifstream + getline построчно:     0.05 с
ifstream.read блоками по 4 КБ:    0.01 с
системный cat:                    0.00 с
```

Вывод получается не тот, который обычно ожидают. Дело не в том, что системные вызовы быстрее потоков: `ifstream`, читающий блоками, идёт вровень с `read`. Дело в способе чтения. Построчный `getline` медленнее в пять раз, потому что на каждую строку выполняет поиск разделителя, копирование в `std::string` и работу форматирующего слоя, — а строк в файле триста тысяч.

Значит, правило звучит так: важен размер порции, а не выбор API. Читайте блоками — и разница между `read` и `ifstream` окажется в пределах шума.

Почему тогда в `mycat` всё-таки `read`? Потому что утилита обязана работать с любым источником, включая тот, у которого нет ни размера, ни возможности перемотки: канал, сокет, терминал. С сырым дескриптором это естественно, а `ifstream` вокруг стандартного ввода — уже фокус с `rdbuf`. Плюс мы в системной части книги, и полезно видеть механику без обёрток.

## mywc

Вторая утилита считает строки, слова и байты. Выглядит просто, но в ней прячутся два поучительных места: определение слова и работа с UTF-8.

```cpp
struct Counts {
    long long lines = 0;
    long long words = 0;
    long long bytes = 0;
    long long chars = 0;   // UTF-8 «первые байты»
};

Counts count_stream(std::istream& in) {
    Counts c;
    char ch;
    bool in_word = false;
    while (in.get(ch)) {
        ++c.bytes;

        // UTF-8: считаем «не-продолжающие» байты. (b & 0xC0) != 0x80
        if ((static_cast<unsigned char>(ch) & 0xC0) != 0x80) {
            ++c.chars;
        }

        if (ch == '\n') ++c.lines;

        bool ws = (ch == ' ' || ch == '\t' || ch == '\n' ||
                   ch == '\r' || ch == '\f' || ch == '\v');
        if (ws) {
            in_word = false;
        } else if (!in_word) {
            in_word = true;
            ++c.words;
        }
    }
    return c;
}
```

Подсчёт слов — крошечный конечный автомат с единственным флагом `in_word`. Слово начинается в тот момент, когда непробельный символ встречается после пробельного, и именно там мы увеличиваем счётчик. Такой подход правильно обрабатывает и несколько пробелов подряд, и пробелы в начале строки, и файл без завершающего перевода строки. Попытка считать слова как «число разделителей плюс один» разваливается на первом же двойном пробеле.

Строки считаются по числу символов `\n`. Отсюда известная особенность: если файл не заканчивается переводом строки, последняя строка не посчитается. Настоящий `wc` ведёт себя так же — он считает не строки, а именно завершённые переводы.

### UTF-8 в две строки

Теперь самое интересное. Как посчитать символы, а не байты, если строка русская?

Вспомним устройство UTF-8 из главы 2. Символ кодируется одним-четырьмя байтами, и старшие биты первого байта говорят, сколько их всего:

| Двоичный вид байта | Смысл |
|--------------------|-------|
| `0xxxxxxx` | односимвольный ASCII |
| `110xxxxx` | первый байт из двух |
| `1110xxxx` | первый байт из трёх |
| `11110xxx` | первый байт из четырёх |
| `10xxxxxx` | продолжение предыдущего |

Ключевое наблюдение: продолжающий байт всегда начинается с битов `10`, и никакой другой — нет. Значит, чтобы посчитать символы, достаточно посчитать байты, которые **не** начинаются с `10`:

```cpp
if ((static_cast<unsigned char>(ch) & 0xC0) != 0x80) ++c.chars;
```

Маска `0xC0` — это `11000000`, она оставляет только два старших бита. Сравнение с `0x80` — с `10000000` — отвечает на вопрос «это продолжение?». Если нет, значит, начался новый символ.

Приведение к `unsigned char` обязательно. Тип `char` в C++ может быть знаковым (на x86 обычно так), и байт `0xD0` в нём станет отрицательным числом; при побитовых операциях он расширится единицами до `int`, и сравнение сломается. Это классическая ловушка, из-за которой «работало на моей машине» превращается в «на ARM всё поехало» — там `char` беззнаковый по умолчанию.

Прелесть приёма в том, что мы не декодируем UTF-8 и вообще не знаем, какие там символы. Никаких таблиц, никакой библиотеки — два бита и одно сравнение.

### Аргументы и вывод

```cpp
int main(int argc, char* argv[]) {
    bool show_chars = false;
    std::vector<std::string> files;
    for (int i = 1; i < argc; ++i) {
        std::string a = argv[i];
        if (a == "-m")      show_chars = true;   // символы (POSIX wc -m)
        else if (a == "-c") show_chars = false;  // байты (POSIX wc -c) — и так по умолчанию
        else files.push_back(a);
    }

    if (files.empty()) {
        Counts c = count_stream(std::cin);
        print_counts(c, "", show_chars);
        return 0;
    }

    Counts total;
    int rc = 0;
    for (const auto& f : files) {
        std::ifstream in(f);
        if (!in.is_open()) {
            std::cerr << "mywc: " << f << ": " << std::strerror(errno) << "\n";
            rc = 1;
            continue;
        }
        Counts c = count_stream(in);
        print_counts(c, f, show_chars);
        total.lines += c.lines;
        total.words += c.words;
        total.bytes += c.bytes;
        total.chars += c.chars;
    }
    if (files.size() > 1) {
        print_counts(total, "total", show_chars);
    }
    return rc;
}
```

Флаги названы так же, как в POSIX, и это стоило исправления: у настоящего `wc` ключ `-c` означает байты (character в старом смысле, когда символ и байт совпадали), а символы — это `-m`. Наша первая версия использовала `-c` для символов, и такая утилита в чужой цепочке вела бы себя обманчиво: `mywc -c` возвращал бы не то, что `wc -c`. Совместимость с общепринятым поведением важнее удобства обозначений.

Вывод форматируется через `std::setw(7)` из `<iomanip>` — числа выравниваются по правому краю в колонке шириной семь, как это делает настоящий `wc`. Итоговая строка `total` печатается, только когда файлов больше одного.

### Проверка

Сверимся с системной утилитой — лучший вид проверки для клона:

```bash
$ echo "Привет мир" | ./build/mywc
      1       2      20
$ echo "Привет мир" | wc
       1       2      20

$ echo "Привет мир" | ./build/mywc -m
      1       2      11
$ echo "Привет мир" | wc -m
      11
```

Числа сходятся с системными. Проверим их вручную: «Привет» — шесть букв, «мир» — три, каждая кириллическая буква в UTF-8 занимает два байта, плюс пробел и перевод строки по одному. Байт получается 6×2 + 1 + 3×2 + 1 = 20, символов — 6 + 1 + 3 + 1 = 11. Именно это обе утилиты и напечатали.

## mygrep

Третья утилита ищет строки по регулярному выражению. Здесь появляется работа с аргументами посерьёзнее и стандартная библиотека регулярных выражений.

```cpp
struct Options {
    bool ignore_case = false;
    bool show_line_numbers = false;
    bool invert = false;
    std::string pattern;
    std::vector<std::string> files;
};

bool parse_args(int argc, char* argv[], Options& opts) {
    int i = 1;
    while (i < argc) {
        std::string a = argv[i];
        if (a == "-i") { opts.ignore_case = true; ++i; }
        else if (a == "-n") { opts.show_line_numbers = true; ++i; }
        else if (a == "-v") { opts.invert = true; ++i; }
        else if (a == "--") { ++i; break; }
        else if (!a.empty() && a[0] == '-' && a != "-") {
            std::cerr << "mygrep: неизвестная опция: " << a << "\n";
            return false;
        }
        else break;
    }
    if (i >= argc) {
        std::cerr << "mygrep: нужен паттерн\n";
        return false;
    }
    opts.pattern = argv[i++];
    while (i < argc) opts.files.push_back(argv[i++]);
    return true;
}
```

Разбор аргументов написан руками, и для трёх флагов это оправданно. Когда флагов станет десяток и появятся значения через пробел (`-A 3`), стоит взять `getopt` из `<unistd.h>` — стандартную функцию, которая умеет и группировку (`-in` вместо `-i -n`), и разбор значений.

Два соглашения в этом коде стоят внимания. Двойное тире `--` означает «опции кончились, дальше только данные»; без него нельзя искать шаблон, начинающийся с минуса. Одиночное тире `-`, наоборот, опцией не считается — это имя, означающее стандартный ввод, и потому в условии стоит `a != "-"`.

### Поиск

```cpp
long long grep_stream(std::istream& in, const std::regex& re,
                      const Options& opts, const std::string& filename) {
    std::string line;
    long long line_no = 0;
    long long printed = 0;
    bool multi_file = opts.files.size() > 1;
    while (std::getline(in, line)) {
        ++line_no;
        bool matched = std::regex_search(line, re);
        if (matched == opts.invert) continue;

        if (multi_file && !filename.empty()) std::cout << filename << ":";
        if (opts.show_line_numbers)          std::cout << line_no << ":";
        std::cout << line << "\n";
        ++printed;
    }
    return printed;
}
```

Строчка `if (matched == opts.invert) continue;` — компактная запись двух случаев сразу. Без инверсии (`invert == false`) она пропускает строки, где совпадения не было. С инверсией — наоборот. Такой приём читается не мгновенно, зато избавляет от дублирования ветки.

`std::regex_search` ищет совпадение **где угодно** в строке, а `std::regex_match` требует, чтобы шаблон покрывал строку целиком. Для `grep` нужен первый: `mygrep error` должен находить строку `2026-07-30 error: timeout`, а не только строку, состоящую из одного слова `error`.

Имя файла печатается перед строкой только тогда, когда файлов несколько, — снова поведение настоящего `grep`, и оно осмысленно: при одном файле имя было бы шумом, при нескольких без него не разобрать, где что нашлось.

### Компиляция шаблона

```cpp
auto flags = std::regex::ECMAScript;
if (opts.ignore_case) flags |= std::regex::icase;

std::regex re;
try {
    re = std::regex(opts.pattern, flags);
} catch (const std::regex_error& e) {
    std::cerr << "mygrep: bad regex '" << opts.pattern << "': " << e.what() << "\n";
    return 2;
}
```

Регулярное выражение компилируется один раз, до цикла. Это не микрооптимизация: построение `std::regex` — дорогая операция, она разбирает шаблон и строит автомат. Создавать объект внутри цикла по строкам — верный способ получить программу, которая работает в сотни раз медленнее необходимого. Правило общее для всех языков, где есть регулярные выражения.

Диалект по умолчанию — ECMAScript, тот же, что в JavaScript. Он близок к расширенному POSIX, который понимает `grep -E`, но не совпадает с ним: в ECMAScript есть `\d`, `\w`, `\b`, ленивые квантификаторы `*?`, а в POSIX их нет. Если нужен именно POSIX-диалект, `std::regex` умеет и его — через флаги `std::regex::extended` или `std::regex::basic`.

Ошибка в шаблоне приходит исключением `std::regex_error`, и ловить его обязательно: `mygrep "([a-z"` без обработки просто уронил бы программу с невнятным сообщением о необработанном исключении.

### Код возврата: три состояния

У `grep` не два исхода, а три, и это одно из самых полезных соглашений в Unix:

```cpp
long long found = 0;

if (opts.files.empty()) {
    found = grep_stream(std::cin, re, opts, "");
    return found > 0 ? 0 : 1;
}

bool had_error = false;
for (const auto& f : opts.files) {
    ...
}
if (had_error) return 2;
return found > 0 ? 0 : 1;
```

Ноль означает «нашёл хотя бы одну строку», единица — «отработал нормально, но не нашёл ничего», двойка — «что-то сломалось: нет файла, плохой шаблон».

Различие между единицей и двойкой — не педантизм. На нём стоят все скрипты вида:

```bash
if grep -q ERROR app.log; then
    echo "в логе есть ошибки"
fi
```

Условие в `if` смотрит именно на код возврата. Если бы `grep` возвращал ноль всегда, ветка срабатывала бы независимо от содержимого лога. В первой версии нашей утилиты так и было — `grep_stream` возвращал ноль, чем бы дело ни кончилось. Теперь она считает найденные строки и сообщает честно:

```bash
$ echo "hello" | ./build/mygrep hello > /dev/null; echo $?
0
$ echo "hello" | ./build/mygrep xyz > /dev/null; echo $?
1
$ ./build/mygrep foo /nosuchfile > /dev/null 2>&1; echo $?
2
```

Точно те же три числа выдаёт системный `grep`.

### Сколько стоит std::regex

Честно измерим себя на фоне взрослого инструмента. Файл — журнал на 300 тысяч строк, 16 мегабайт, ищем слово `timeout`, обе программы собраны с оптимизацией:

```
mygrep (std::regex):   0.97 с
системный grep:        0.16 с
```

В шесть раз медленнее. Причин две, и обе поучительные.

Первая — реализация `std::regex` в стандартной библиотеке действительно медленная. Она разбирает шаблон в дерево и обходит его на каждой строке, вместо того чтобы построить конечный автомат один раз. Это известная беда стандарта: интерфейс задан так, что быстрые реализации сделать сложно, и все три крупные библиотеки (libstdc++, libc++, MSVC) проигрывают специализированным движкам вроде RE2 или PCRE2 на порядок.

Вторая — системный `grep` не использует регулярные выражения там, где может обойтись без них. Увидев шаблон без спецсимволов, он ищет подстроку алгоритмом Бойера — Мура, который пропускает целые куски текста, не глядя на них.

Практический вывод: `std::regex` годится для разбора конфигов, проверки полей формы, обработки пользовательского ввода — везде, где строк единицы и тысячи. Для потоков в миллионы строк берите готовый быстрый движок или проверьте сначала простым `line.find(pattern) != npos`, не обходится ли задача без регулярного выражения вовсе.

## myhead и умение вовремя остановиться

Четвёртая утилита короткая, но показывает свойство, которого нет у первых трёх: она читает не всё.

```cpp
// Печатает не больше limit строк. Возвращает, сколько напечатала.
long long head_stream(std::istream& in, long long limit) {
    std::string line;
    long long printed = 0;
    while (printed < limit && std::getline(in, line)) {
        std::cout << line << "\n";
        ++printed;
    }
    return printed;
}
```

Условие `printed < limit` стоит **перед** чтением, и это принципиально: как только напечатано нужное количество, программа не делает лишнего `getline` и сразу выходит. Проверить легко — натравим её на бесконечный поток:

```bash
$ time (yes | ./build/myhead -n 3)
y
y
y
( yes | ./build/myhead -n 3; )  0.00s user 0.00s system 0.006 total
```

Шесть миллисекунд на бесконечном источнике. Если бы условие стояло после чтения или если бы мы, скажем, сначала собирали все строки в вектор, а потом печатали первые три, — программа не закончилась бы никогда.

Разбор аргументов заслуживает отдельного слова, потому что `-n` — первый ключ со значением:

```cpp
if (a == "-n") {
    if (i + 1 >= argc) {
        std::cerr << "myhead: у -n нет значения\n";
        return 2;
    }
    char* end = nullptr;
    long long v = std::strtoll(argv[++i], &end, 10);
    if (!end || *end != '\0' || v < 0) {
        std::cerr << "myhead: плохое число строк: " << argv[i] << "\n";
        return 2;
    }
    limit = v;
} else if (a.size() > 2 && a.compare(0, 2, "-n") == 0) {
    // Слитная форма: -n5
    ...
}
```

`std::strtoll` из `<cstdlib>` разбирает число и через второй параметр сообщает, где остановилась. Проверка `*end != '\0'` ловит мусор вроде `-n 5x`: без неё `strtoll` вернул бы пятёрку и молча съел бы `x`. Именно поэтому `strtoll` предпочтительнее `atoi`, который на плохом вводе просто возвращает ноль и не говорит ни слова.

Слитная форма `-n5` разобрана отдельно, потому что традиция допускает и её. Когда таких ключей становится много, ручной разбор надоедает — и тогда берут `getopt`:

```cpp
#include <unistd.h>

int opt;
while ((opt = getopt(argc, argv, "n:iv")) != -1) {
    switch (opt) {
        case 'n': limit = std::atoll(optarg); break;
        case 'i': ignore_case = true; break;
        case 'v': invert = true; break;
        default: return 2;
    }
}
// после цикла optind указывает на первый неопционный аргумент
```

Двоеточие после буквы в строке `"n:iv"` означает «у этого ключа есть значение». `getopt` сам разбирает и слитную форму, и группировку `-iv`, и `--` как конец опций. Для утилиты с пятью и более ключами это правильный выбор.

Наконец, при нескольких файлах `head` печатает заголовки — и мы повторяем формат в точности:

```bash
$ ./build/myhead -n 2 Makefile include/pipeline.h
==> Makefile <==
# Makefile для demo-shell.
# Зеркало стиля demo-rpg/Makefile: -MMD для авто-зависимостей,

==> include/pipeline.h <==
#ifndef SHELL_PIPELINE_H
#define SHELL_PIPELINE_H
```

Совпадение с системной утилитой проверяется всё тем же способом:

```bash
$ head -3 Makefile | cmp - <(./build/myhead -n 3 Makefile)
совпадает с head -3
```

## Что происходит, когда читатель уходит раньше

У раннего выхода есть последствие для соседа слева по конвейеру. Соберём цепочку, где `mycat` читает шестнадцатимегабайтный журнал, а `myhead` берёт одну строку:

```bash
$ ./build/mycat big.log | ./build/myhead -n 1
0 debug retry ok timeout info timeout failed info
$ echo "коды: ${PIPESTATUS[0]} ${PIPESTATUS[1]}"
коды: 141 0
```

Код 141 у первой команды — это, как мы считали в главе 27, 128 + 13, то есть SIGPIPE. `myhead` напечатал строку и закрыл свой стандартный ввод; `mycat` попытался писать в канал без читателя и был убит ядром.

Это не поломка, а именно тот механизм, благодаря которому `head` на гигабайтном файле возвращается мгновенно. Никто не дочитывает файл до конца — источник просто убивают, как только результат перестаёт быть нужным.

Для утилиты-фильтра отсюда следует практический вывод: не надо ловить SIGPIPE и продолжать работу. Смерть от него — правильное поведение в конвейере. А вот для сервера или демона, который пишет в сокет, всё наоборот — там сигнал нужно отключить и обрабатывать `EPIPE` как обычную ошибку. Мы этим займёмся в Части V.

## Буферизация: почему вывод иногда «залипает»

Есть ещё одна особенность, о которой стоит знать заранее, потому что она порождает жалобы вида «программа зависла, ничего не печатает».

Стандартный вывод буферизуется по-разному в зависимости от того, куда направлен. Если это терминал — буферизация построчная, и каждая строка появляется сразу. Если файл или канал — буферизация полная, и данные уходят порциями по несколько килобайт.

Проверить, куда мы пишем, можно вызовом `isatty` из `<unistd.h>`:

```cpp
#include <unistd.h>

if (isatty(STDOUT_FILENO)) {
    // человек смотрит на экран
} else {
    // нас перенаправили в файл или конвейер
}
```

Утилиты этим пользуются. Тот же `grep` при выводе в терминал подсвечивает совпадения цветом, а при перенаправлении — нет, чтобы управляющие последовательности не портили файл. Проверяется это ровно через `isatty`.

Побочный эффект полной буферизации проявляется на длинных конвейерах с долгой работой. Скажем, `./monitor | grep ERROR` может молчать минутами: `monitor` накапливает вывод в буфере, `grep` ждёт данных, а вы смотрите на пустой экран и думаете, что всё повисло. Лечится это со стороны источника — сбросом буфера после каждой записи (`std::cout.flush()` или `std::endl`) либо переключением потока в небуферизованный режим. Снаружи помогает утилита `stdbuf -oL` на Linux, которая заставляет чужую программу перейти на построчный режим.

В наших утилитах специальных мер нет, и это осознанно: они работают быстро и завершаются, так что заметить задержку негде. Но если бы `mygrep` работал на потоке, приходящем в реальном времени, флаг `-L` для построчного вывода стал бы первой же просьбой пользователей.

## Всё вместе

Соберём цепочку из наших программ и запустим её в нашей оболочке:

```
myshell$ ./build/mycat Makefile | ./build/mygrep -i make | ./build/mywc
      2      11     124
myshell$ ./build/mygrep -n "^CXX" Makefile
5:CXX      := g++
6:CXXSTD   := -std=c++11
18:CXXFLAGS := $(CXXSTD) $(WARNINGS) $(OPT) -Iinclude -MMD -MP
myshell$ echo "Привет, мир" | ./build/mywc -m
      1       2      12
```

Первая строка — полный круг. Наша оболочка разобрала команду, создала два канала, запустила три процесса, переставила им дескрипторы. Первый процесс прочитал файл системным вызовом `read` и отдал байты в канал. Второй прочитал их оттуда, прогнал через регулярное выражение и отдал дальше. Третий посчитал и напечатал в терминал. Каждая часть этой цепочки написана нами и разобрана в предыдущих главах.

Обратите внимание, что утилиты ничего не знают о своём окружении. `mygrep` не подозревает, что слева `mycat`, а справа `mywc`; для него это просто стандартный ввод и стандартный вывод. Поменяйте местами, вставьте системный `sort` посередине, отправьте результат в файл — всё продолжит работать. Это и есть та самая композиция, ради которой Unix устроен именно так.

## Что не сделано

Настоящие утилиты обросли десятками ключей. У `cat` есть `-n` для нумерации строк, `-E` для показа концов строк, `-T` для табуляций. У `wc` — ключи `-l`, `-w`, `-c`, `-m` для вывода одного числа вместо трёх и `-L` для максимальной длины строки. У `grep` — рекурсивный обход каталогов `-r`, вывод только имён файлов `-l`, подсчёт совпадений `-c`, показ соседних строк `-A` и `-B`, поиск фиксированной строки без регулярных выражений `-F`.

Ни одна из этих возможностей не требует новых знаний — это работа с аргументами и небольшие изменения в цикле. Несколько штук вынесены в упражнения; остальное допишете, когда понадобится.

Отдельно упомяну приём, который иногда даёт заметный выигрыш на больших файлах, — отображение файла в память:

```cpp
#include <sys/mman.h>
#include <sys/stat.h>

int fd = open("big.log", O_RDONLY);
struct stat st;
fstat(fd, &st);
char* data = static_cast<char*>(
    mmap(nullptr, st.st_size, PROT_READ, MAP_PRIVATE, fd, 0));
// теперь data[0..st.st_size-1] — содержимое файла, как обычный массив
munmap(data, st.st_size);
close(fd);
```

После `mmap` файл доступен как массив байтов: ядро подгружает страницы по мере обращения, и лишнего копирования из своего кэша в наш буфер не происходит. Для поиска по большому файлу это иногда даёт двукратное ускорение. Но у приёма есть жёсткое ограничение: отобразить можно только то, у чего есть размер и произвольный доступ. Канал, сокет, терминал отобразить нельзя — а именно из них наши утилиты чаще всего и читают. Плюс на файле, лежащем на сетевой файловой системе, исчезновение файла даёт SIGBUS вместо аккуратной ошибки. Поэтому в универсальной утилите-фильтре `read` остаётся правильным выбором, а `mmap` берут для специализированных задач.

## Часть III закончена

Шесть глав назад у нас не было ничего, кроме желания написать оболочку. Сейчас в `demo-shell/` лежит около тысячи строк кода: сама оболочка в `src/`, четыре утилиты в `utils/`, тесты токенизатора в `tests/`.

Что теперь умеет `myshell`: запускать программы, соединять их в цепочки любой длины, перенаправлять ввод, вывод и поток ошибок в шести формах, разбирать кавычки и экранирование, выполнять шесть встроенных команд, переживать Ctrl+C, помнить историю между запусками.

Что теперь умеете вы. Из системного интерфейса Unix — `fork`, `exec`, `wait`, `pipe`, `dup2`, `open`, `read`, `write`, `close`, `chdir`, `getcwd`, `setenv`, `sigaction`, `kill`. Из общих приёмов — токенизатор на конечном автомате, разделение разбора и выполнения, обработка коротких чтений и `EINTR`, подсчёт символов UTF-8 без декодирования, регулярные выражения стандартной библиотеки и понимание их цены.

Это и есть системное программирование в его повседневном виде. Той же техникой пишутся утилиты сборки, обёртки для запуска сервисов, обработчики логов и всё, что живёт в командной строке.

## Главные правила главы

1. Утилита без аргументов читает стандартный ввод — это то, что позволяет ей встать в конвейер.
2. `read` и `write` могут обработать меньше запрошенного; обе всегда оборачивают в цикл.
3. `EINTR` — не ошибка, а просьба повторить вызов.
4. Читайте блоками, а не по строкам: разница в пять раз, и она не про выбор между `read` и `ifstream`.
5. Символы UTF-8 считаются подсчётом байтов, у которых старшие два бита не равны `10`.
6. Приводите `char` к `unsigned char` перед побитовыми операциями — знаковость `char` зависит от платформы.
7. Регулярное выражение компилируют один раз до цикла; `std::regex` медленный, для больших объёмов ищите альтернативу.
8. Коды возврата — часть интерфейса программы: у `grep` ноль, единица и двойка означают три разные вещи, и на этом стоят скрипты.

## Упражнения

1. Соберите утилиты (`make`) и сверьте каждую с системной: `mycat` через `cmp`, `mywc` на файле с кириллицей, `mygrep` по кодам возврата. Найдите хотя бы одно расхождение с системной версией и объясните его.

2. Проверьте обработку коротких чтений: запустите `./build/mycat < /dev/urandom | head -c 1000000 | ./build/mywc -c`. Убедитесь, что счёт сходится и ничего не потерялось.

3. Добавьте в `mycat` ключ `-n` — нумерацию строк, как у настоящего `cat`. Учтите, что нумеровать надо сквозным счётом по всем файлам, а не начинать заново для каждого.

4. Добавьте в `mywc` ключи `-l`, `-w`, `-c`, `-m` в их POSIX-смысле: при указании любого из них печатается только запрошенное число, при нескольких — только они и в фиксированном порядке.

5. Добавьте в `mygrep` ключ `-c` (печатать только количество совпадений) и `-l` (только имена файлов, где нашлось). Проверьте, что код возврата остаётся правильным.

6. Замерьте `mygrep` на своём большом файле и сравните с системным `grep`. Затем добавьте оптимизацию: если в шаблоне нет спецсимволов регулярных выражений, искать через `line.find`. Насколько сократился разрыв?

7. (Сложнее) Добавьте в `myhead` ключ `-c N` — печатать первые N **байт**, а не строк. Проверьте на бинарном файле, что счёт точный и лишнего не читается.

8. (Сложнее) Напишите `mytail` — последние N строк. В отличие от `head`, конец потока заранее неизвестен: понадобится кольцевой буфер на N строк. Для файла можно схитрить и читать с конца через `lseek`, но сначала сделайте общий вариант, работающий и с каналом.

# Глава 28. Сигналы

В предыдущих главах мы построили shell, который запускает программы и собирает их в пайплайны. Сейчас попробуйте `sleep 10` в shell, потом Ctrl+C. Что произойдёт? Скорее всего, **умрут оба** — и `sleep`, и сам shell. Это потому, что Ctrl+C — это **сигнал**, и он по умолчанию идёт всем процессам в группе. В этой главе разберёмся с сигналами и сделаем так, чтобы shell их игнорировал, а ребёнок — нет.

Сигналы — старейший механизм межпроцессного взаимодействия в Unix. Простой и мощный, но с подводными камнями (asynchronous-safe функции, race conditions). К концу главы вы поймёте, почему «программа со сложной логикой в обработчике» — это плохая идея, и почему `sigaction` лучше старого `signal`.

## Что такое сигнал

**Сигнал** — это асинхронное уведомление от ядра процессу. «Тебе кто-то послал номер N — обработай как-нибудь».

Каждый сигнал имеет:
- **Номер** (например, 2).
- **Имя** (например, `SIGINT`).
- **Действие по умолчанию** (например, «убить процесс»).

Когда сигнал приходит, ядро **прерывает** обычное выполнение процесса и запускает обработчик. Если обработчика нет — выполняется действие по умолчанию.

Сигнал — **асинхронный**: процесс не знает, когда он придёт. Может прийти в середине вычисления, посреди вызова `printf`, между двумя инструкциями процессора. Поэтому обработчики сигналов — очень тонкая штука.

## Распространённые сигналы

Я перечислю самые часто встречающиеся.

| Номер | Имя | По умолчанию | Когда |
|-------|-----|---------------|-------|
| 1 | SIGHUP | Завершить | Терминал отключён (закрыли SSH-сессию) |
| 2 | SIGINT | Завершить | Ctrl+C в терминале |
| 3 | SIGQUIT | Завершить + core dump | Ctrl+\\ |
| 9 | SIGKILL | Завершить (НЕВОЗМОЖНО ПЕРЕХВАТИТЬ) | `kill -9` |
| 11 | SIGSEGV | Завершить + core dump | Обращение к невалидной памяти |
| 13 | SIGPIPE | Завершить | Запись в пайп без читателей |
| 15 | SIGTERM | Завершить | `kill` без аргумента — «вежливая просьба завершиться» |
| 17 | SIGCHLD | Игнорируется | Ребёнок изменил состояние (умер, остановлен) |
| 19 | SIGSTOP | Приостановить (НЕВОЗМОЖНО ПЕРЕХВАТИТЬ) | `kill -STOP` |
| 18 | SIGCONT | Продолжить остановленный | После SIGSTOP |

Особый случай — **SIGKILL** и **SIGSTOP**: их **невозможно** перехватить или проигнорировать. Это страховка ОС от зависших процессов: какой-бы код не был в программе, ядро гарантированно её убьёт/остановит.

Все остальные сигналы можно:
- **Игнорировать** (`SIG_IGN`).
- **Установить свой обработчик**.
- **Восстановить действие по умолчанию** (`SIG_DFL`).

## Как послать сигнал

Команда `kill` посылает сигнал процессу:

```bash
$ kill -INT 1234        # послать SIGINT процессу 1234
$ kill -9 1234           # послать SIGKILL
$ kill 1234              # послать SIGTERM (15) по умолчанию
```

В C++:

```cpp
#include <signal.h>
#include <sys/types.h>

int rc = kill(pid, SIGTERM);
```

Возвращает 0 при успехе, -1 при ошибке (нет такого pid, нет прав, ...).

Терминал автоматически посылает сигналы:
- Ctrl+C → SIGINT всем процессам в **foreground group**.
- Ctrl+\\ → SIGQUIT.
- Ctrl+Z → SIGTSTP (приостанавливает, можно вернуть через `fg`).

«Foreground group» — это процессная группа, которая сейчас «владеет» терминалом. Когда вы запускаете `sleep 10` в bash, sleep становится foreground; Ctrl+C идёт ему. В фоне (`sleep 10 &`) — Ctrl+C не доходит.

## Старый API: signal()

`signal(SIGNUM, handler)` — установить обработчик. Простой, но **проблемный**:

```cpp
#include <signal.h>
#include <iostream>

void handler(int sig) {
    std::cout << "got signal " << sig << "\n";
}

int main() {
    signal(SIGINT, handler);
    
    while (true) {
        pause();   // спать до сигнала
    }
}
```

Проблемы `signal`:

1. **Поведение различается** на разных Unix (BSD vs SysV). После срабатывания обработчика на SysV — `signal` восстанавливается в `SIG_DFL`; на BSD — остаётся. Современный POSIX следует BSD.

2. **Нет контроля флагов** — какие сигналы блокировать на время обработчика, рестартовать ли прерванные syscalls.

3. **Race condition** на установке — может между восстановлением `SIG_DFL` и повторной установкой прийти второй сигнал.

Поэтому в новом коде — `sigaction`.

## Современный API: sigaction()

```cpp
#include <signal.h>

void handler(int sig) {
    // ...
}

int main() {
    struct sigaction sa;
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;
    
    sigaction(SIGINT, &sa, nullptr);
}
```

`struct sigaction` имеет три поля (упрощённо):
- **`sa_handler`** — указатель на обработчик. Или `SIG_IGN`, или `SIG_DFL`.
- **`sa_mask`** — какие сигналы блокировать на время выполнения обработчика. `sigemptyset` — пустая маска.
- **`sa_flags`** — флаги (например, `SA_RESTART`).

`sigaction` детерминированный, переносимый, со всеми возможностями. Используйте его.

## Что можно делать в обработчике

Главная ловушка сигналов: обработчик может **прервать что угодно**. Включая саму программу посреди `printf`, посреди `malloc`, посреди обновления связного списка.

Если обработчик вызовет `printf`, который внутри использует те же буферы, что и прерванный `printf` — **race condition**. Может быть UB, краш, испорченный вывод.

POSIX определяет **async-signal-safe функции** — функции, безопасные для вызова из обработчика. Список ограничен:

- `write`, `read`, `close`, `open` — низкоуровневый I/O.
- `_exit`, `kill`, `getpid`.
- `signal`, `sigaction`.
- Несколько других.

**`printf`, `malloc`, `std::cout` — НЕ async-signal-safe.** Использовать в обработчике — играть с огнём.

Что делают грамотные обработчики:

1. Устанавливают глобальный **флаг** (`volatile sig_atomic_t got_sigint = 1`).
2. Главная программа этот флаг проверяет и реагирует.

```cpp
volatile sig_atomic_t got_sigint = 0;

void handler(int) {
    got_sigint = 1;   // только флаг, ничего больше
}

int main() {
    // установка...
    
    while (true) {
        if (got_sigint) {
            got_sigint = 0;
            std::cout << "interrupt detected\n";   // безопасно вне обработчика
        }
        // обычная работа
    }
}
```

`volatile sig_atomic_t` — тип целого числа, **атомарно** считываемого/записываемого. Стандарт C гарантирует это; в C++ — практически то же.

## SA_RESTART и системные вызовы

Когда сигнал приходит во время **блокирующего системного вызова** (например, `read` ждёт ввода от пользователя), у вызова два варианта:

1. **Прерваться** — вернуть -1 с `errno == EINTR`. Программа должна перезапустить вызов сама.
2. **Перезапуститься** — после обработки сигнала продолжить ждать.

С `signal()` (BSD) обычно перезапуск. С `sigaction()` без флагов — прерывание. С `SA_RESTART` — перезапуск.

```cpp
sa.sa_flags = SA_RESTART;
```

Для shell мы хотим, чтобы `getline` не прерывался от SIGCHLD (ребёнок умер). Поставим `SA_RESTART`. Но для `waitpid` это другой случай — там цикл.

## Игнорирование сигнала

Установка `SIG_IGN`:

```cpp
sa.sa_handler = SIG_IGN;
sigaction(SIGINT, &sa, nullptr);
```

Сигнал приходит, но **ничего не происходит**. Действие по умолчанию отменено, нет вызова обработчика. Просто игнор.

**SIG_IGN сохраняется при `exec`**. Это критично: если shell установит SIG_IGN для SIGINT, **ребёнок после exec тоже его игнорирует**. То есть Ctrl+C не будет работать на запущенные программы.

Поэтому в ребёнке мы **восстанавливаем** SIG_DFL перед exec.

## SIGCHLD и зомби

Когда ребёнок умирает, родителю приходит **SIGCHLD**. По умолчанию игнорируется, но процесс остаётся зомби, пока родитель не сделает `waitpid`.

Способы:

1. **Синхронный `waitpid`** — как у нас. После запуска ребёнка ждём его. Зомби нет.

2. **Обработчик SIGCHLD**:
   ```cpp
   void sigchld_handler(int) {
       while (waitpid(-1, nullptr, WNOHANG) > 0) {
           // забираем всех завершившихся детей
       }
   }
   ```
   Полезно для **фоновых задач** (`cmd &`). Дети умирают в произвольное время; обработчик их подбирает.

3. **`signal(SIGCHLD, SIG_IGN)`** — POSIX-расширение: ядро автоматически чистит за вами. Удобно, но прячет статус.

В нашем shell — синхронный `waitpid`. Никаких обработчиков SIGCHLD не нужно.

## SIGPIPE

Запись в пайп, у которого нет читателей, приводит к **SIGPIPE**. По умолчанию — смерть процесса.

Это бывает: пайплайн `yes | head -1` — `head` берёт строку и закрывает stdin. `yes` пишет в закрытый пайп — SIGPIPE — `yes` умирает.

Если хотите ловить ошибку самостоятельно:

```cpp
sa.sa_handler = SIG_IGN;
sigaction(SIGPIPE, &sa, nullptr);
```

Теперь `write` в закрытый пайп вернёт `-1` с `errno == EPIPE`. Программа сможет обработать корректно.

В нашем shell игнорируем SIGPIPE — иначе одна неудачная программа в пайплайне могла бы убить shell.

## Применение в demo-shell

`include/signals.h`:

```cpp
namespace shell {

void install_shell_signal_handlers();
void restore_default_signal_handlers();

}
```

`src/signals.cpp`:

```cpp
#include "signals.h"
#include <csignal>

namespace shell {

void install_shell_signal_handlers() {
    struct sigaction sa;
    sa.sa_handler = SIG_IGN;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;

    sigaction(SIGINT, &sa, nullptr);
    sigaction(SIGQUIT, &sa, nullptr);
    sigaction(SIGPIPE, &sa, nullptr);
}

void restore_default_signal_handlers() {
    struct sigaction sa;
    sa.sa_handler = SIG_DFL;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;

    sigaction(SIGINT, &sa, nullptr);
    sigaction(SIGQUIT, &sa, nullptr);
    sigaction(SIGPIPE, &sa, nullptr);
}

}
```

Две функции. Первая — для shell: игнорировать SIGINT/SIGQUIT/SIGPIPE. Вторая — для ребёнка после `fork`, перед `exec`: вернуть всё в дефолт.

В `main.cpp`:

```cpp
int main() {
    shell::install_shell_signal_handlers();
    // ... REPL ...
}
```

В `pipeline.cpp`, в ребёнке после `fork`:

```cpp
if (pid == 0) {
    // Ребёнок i.
    restore_default_signal_handlers();
    // ... dup2, exec ...
}
```

## Что в итоге

Сценарий: пользователь набирает `sleep 10`, нажимает Ctrl+C.

1. Терминал ловит Ctrl+C, посылает SIGINT всем процессам в **foreground group**. Это сейчас shell + ребёнок sleep.
2. **Shell**: SIGINT игнорируется (мы поставили SIG_IGN). Продолжает ждать `waitpid`.
3. **Sleep**: SIGINT с действием по умолчанию (мы восстановили SIG_DFL). Sleep умирает.
4. Shell `waitpid` пробуждается, видит `WIFSIGNALED(status)` с сигналом 2 (SIGINT).
5. Shell печатает «процесс прерван сигналом 2», возвращает 130 (= 128 + 2) как exit code.
6. REPL продолжается.

То, что нужно. Shell живой, sleep умер, пользователь видит сообщение.

Без наших правок:
1. SIGINT приходит и в shell, и в sleep.
2. Оба используют action по умолчанию (SIGINT убивает).
3. Оба умирают. Терминал возвращается к bash.

Ctrl+\\, кстати, делает то же самое, но шумнее — он дампит core file (с настройками по умолчанию). Поэтому мы игнорируем и SIGQUIT.

## Тонкости и углы

### Заранее заблокированные сигналы

`sigprocmask` блокирует доставку сигналов. Они остаются в **очереди** и приходят, когда разблокируешь:

```cpp
sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGINT);

sigprocmask(SIG_BLOCK, &mask, nullptr);
// ... критическая секция ...
sigprocmask(SIG_UNBLOCK, &mask, nullptr);
// если SIGINT пришёл — сейчас сработает
```

Это нужно для атомарных операций. Например, обновление структуры данных, которую и обработчик может трогать.

### Group leader и tcsetpgrp

Настоящий shell делает больше. Он создаёт для каждого ребёнка **свою группу процессов** (через `setpgid`), и делает её **foreground** через `tcsetpgrp`. Тогда терминал шлёт сигналы только этой группе, не shell.

Сложный код с возможностью race conditions. Мы обошлись простым «shell игнорирует, ребёнок реагирует». Если хотите job control (`fg`/`bg`/`jobs`) — нужно делать как bash.

### SIGCHLD в реальном shell

Bash подписан на SIGCHLD, чтобы реагировать на завершение фоновых задач. В нашей версии — нет фоновых задач, нет необходимости.

### sigaction с siginfo

`struct sigaction` имеет ещё поле `sa_sigaction` (вместо `sa_handler`) и флаг `SA_SIGINFO`:

```cpp
sa.sa_flags = SA_SIGINFO;
sa.sa_sigaction = [](int sig, siginfo_t* info, void*) {
    // info содержит детали — кто послал, какой адрес и т.д.
};
```

Полезно для SIGSEGV (узнать, какой адрес вызвал сегфолт). Для наших целей не нужно.

## Главные правила главы

1. **`sigaction` вместо `signal`** — портабельнее и контролируемее.
2. **В обработчике — только флаг.** `printf`/`malloc`/`std::cout` — не async-signal-safe.
3. **Используйте `volatile sig_atomic_t`** для флагов из обработчика.
4. **SIGKILL и SIGSTOP — не перехватываются.** Это страховка ОС.
5. **`SIG_IGN` сохраняется при `exec`**, custom-handler — нет (резется в SIG_DFL).
6. **Восстанавливайте SIG_DFL в ребёнке** перед exec, если родитель что-то менял.
7. **SIGCHLD** — для асинхронной обработки умерших детей. Если синхронно `waitpid` — не нужно.
8. **SIGPIPE игнорируйте в shell**, иначе одна сломанная программа в пайплайне убьёт shell.

## Маленькое упражнение

1. Соберите обновлённый shell. Запустите `sleep 5` и сразу нажмите Ctrl+C. Должно умереть только sleep, shell — нет.

2. Запустите `cat` (без аргументов — он ждёт ввода) и нажмите Ctrl+C. Cat умирает? Shell живой? Прочему cat не использует наш SIG_IGN, который был у shell?

3. Запустите `yes | head -1`. Где умирает `yes` — от SIGPIPE? У нас включен SIG_IGN для SIGPIPE в shell — но `yes` это **ребёнок** с восстановленными дефолтами. Запустите. Объясните вывод.

4. Снимите `restore_default_signal_handlers()` в `pipeline.cpp` (закомментируйте). Соберите. Запустите `sleep 5` и нажмите Ctrl+C. Что произойдёт? Объясните.

5. Напишите программу из 15 строк: устанавливает обработчик SIGINT через `sigaction`, обработчик ставит `got_signal = 1`. Главный цикл проверяет флаг и печатает. Запустите, нажимайте Ctrl+C. Сколько срабатываний поймали?

6. (Сложнее) Прочитайте `man 7 signal-safety`. Найдите функции из вашего любимого языка C — какие можно вызывать из обработчика, какие нет?

7. (Сложнее) Реализуйте таймер: программа печатает сообщение каждую секунду через `alarm(1)` + обработчик SIGALRM. После 10 повторов завершается. Что произойдёт, если внутри обработчика вызвать `printf`? Соберите с `-fsanitize=undefined` и проверьте.
